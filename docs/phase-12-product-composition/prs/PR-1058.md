# PR-1058 — Cart/Checkout Purchasability Gate + Hook Point

Status: planned

## Summary

- `cart.Service.AddItem` rejects a non-`Purchasable` product/variant with a clear `apperror`.
- Reuses the existing `HookCartAddItemBefore`/`HookCartValidate` plugin hook points as the extension seam later tracks build on.

## Why

PR-1054 fixed the `Status` gap in `AddItem`; this PR adds the real `Purchasable` check on top of it, and — importantly — does it through the hook points already wired into `AddItem` rather than a bespoke inline check, so Track D's `RequiresLinkedParent` rule (PR-1068) and any future plugin-driven purchasability rule can layer on without touching `cart.Service` again.

## Scope

- `internal/application/cart/service.go`'s `AddItem`: check `Purchasable` before accepting a line item; on failure, a clear `apperror.Validation` (or a dedicated code if the existing taxonomy doesn't fit) naming *why* — "not currently purchasable," distinct from "no price found" or "product not found."
- Confirm `HookCartAddItemBefore`/`HookCartValidate` are the right seam for this specific check vs. a direct field check in `AddItem` itself — `Purchasable` is a core-domain field (not plugin-defined), so the base check likely belongs inline in `AddItem`, with the hooks reserved for *additional* rules (like Track D's) layered on top. Confirm this split during implementation rather than defaulting everything to the hook mechanism.

## Out Of Scope

- Track D's `RequiresLinkedParent` rule itself — PR-1068, built on top of this PR's gate.

## Follow-up

- PR-1068 (Track D) is the first real consumer of the hook seam this PR establishes.
