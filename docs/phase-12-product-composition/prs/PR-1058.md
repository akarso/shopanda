# PR-1058 — Cart/Checkout Purchasability Gate + Hook Point

Status: done

## Summary

- `cart.Service.ensureVariantPurchasable` (used by `AddItem`, qty-increase, guest claim/merge) rejects when the PR-1055 `Purchasable` axis resolves false, with `apperror.Validation("product is not currently purchasable")` — distinct from the PR-1054 status message (`"not available for purchase"`) and from `"no price found"` / `"variant not found"`.
- `checkout.ValidateCartStep` applies the same axis check so lines that became non-purchasable after add cannot be ordered. Facts load once per checkout for the distinct products in the cart.
- Guest-cart claim on login **drops** unavailable lines (status or axis) and merges the rest, instead of failing the whole claim. This replaces the PR-1054 behaviour.
- Core check is **inline**; `HookCartAddItemBefore` / `HookCartValidate` remain the extension seam for *additional* rules (Track D / PR-1068).

## Why

PR-1054 closed the `Status` gap; PR-1055 defined the four-axis model (including `Purchasable` via `VisibilityMode` + `AutoBasis`). Storefront reads already enforce catalog/search/individually axes (PR-1057). This PR closes the purchasability gap on cart mutations and checkout so a product forced `Purchasable=hidden` (or auto-resolved false) cannot be sold.

## Scope

- Extend existing `ensureVariantPurchasable`: keep `ActiveForPurchase`, then `catalog.AllowWithFacts(..., VisibilitySurfacePurchasable, facts, opts)`.
- Wire `VisibilityFactsSource` into cart + `ValidateCartStep` the same way storefront does when `catalog.visibility.enforce` is on (nil facts = axis gate off; status gate always on).
- Run the purchasable check **before** extension `ValidateBatch` in `AddItem`.
- Confirm hooks are for *additional* rules only — base Purchasable is core-domain resolution, not a plugin hook.

## Design decisions made during implementation

- **No stored `purchasable` boolean.** PR-1055 already owns the axis (`visibility_purchasable_mode` + resolved `Visibility.Purchasable`). A second column would contradict that model.
- **Inline gate, hooks for extras.** Same split the PR asked to confirm: core axis in `ensureVariantPurchasable` / `ValidateCartStep`; `HookCartAddItemBefore` / `HookCartValidate` for plugin/Track D rules.
- **`WithVisibilityFacts` setter, always called from wire.** Matches storefront. Nil facts when enforce is off is intentional (axis off). Catalog repos stay required constructor args (PR-1054) so the status gate never fail-opens.
- **Checkout re-check required.** A cart-only gate would let previously added lines check out after a product became non-purchasable.
- **One facts query per checkout.** `ValidateCartStep` keeps per-line variant/product/status checks, then calls `catalog.FilterIDsWithFacts` once over the distinct product IDs and rejects the first blocked line in cart order. A per-line `AllowWithFacts` cost one query (three `EXISTS` subqueries) per line.
- **Guest claim drops, does not fail.** On a failed claim, `syncStorefrontGuestCart` leaves the guest cookie in place, so every later login retried and failed. With enforce on, any OOS guest line would have blocked the claim forever. `unclaimableGuestLines` still validates every line before any cart or extension mutation (the PR-1054 invariant). Lines that fail with `validation` / `not_found` are dropped, their guest extension values deleted, and a `cart.guest.claim.lines_dropped` warning logged. Infrastructure errors still abort the claim unchanged.
- **Admin bypass kept.** `AllowWithFacts` / `FilterIDsWithFacts` honour `BypassProductVisibility` (set on admin API paths), so operator contexts skip the axis but not `ActiveForPurchase`. Pinned by `TestValidateCartStep_PurchasableAxis_BypassContextSkipsAxis`. Revisit if an admin "create order" flow lands and should respect `Purchasable=hidden`.

## Follow-up

- PR-1068 layers `RequiresLinkedParent` on this seam (hooks and/or purchasable resolution context).
- Surface blocked lines on cart GET via `HookCartValidate` / `ValidationIssues`, so customers learn before checkout submit.
- Return a reason from axis resolution (forced `hidden` vs auto/no stock vs auto/no price), so OOS can map to an inventory-style message instead of "not currently purchasable".
- Build `catalog.VisibilityOptions` once from config and share it between storefront handlers and cart/checkout. Today both use the zero value independently.
- Guest claim still checks lines one at a time (variant + product + facts per line); batch it if claim latency shows up.

## HTTP / API notes

- Variant missing still returns `not_found` from `ensureVariantPurchasable` (unchanged from PR-1054).
- Non-purchasable axis → `validation` with `"not currently purchasable"` (new).
- Non-active status → `validation` with `"not available for purchase"` (unchanged).
- Guest-cart claim: previously failed with `validation` when any guest line was unavailable; now succeeds with those lines removed. Callers that relied on the claim error (only `syncStorefrontGuestCart` today) now see success and clear the cookie.
