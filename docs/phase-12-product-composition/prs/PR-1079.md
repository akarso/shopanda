# PR-1079 — Search Index Schema Extension

Status: done

## Summary

- Extend `search.Product` with `Type`, `Status`, and the four visibility axes (storefront-effective at index time).
- Denormalize axes into Postgres `search_visible_*` columns and Meilisearch filterable fields (`type`, `status`, visibility bools).
- Storefront search/suggest/HTML listings apply index filters (`visible_in_search` / `visible_in_catalog`) **only when enforce is on**, with a fail-closed post-filter safety net. Suggest does not bake visibility into engine semantics.

## Why

Without this, a **hidden** product (Track B) still shows up in search after every other enforcement point in this phase is correct — the index is a separate data copy that needs its own filter.

**Track D / linked-child honesty:** index-time Resolve with empty Assignment leaves `RequiresLinkedParent` children with `Purchasable=false`, and that bool is denormalized + filterable via `FilterPurchasable`. Display axes are **intentionally unaffected**, and storefront search does **not** force Purchasable — so an unassigned ticket can still appear in search/suggest. Hiding unassigned tickets from search is not a goal of this PR (callers that need it can pass `FilterPurchasable`).

## Scope

- **Hard dependency:** Phase 11 Track B (search indexing rework, PR-1033–1038) — this PR extends `search.Product` and the indexer additively.
- Add `Type` + `Status` + four visibility bools to `search.Product` and both `SearchEngine` implementations (Postgres tsvector, Meilisearch).
- `SearchProductSource.WithVisibility` resolves axes via `LoadManyAnyStatus` + Resolve; non-active status → all four bools false (EffectiveAxis / storefront truth). Missing snapshot → fail closed.
- Query-time filtering via well-known filter keys; storefront uses VisibleInSearch / VisibleInCatalog only when enforce is on (does **not** force Purchasable on search).
- `SuggestQuery.Filters` — same filter keys as Search; engines apply only what callers pass.
- Meili visibility **and** status filters fail open for missing attrs: `(attr = true OR attr NOT EXISTS)` and `(status = "active" OR status NOT EXISTS)` until reindex; status stays filterable.
- Migration `110` adds denormalized columns with `DEFAULT true`; operators must full-reindex after deploy **before** enabling enforce (Meili).
- Fail-closed post-filter when facts are wired (facts≠nil is not proof the engine honored new keys).

## Out Of Scope

- Bundle/grouped/linked-specific faceting (e.g. "show only bundles").
- On-save reindex triggers for visibility-affecting changes — PR-1080.
- Always forcing Purchasable on storefront search (field + `FilterPurchasable` are available for callers).
- Hiding unassigned `RequiresLinkedParent` products from search via display axes.

## Design decisions

- **Index-time Resolve, not resolveForRequest.** Indexing must not depend on request assignment context. Empty Assignment → `Purchasable=false` for RequiresLinkedParent; display axes unchanged.
- **Storefront-effective axes:** `Status != active` → all four bools false (forced-visible drafts must not enter public search as visible). Meili also filters fail-open `(status = "active" OR status NOT EXISTS)`.
- **Missing snapshot → all four bools false** (fail closed for index).
- **Nil factsAdmin:** active → all four true; non-active → all false.
- **Suggest is not storefront-only at the engine.** Callers pass `FilterVisibleInSearch` when enforce is on (same as Search).
- **Meili missing attrs fail open** via `OR NOT EXISTS` (visibility bools **and** `status`), matching Postgres `DEFAULT true`. Do not default empty indexed `status` to `"active"` (would resurrect drafts). Ordered deploy: migrate → reindex → enable enforce.
- **Post-filter when enforce on** as fail-closed safety net; do not treat facts≠nil alone as proof the index is authoritative.
- **One `catalogVisibilityOptions(cfg)`** shared across serve / worker / CLI index wiring.
