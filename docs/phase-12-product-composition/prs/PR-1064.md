# PR-1064 — Order Line Explosion + Returns Integration

Status: done

## Summary

- `products.explode_order_lines` (`BOOLEAN NOT NULL DEFAULT false`). True is valid only on `type = bundle` with both `pricing_mode` and `stock_mode` `dynamic`. Any other combination is rejected by `Product.Validate` and by admin create/update (422). An omitted flag is stored false whenever the product is no longer allowed to explode: a type change off bundle, or a pricing or stock mode change that leaves the bundle ineligible. A bundle that still has both modes dynamic and omits the field keeps the locked flag.
- Checkout still reserves inventory as PR-1063 left it. `ReserveInventoryStep` stores `Meta["reserved_variant_qty"]` (`map[string]int` of the quantity it actually held per variant) and `Meta["reservation_holds"]` (id, variant, quantity, bundle parent). Explosion happens only in `CreateOrderStep`.
- Flag false (the default): one order line for the cart variant at the pricing-snapshot unit price. `Restockable` is false for a virtual or downloadable parent, and for a dynamic-stock bundle parent (the reservation is on the leaves). It is true otherwise, including a fixed-stock bundle. Historical `order_items` rows are not rewritten for that bundle case.
- Flag true: the parent line is dropped. Each required leaf, including virtual and downloadable, becomes an order line. Leaf unit prices are loaded once with `pricing.LookupComponentPrices` (stored store-then-global price; a leaf is not priced as a dynamic bundle). Quantity is `component.quantity * cart quantity`. Lines that share a variant id are merged when the unit price and `Restockable` flag match; a disagreement fails the step as validation. The exploded total for that cart line must equal the pricing-snapshot line total before included tax is removed from `PricingItem.Total`. Exclusive tax does not change that total.
- When a line exploded and `reserved_variant_qty` is present, those quantities must equal what reserve held: exploded simple leaves at `component.quantity * cart quantity`, plus each non-exploded line's reserve targets (the cart variant and its quantity, or the simple leaves of a non-exploded dynamic-stock bundle). Digital exploded leaves are on the order and are not reserved. A standalone virtual or downloadable line is still reserved, so its quantity is part of the map. A quantity mismatch is validation. The checkout reservations are released because the order was not saved. That release logs a failed `Release` and, on success, publishes `inventory.EventStockUpdated` for the variant and the dynamic-bundle parent, the same path `ReserveInventoryStep` uses when it rolls a reservation back. A successful release clears `Meta["reserved"]` and the hold lists. A failed release clears `Meta["reserved"]` as well and keeps only the holds that are still active, so the context does not treat that reservation as valid. The next `ReserveInventoryStep` releases those leftover holds before reserving again.
- `order_items.restockable` snapshots that decision. `Receive` classifies every return line from the order line before the transaction. Virtual and downloadable lines are not restocked. Inside the transaction the return row is locked `FOR UPDATE`. If `RestockedAt` is already set, Receive rolls back and returns success without adding stock. Otherwise `MarkReceived`, the stock increments, and `RestockedAt` commit together. The restock update matches only `WHERE restocked_at IS NULL`; zero rows is an idempotent success and the stock writes roll back. Status transitions (`Approve`, `Reject`, `Cancel`, `MarkReceived`, `Refund`) update only while `status` is still the loaded `StoredStatus`. `restocked_at` and `refunded_at` use `COALESCE`, so a stale write cannot clear a timestamp that is already stored. A lost check is `ErrStatusConflict` (HTTP 409).
- Cart-item extension snapshots are skipped for a cart variant that has no order line (an exploded parent). Other cart lines still snapshot.

## Why

Some tax and invoice jurisdictions need one line per component. Other merchants are fine with a single bundle line. The choice is per bundle, and only when both price and stock already come from the components, so a return restocks the same SKU checkout reserved. The restock decision is the order-line snapshot, so a later type change cannot invent a stock row for a digital line or skip a physical one.

## Scope

- Domain flag, admin create/update, and OpenAPI.
- `CreateOrderStep` itemization, merge, total check, reservation match, and release on failure.
- `order_items.restockable` and receive that trusts it.

## Out of scope

- Omnibus/VAT price history per component (PR-1065).
- Admin GUI and product CSV for `explode_order_lines` (PR-1066).
- Fixed-price or fixed-stock explosion.
- One-line dynamic restock of the bundle parent.
- A `bundle_components` snapshot table on the order.
- Re-targeting cart extension snapshots onto component variants. An exploded parent is not snapshotted. A kept cart line still snapshots under the cart variant id.
- Changing which SKUs `ReserveInventoryStep` reserves (unchanged). It records the quantities it already reserved.

## Design decisions

- **Both modes dynamic.** A fixed price cannot be split into component catalog prices without inventing an allocation. Fixed stock decrements the kit SKU, so an itemized return would restock the wrong identity. Admin and create-order share `catalog.ExplodeOrderLinesRequiresDynamicMessage`.
- **Omitted flag follows eligibility.** Sending true on an ineligible product is 422. Omitting the field stores false when the product is not a bundle with both modes dynamic, including a stock or pricing mode patch that leaves explode true on the locked row. Omitting it on a still-dynamic bundle keeps the locked flag.
- **Cart stays one line.** Explosion is only at order creation. Reserve is unchanged: a dynamic-stock bundle still reserves required simple leaves and skips digital leaves. The reserved quantity map is what create-order compares.
- **Required leaves only.** The walk is `catalogapp.RequiredLeafVariants`, the same one pricing and reserve use. Optional components are not order lines. Virtual and downloadable required leaves are included so the line totals can match the dynamic rollup. Their `Restockable` snapshot is false.
- **One price batch per exploded cart line.** Leaf unit price is the stored component price from `LookupComponentPrices`, not `ResolveUnitPrice` per leaf and not a second dynamic rollup.
- **Merge, then check.** Within one exploded cart line, the same variant id adds quantity when the unit price and `Restockable` flag match. That line's total must equal `PricingItem.Total` plus any included tax adjustments (inclusive tax stores the net on `Total`). Exclusive tax is not added back. Across cart lines the same rule merges into one order item. `order.NewOrder` still rejects a duplicate variant id, so the merge happens before `NewOrder`.
- **Reservation quantities.** Compared only when something exploded and `reserved_variant_qty` is set (unit tests that never reserve skip the check). The expected map is what reserve held, not every restockable order line. Exploded lines contribute restockable simple leaves at the reserved quantity; digital exploded leaves are excluded. A non-exploded line contributes its cart variant and cart quantity, including virtual and downloadable, because reserve still holds those. A non-exploded dynamic-stock bundle contributes its simple leaf quantities, not the parent order line, and that parent line is `Restockable` false. The error names the expected quantities first and the quantities reserve held second. Mismatch does not save the order. Release reuses `releaseCheckoutHolds`: a failed `Release` is logged, and a successful one publishes `inventory.EventStockUpdated` for each released variant (positive delta) and one parent event per dynamic bundle. After the attempt, `Meta["reserved"]` is false. Holds whose `Release` failed stay in meta. `ReserveInventoryStep` does not skip while that flag is false; it releases any leftover holds before creating new ones.
- **Non-exploded dynamic parent.** `orderLineRestockable` is unchanged for virtual, downloadable, simple, and fixed-stock bundles. A bundle parent that stays one line and uses dynamic stock is `Restockable` false, because the reservation was on the leaves. Migration 095 is not extended for that case.
- **Extension snapshots.** `SnapshotCartItemToOrderItem` runs only for a cart variant id that is also an order line. An exploded parent is skipped so the snapshot is not an orphan. Component lines are not given the parent's cart extensions.
- **Receive locks, then commits.** Order lines are loaded once, before the transaction. Every return line must match an order line. Restock targets are the lines with `Restockable` true. No `SetStock` and no `MarkReceived` run if that lookup fails. Inside the transaction `LockForRestock` takes `SELECT … FOR UPDATE` on the return. If `RestockedAt` is already set, the transaction rolls back and Receive returns success. Otherwise `MarkReceived` (when still approved), the locked stock increments, and `UpdateIfUnrestocked` (`WHERE restocked_at IS NULL`) commit together. Zero rows is `ErrAlreadyRestocked`: this transaction rolls back, so its stock increments do not stick, and Receive returns the return the other writer stored. A second `Receive` after `RestockedAt` is set does not add stock again. A row already `received` with `RestockedAt` nil was written by the previous non-transactional receive; the next `Receive` restocks again and then sets `RestockedAt`. Do not retry those legacy rows if stock was already incremented. New failures do not land in that state. A later `Approve` that loaded `requested` cannot write over that row: `Update` requires the loaded status and will not null `restocked_at`.
- **OpenAPI omit exception.** Omitting `explode_order_lines` on update keeps the locked flag only while the product is still a bundle with both modes dynamic. A mode change that leaves dynamic, or a type change off bundle, stores false when the field is omitted. The update schema says that explicitly.
- **Historical restockable backfill.** Migration 095 adds the column with `DEFAULT true`, which fills every existing row, then sets `restockable = false` for lines whose variant's product type is `virtual` or `downloadable`, and for lines with no matching variant. A missing catalog row is not restockable.
- **Digital restock.** Receive does not look up the live product type. The order-line snapshot is the decision. `returns.Service` does not take a product repository.
