# PR-1049 — `Type` Field + Migration

Status: planned

## Summary

- New `catalog.Type` enum on `Product`: `simple | virtual | bundle | grouped | configurable | downloadable`.
- Migration adds the column `NOT NULL DEFAULT 'simple'`, backfilling every existing product with zero behavior change.

## Why

`catalog.Product` (`internal/domain/catalog/product.go`) has no type concept at all today — only a lifecycle `Status` (draft/active/archived). Every later track in this phase (visibility rules, bundle/grouped, linked products, downloadable) needs something to key off; this PR is the foundation, not a feature by itself.

## Scope

- `internal/domain/catalog/product.go` — add `Type` field + `Type` enum type + constants, following the same pattern as `Status` (typed string, doc comment explaining it's type-separation not enum-validation at the Go level — validation happens at the application layer, see below).
- Migration: `ALTER TABLE products ADD COLUMN type TEXT NOT NULL DEFAULT 'simple'` + a CHECK constraint listing the six values (same locking-awareness pattern as `migrations/067_add_jobs_cancelled_status.sql` if the `products` table is busy enough to warrant the `NOT VALID` → `VALIDATE CONSTRAINT` split — confirm table write volume during implementation).
- Application-layer validation on create/update: reject an unknown `type` value explicitly, don't rely on the DB constraint alone to surface a clear error to the caller.
- `internal/infrastructure/postgres/product_repo.go` — `Type` round-trips through `Create`/`Update`/`Get`/`List`.

## Out Of Scope

- Any type-specific *behavior* (shipping rules, bundle components, etc.) — that's PR-1050 onward. This PR is the field and its validation only.
