# PR-1049 — `Type` Field + Migration

Status: done

> **Numbering note:** Phase 11 also shipped a different **PR-1049** (stock-change indexing) under `docs/phase-11-jobs-search-cache/prs/`. This is Phase 12 Track A’s product-type foundation — disambiguate by phase folder.

## Summary

- New `catalog.Type` enum on `Product`: `simple | virtual | bundle | grouped | configurable | downloadable`.
- Migration adds `products.type` `NOT NULL DEFAULT 'simple'` (existing rows backfill to `simple`) plus a CHECK of the six values.
- `Product.Validate` + `ProductRepo` / admin create-update reject unknown types with a clear validation error (DB CHECK remains defense-in-depth).

## Why

`catalog.Product` had only lifecycle `Status`. Later Phase 12 tracks need an explicit type to key shipping, composition, and downloadable behavior. This PR is field + persistence only — no type-specific behavior yet.

## Scope

- `internal/domain/catalog/product.go` — `Type` + `AllTypes` + `IsValid` + `Product.Validate`; `NewProduct` defaults to `TypeSimple`.
- Migrations `083` (ADD COLUMN + CHECK NOT VALID) + `084` (VALIDATE in a separate TX — ACCESS EXCLUSIVE from ADD must not span the validation scan).
- `internal/infrastructure/postgres/product_repo.go` — persist/scan `type`; call `Validate` on Create/Update; map `products_type_check` violations to validation errors.
- Admin product create/update call `Validate` before persist (application-layer guard; accept/`?type=` filter remains PR-1051).

## Out Of Scope

- Type-specific behavior (shipping, bundle components, etc.) — PR-1050+. **Persisting a non-`simple` type has no runtime shipping/tax/composition effect until those PRs land.**
- Admin API accept/filter of `type` — PR-1051 (responses already include `Type` because handlers serialize `catalog.Product`; document that additive field there / in OpenAPI).
- CSV / admin GUI — PR-1052 / PR-1053.
- Search / GraphQL exposure of `type` — Track F.
- Index on `products.type` — add when PR-1051 ships `?type=` filtering.
