# PR-1063 — Stock Rollup Per Type

Status: done

## Summary

- `products.stock_mode` (`fixed` | `dynamic`), default `fixed`. `dynamic` is valid only on `type = bundle`.
- Fixed stock uses the product's own stock row. A dynamic bundle's available quantity is `min(floor(component stock / required quantity))` across required components. Optional components do not gate availability. That quantity is not written to `stock`. Virtual and downloadable required leaves do not gate the minimum (no stock row required). A physical simple leaf still needs a stock row. When every required leaf is digital, the sellable line is `catalog.MaxDigitalBundleLineQty` (100), not an unlimited count.
- Grouped parents have no parent stock. `QuantityPositive` is false even when a stale stock row exists.
- Checkout reserves each required simple leaf for `component.quantity * line quantity` when the bundle is dynamic-stock, and does not reserve the bundle variant. Virtual and downloadable required leaves are skipped (no stock row, no reservation). A required set that is only digital reserves nothing for that line and checkout still succeeds with `reserved` true. Every other line still reserves the cart variant. Customer-facing leaf failures and a component `Reserve` failure say `bundle cannot be reserved` (HTTP Message). The leaf or stock detail stays wrapped for logs.
- Listing `QuantityPositive`, search `in_stock`, and storefront cards (they read `InStock`) use the same dynamic rollup, so a dynamic bundle is in stock when required components cover it even if the bundle's own row is 0. Fixed search `in_stock` still subtracts active reservations. Cart add previews a line against `ResolveAvailableQty` (`only N available`, including the digital-only cap of 100). Checkout `ValidateCartStep` is the gate: every line is rejected the same way before reserve. Guest-cart claim merge runs the purchasable and available-quantity check on the merged total (customer quantity + guest quantity) and drops that guest line as unclaimable when the total is above available, so the customer line is not raised past the cap. A leaf-walk validation or not-found error, and a dynamic-price component failure on add or recalculate, use `catalog.BundleCannotBeReservedMessage` (`bundle cannot be reserved`). The component or variant id stays on Unwrap and is not copied into `Message`. A missing stored price uses `bundle cannot be reserved` only when the product is a bundle (fixed or dynamic). Simple, virtual, and downloadable SKUs use the neutral message `price is not available`, with no variant id in `Message`. Claim merge drops the whole guest line when the merged total exceeds available quantity. That discard is silent: the claim succeeds, the customer quantity is left unchanged, and the guest units are not partially applied.
- JSON-LD still omits the Offer when `pricing_mode` is dynamic. When an Offer is built and `stock_mode` is dynamic, `availability` comes from one `ResolveAvailableQty` call. PDP composition does not load visibility facts into product context Meta, so JSON-LD does not read `quantity_positive` or `visibility_inputs`.
- Issue follow-up: `RejectQtyAboveAvailable` returns stock and repository infrastructure errors unchanged (it does not wrap them as `CodeValidation`). Inventory adjust, the stock CSV importer, and `StockSyncService.UpsertBySKU` lock the product row with `LockTypeAndModes` in the same transaction as `SetStock` / `SetStocks`. Enabling dynamic stock reads variant quantities with `GetStockForUpdate` on that same product-update transaction.
- Issue 3 N/A — Offer is live; FPC optional; parent `EventStockUpdated` already purges the bundle tag on checkout.

## Why

Without an explicit rollup rule, "is this bundle in stock" has no defined answer — a bundle could show as purchasable while a required component is out of stock, or a merchant with a pre-assembled kit would be forced into a rollup that does not match the physical inventory. Reservation has to follow the same rule or concurrent checkout disagrees with the listing.

## Scope

- `fixed` mode: the bundle has its own stock quantity, tracked like a `simple` product. Component stock does not affect the bundle's availability.
- `dynamic` mode: available quantity is the minimum of `floor(stock / quantity)` across `required = true` components. Optional components are ignored. Virtual and downloadable required leaves do not enter that minimum. A required set that is only digital returns `catalog.MaxDigitalBundleLineQty` (100).
- Dynamic checkout reserves the underlying simple components, not a bundle-level stock row and not digital leaves.
- Admin create/update accept `stock_mode` with the same omitted-field and type-change rules as `pricing_mode`. Enabling `dynamic` while any bundle variant still has `stock.quantity > 0` is 422 (`remove bundle stock before enabling dynamic stock`). Inventory adjust and the stock CSV importer reject a stock write on a dynamic bundle (`dynamic bundle products cannot have their own stock`). `StockSyncService.UpsertBySKU` skips a dynamic-bundle SKU, increments `Skipped`, appends it to `RejectedSKUs`, writes the other rows, and returns nil. A missing product for a known sync SKU still fails the call before any write. The product row lock is `LockTypeAndModes` and returns type, pricing mode, and stock mode.

## Out of scope

- Order-line explosion and stock decrement on the order/fulfillment record (PR-1064). This PR reserves component stock for a dynamic bundle; it does not change how the order line is stored.
- Admin GUI and CSV column for `stock_mode` (PR-1066).
- Product CSV column beyond the admin API (PR-1081) and a GraphQL field (PR-1082).

## Design decisions

- **Same mode rules as pricing.** An explicit `dynamic` token on a non-bundle is 422. An omitted mode becomes `fixed` only when the product is not a bundle, using the mode re-read under `SELECT type, pricing_mode, stock_mode FOR UPDATE`. A bundle that omits the field keeps the locked mode. Unknown tokens are rejected. The SQL CHECK allows both tokens; the type combination stays in `Product.Validate`.
- **Required components only.** Optional rows are ignored. An empty required set is not in stock and cannot be reserved. More than `catalog.MaxBundleRequiredComponents` (50) required components fails closed.
- **Exactly one active leaf variant.** Zero or many variants, a non-leaf, or an inactive component makes `QuantityPositive` false and makes checkout reservation fail with the customer message `bundle cannot be reserved` (the leaf-walk detail stays wrapped for logs). The shared probe limit is `ComponentVariantProbe` (2).
- **Integer floor, digital-only line cap.** A simple required leaf needs `floor(stock.quantity / component.quantity) > 0`. PostgreSQL integer division is that floor for these non-negative quantities. Virtual and downloadable required leaves pass with no stock row and do not lower the minimum. When at least one simple leaf gates, available quantity stays `min(floor(...))`. When every required leaf is digital, `ResolveAvailableQty` returns `catalog.MaxDigitalBundleLineQty` (100). That cap is an anti-abuse line maximum for a kit with no stock gate; it is not unlimited and it is not a stock level. Listing `in_stock` stays the boolean "at least one kit", which is true for that cap. Cart add previews the same integer (`only N available`). Checkout `ValidateCartStep` enforces it for every line, including the digital cap and a physical simple-leaf rollup, before reserve. The bundle's own stock row is not read in dynamic mode.
- **Claim merge uses the merged total.** `unclaimableGuestLines` passes the quantity the line would have after the claim into `ensureVariantPurchasable`. Assign checks the guest line alone. Merge checks customer quantity plus guest quantity. When that total is above available, the whole guest line is dropped as unclaimable and the customer line is left as it was. The drop is silent: claim returns the customer cart without an error, and no partial guest quantity is applied (a customer line of 1 plus a guest line of 1 stays 1 when `floor(stock/required)` is 1; a customer line of 100 plus a guest line of 100 stays 100).
- **Own stock before dynamic.** Enabling dynamic stock while any variant of the bundle has `stock.quantity > 0` is 422. That read is `GetStockForUpdate` on the stock repo bound to the open product-update transaction, after `LockTypeAndModes`, so an adjust cannot commit a quantity between the check and the mode commit. A missing stock repository on that write is 500. Name-only edits do not run the check. Admin adjust, the stock CSV importer, and warehouse `UpsertBySKU` lock the product row in the same transaction as the stock write. Adjust and the importer reject a dynamic bundle. `UpsertBySKU` skips the kit SKU, records it on `RejectedSKUs`, stores the remaining rows, and returns nil. Returning an error after a partial write would make ERP retries loop. A missing transaction starter or a repository that cannot join the transaction fails closed.
- **Reserve what the rollup counts.** A dynamic bundle does not reserve its own variant. Each required simple component is reserved for `component.quantity * line quantity`. Virtual and downloadable required leaves are not targets. A digital-only required set returns an empty target list; Execute succeeds and sets `reserved` true with no reservation ids for that line. A fixed bundle, including one that has components, still reserves the cart variant once. Component reserves also publish one stock event for the parent product. A component `Reserve` failure (including insufficient stock) uses the same customer message, `bundle cannot be reserved`.
- **JSON-LD and search.** Dynamic pricing still skips the Offer. Dynamic stock sets `availability` from one `ResolveAvailableQty` call. A nil `ProductContext.Ctx` fails closed (OutOfStock) instead of querying on `context.Background()`. The unused Meta fact branch was removed: stuffing `quantity_positive` or `visibility_inputs` does not override the rollup, because the PDP pipeline never loads those facts. Search `in_stock` uses the same dynamic SQL as `QuantityPositive`, including a virtual required component with no stock row. Storefront cards read that `InStock` flag.
- **Customer message.** Cart and checkout share `catalog.BundleCannotBeReservedMessage`. `RequiredLeafVariants`, the dynamic price check on add, and cart `lookupPrice` / recalculate return that message for a bundle missing price and for leaf-walk or component-price failures, with the leaf or variant detail on Unwrap. `Message` does not include the component variant id. A missing price on a simple, virtual, or downloadable SKU uses `price is not available` and does not say "bundle". `ResolveUnitPrice` stamps that product type with `errors.As`. A component `MulChecked` overflow or a component currency that does not match the requested currency uses the same customer message; the component id stays on Unwrap. `RejectQtyAboveAvailable` keeps a validation or not-found `Message` when it is set. An empty `Message` on those codes is wrapped as `available quantity` with the original error on Unwrap, so `err.Error()` is not copied onto `Message`. A stock or repository failure that is not validation or not-found is returned unchanged, so guest-cart claim aborts instead of dropping the line.
- **Parent stock event on a digital-only reserve.** N/A. Checkout still publishes `EventStockUpdated` for the parent only when a component reservation was created. A digital-only required set has zero targets, so no parent event is published. Search refresh for that case stays on the next reindex.
