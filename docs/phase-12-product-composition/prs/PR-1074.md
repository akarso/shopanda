# PR-1074 — `Downloadable` Type + File Asset Attachment

Status: planned

## Summary

- Reuses the existing Media domain/storage (local or S3-compatible, `media.Storage` port) for the underlying file.
- `Type = downloadable` implies no shipping (per PR-1050).

## Why

`downloadable` needs to be more than "virtual with a file attached" for delivery, expiry, and licensing to work correctly (PR-1075), but the *storage* of the file itself has no reason to be a new mechanism — the Media domain already handles upload/storage.

## Scope

- Product-to-asset attachment: one or more files per `downloadable` product, referencing the existing Media domain's asset records rather than a parallel file-storage path.
- `Type = downloadable` products get `RequiresPhysicalShipping = false` via PR-1050's derivation — no new logic here, just confirming the type participates in that existing rule.
- Domain-level validation: a `downloadable` product should have ≥1 attached file before it can be `active`/purchasable — decide during implementation whether this is a hard validation or a soft warning surfaced in the admin GUI.

## Out Of Scope

- Download link generation, expiry, limits — PR-1075.
- Actual delivery endpoint — PR-1077.

## Follow-up

- PR-1075 builds the grant/expiry model on top of this PR's file attachment.
