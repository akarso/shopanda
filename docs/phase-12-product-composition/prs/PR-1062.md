# PR-1062 — Bundle/Grouped Pricing Rollup

Status: planned

## Summary

- Bundle: `fixed` (merchant sets one price, ignoring component prices) or `dynamic` (sum of selected components, optionally minus a bundle-level discount).
- Grouped: no parent price at all — only members are priced.

## Why

A bundle's price has to come from somewhere real, and "somewhere" needs to be a documented, merchant-chosen mode rather than an implicit default, since fixed and dynamic have genuinely different implications for margin and for what happens when a component's price changes. This depends on PR-1048 (zero-price products) for the case where a dynamic bundle's selected components legitimately sum to 0 (e.g. a promotional bundle).

## Scope

- `dynamic` mode: bundle-aware base-price step integrated into the existing pricing pipeline (`BasePriceStep` → plugin steps → `FinalizeStep`), summing selected required components (+ any selected optional ones) at the moment of pricing, not cached at catalog-edit time — a component price change should be reflected immediately, same as any other price change.
- `fixed` mode: bundle has its own `Price` row, exactly like a `simple` product; components exist for stock rollup (PR-1063) and order-line explosion (PR-1064) purposes, not pricing.
- Grouped: confirm no code path attempts to price a `grouped` product directly — reject at the domain layer if someone tries to set a price on one, rather than silently ignoring it.

## Out Of Scope

- Stock rollup — PR-1063.
- Per-component Omnibus/VAT tracking — PR-1065.

## Follow-up

- PR-1063, PR-1064, PR-1065 all build on the pricing-mode decision this PR makes.
