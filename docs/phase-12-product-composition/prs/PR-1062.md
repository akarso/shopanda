# PR-1062 — Bundle/Grouped Pricing Rollup

Status: done

## Summary

- `products.pricing_mode` (`fixed` | `dynamic`), default `fixed`. `dynamic` is valid only on `type = bundle`.
- `pricing.ResolveUnitPrice` is the shared base-price lookup for `BasePriceStep` (step name stays `base`) and cart `lookupPrice` / recalculate. A dynamic bundle's unit price is the sum of required components at resolution time. That sum is not written to `prices` or `price_history`.
- A grouped parent is not purchasable. `ensureVariantPurchasable` rejects it before price lookup, even when a stale price row exists. `HasPrice` is always false for grouped. Admin price PUT and the CSV price importer still reject price writes.
- A dynamic bundle cannot have its own price row. Admin price PUT and the CSV price importer reject those writes. The price PUT begins a transaction, locks the product (`LockTypeAndModes` through `ProductRepo.WithTx`), and upserts on that same transaction (`PriceRepo.WithTx`). Grouped and dynamic are rejected from the locked type and mode, so a concurrent mode switch cannot commit an own price. Create/update that results in `dynamic` returns **422** (`remove bundle prices before enabling dynamic pricing`) while any variant of that product still has a `prices` row. Unwired variant or price repos on that write return **500** (`product admin: variant price check is not configured`). A create with those repos wired and no variants yet is allowed; an empty product id skips the row scan after the repos are confirmed. Cart prices the bundle with `ResolveUnitPrice`. PDP and PLP price indication skip a stored price when `pricing_mode` is dynamic. JSON-LD emits no Offer for that mode until `ResolveUnitPrice` supplies the price (a stock-only Offer is omitted).
- PDP Add is shown when the product has a variant. It does not read the request currency. PLP cards have no Add control. Listing `HasPrice` stays currency-agnostic, so a later PLP Add that keys off `HasPrice` / `Purchasable` can show for a dynamic bundle whose components are priced in another currency. `AddItem` still rejects that cart. Follow-up: hide Add when `ResolveUnitPrice` fails for the request currency.
- Listing `HasPrice` is a coarse, currency-agnostic flag. It does not match the resolver on currency. It is true only when the required count is between 1 and `catalog.MaxBundleRequiredComponents` (50) and every required component is an active leaf with exactly one variant and a **global** price row (`prices.store_id = ''`). Amount 0 counts. A global USD row counts for PLP; a store-only row does not. AddItem does not trust that flag for dynamic bundles: after status and visibility, `ensureVariantPurchasable` calls `ResolveUnitPrice` with the cart currency and request store, and a failed resolve is validation (not 500). A component priced only in global EUR cannot be added to a USD cart. Fixed products still need their own row.
- `pricing_mode=dynamic` on a non-bundle is **422**. Changing type off bundle coerces to `fixed` only when `pricing_mode` is omitted, and that default uses the mode re-read from the locked row. Every product update that persists takes that lock, including a name-only edit, so an omitted `type` / `pricing_mode` cannot write back a stale `FindByID` mode.
- Cart reprice of lines already in the cart loads products with `IncludeNonActiveProducts`. Decrease-quantity and removing another line still reprice an archived line. Add and quantity increase stay on the active-only purchasability check.
- Dynamic-bundle purchase does not use listing `HasPrice` as the price gate. Other purchasable axes still apply. `ResolveUnitPrice` with the cart currency and store accepts a store-only component price.
- CSV price import locks the product (`LockTypeAndModes` on `ProductRepo.WithTx`) in the same transaction as the price upsert (`PriceRepo.WithTx`) and re-checks grouped/dynamic before the write.

## Why

A bundle's price has to come from a merchant-chosen mode. Fixed and dynamic disagree about what happens when a component price changes, and the cart's pre-pipeline lookup must not diverge from `BasePriceStep`. Grouped products are a display group: only members are priced.

## Design decisions

- **One resolver.** Cart add prices the line before the pipeline runs, then recalculate prices it again. Both call `ResolveUnitPrice`. `NewService` builds `UnitPriceSources` from the required repos; `NewBasePriceStep` receives the same repos from `wire_services.go`. Results are cached for that cart operation by `(variantID, currency, storeID)`.
- **Dynamic sum is not stored.** A component price change shows up on the next resolution. `Upsert` is not called for the bundle variant. Price PUT locks the product row and rejects a dynamic bundle from that locked mode before the price upsert on the same transaction. CSV import rejects a dynamic bundle. Switching a product to dynamic is 422 until its own price rows are deleted, and 500 when `WithVariantPrices` is missing. Price indication skips a stored price when the mode is dynamic. JSON-LD emits no Offer for that mode. A follow-up wires `ResolveUnitPrice` into those surfaces. PDP Add stays variant-based; a currency-aware Add for dynamic bundles is the same follow-up.
- **Required components only.** Optional rows are ignored. Selecting optional components is out of scope. An empty required set is an error. A sum of 0 is allowed (PR-1048). More than `catalog.MaxBundleRequiredComponents` (50) required components is a validation error, and `HasPrice` is false past that cap. Variant reads use `ListByProductIDs`. Component prices use store-then-global: the batch port, then a singular global lookup for any variant the batch left empty.
- **Exactly one variant per required component.** Zero or many variants is a validation error. The probe limit is 2. `HasPrice` uses the same rule in SQL.
- **Active leaf components.** A required component must be `simple`, `virtual`, or `downloadable` and `active`, unless the context has operator scope (`IncludeNonActiveProducts`). `HasPrice` always requires active leaves; it has no operator bypass.
- **Store then global** for the bundle's own row (fixed) and for each component variant (dynamic), matching `FindByVariantCurrencyAndStore`. Listing `HasPrice` stays coarser: only a global row (`store_id = ''`) counts, in any currency. Dynamic-bundle add does not fail that axis on `HasPrice`; `ResolveUnitPrice` with the cart currency and store is the price gate, so a store-only component price can be added. Cart reprice of an existing line includes non-active products so an archived line can be decreased or left in place when another line is removed. Add and quantity increase still require an active product.
- **Grouped is not purchasable.** `ensureVariantPurchasable` returns `grouped products are not purchasable` before price lookup. `HasPrice` is false even when a stale row exists. Price PUT, CSV import, and `ResolveUnitPrice` still reject pricing the parent. The guard is not inside `NewPrice`.
- **`dynamic` only on bundles.** An explicit `dynamic` token on any other type is 422. Coerce to `fixed` only when the field is omitted and the product is not a bundle (including a type change off bundle). The type-change path re-reads `pricing_mode` with `SELECT type, pricing_mode FOR UPDATE` before that default. Every persisting product update uses that same lock, so a name-only edit keeps the locked mode instead of the pre-lock `FindByID` value. Unknown tokens are rejected. The SQL CHECK allows both tokens; the type combination stays in `Product.Validate`. Enabling dynamic while any own price row exists is 422.
- **`HasPrice` for dynamic bundles** does not require a price row on the bundle. Amount 0 on a required component counts. It is a listing flag: global row, any currency, required count ≤ 50. It does not match the resolver on currency. Fixed bundles still need their own row, so a component price does not make a fixed bundle purchasable.
- **Production price sources are required.** `NewBasePriceStep` panics unless prices, variants, products, and bundle components are all set. `cart.NewService` panics on the same nil set. `ResolveUnitPrice` errors instead of returning a stored row when variants or products are nil. `NewBasePriceStepLegacy` is the stored-row test helper. `wire_services.go` fails startup when a dependency is missing and passes the repos into both constructors. CSV price import errors when the product repository is nil.

## Out of scope

- Optional component selection, bundle discount, stock rollup (PR-1063), order-line explosion (PR-1064), Omnibus catalog history for kits (PR-1065). Per-line VAT stays PR-1076.
- PDP / PLP / JSON-LD display of the dynamic sum. Price indication skips a stored price. JSON-LD omits the Offer. None of them call `ResolveUnitPrice` yet. PDP Add is shown for any product that has a variant; it does not hide a dynamic bundle whose components lack a price in the request currency. PLP has no Add button. A follow-up should hide Add when `ResolveUnitPrice` fails for that currency, because listing `HasPrice` is currency-agnostic.
- Admin composition GUI and a `pricing_mode` control (PR-1066).
- Product CSV column for `pricing_mode` (PR-1081).
- GraphQL field (PR-1082).
