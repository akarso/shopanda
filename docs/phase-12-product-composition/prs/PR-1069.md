# PR-1069 — `ProductAssignment` Instance Domain

Status: planned

## Summary

- New domain binding one purchased/issued child unit (an order item, or a serialized unit for a digital "card in a phone" case) to one purchased parent unit.
- State machine: `unassigned → assigned → revoked` (revoke, not delete).

## Why

This is the piece with no existing analog anywhere in the codebase — every other new concept in this phase extends something that already exists (pricing pipeline, stock, tax, returns); this one doesn't. The closest precedent *in shape* (not in domain) is the store-credit ledger's append-only entry model — worth reviewing during implementation for conventions (audit trail, no hard deletes) even though the domain is unrelated.

## Scope

- `product_assignment(id, parent_order_item_id, child_order_item_id, status, created_at, revoked_at)` — `revoked`, not deleted, so a ticket's assignment history is preserved even after a reassignment.
- Domain type `catalog.ProductAssignment` (or a new `internal/domain/assignment` package if it doesn't fit cleanly under `catalog` — decide during implementation based on how much it needs to reference order-item internals vs. catalog internals).
- State transitions: `unassigned` (default, set when a `RequiresLinkedParent` item is purchased without an assignment target — see PR-1070) → `assigned` (either at cart time or post-purchase) → `revoked` (admin or customer self-service action; a revoked assignment can be replaced by a new `assigned` record, not resurrected).
- No business logic about *when* assignment can happen lives here — that's PR-1070. This PR is the state model and its valid transitions only.

## Out Of Scope

- Cart-time vs. post-purchase assignment flow — PR-1070.
- Admin-facing list/create/revoke API — PR-1071.
