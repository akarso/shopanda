# PR-1069 — `ProductAssignment` Instance Domain

Status: done

## Summary

- New domain binding one purchased/issued child unit to one purchased parent unit.
- State machine: `unassigned → assigned → revoked` (revoke, not delete). A revoked row stays for history; reassignment inserts a new `assigned` record.

## Why

This is the piece with no existing analog anywhere in the codebase — every other new concept in this phase extends something that already exists (pricing pipeline, stock, tax, returns); this one doesn't. The closest precedent *in shape* (not in domain) is the store-credit ledger's append-only entry model — audit trail, no hard deletes — even though the domain is unrelated.

## Scope

- `product_assignments(id, parent_order_item_id, child_order_item_id, status, created_at, revoked_at)` — `revoked`, not deleted, so a ticket's assignment history is preserved even after a reassignment.
- Domain type `assignment.ProductAssignment` in `internal/domain/assignment` (not under `catalog` — see design decisions).
- State transitions: `unassigned` (default, set when a `RequiresLinkedParent` item is purchased without an assignment target — see PR-1070) → `assigned` (either at cart time or post-purchase) → `revoked` (admin or customer self-service action; a revoked assignment can be replaced by a new `assigned` record, not resurrected). `unassigned → revoked` is also legal, with a null parent, so a never-assigned unit can be released (cancel/return) without inventing a stand-in parent. `CurrentByChild` then returns nil.
- No business logic about *when* assignment can happen lives here — that's PR-1070. This PR is the state model and its valid transitions only.

## Out Of Scope

- Cart-time vs. post-purchase assignment flow — PR-1070.
- Admin-facing list/create/revoke API — PR-1071.
- Returns auto-revoke — PR-1072.

## Design decisions

- **New `assignment` package, not `catalog`.** Instance assignment references opaque unit ids (order lines / serialized units), not catalog products. `catalog.AssignmentContext` is a purchase-time hint (PR-1068) and must stay a different type. Eligibility stays in `catalog` (PR-1067).
- **Table name is plural.** Spec drafted `product_assignment`; `product_assignments` matches `orders` / `order_items` / `linked_eligible_parents`.
- **Unit ids are opaque TEXT, not FKs.** `order_items` has composite PK `(order_id, variant_id)` and no unique id. A digital "card in a phone" is not an order line. PR-1070 decides how ids are minted. Domain `Validate` only checks non-empty child, parent-required-when-assigned, and no self-bind.
- **`parent_order_item_id` is NULL when unassigned.** Assigned rows require a non-empty parent. A revoked row may have a parent (was assigned) or NULL (never assigned, then released). `revoked_at` is set iff status is `revoked`.
- **One current row per child.** Partial unique index `product_assignments_child_current` on `child_order_item_id WHERE status IN ('unassigned', 'assigned')`. Many revoked rows are allowed. After revoke, `CreateAssigned` inserts a new row. `CurrentByChild` is the live row only; a leftover `unassigned` is still live until it is assigned or revoked.
- **Cart-time skips `unassigned`.** `NewAssigned` / `CreateAssigned` insert `assigned` directly. Post-purchase uses `CreateUnassigned` then `Assign`. Do not `CreateAssigned` on top of an existing current row — that is a conflict; transition the existing row with `Assign`.
- **Revoke is terminal on that row.** `Assign` is only `unassigned → assigned`. `Revoke` is `assigned → revoked` or `unassigned → revoked` (null parent). No `revoked → assigned`.
- **Parent is written once.** `NewAssigned` and `Assign` are the only writers of `ParentOrderItemID`. `storedParent` snapshots the persisted parent the same way `storedStatus` snapshots status. `Update` writes `parent_order_item_id` only on `unassigned → assigned`. Any other in-memory parent change is validation and is not written — a revoked history row cannot be rewritten.
- **Optimistic status write.** `storedStatus` + `Update ... WHERE status = storedStatus`, same shape as returns. Zero rows is `ErrStatusConflict` (mapped to `conflict` in the service). `revoked_at` uses `COALESCE` so a stale write cannot clear it.
- **Assignment id is UUID.** `FindByID` rejects a non-UUID with `id.IsUUID` before the query (`validation`). Query `22P02` is also mapped to `validation`.
- **`Validate` does not mutate ids.** Trimming happens in `New*`, `Assign`, and the service.
- **`WithTx` is postgres-only.** The domain port does not declare it. PR-1070 type-asserts the adapter to insert in the checkout transaction. `TestProductAssignmentRepo_WithTx_RollbackInvisible` inserts on the bound repo, rolls back (base `FindByID` is nil), then commits a second insert (base `FindByID` sees the row).
- **No order/product lookup.** This PR does not load `order_items` or check `IsEligible` / `RequiresLinkedParent`. Those are PR-1070.
- **No admin HTTP.** Wired at serve startup (`ProductAssignmentRepo` + `ProductAssignmentService` on `serveRuntime`). Admin API ships in PR-1071.

## Follow-up

- PR-1070 writes `ProductAssignment` at cart-time (`CreateAssigned`) and post-purchase (`CreateUnassigned` then `Assign`), and calls `IsEligible` there. It must not treat an `unassigned` unit as "not purchasable" — that flag is `RequiresLinkedParent` (PR-1068), evaluated before purchase.
- PR-1071 — admin list/create/revoke API.
- PR-1072 — return approval/refund transitions the associated row to `revoked`, including a never-assigned (`unassigned`) unit, which keeps a null parent.
