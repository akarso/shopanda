# PR-1054 — Enforce `Status = active` in Core Read Paths

Status: planned

## Summary

- `internal/infrastructure/postgres/product_repo.go`'s `List`, `FindByID`, and `FindByCategoryID` apply no status filter today — fix that.
- `cart.Service.AddItem` never checks product status — fix that too.

## Why

This is a real, standalone bug, independent of the rest of Track B or this phase: a `draft` or `archived` product is returned by the public product API/PDP/PLP today, and is addable to cart, because nothing in the core read/write path checks `Status` at all. Only the search index (`internal/infrastructure/postgres/search_engine.go`) and the sitemap generator filter on `Status = active` today — the two places that happened to need it for an unrelated reason, not because visibility was deliberately designed. Ships first in Track B because it's correct regardless of whether the rest of the four-axis visibility model (PR-1055) lands.

## Scope

- `product_repo.go`: `List`, `FindByID`, `FindByCategoryID` — add `WHERE status = 'active'` for public/storefront-facing calls. Admin-facing calls (which need to see drafts) must retain an unfiltered path — this PR needs to thread a "caller context" (admin vs. public) through the repository interface or add an explicit `FindByIDIncludingDrafts`-style method for admin use, not silently filter admin calls too.
- `cart.Service.AddItem` (`internal/application/cart/service.go`): check the product's `Status` before adding a line item; reject non-`active` with a clear `apperror`.
- Confirm no admin workflow (e.g. previewing a draft product) breaks — this is exactly the kind of change that needs an explicit admin-vs-public distinction, which PR-1056 formalizes properly; this PR does the minimum to close the bug without waiting for that full split.

## Out Of Scope

- The four-axis visibility model itself — PR-1055. This PR only fixes the pre-existing `Status` gap.

## Follow-up

- PR-1056 formalizes the admin-vs-public API boundary this PR has to informally respect.
