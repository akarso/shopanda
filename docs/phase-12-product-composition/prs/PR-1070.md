# PR-1070 — Assignment Flow: Cart-Time + Post-Purchase

Status: done

## Summary

- Cart-time assignment: HTTP writers stamp `AssignmentContext` (parent product, parent unit, or deferred). When a parent is present, `IsEligible` and ownership run. On order create, one application function writes `ProductAssignment` — `CreateAssigned` if a parent unit was selected, otherwise `CreateUnassigned`.
- Ownership is payment-complete or payable 0. A declined or in-flight pending payment is not an owned parent. Checkout failure after `create_order` fails a still-pending order with no accepted charge, restores redeemed store credit without the issuance cap, and revokes current rows. An accepted pending Stripe payment (provider ref set) is left for the webhook. `initiate_payment` still revokes on decline and provider error. One `payment.failed` handler fails a still-pending order, restores `StoreCreditApplied` once (order-id idempotency key, no issuance cap), then revokes. A publish error returns 500 so the webhook retries.
- Post-purchase assignment: a signed-in customer binds an owned unassigned child unit to an owned eligible parent unit via `POST /api/v1/account/assignments`.

## Why

Real usage needs both paths. A customer topping up an already-owned card selects that instance at cart time. Buying card and ticket together (or skipping selection) stays purchasable per PR-1068 and starts `unassigned` until a later self-service assign. Purchasable and “has a completed assignment” stay different questions.

## Scope

- Unit id mint: `assignment.UnitID(orderID, variantID)` → `orderID + "/" + variantID`.
- `catalog.AssignmentContext.ParentUnitID`. Empty is deferred, parent product, or parent unit.
- Cart line persist `assignment_parent_unit_id` (migration 100). HTTP cart add (REST, storefront form, storefront JSON) writes the context. Cart JSON returns the stamped fields.
- `application/assignment.Flow`: `CheckPurchase`, `CheckPurchaseAll`, `RecordPurchase`, `RevokeForOrder`, `AssignOwned`, `CurrentOwned`, `ListOwnedParents`. State transitions stay on `Service`.
- Cart `ensureVariantPurchasable` and checkout `ValidateCartStep` call `CheckPurchaseAll` on the products that require a parent (the line itself, or each required linked leaf of a bundle).
- `CreateOrderStep` writes assignments through `RecordPurchase` only. Assignment lines fail closed unless the order repo, the assignment repo, and `*sql.DB` share one transaction. Duplicate exploded leaf variants collapse to one unit; different assignment contexts for the same leaf are rejected before `BeginTx`. Exploded bundles record each linked leaf; a non-exploded bundle is one unit whose eligibility uses the linked leaves.
- Workflow compensation: after `created_order_id` is set, `FailIfPending` marks the order failed only when the stored row is still pending. Confirmed or cancelled orders are left alone. A failed unpaid order restores `StoreCreditApplied` via `storecredit.Restore` (no issuance cap), including when it is already failed, and publishes `checkout.unpaid_failed` so the same key can be retried. Completed and accepted pending payments are left for the webhook. Create-order rollback also uses `Restore`.
- Storefront account API: list eligible owned parents, get current assignment, assign. Admin API remains PR-1071.

## Out Of Scope

- Admin-facing assignment management UI — PR-1071 (API), PR-1073 (GUI).
- Returns auto-revoke — PR-1072.
- Same-cart auto-bind of a card bought in the same order (that path is deferred + post-purchase).

## Design decisions

- **One write function.** Checkout does not call `CreateAssigned` / `CreateUnassigned` itself. `Flow.RecordPurchase` is the only policy: parent unit → assigned; otherwise unassigned.
- **Eligibility when a parent is present.** Deferred-only skips `IsEligible`. A parent product or unit requires a matching rule. A unit also requires the customer to own that order line. Ownership is a completed payment or payable 0 — not `pending` order status.
- **Shared transaction or fail closed.** Checkout does not save the order and then insert assignments. If the adapters cannot share a transaction, credit is restored and no order is written.
- **Post-commit failure fails the order unless a charge was accepted.** `FailIfPending` writes `failed` only when the stored status is still pending. Shipping, a decline, a provider error before accept, or payable 0 restore credit via `storecredit.Restore` (including create-order rollback) and revoke. An already-failed order still restores (idempotent key). Confirmed or cancelled is not overwritten. A synchronous approve and an accepted pending payment set payment meta before `UpdateStatus` so persist errors do not look like “no charge.” `AssignOwned` / `ListOwnedParents` resolve required linked leaves the same way checkout does. Unit ids are rebuilt with `CanonicalUnitID` before lookup and write.
- **Parent picker pagination** is out of this PR. `ListOwnedParents` still loads the customer’s order history and filters in process; a bounded SQL read that selects eligible owned lines first is a follow-up persistence/API change.
- **Units follow order lines.** An exploded linked leaf is the unit. A non-exploded bundle line is the unit; `IsEligible` still uses the leaf product ids. Two exploded lines that share a leaf collapse to one unit.
- **Unit ids are minted here.** Opaque TEXT from PR-1069; this PR picks `orderID/variantID` (one unit per order line).
- **Guest cannot name a parent unit.** Deferred or a parent product still leaves the PR-1068 gate; instance binding needs a signed-in owner.
- **Unassigned is not “not purchasable”.** `RequiresLinkedParent` stays the pre-purchase gate.
