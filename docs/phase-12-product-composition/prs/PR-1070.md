# PR-1070 — Assignment Flow: Cart-Time + Post-Purchase

Status: planned

## Summary

- Both assignment paths are supported: cart-time (customer selects an existing owned card instance while buying a ticket) and post-purchase (an unassigned, already-purchased ticket gets assigned later via self-service or admin action).

## Why

Real usage needs both, not one — a customer topping up an already-owned card with more tickets is a different flow from buying card and ticket together in the same order, and neither should be forced through the other's UX. This was an explicit design decision during planning (see the phase `ROADMAP.md`'s "Design notes"), not something left ambiguous.

## Scope

- Cart-time: if the customer has ≥1 eligible card instance (via PR-1067's eligibility rules) associated with their account, cart UI/API can offer selecting one; on order completion, a `ProductAssignment` (PR-1069) is created directly in `assigned` state.
- No selection at cart time (or no eligible card yet owned): the ticket is still purchasable per PR-1068 (a `RequiresLinkedParent` item's `Purchasable` computation must allow "purchasable now, assign later" as a valid path, not force assignment before purchase) — the resulting order item's `ProductAssignment` starts `unassigned`.
- Post-purchase assignment: a self-service account-page action or an admin action that creates the `assigned` record for a previously `unassigned` order item, choosing from the customer's eligible card instances at that time.
- Confirm this doesn't conflict with PR-1068's purchasability gate: "purchasable" and "has a completed assignment" are different questions evaluated at different times — a `RequiresLinkedParent` product being `Purchasable=true` does not require an assignment to exist yet, only that a valid path to eventually assign it exists.

## Out Of Scope

- Admin-facing assignment management UI — PR-1071 (API), PR-1073 (GUI).

## Follow-up
