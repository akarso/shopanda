# PR-1082 — GraphQL Read Parity

Status: planned

## Summary

- Extend `plugins/core/graphql`'s existing product schema with `Type`, the visibility axes, and bundle/grouped/linked-child relationships.

## Why

`plugins/core/graphql` already exposes `product`/`products`/`productBySlug` queries (`schema.go`), read-only, mapping `catalog.Product` directly — this is schema extension of something already shipped, not new infrastructure, matching Phase 7 Track E's established "same operation via admin REST, GraphQL, and plugin registration" parity precedent. This is a different question from Phase 11's "REST only for the new jobs/cache/scheduler admin endpoints" decision, which was about *new admin surfaces* with no existing GraphQL presence — the product catalog already has one.

## Scope

- Add `type` and the four visibility-axis fields to `productGraph`/`productType` (`plugins/core/graphql/schema.go`).
- Add resolvers for bundle components, grouped members, and linked-eligibility/assignment relationships — read-only, matching what the GraphQL surface already is today (no mutations added by this PR).
- Apply PR-1056's public/storefront visibility-enforcement boundary here too — GraphQL is a public read surface, so it needs the same enforcement REST got in PR-1057, not a separate unfiltered path.

## Out Of Scope

- Any GraphQL mutation surface for admin actions (assignment create/revoke, bundle component management, etc.) — matches the existing GraphQL surface's read-only scope; admin actions stay REST-only, consistent with the rest of the admin API.

## Follow-up

- None further within Track F for GraphQL specifically.
