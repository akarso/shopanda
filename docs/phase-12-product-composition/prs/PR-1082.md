# PR-1082 — GraphQL Read Parity

Status: done

## Summary

- Extended `plugins/core/graphql` product schema with `type`, nested `visibilityModes`, `requiresLinkedParent`, and read-only `bundleComponents` / `groupedMembers`.
- **Public schema only:** linked-eligibility allowlist fields (`linkedEligibleParents` / `linkedEligibleCategories`) are **not** exposed on GraphQL (admin REST / ProductsRead only). `requiresLinkedParent` remains as product state.
- Listings return `ProductConnection` (`items`, `truncated`, `hasMore`, `nextAfter`, `depthLimited`) with `after` resume (mirrors REST `visibilityListMeta` / `ListVisiblePage`).
- **Breaking listing type:** clients must read `items` (not a bare product array) and resume with `nextAfter` when `truncated` is true.
- Wired PR-1056/1057 visibility enforcement: `AllowWithFacts` on `product` / `productBySlug` (Individually → null when denied); `ListVisiblePage` on `products` / `categoryProducts` (Catalog). Facts attached only when `catalog.visibility.enforce` is on.
- Composition children: batch `ListByIDs`, gate once with `FilterWithFacts` (Individually), omit hidden/missing rows, fail the field on ListByIDs/facts errors.
- Registered GraphQL root fields in `storefront.PublicProductVisibilityRoutes()` (`GQL` method, EnforceIn `PR-1082`); schema sync test pins product-returning Query roots to that audit list.

## Why

`plugins/core/graphql` already exposes `product`/`products`/`productBySlug` queries (`schema.go`), read-only, mapping `catalog.Product` directly — this is schema extension of something already shipped, not new infrastructure, matching Phase 7 Track E's established "same operation via admin REST, GraphQL, and plugin registration" parity precedent. This is a different question from Phase 11's "REST only for the new jobs/cache/scheduler admin endpoints" decision, which was about *new admin surfaces* with no existing GraphQL presence — the product catalog already has one. GraphQL remains a public surface, so admin-only allowlists stay off it.

## Scope

- Add `type` and the four visibility-axis fields to `productGraph`/`productType` (`plugins/core/graphql/schema.go`).
- Add resolvers for bundle components and grouped members — read-only, public-gated.
- Apply PR-1056's public/storefront visibility-enforcement boundary — GraphQL needs the same enforcement REST got in PR-1057, not a separate unfiltered path.
- Expose listing truncation/resume meta so clients do not treat an empty truncated page as end-of-catalog.

## Out Of Scope

- Any GraphQL mutation surface for admin actions (assignment create/revoke, bundle component management, etc.) — matches the existing GraphQL surface's read-only scope; admin actions stay REST-only.
- GraphQL assignment-instance APIs / linked-eligibility allowlist reads — follow-up if a public assignment story appears; allowlist remains admin REST.
- Resolved visibility bools on the GraphQL product (modes only — Resolve without AutoBasis facts is not storefront-useful).
- GraphQL query complexity / depth limits framework — follow-up if abuse becomes a concern; not in this PR.
