# PR-1055 — Four-Axis Visibility Model

Status: planned

## Summary

- New fields: `VisibleInCatalog`, `VisibleInSearch`, `VisibleIndividually` (direct PDP access), `Purchasable`.
- Each computed by a documented default rule, with a per-axis `VisibilityMode: auto | visible | hidden` override.

## Why

A single visibility flag can't express real cases: a promo-only product that's visible but not purchasable, a ticket that must be invisible *and* unpurchasable until assigned (Track D), a product intentionally excluded from search but still directly linkable. Four independent axes, each overridable, covers all of these without a proliferation of one-off boolean flags per feature.

## Scope

- Default computation rule (applies when `VisibilityMode = auto`, the default): `Status = active AND quantity > 0 AND a price exists AND assigned to ≥ 1 store/view`. Category assignment is a config-level toggle (off by default) — many legitimate products are intentionally uncategorized (up-sell items, gift cards, and Track D's tickets), so requiring a category by default would be wrong.
- `VisibilityMode: auto | visible | hidden` per axis — `visible`/`hidden` force the axis regardless of what the default rule would compute, for the cases merchants need to override in either direction.
- This PR is the domain model and computation only — enforcement at the read paths is PR-1057, the API-surface split is PR-1056.

## Out Of Scope

- Enforcement — PR-1056/PR-1057.
- The specific `Purchasable = false` trigger from Track D's `RequiresLinkedParent` — that's PR-1068, built on top of this PR's `Purchasable` axis.
