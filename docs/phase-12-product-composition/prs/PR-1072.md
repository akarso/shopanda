# PR-1072 — Returns Integration for Assigned Children

Status: done

## Summary

- A ticket order line remains independently returnable through the existing Returns/RMA path (Phase 6 / PR-1064 groundwork). Returning it does not touch the card's order line.
- On return approve (and again on refund as an idempotent safety net), any current `ProductAssignment` for that child unit — `assigned` or never-assigned `unassigned` — transitions to `revoked` in the **same transaction** as the return status write. Domain transition runs first; wrong-status calls never revoke.
- Returning a **card** (parent unit) that still has live assigned children **not also on the same RMA** is **blocked**. Same-order "return card and its tickets" is allowed (children on the request are skipped). Cascade-revoke and warn-only were rejected.
- `AssignOwned` / `AdminAssign` / `CheckPurchase` / `RecordPurchase` refuse when the child or parent unit is on a non-terminal return (`requested` / `approved` / `received`). `ListOwnedParents` omits parents on an open RMA.
- `ReturnableLines` lists a parent card only when every live assigned child is also still returnable on the same order; storefronts must submit card+those tickets together (card-only still 422s with required child unit ids).

## Why

Direct extension of the card/ticket use case: a customer should be able to return one ticket without affecting the card it was assigned to (or other tickets on the same card). Extends Returns/RMA the same way PR-1064 did for bundle components, at assignment granularity instead of bundle-component granularity — reusing that groundwork rather than building a second returns mechanism.

## Scope

- Confirm a ticket's order item is already returnable independently through the existing Returns/RMA domain (it is — `RequiresLinkedParent` does not change order-line structure, only purchasability). Each return line is still one order variant; the card line is only on the return when the requester includes it.
- On return approval/refund: the associated `ProductAssignment` (PR-1069) transitions to `revoked` automatically — a returned ticket must not remain `assigned` (or live `unassigned`) to a card it is no longer valid for.
- Explicit merchant-facing policy for returning a card with assigned tickets: **block** unless those tickets are on the same RMA (see design decisions).
- Block post-purchase / admin re-bind **and** checkout stamping onto a parent while a unit is on an open RMA; hide such parents from `ListOwnedParents`.

## Out Of Scope

- Bundle component returns — already covered by PR-1064, this PR is Track D-specific.
- CSV / admin GUI for assignments — PR-1073.
- Changing which order lines are returnable by product type (virtual / downloadable restock stays PR-1064).

## Design decisions

- **Block parent return while children are assigned (unless on the same RMA).** Options considered: block, warn, cascade-revoke. Warn-only is not enforceable on an RMA API. Cascade-revoke would silently detach purchased tickets from a card the customer is returning. Block forces an explicit path: return or revoke the assigned tickets first (ticket return already auto-revokes on approve), then return the card — **or** include those ticket lines on the same request. Message: `cannot return a parent unit that still has assigned children; revoke or return those children first (required: <child unit ids>)`.
- **Same-RMA skip.** Children that are themselves lines on the *current* return request are treated as already being returned: `AssertParentReturnable` skips those child unit IDs. That makes same-order "return card and its tickets" possible in one RMA. Cross-order assigned tickets still block the card.
- **Revoke on Approve (primary), Refund (idempotent), after successful in-memory transition, in one TX.** Spec said approval/refund. Approve is the merchant acceptance that the unit is leaving the customer's usable set. Sequence: parent gate → `ret.Approve()` / `MarkRefunded()` in memory → `BeginTx` → `Flow.WithTx` revoke → `returns.WithTx` Update → Commit. If persist fails, assignment rolls back with the TX. Wrong-status calls fail the domain transition before any revoke. Refund also revokes so a reassignment outside Flow, or a return approved before this wiring, still ends revoked.
- **Parent gate on RequestReturn, Approve, Receive, and Refund.** Request refuses creating an RMA for a blocked parent. Approve / Receive / Refund re-check so an assignment that lands mid-workflow cannot proceed.
- **Assign / purchase blocked on open RMA.** `returns.Service.AssertNotOnOpenReturn` is wired into `Flow` via `WithOpenReturnChecker`. `AssignOwned` / `AdminAssign` / `CheckPurchase` / `RecordPurchase` refuse when the child or parent unit appears on a non-terminal return. `ListOwnedParents` filters those parents out. Message: `cannot assign a unit that is on an open return`. RequestReturn itself does **not** revoke.
- **ReturnableLines keeps same-RMA cards only.** A parent is listed only when every live assigned child is also still returnable on that order. Storefront responsibility: selecting the card means including those ticket lines on the same request. Card-only `RequestReturn` still 422s and lists required child unit ids. Cross-order assigned tickets hide the card.
- **Audit/event.** Returns publish `assignment.revoked` (`AssignmentRevokedData`) on the event bus after a successful commit, with reason `return_approved` or `return_refunded`. Admin HTTP audit (`assignment.revoke`) stays on the admin revoke path; there is no separate assignment audit table for application-layer revoke.
- **Optional wiring.** `returns.Service.WithAssignmentFlow` is nil-safe (existing unit tests without assignment keep working). Production wires `assignmentFlow` and `WithOpenReturnChecker(returnService)` in `cmd/api/wire_services.go`.
- **Reuse `Flow`, not a second revoke path.** `AssertParentReturnable` and `RevokeForUnit` live on `assignment.Flow`. Returns holds a small `assignmentHooks` port. `RevokeForOrder` delegates per-line revoke to `RevokeForUnit`.
