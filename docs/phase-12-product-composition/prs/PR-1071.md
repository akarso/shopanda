# PR-1071 — Admin API for Assignment

Status: done

## Summary

- Operators can list a parent unit's assignments and a child unit's current assignment.
- Operators can assign a child unit to a parent unit, and revoke an assignment by id.
- Create and revoke are audited. Reads use `assignments.read`. Create and revoke use `assignments.write`. Admin, Manager, and Support have both. Editor has neither.

## Why

PR-1069 and PR-1070 build the domain and the flow. This PR is what makes assignment state operable by support without direct SQL: "this card's assigned tickets" and "this ticket's current card." Support holds `assignments.write`, so a support operator can correct a binding. Editor does not.

## Scope

- `ProductAssignmentRepository.ListByParentID`. Postgres reads `parent_order_item_id` so the planner can use `product_assignments_parent`. Newest first. `status`, `limit`, and `offset` are applied in that query. Default `status` is `assigned`. Default and max `limit` is 100. The query reads `limit+1` rows and the HTTP body returns `has_more`. `status=revoked` and `status=all` are optional. Unassigned rows have a null parent and are omitted.
- `Flow.AdminAssign`. `CanonicalUnitID` rejects a non-UUID order part and lowercases a UUID order id before any read or write. The variant id is not lowercased. PostgreSQL `22P02` is mapped to validation in the order and variant postgres adapters, not in the flow. The order line must exist. A missing catalog variant is a distinct error from a missing unit. A new row requires `RequiresLinkedParent` (or a required linked leaf). An existing unassigned row may be assigned without that flag. A live assigned row is 409. Cancelled, failed, or unpaid orders are refused unless `force` is true and `reason` is non-empty and at most 500 characters. HTTP applies that length check only when `force` is true. `SetForced` enforces the same rune cap. `Validate` keeps the `forced_at` / `forced_reason` pairing rules and does not apply the cap, so one oversized stored row can still be listed. Migration `103` checks `char_length(forced_reason) <= 500` when `forced_reason` is not null. That override is stored as `forced_at` and `forced_reason` (migration `102`) only when the child or the parent is not bindable. `force` on an already-bindable pair is 422 `force not applicable`. Customer id is not an ownership check. A new insert is 201. Unassigned → assigned is 200. The support path after checkout (unassigned insert, then assign plus `SetForced`, then update) persists the forced columns.
- List, current, and revoke responses include live unit facts for the parent and the child: customer id, order status, and payment status. `FactsForUnits` loads those orders with `OrderRepository.FindByIDs` (one query for the unique ids; `FindByID` remains the fallback), lowercases a UUID order id before the order map lookup, and keys the result by `CanonicalUnitID`. `forced` / `forced_at` are returned when the row was force-bound. The stored `forced_reason` is the JSON field `reason` only. The response does not also emit `forced_reason`. If that fact read fails, list, current, and revoke still return 200 with the assignment rows and empty fact fields and log `admin.assignment.facts_failed` (`route` `list`, `current`, or `revoke`, plus `error`). List logs that once with `count` (the row count). `assignment_id` is included when that read is a single row. A failed fact read does not undo a revoke.
- Revoke is `Service.Revoke` by assignment id. The row stays, including force columns. An already-revoked row returns 200 with the same body (including live facts) and does not write another audit entry.
- Admin HTTP, query parameters because unit ids contain `/`:
  - `GET /api/v1/admin/assignments?parent_unit_id=` — `assignments.read`
  - `GET /api/v1/admin/assignments/current?child_unit_id=` — `assignments.read`
  - `POST /api/v1/admin/assignments` — body `child_unit_id`, `parent_unit_id`, optional `force` and `reason` — `assignments.write` — `AdminAssign`
  - `POST /api/v1/admin/assignments/{id}/revoke` — `assignments.write` — `Service.Revoke`
- Audit actions `assignment.create` and `assignment.revoke`. A failed create uses the attempted child unit id as `ResourceID`. JSON is snake_case. The create response also includes order status, payment status, and customer ids for both units.
- `assignments.read` and `assignments.write` are granted to Admin, Manager, and Support (migration `101`). Editor is not granted either.
- Wired in `cmd/api/wire_services.go` and `cmd/api/wire_routes.go`. OpenAPI updated.

## Design decisions

- **Query parameters for unit ids.** `orderID/variantID` contains `/`, so a path segment would split the id. Assignment ids (UUIDs) stay in the path for revoke.
- **Support can correct a binding.** `assignments.write` is on Admin, Manager, and Support. That matches the reason this API exists: support fixes a card without SQL. Editor does not get the permission. Catalog write (`products.write`) does not include it.
- **Refuse bad orders unless forced.** Cancelled, failed, and unpaid parent or child orders are 422. `force: true` plus a non-empty `reason` (max 500 characters) overrides that, and only then. HTTP does not 422 a longer reason when `force` is false, because that reason is not stored. The reason is stored on the row (`forced_at`, `forced_reason`), returned as `reason` on create, list, current, and revoke, and written to the audit entry. The 500-character cap is enforced on write (`SetForced` and HTTP). `Validate` does not apply it. Migration `103` checks `char_length(forced_reason) <= 500` when the reason is not null. `force` on an already-bindable pair is 422 `force not applicable`. Support holding `assignments.write` may do this on purpose.
- **Order UUIDs compare in lowercase.** `CanonicalUnitID` lowercases the order part only. An uppercase order UUID hits the row minted at purchase instead of inserting a second one.
- **Linked parent, not only a catalog rule.** A new row requires `RequiresLinkedParent` or a required linked leaf. An existing unassigned row can still be assigned; eligibility uses the product id on the order line when the flag no longer yields a leaf. A live assigned row stays a conflict; reassignment is revoke, then a new row.
- **Card view is the assigned rows.** `status` defaults to `assigned`. `status=all` is the history view. The page is capped at 100 in SQL and `has_more` says whether another row exists.
- **Revoke is not a delete, and it is idempotent.** A second revoke of the same id is 200 with the same body and skips the audit write. History stays on `status=all`. A fact-read failure on list, current, or revoke is still 200 with empty fact fields and logs `admin.assignment.facts_failed` once (`count` on list; `assignment_id` when the read is a single row). The revoke stays written.

## What changed

- `internal/domain/assignment` — `CanonicalUnitID` rejects a non-UUID order part and lowercases the order UUID. `ForcedAt` / `ForcedReason` on the row. Migration `102` adds those columns. Migration `103` caps `forced_reason` at 500 characters. `Validate` does not apply that cap.
- `internal/domain/rbac` — `assignments.read` / `assignments.write`. Migration `101` backfills Admin, Manager, and Support.
- `internal/application/assignment` — list page in SQL (`has_more`), idempotent revoke, `AdminAssign` safety, live unit facts on list, current, and revoke. `FactsForUnits` uses `OrderRepository.FindByIDs` and keys results by `CanonicalUnitID`. A fact-read failure returns the rows with empty fact fields. Order and variant postgres adapters map `22P02` to validation.
- `internal/domain/order` — `OrderRepository.FindByIDs`. Postgres loads headers with `id = ANY($1)` and items in one batch.
- `internal/interfaces/http/admin/assignment_admin.go` — permissions, 201/200, force, audit resource id.
- `cmd/api/wire_routes.go`, `openapi.yaml`.
- `RUNBOOK.md` and C4 point at `docs/guides/DEVELOPER.md` for the contract. No C4 container change.
