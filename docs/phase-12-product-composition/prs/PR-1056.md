# PR-1056 — Admin vs. Public/Storefront API Split

Status: planned

## Summary

- Formalize the boundary: admin API sees every product regardless of computed/overridden visibility (as today); a new public/storefront-read boundary enforces all four axes (PR-1055) consistently.

## Why

In a headless deployment, the public/storefront API *is* the storefront — there's no separate rendering layer to "additionally" filter in. Visibility has to be enforced at the API boundary itself, not left as a per-handler convention that some routes happen to apply (as PR-1054 found: today it's applied nowhere except search and the sitemap, by accident). This also directly answers the "should the API ignore visibility" question this track exists to resolve: no — the public API is exactly where it has to be enforced, since nothing downstream of it will do it instead.

## Scope

- Audit every existing storefront-facing route: PDP → should check `VisibleIndividually`, category listing → `VisibleInCatalog`, search → `VisibleInSearch`, cart `AddItem` → `Purchasable`.
- Centralize the filtering logic in one place (a shared helper/middleware/repository-layer filter) rather than reimplementing the check per handler — reimplementing it per handler is exactly how PR-1054's bug happened in the first place.
- Admin API routes are explicitly exempted from this filtering — confirm the boundary is enforced at the route-registration/wiring layer (e.g. `cmd/api/wire_routes.go`'s existing admin-vs-public route grouping), not left to each handler to remember.

## Out Of Scope

- Actually wiring the filter into each storefront route — PR-1057.
- GraphQL — the same boundary applies there too, but GraphQL parity is Track F (PR-1082), after the REST boundary is proven out.

## Follow-up

- PR-1057 applies this PR's boundary to every storefront read path.
- PR-1082 (Track F) applies the same boundary to GraphQL.
