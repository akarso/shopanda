# PR-1059 — Visibility Admin GUI

Status: done

## Summary

- Per-axis mode selects (`auto` / `visible` / `hidden`) for all four `VisibilityAxes` on the product edit form, writable through the existing create/update admin API via a **partial** `visibility_modes` merge (an omitted axis keeps its current/default value — no need to resend all four).
- An override indicator next to each select describing the **storefront-facing outcome**: `Auto — visible/hidden`, `Forced visible`, `Forced visible — not live (product inactive)`, `Forced hidden`. No per-badge prefix; two section-level captions instead — `"Enforcement off — preview"` when `catalog.visibility.enforce` is off, and `"Preview as of form status (save to persist modes)."` always (the main form's `status` select rebinds badges to the currently selected, possibly-unsaved status).
- A "why hidden" explanation — the specific failing `AutoBasis` conditions, as **stable codes** (`status_inactive`, `no_stock`, `no_price`, `no_store_assignment`, `no_category`) — shown under an axis only when it is `auto` and `AutoBasis` is currently false.
- A **live** status preview: the GET payload's `input_failure_codes` (`status_inactive` always excluded) lets the SPA recompute `auto_basis`/`failure_codes` and refresh every badge and failure-list client-side when the form's (unsaved) `status` select changes.
- A distinct `"Visibility facts unavailable — reload to retry"` state for an existing product whose facts failed to load (`visibility_error` set), separate from the `"<Mode> — computed after save"` pending state used for a not-yet-saved create (or the rare concurrent-delete missing-snapshot case).
- A new type-agnostic `product.form` section (`Types: nil`), the one deliberate exception to "sections use their own save APIs."

## Why

Track B gave visibility four independent axes plus a per-axis override mode (PR-1055), enforced it on storefront reads (PR-1057) and cart/checkout (PR-1058) — but merchants had no way to see or set any of it from the admin GUI. Four boolean-ish conditions multiplied by an override mode is too much to reason about blind; without surfacing *why* the computed default landed where it did, this becomes a confusing feature instead of a useful one. This PR closes Track B.

## Scope

- `catalog.AutoBasisFailureCodes` + stable failure codes, mirroring `AutoBasis`'s check order.
- `catalog.EffectiveAxis` — the public-gate truth (a forced-visible axis on a non-active product is never on the storefront) — distinct from the pre-existing domain-level `ResolveAxis` (which ignores `Status`).
- `catalog.ExplainAxis` / `catalog.ExplainAxes` — build the full per-axis explanation (`mode`, `override`, `resolved`, `effective`, `failure_codes`) for the admin GET payload.
- `catalog.VisibilityFactsAdminSource.LoadManyAnyStatus` (postgres) — the same facts `LoadMany` already queries, but without the `status = 'active'` filter, so a draft/archived product's AutoBasis failures can still be explained.
- Admin API: partial `visibility_modes` merge on create/update requests; a `visibility` object on `GET /api/v1/admin/products/{id}` (`enforced`, `status`, `auto_basis`, `failure_codes`, per-axis `axes`).
- A type-agnostic `product.form` section (`id: "visibility"`), registered after `RegisterProductSchemas`.
- SPA: `product_visibility_section.js` + `admin.js` wiring (render, badge, failures, save).
- `openapi.yaml`: `VisibilityModesInput` (partial), GET `/api/v1/admin/products/{id}` response, `AdminProductVisibility` / `VisibilityAxisExplanation` schemas.

## Out Of Scope

- Changing `AutoBasis`, `ResolveAxis`, or `VisibilityOptions.RequireCategory` config wiring (see "Design decisions" below), or the public/storefront gates (PR-1056/1057/1058) — this PR is read/write admin surface only.
- A dedicated per-axis failure breakdown. All four axes share one `AutoBasis` when `auto`; `failure_codes` is one list, not four (repeated on each auto+hidden axis for convenience, not independently computed).
- Wiring `catalog.AutoBasisCodeNoStoreAssignment` to an actual store-assignment model — reserved; every `VisibilityFactsSource` hard-codes `HasStoreAssignment=true` today (no product↔store table exists).
- Track D's `RequiresLinkedParent` (PR-1068) explanation — flagged as a follow-up in the original spec; revisit once PR-1068 defines what it needs.

## Design decisions made during implementation

- **Effective vs. resolved — the key fix from code review.** The original implementation only exposed `ResolveAxis` (domain-level: `visible` always resolves `true`, ignoring `Status`). That let a merchant forcing an axis `visible` on a **draft** product see a misleading "visible" badge, even though the public gate (`LoadMany`, active-only) would never actually serve that product. `catalog.EffectiveAxis(mode, status, auto)` adds the real public-gate truth: non-active is always `effective=false`, no matter the mode. `AxisExplanation` now carries both `Resolved` (domain) and `Effective` (public-gate); the admin GUI badge always describes `Effective`, never bare `Resolved`.
- **Stable failure codes, not sentence strings.** `AutoBasisReasonStatus = "status is not active"` (a prose string) was a public contract that baked English text into the API and made the SPA's "why hidden" list unlocalizable and brittle to copy edits. `AutoBasisFailureCodes` returns machine-stable codes (`status_inactive`, `no_stock`, `no_price`, `no_store_assignment`, `no_category`); the SPA owns a `FAILURE_LABELS` map from code to merchant-facing text. `no_stock` (was `"quantity is 0"`) is named for what it means today — no variant with stock quantity > 0 — not the literal check.
- **`VisibilityFactsAdminSource` is a separate interface, not a parameter on `VisibilityFactsSource.LoadMany`.** `LoadMany` is correct for every public-gate caller (storefront, cart, checkout) — adding an "include non-active" flag there would let a status filter silently get bypassed by a caller that forgot to pass it. A second, narrower interface makes "this caller can see non-active products" explicit at the type level. `postgres.VisibilityFactsRepo` implements both; the SQL is shared via a private `loadMany(ctx, ids, activeOnly bool)` helper, now with `activeOnly` as a bound `$2::bool` parameter instead of string-concatenated SQL.
- **Admin facts are wired unconditionally, not gated by `catalog.visibility.enforce`; the handler now also knows whether enforce is actually on.** The public axis gate (storefront/cart) stays off until a merchant opts in. The admin GUI's "why hidden" explanation is informational, not a gate: it is always available so merchants can see what *would* happen before enabling enforcement. `ProductAdminHandler.enforced` (set via `WithVisibilityFacts(facts, opts, enforced)`) mirrors `cfg.Catalog.Visibility.Enforce` so the SPA can label outcomes as `Would be …` when the gate isn't live, instead of presenting a hypothetical as current fact. `wire_services.go` reuses the enforce-path `VisibilityFactsRepo` for admin when enforce is already on (one query implementation, one instance), constructing a second instance only when enforce is off.
- **`visibility_modes` is now a *partial* merge, not a full replace.** The original `visibilityModesRequest` required all four string fields (bare strings, zero value `""` silently became an invalid mode); a merchant flipping one axis had to resend the other three correctly or risk clobbering them. `visibilityModesRequest` now uses four `*string` pointers; `mergeVisibilityModes(base, req)` applies only the present fields onto `base` (`DefaultVisibilityAxes()` on create, the product's existing modes on update) and validates the result. `{"catalog":"hidden"}` alone now works on both create and update.
- **Audit entries record `visibility_modes_before`/`visibility_modes_after` on Update.** Previously an audit entry for a visibility-mode change recorded only the generic scope details, with no record of what actually changed. `Update()` now captures a before/after string-map snapshot (only when `visibility_modes` is present in the request) and adds both to `Details`, matching the existing `quantity_before`/`quantity_after` pattern in `inventory_admin.go`.
- **A visibility-facts load failure degrades, it does not 500 the product read.** The original `Get()` returned the facts-load error straight to the client (500), turning a transient/independent subsystem failure into "you can't view this product at all." Visibility is informational, not load-bearing: a failure now logs `h.log.Warn` and sets `visibility_error: "visibility facts unavailable"` in the response, with `visibility` omitted and the product itself still returned with 200.
- **`require_category` removed from the payload; `RequireCategory` config wiring stays a pre-existing gap.** `catalog.VisibilityOptions.RequireCategory` has no config/env binding anywhere in the codebase — every caller uses the zero value (`false`). The prior revision surfaced this zero value as a `require_category` field, which read as a (non-existent) configured toggle rather than a scope note. Removed from the response; `VisibilityOptions{}` stays the zero value everywhere, with no invented config key.
- **GET payload uses explicit snake_case JSON via an admin DTO, not raw domain structs.** `catalog.AxisExplanation` has no JSON tags (domain stays HTTP-agnostic). `product_admin.go`'s `adminAxisExplanation` owns the wire shape (`mode`, `override`, `resolved`, `effective`, `failure_codes` always present). The handler builds the top-level `visibility` object as an explicit map (`enforced`, `status`, `auto_basis`, `failure_codes`, `input_failure_codes`, `axes: {catalog, search, individually, purchasable}`).
- **SPA distinguishes facts errors from pending state.** `visibility_error` renders `"Visibility facts unavailable — reload to retry"`; `"<Mode> — computed after save"` is reserved for create or the rare missing-snapshot race before an error was returned.
- **`input_failure_codes` powers unsaved status preview.** Excludes `status_inactive` so the SPA can combine a candidate form status with persisted facts via `deriveAutoBasis`/`deriveFailureCodes`, aligned with `catalog.AutoBasisInputFailureCodes`.
- **Missing visibility snapshot sets `visibility_error`.** When `FindByID` succeeds but `LoadManyAnyStatus` has no row (concurrent delete), the handler returns `visibility_error: "product not found in visibility facts"` instead of silent omission.
- **`ExplainAxis` copies the shared failure-code slice** so mutating one axis's `FailureCodes` cannot corrupt the others or `ExplainAxes`' returned list.
- **The handler prefers the loaded product row's `Status`/`VisibilityModes` over the snapshot's.** `ExplainAxes` is called with `product.VisibilityModes`/`product.Status` (from the `FindByID` already on hand) rather than `snap.Modes`/`snap.Status`, since the two reads can diverge if the product changed between them; `snap.Inputs` (stock/price/category facts) is still the snapshot's.
- **Visibility section registered in `wire_services.go`, not inside `RegisterProductSchemas`.** `product_schema_test.go`'s `TestRegisterProductSchemas_Form` asserts `RegisterProductSchemas` alone registers **zero** sections ("until later tracks register type-specific panels"). Registering `visibility` inside that function would break that assertion's premise. Calling `RegisterProductFormSection` once, directly in `wire_services.go`, right after `adminApp.RegisterProductSchemas(adminRegistry)`, keeps that test describing `RegisterProductSchemas` in isolation and matches how every other section (bundle components, etc., in later tracks) is expected to register.
- **The visibility section is the one exception to "sections use their own save API."** Every other `product.form` section (PR-1053's pattern) renders outside `#product-form` and is explicitly documented as needing a dedicated save endpoint, not picked up by `collectProductPayload`. `VisibilityModes` is different: it's a core `Product` field (like `name`/`slug`/`type`), already saved through the same `POST`/`PUT` body. `admin.js`'s `collectProductPayload` therefore reads the four visibility selects (via `product_visibility_section.js`'s `collectModes()`) and merges `visibility_modes` into the normal save payload — no new save endpoint. This is called out explicitly in `DEVELOPER.md` as a documented exception, not an inconsistency.
- **SPA badges are always recomputed client-side from `{mode, autoBasis, status}`, never from a stale per-axis `effective`.** The GET payload's per-axis `effective`/`resolved` are only valid for whichever mode happens to be persisted at load time. When a merchant changes the select (without saving), `effectiveForMode(mode, autoBasis, status)` (mirroring `catalog.EffectiveAxis`) recomputes the badge for the *candidate* mode, so switching from `hidden` to `auto` immediately shows the correct `Auto — visible/hidden` instead of the previous mode's stale badge.
- **Drive-by fix, called out separately:** `internal/interfaces/http/admin/extension_value_admin_test.go`'s `mockExtensionValueRepo` was missing `ListTargetIDsByTypeAndIDPrefix`, a method `domainext.ValueRepository` has required since PR-1058. Added the missing method to the mock (same semantics as the real postgres implementation). Unrelated to the visibility feature, retained from the prior revision. (Note: a sibling gap in `internal/interfaces/http/storefront/storefront_extension_form_test.go`'s own mock exists but is out of scope for this PR's validation commands — not touched.)

## HTTP / API notes

- `POST /api/v1/admin/products` / `PUT /api/v1/admin/products/{id}`: `visibility_modes` is now a **partial** object — `{"catalog": "hidden"}` alone changes only that axis; every other field is independently optional on both create and update. Omitted whole object on create → all `auto` (`DefaultVisibilityAxes()`). Omitted whole object on update → unchanged. Invalid value on a present axis → 422 (`invalid visibility mode "..."`, same `Product.Validate()` path as every other field).
- `GET /api/v1/admin/products/{id}`: new `visibility` object — `{enforced, status, auto_basis, failure_codes, input_failure_codes, axes: {catalog, search, individually, purchasable}}`, each axis `{mode, override, resolved, effective, failure_codes}`. `input_failure_codes` is `failure_codes` with `status_inactive` always excluded — the admin SPA's source of truth for recomputing `auto_basis`/`failure_codes` live, client-side, whenever the form's status select changes without saving. Present only when the handler has `WithVisibilityFacts` wired (always true via `wire_services.go`) and a snapshot exists for the product. On a visibility-facts load error **or** a missing snapshot, `visibility` is omitted and `visibility_error` is set instead (`"visibility facts unavailable"` or `"product not found in visibility facts"`, respectively) — the product itself is still returned with 200.
