# PR-1057 — Enforce Visibility in Storefront Read Paths

Status: planned

## Summary

- Apply PR-1056's admin/public API boundary to product listing, PDP, category listing, and sitemap generation.

## Why

PR-1056 defines the boundary; this PR is where it actually gets wired into every route that needs it, consistently — not just the two places (search, sitemap) that happened to filter on `Status` before this phase existed.

## Scope

- Product listing (`VisibleInCatalog`), PDP (`VisibleIndividually`), category listing (`VisibleInCatalog`), sitemap (already filters on `Status` — extend to the full visibility computation rather than leaving it as a separate, narrower check).
- Search (`VisibleInSearch`) is covered here at the query layer for consistency, but the index itself doesn't carry these fields yet until Track F (PR-1079) — confirm during implementation whether this PR needs a temporary query-time join/filter against the `products` table until the index catches up, or whether it's cleaner to sequence this PR's search-specific piece after PR-1079. Flag this dependency explicitly when scoping the actual PR.

## Out Of Scope

- GraphQL — PR-1082.
- Cart/checkout purchasability — PR-1058 (a different axis, enforced at a different entry point).
