# PR-1060 — Bundle Domain Model

Status: done

## Summary

- Relational model `bundle_components(bundle_product_id UUID, component_product_id UUID, quantity, required)` with FK to `products`: bundle side `ON DELETE CASCADE`, component side `ON DELETE RESTRICT`.
- Domain `catalog.BundleComponent` with `NewBundleComponent` (defaults `Required: true`), field validation (quantity 1–9999, non-empty IDs), and composition rules (bundle parent only; component types `simple`, `virtual`, or `downloadable` only). IDs are trimmed in `NewBundleComponent` and `BundleService.Add`; `Validate` does not mutate.
- Repository port `BundleComponentRepository` (list, count-by-bundle, count-by-component, upsert, remove), postgres adapter with pg error mapping (`22P02` on list/count/upsert/remove), and `application/catalog.BundleService` (list checks parent bundle; add trims and validates before product loads).
- Admin product type-change guards via `ProductAdminHandler.WithBundleComponents` (block leaving `bundle` when components exist; block non-leaf types when the product is used as a component). A type change with a nil guard fails closed. Same-type updates still succeed when the guard is unwired.
- `BundleService.Add` and admin product type changes share `SELECT type FROM products WHERE id = $1 FOR UPDATE` inside one transaction, so a component link and a type change cannot pass each other's checks on a stale type. Non-type-changing product updates stay on the existing non-transactional path.
- Wired at serve startup (`BundleComponentRepo` + `BundleService` on `serveRuntime`); no bundle admin HTTP yet (PR-1066).

## Why

Catalog-time composition — a fixed set of components sold as one unit — has no existing analog in this codebase (`Variant` is SKU variation of *one* product, not composition of *several*). This PR is the relational model only; pricing (PR-1062) and stock (PR-1063) rollup come after.

## Design decisions

- **Table name `bundle_components` (plural)** matches other join-style tables in migrations and keeps room for multiple rows per bundle.
- **UUID FK columns** align with `products.id` (migration 001).
- **Component delete is RESTRICT**, not cascade — operators must remove bundle links before deleting a component product.
- **Type rules in application, not SQL.** Only `Type = bundle` products may own components; component products must be leaf types (`simple`, `virtual`, `downloadable`). Self-reference is blocked in domain `Validate()` and by a table CHECK.
- **`NewBundleComponent` defaults `Required: true`.** Callers override on the struct before `Add` when optional components are needed.
- **`BundleService.Add` is an upsert.** Same entry point for create and update of `quantity` / `required`; postgres uses `ON CONFLICT DO UPDATE`. `Add` trims IDs, then domain `Validate()` runs before product loads. The repo calls `Validate()` again before exec and does not trim.
- **Type change fails closed.** `validateProductTypeChange` returns an internal error when the type is changing and `WithBundleComponents` was not called. Leaving `bundle` is allowed when the component count is 0. A leaf-to-leaf change is allowed while the product is still used as a component.
- **`BundleService.List` loads the parent product** and rejects missing products or non-bundle types before listing (empty component list is OK).
- **`Remove` returns `NotFound`** when the row did not exist, matching other repos that distinguish missing rows from success.
- **Product loads use the caller's context.** Operator/admin callers must pass `catalog.WithOperatorProductReadScope` when resolving draft bundle or component products (same as reviews and future admin API in PR-1066). `Add` no longer loads products for composition checks; it locks both rows and reads `type` with no status filter.
- **Add and type-change share `FOR UPDATE` on `products` within a transaction.** After `Validate`, `Add` begins a transaction, binds product and bundle-component repos with `WithTx`, locks both product ids in sorted order, runs `ValidateComposition` on the locked types, upserts, and commits. Admin `PUT` does the same when `type` is present and differs from the loaded product: lock that product, `validateProductTypeChange` uses the locked type and the transaction-bound counts, then `Update` commits in the same transaction. `ProductRepo.LockForUpdate` requires `WithTx` and returns `NotFound` when the row is missing. `NewBundleService` takes a `TxStarter` (`*sql.DB`). `ProductAdminHandler.WithTxStarter` wires the same `*sql.DB`. A type change without a starter or without `WithTx` fails closed.

### Race-fix validation

```bash
go test ./internal/domain/catalog/ ./internal/application/catalog/ ./internal/interfaces/http/admin/ -count=1
go build -o /dev/null ./cmd/api/

export SHOPANDA_TEST_DSN='postgres://shopanda:shopanda@localhost:5433/shopanda_test?sslmode=disable'
go test ./internal/infrastructure/postgres/ -run 'BundleComponent|ProductRepo_LockForUpdate' -count=1
```

`BundleComponentRepo.WithTx` rollback/commit and `ProductRepo.LockForUpdate` (draft row, no status filter, `NotFound` on a missing id) passed against Postgres 17. `LockForUpdate` without a transaction fails before any query.
