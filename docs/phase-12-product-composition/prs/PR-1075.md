# PR-1075 — `DownloadGrant` Domain

Status: done

## Summary

- Created when an order containing a downloadable item is paid (`order.paid` event subscriber — not inline in payment capture).
- Carries an expiry (configurable window from grant creation) and a download-count limit.
- Deliberately **not** modeled on `ProductAssignment` (Track D) — no parent-binding step.

## Why

Digital delivery needs its own lifecycle — a customer shouldn't get a permanent, unlimited link the moment they buy, and the grant needs to survive independently of the order/payment record it originated from (a grant can be revoked, extended, or re-issued without touching order history).

## Scope

- Migration `105_create_download_grants.sql` — `download_grants` + `downloadable_grant_settings`.
- Domain `download.DownloadGrant` + `GrantSettings` / `Resolve` defaults; repository ports; postgres adapters.
- `application/download.Service` (issue / get / list / record / extend / revoke / reset) and `Issuer.HandleOrderPaid`.
- Global defaults via `catalog.downloadable` config (env overrides); per-product overrides in `downloadable_grant_settings` (admin write HTTP is PR-1078).
- Wired at serve: repos, service, issuer subscribed to `order.EventOrderPaid`.
- **`order.paid` publishers:** sync `InitiatePaymentStep` success, `$0` / `payment_skipped`, `payment.completed` webhooks (after persist), admin + integration `ApplyStatus(paid)`.
- Unpaid refuse; missing files/variant/product hard-fail; required downloadable bundle leaves; TX per order; returns revoke; media grant count; sentinel errors.

## Out Of Scope

- Digital-goods VAT — PR-1076.
- Storefront delivery endpoint that checks/consumes a grant — PR-1077.
- Admin API / CSV / GUI for grant list/revoke/re-issue and product override editors — PR-1078.
- Guest-order grant rebind on `LinkToCustomer` — follow-up (`ListByCustomer("")` rejected; list by order item).
- Full durable outbox/job queue for issuer retries — TX + UNIQUE + republish `order.paid` is enough here; note retry gap if async handler fails after publish.
- N+1 batching of variant/product/file loads.
- Separate `revoked_at` column (revoke still sets `expires_at = now`).
- Optional / nested bundle downloadable leaves; grouped-member auto-grants.
- Live type/files snapshot at order-create (issuance still reads current catalog; note for follow-up).
- Overflow check / shared `asset_id` on two leaves; repo `ListByCustomer` empty-footgun comment polish.

## Design decisions

- **New `download` package, not `catalog`.** Grants are post-purchase entitlements keyed by opaque order-line ids and media assets, not catalog composition. Attachment rows stay in `catalog` / `downloadable_files` (PR-1074).
- **Table name is plural.** Spec drafted `download_grant`; `download_grants` matches `downloadable_files` / `product_assignments`.
- **`order_item_id` reuses `assignment.UnitID`** (`orderID/variantID`) so returns/assignments/grants share one scheme.
- **UNIQUE `(order_item_id, asset_id)`** makes `order.paid` re-delivery idempotent. One grant per attached asset per line; `download_limit` is multiplied by line quantity (capped at 10000).
- **IssueIdempotent conflict:** return existing row **unchanged** (`existed=true`) — including expired/revoked. Paid redelivery must **not** resurrect a revoked grant. Support re-issue is **Extend + ResetCount** from PR-1078, not a side effect of `order.paid`.
- **Webhook / already-paid heal:** Stripe `already_processed` (completed) and generic webhook success-on-non-pending **republish `order.paid`** (mirror `payment.failed` retry). After payment/status persist succeeds, publish failure is logged/swallowed (HTTP 200 / step nil) so retries can still heal.
- **`grant.issued` after Commit:** Issuer collects newly inserted grant ids and publishes only after successful `tx.Commit()` (or after the non-tx path finishes inserts).
- **Revoke without a `revoked_at` column.** `Revoke` sets `expires_at = now`. Returns approve/refund revoke grants like assignments.
- **Returns partial qty:** reject partial quantity on lines that already have DownloadGrant rows (full-line return required until limit scaling exists). Approve/refund fully revokes; a later `order.paid` does not restore.
- **Global config + optional product overrides.** Explicit `default_download_limit: 0` is rejected (not coerced to 5). Expiry capped at 3650 days (`MaxExpiryDays`).
- **Event-bus issuance, not payment-capture inline.** Publishers emit `order.paid`; issuer is the single subscriber (with notification). Do **not** hook `checkout.completed` alone (would grant before Stripe capture).
- **Unpaid refuse:** order status `paid`, or completed payment, or payable 0 with no payment row (`payment_skipped`).
- **Hard fail** when a downloadable line has no files, a missing variant, or a missing product (paid customer must not get warn-and-skip). Bundle line with nil components fails closed (internal).
- **Bundles:** non-exploded parents walk required downloadable leaves (one level). Optional/nested out of scope.
- **TX:** all grants for one order via `WithTx` when the postgres adapter is wired.
- **`CanDownload` / `RecordDownload` / CAS `UpdateCount`.** Sentinels `ErrExpired` / `ErrExhausted` / `ErrCountConflict` via `errors.Is` on service returns (`apperror.Wrap`).
- **media.Delete** counts **live** grants (`expires_at > now`) so expired rows do not pin blobs; nil grant counter fails closed like attachments. `AssetRepo.Delete` maps `download_grants` FK `23503` distinctly.
- **Review hardenings:** skip issuance for lines on open/refunded returns; post-purchase product reads use `WithIncludeNonActiveProducts`; purge expired/revoked grant rows before asset delete (RESTRICT remains for live); confirmation email deduped via `notification_dedupe` UNIQUE `(subject_key, kind)` (job id secondary); `Insert` uses `ON CONFLICT DO NOTHING` so concurrent losers can reload in-TX; `Update` omits `download_count` and `UpdateCount` requires live `expires_at`.
- **Return Reject/Cancel grant retry:** requested returns still skip issuance (no live grants while an RMA may approve). After `Reject` / `Cancel`, returns calls `Issuer.IssueForOrder` so lines skipped during the open return get grants once the block is gone (`IssueIdempotent` leaves existing rows). Refunded/approved/received still block.
- **media.Delete TX:** purge expired/revoked + live count + asset row delete run in one transaction when a TX starter and TX-capable repos are wired; live-grant rejection rolls the purge back. Without TX wiring, live count runs first so a rejected delete never erases grant history.
- **No delivery HTTP / signed URLs in this PR.**
