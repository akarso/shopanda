# PR-1075 — `DownloadGrant` Domain

Status: planned

## Summary

- Created when an order containing a downloadable item is paid.
- Carries an expiry (configurable window from grant creation) and a download-count limit.

## Why

Digital delivery needs its own lifecycle — a customer shouldn't get a permanent, unlimited link the moment they buy, and the grant needs to survive independently of the order/payment record it originated from (a grant can be revoked, extended, or re-issued without touching order history).

## Scope

- `download_grant(id, order_item_id, customer_id, asset_id, expires_at, download_limit, download_count, created_at)`.
- Created on the existing order-paid event (reuse the event bus, same pattern as notification/webhook subscribers elsewhere in this codebase), not inline in the payment-capture code path.
- Deliberately **not** modeled on `ProductAssignment` (Track D) — downloadable delivery has no "assign to a parent" step, so a separate, simpler grant model is the right level of complexity, not a forced reuse of Track D's state machine.
- Configurable defaults: expiry window and download-count limit, at the product level (per-`downloadable`-product override) with a global config fallback.

## Out Of Scope

- Digital-goods VAT — PR-1076 (unrelated: this PR is delivery lifecycle, that PR is tax category).
- The actual delivery endpoint that checks/consumes a grant — PR-1077.
