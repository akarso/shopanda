# PR-1068 — `RequiresLinkedParent` Purchasability Gate

Status: planned

## Summary

- A product flagged `RequiresLinkedParent = true` computes `Purchasable = false` (Track B's axis) until an assignment context makes it eligible.

## Why

This is the direct mechanism behind "a ticket must not be sellable or visible until assigned to a card." It reuses Track B's `Purchasable` axis (PR-1055) and the `HookCartAddItemBefore`/`HookCartValidate` seam PR-1058 established, rather than inventing a bespoke check — a plugin or a future feature that needs a similar "not purchasable until X" rule can follow the same pattern.

## Scope

- `RequiresLinkedParent bool` on the product (or derived from "has ≥1 `LinkedProduct` eligibility rule," PR-1067 — decide during implementation which is more correct; an explicit flag is probably clearer than an implicit derivation).
- `Purchasable` computation (PR-1055's default rule) additionally evaluates: if `RequiresLinkedParent`, `Purchasable` stays `false` unless the current purchase context provides a valid assignment target (see PR-1070 for what "context" means at cart time) — this is the one axis where the default computation isn't purely a function of the product's own static state, it depends on the request.
- Confirm this doesn't fight PR-1055's "auto" default model — document it as a documented, deliberate extension of that rule (a linked child's `Purchasable=auto` computation is context-dependent by design), not a special case bolted on separately.

## Out Of Scope

- The actual assignment record — PR-1069.
- Where the assignment context comes from (cart selection vs. post-purchase) — PR-1070.

## Follow-up

- PR-1070 defines exactly when/how a purchase can proceed for a `RequiresLinkedParent` product.
