# PR-1077 — Storefront Download Delivery Endpoint

Status: planned

## Summary

- Auth-gated, signed/token URL (not a permanent public link) that checks the requesting customer's `DownloadGrant` state before streaming/redirecting to the underlying asset.

## Why

The grant (PR-1075) is meaningless without an endpoint that actually enforces it — this closes the loop from "order paid" to "customer can download the file, within the limits that were set."

## Scope

- `GET /account/downloads/{grantID}` (or similar, under the existing customer-authenticated account routes) — validates the requesting customer owns the grant, checks `expires_at` and `download_count < download_limit`, increments `download_count` on successful delivery, then streams or redirects to the underlying Media asset (signed URL if the storage backend supports it, e.g. S3; direct stream for local storage).
- Expired or limit-exhausted grant: clear error response, not a silent 404 (the customer needs to know *why*, e.g. to contact support for a re-issue).
- Confirm the signed-URL/redirect approach doesn't leak a permanently-valid direct asset URL — the delivery endpoint must remain the only path to the file, or the grant's expiry/limit becomes unenforceable.

## Out Of Scope

- Admin-facing grant management (re-issue, revoke) — PR-1078.

## Follow-up

- PR-1078 — admin API/CSV/GUI, including grant management this endpoint's failure responses point customers toward.
