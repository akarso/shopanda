# PR-1067 — `LinkedProduct` Catalog Eligibility

Status: done

## Summary

- Many-to-many eligibility relation: which child products are assignable to which parent products.
- Two scoping mechanisms, both supported and OR-combined: an explicit parent-product-ID allowlist per child, or a category-based rule (any product assigned to that category via `product_categories`).

## Why

This is the mechanism the card/ticket use case actually needs, and it's deliberately not Bundle or Grouped: a ticket product must remain independently purchasable-in-principle (gated by `Purchasable`, PR-1068, not composed into a fixed catalog-time set), and the same ticket *product* legitimately ends up eligible for — and later assigned to — many different card *instances* across many different orders (e.g. a "Zone 1 monthly pass" ticket type sold against hundreds of different virtual and physical card instances). Bundle's fixed, catalog-time-only composition can't express that; this relation can.

## Scope

- New tables expressing eligibility: `linked_eligible_parents(child_product_id, parent_product_id)` for the allowlist case (spec name was singular; plural matches `bundle_components` / `grouped_members`), and `linked_eligible_categories(child_product_id, category_id)` for the category case. Category matching reuses catalog membership (`product_categories`) — the same scoping idea as catalog promotions matching catalog entities — rather than a second condition DSL.
- Domain `catalog.LinkedEligibleParent` / `LinkedEligibleCategory` with `New*` constructors (trim IDs), field validation (non-empty IDs; no self-parent), repository port `LinkedEligibilityRepository`, postgres adapter (`WithTx` adapter-only), and `application/catalog.LinkedEligibilityService` (list/add/remove/`IsEligible`/`HasRules`). Both predicates are join-table checks: they do not read product status.
- A child product declares eligibility rules; a parent product doesn't need any corresponding declaration.
- This PR is the eligibility relation only — it does not itself gate purchasability (PR-1068) or track actual assignment (PR-1069).

## Out Of Scope

- Purchasability gating — PR-1068.
- Instance-level assignment — PR-1069.
- Admin API, CSV, and GUI — PR-1073.

## Design decisions

- **Table names are plural.** Spec drafted `linked_eligible_parent`; `linked_eligible_parents` / `linked_eligible_categories` match other join-style tables.
- **UUID FKs for products, TEXT for categories.** Matches `products.id` (UUID) and `categories.id` (TEXT).
- **Both sides `ON DELETE CASCADE`.** Deleting a child, parent, or category silently drops the rule. Eligibility is a catalog rule, not composition: a future product delete API must not return 422 because a rule exists. Bundle components stay `RESTRICT` on the component side.
- **Self-link blocked twice.** Domain `Validate` rejects equal trimmed child/parent IDs; the table `CHECK (child_product_id <> parent_product_id)` is the SQL backstop (`23514`). `IsEligible` returns false for a self pair, including when the two arguments are different spellings of one UUID (`$1::uuid <> $2::uuid`). The service folds case before that call. A product in one of its own eligible categories is not its own parent.
- **No product-type restriction.** Linked eligibility is not a `Type`. A simple/virtual ticket may list a simple/virtual card; a bundle or grouped product is allowed if a merchant writes that row.
- **OR across mechanisms.** A child may have an allowlist, category rules, both, or neither. `IsEligible` is true when either an explicit parent row exists or the parent is assigned to any of the child's eligible categories. An empty rule set is false.
- **Category match is exact membership.** `product_categories` for the parent + `linked_eligible_categories` for the child. No ancestor walk.
- **`Validate` does not mutate ids.** Trimming happens in `New*` and in the service. `Validate` only reads trimmed copies for the empty and self-link checks.
- **Insert is insert-ignore.** There are no mutable columns. Postgres uses `ON CONFLICT DO NOTHING`. A second add of the same pair succeeds and leaves the existing row.
- **`IsEligible` and `HasRules` are a predicate pair, not product reads.** Empty IDs are validation. Missing products or no matching rule are false, not `NotFound`. Neither consults `products.status` or visibility: a draft child with a matching rule is true. `List*` / `Remove*` still load the child through `FindByID`. Callers that already loaded the product apply status/visibility themselves. Do not treat `errors.Is(err, NotFound)` as "no rules."
- **No reverse-count methods.** `CountRulesByChildID` backs `HasRules`. `CountByParentID` / `CountByCategoryID` are omitted until a real caller exists. An allowlist-only parent count would under-count category-scoped eligibility; when admin needs "incoming eligibility," add a method that ORs both mechanisms and name it so it cannot be mistaken for allowlist-only.
- **`WithTx` is postgres-only.** The domain port does not declare it. `AddParent` and `AddCategory` type-assert the adapter.
- **Add locks products.** `AddParent` begins a transaction, binds both repos with `WithTx`, locks both product ids in sorted lowercase order (so case variants of the same UUID cannot deadlock), rejects a non-active product unless `catalog.IncludeNonActiveProducts` is set, insert-ignores, and commits. `AddCategory` locks the child only, then `CategoryRepository.FindByID` (nil → `NotFound`) on a non-tx connection (`CategoryRepo` has no `WithTx`). PR-1073 should map insert `23503` on `linked_eligible_categories_category_id_fkey` to `"category not found"`. `WithOperatorProductReadScope` sets the non-active flag. `Remove*` do not lock.
- **No admin type-change guard.** Eligibility is type-agnostic, so `ProductAdminHandler` is unchanged. Fail-closed unwired-repo behavior is not needed here.
- **No admin HTTP.** Wired at serve startup (`LinkedEligibilityRepo` + `LinkedEligibilityService` on `serveRuntime`). Admin API / CSV / GUI ship in PR-1073.

## Follow-up

- PR-1068 should use an explicit `RequiresLinkedParent` product flag (not derive it from `HasRules`). `IsEligible` / `HasRules` are catalog-rule predicates only: they do not mean purchasable or assignable, and they do not check active/visible. After the product is known to be in scope, `IsEligible` answers "does this parent match a rule."
