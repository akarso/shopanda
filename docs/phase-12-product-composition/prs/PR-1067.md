# PR-1067 — `LinkedProduct` Catalog Eligibility

Status: planned

## Summary

- Many-to-many eligibility relation: which child products are assignable to which parent products.
- Two scoping mechanisms, both supported: an explicit parent-product-ID allowlist per child, or a category-based rule.

## Why

This is the mechanism the card/ticket use case actually needs, and it's deliberately not Bundle or Grouped: a ticket product must remain independently purchasable-in-principle (gated by `Purchasable`, PR-1068, not composed into a fixed catalog-time set), and the same ticket *product* legitimately ends up eligible for — and later assigned to — many different card *instances* across many different orders (e.g. a "Zone 1 monthly pass" ticket type sold against hundreds of different virtual and physical card instances). Bundle's fixed, catalog-time-only composition can't express that; this relation can.

## Scope

- New table expressing eligibility, supporting both scoping mechanisms: an explicit `linked_eligible_parent(child_product_id, parent_product_id)` table for the allowlist case, and a category-based rule reusing the existing catalog-rule scoping pattern from Promotions (`internal/application/pricing/catalog_promotion_step.go`) rather than building a second rule engine from scratch.
- A child product declares eligibility rules; a parent product doesn't need any corresponding declaration (eligibility is defined from the child's side, since it's the child whose purchasability depends on it — see PR-1068).
- This PR is the eligibility relation only — it does not itself gate purchasability (PR-1068) or track actual assignment (PR-1069).

## Out Of Scope

- Purchasability gating — PR-1068.
- Instance-level assignment — PR-1069.

## Follow-up

- PR-1068 consumes this PR's eligibility rules to compute `Purchasable`.
