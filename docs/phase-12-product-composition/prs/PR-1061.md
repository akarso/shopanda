# PR-1061 — Grouped Domain Model

Status: done

## Summary

- Display-only membership `grouped_members(group_product_id UUID, member_product_id UUID)` with both FKs `ON DELETE CASCADE`. No quantity and no required flag.
- Domain `catalog.GroupedMember` with `NewGroupedMember` (trims IDs), field validation (non-empty IDs, no self-link), and composition rules (grouped parent only; member types `simple`, `virtual`, or `downloadable` via `Type.IsGroupedMemberLeafType`, a helper separate from the bundle leaf check).
- Repository port `GroupedMemberRepository` (list, count-by-group, count-by-member, insert-ignore, remove). Postgres adapter maps `23503` / `22P02` / `23514`. `WithTx` is on the postgres adapter only.
- `application/catalog.GroupedService` lists only grouped parents, and `Add` locks both product rows before insert. Admin type changes run bundle and grouped counts in the same product-row transaction and fail closed if either repo is nil.
- Grouping never affects a member's `Purchasable` result or visibility (PR-1055). Members stay independently purchasable.

## Why

A grouped display (several standalone products shown together, each independently purchasable) is a different mechanic from a bundle (fixed composition) and from Track D linked products (dependency-gated purchasability). A separate table keeps each rule set small.

## Design decisions

- **Table name `grouped_members` (plural)** matches `bundle_components` and other join-style tables.
- **UUID FK columns only.** No quantity, no required. Both sides stay `ON DELETE CASCADE`, including `member_product_id`. The row is a display link: deleting a SKU silently unlinks it from every group, and deleting the group product removes its membership rows. Member products remain. A future product delete API must not return 422 because of grouped membership — silent unlink is intentional for members (and for the group parent). Bundle components stay different: the component side is `ON DELETE RESTRICT`.
- **Self-link blocked twice.** Domain `Validate` rejects equal trimmed IDs; the table `CHECK (group_product_id <> member_product_id)` is the SQL backstop (`23514`).
- **Type rules in application, not SQL.** Only `Type = grouped` products may own members. Members must be leaf types. `IsGroupedMemberLeafType` is intentionally separate from `IsBundleComponentLeafType` even though both currently allow `simple`, `virtual`, and `downloadable`.
- **Membership is not an input to purchasability or visibility.** Comments on the domain type, `Validate`, `ValidateComposition`, the repository port, and `GroupedService` state that adding or removing a row does not change the member's `Purchasable` result or visibility axes.
- **`Insert` is insert-ignore.** There are no mutable columns. Postgres uses `ON CONFLICT DO NOTHING`. A second add of the same pair succeeds and leaves the existing row.
- **`GroupedService.List` loads the parent** and returns `NotFound` for a missing product or validation for a non-grouped type before listing. An empty member list is a non-nil slice.
- **`Remove` returns `NotFound`** when the row did not exist.
- **`WithTx` is postgres-only.** The domain port does not declare it. `GroupedService.Add` and the admin type-change path type-assert the adapter.
- **Multi-group membership is allowed.** The primary key is `(group_product_id, member_product_id)`. The same member can appear in more than one group. `CountByMemberID` is that number. Changing that member to a non-leaf type (for example `bundle`) is still rejected.
- **`Validate` does not mutate ids.** Trimming happens in `NewGroupedMember` and in `GroupedService` `List`, `Add`, and `Remove` (and the bundle service equivalents). `Validate` only reads trimmed copies for the empty and self-link checks.
- **`Insert` stays on the port.** `GroupedService.Add` needs it. `ValidateComposition` is service-only. The repository does not read or store product types. The safety net is the row-gated admin type-change guard.
- **Add and type-change share `FOR UPDATE`.** After `Validate`, `Add` begins a transaction, binds both repos with `WithTx`, locks both product ids in sorted order, rejects a non-active product unless `catalog.IncludeNonActiveProducts` is set, runs `ValidateComposition` on the locked types, inserts, and commits. `WithOperatorProductReadScope` sets that flag, so an operator can add a member to a draft group. Without it, `Add` returns `NotFound`, matching `List`. Admin `PUT` locks the product whenever the payload includes `type`, then compares that locked type to the request. A stale `FindByID` that already matches the payload does not skip the guard. Updates that omit `type` do not take the lock.
- **Type change is row-gated.** `CountByGroupID > 0` rejects any target other than `grouped`, even when the locked type is not `grouped` (illicit rows). `CountByBundleID > 0` does the same for any target other than `bundle`. The non-leaf checks (`CountByMemberID`, `CountByComponentID`) are unchanged. Fail-closed when either repo or `WithTxStarter` is nil lives on `ProductAdminHandler`, not on `GroupedService`.
- **`Remove` does not lock products.** It trims the two ids and deletes the link. Product deletion is the cascade path, not this method.
- **Product loads use the caller's context.** Operator/admin callers must pass `catalog.WithOperatorProductReadScope` when resolving draft grouped or member products, including `Add`.
