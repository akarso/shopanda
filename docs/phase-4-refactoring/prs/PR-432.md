# PR-432 — REST Guest Checkout Parity (Track D)

Status: planned

## Summary

- align headless `POST /api/v1/checkout` guest path with SSR guest checkout: contact email, no forced registration, same validation and order outcome

## Why

Phase 3 validated guest checkout on SSR but deferred REST API parity. Headless storefronts and mobile clients need the same guest flow without account creation.

## Current state (pre-implementation)

Today the REST checkout and cart routes are wrapped in `requireAuth()` in `cmd/api/main.go`. Unauthenticated requests receive **401** before the handler runs (`TestCheckoutHandler_StartCheckout_Unauthenticated`). This contradicts the guest-checkout goal until middleware is changed.

SSR guest checkout does **not** use `requireAuth`: global `AuthMiddleware` injects `identity.Guest()` when no Bearer token or storefront session cookie is present, and the checkout handler passes an empty `customerID` plus `contact_email` from the form.

## Authentication design (to implement)

**Approach:** remove `requireAuth()` from guest-capable REST cart and checkout routes; keep global `AuthMiddleware` so guest identity is explicit in context.

| Route group | Middleware change | Identity |
| --- | --- | --- |
| `POST/GET /api/v1/carts…` | drop `requireAuth`; authorize by cart ownership rules in handler/service | guest session cookie (same `storefrontSessionToken` path as SSR) or Bearer customer token |
| `POST /api/v1/checkout` | drop `requireAuth` | `identity.Guest()` when unauthenticated; empty `customerID` + `contact_email` in request body |

**Not planned:** a separate `/api/v1/checkout/guest` route or a new guest JWT type. One route, guest vs account distinguished by context + payload (mirrors SSR).

**Account holder path unchanged:** Bearer token or storefront session cookie → non-guest identity → existing `customerID` binding.

## Scope

- REST checkout handler: accept guest payload (`contact_email`, addresses, cart id per existing API shape)
- extend `checkoutRequest` with `contact_email` when `customerID` is empty
- remove `requireAuth` from cart + checkout routes (or equivalent guest-aware middleware)
- reuse checkout application service / workflow used by SSR; no duplicate business logic
- error mapping consistent with SSR (stock, payment, validation)
- tests: REST guest checkout creates order with empty `customer_id`; registered user path unchanged; update `TestCheckoutHandler_StartCheckout_Unauthenticated` expectation

## Out Of Scope

- New payment methods
- GraphQL
- Cart merge on login (unless already exists)

## Validation

- `POST /api/v1/checkout` with guest session + `contact_email` completes order with empty `customer_id`
- authenticated checkout still requires matching cart ownership
- same cart constraints as SSR guest (promotions, shipping, tax if applicable)
- `go test ./internal/interfaces/http -run Checkout -count=1`
