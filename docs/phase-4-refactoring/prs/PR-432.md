# PR-432 — REST Guest Checkout Parity (Track D)

Status: planned

## Summary

- align headless `POST /api/v1/checkout` guest path with SSR guest checkout: contact email, no forced registration, same validation and order outcome

## Why

Phase 3 validated guest checkout on SSR but deferred REST API parity. Headless storefronts and mobile clients need the same guest flow without account creation.

## Scope

- REST checkout handler: accept guest payload (email, addresses, line items/cart token per existing API shape)
- reuse checkout application service / workflow used by SSR; no duplicate business logic
- auth: guest checkout does not require session customer id; optional account linking unchanged
- error mapping consistent with SSR (stock, payment, validation)
- tests: REST guest checkout creates order; registered user path unchanged; OpenAPI or handler tests

## Out Of Scope

- New payment methods
- GraphQL
- Cart merge on login (unless already exists)

## Validation

- `POST /api/v1/checkout` with guest email completes order without `customer_id`
- same cart constraints as SSR guest (promotions, shipping, tax if applicable)
- `go test ./internal/interfaces/http -run Checkout -count=1`
