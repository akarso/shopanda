# PR-416 — RabbitMQ Queue Driver + Core Plugin (Track B)

Status: done

## Summary

- implement `jobs.Queue` AMQP backend for RabbitMQ
- package as `plugins/core/rabbitmqqueue`; activate when `queue.driver=rabbitmq`
- add Docker Compose `queue` profile with RabbitMQ service and documented env overlay
- Postgres job queue remains default

## Why

RabbitMQ was previously listed as explicitly deferred. It is now a first-class **core plugin** — an alternative queue backend for deployments that already run RabbitMQ. Postgres stays the zero-dependency default; Redis (PR-415) and RabbitMQ are mutually exclusive via `queue.driver`.

## Scope

- AMQP `jobs.Queue` implementation: durable queues, ack/nack, retry via re-publish or delay queue (document chosen strategy), compatible with existing worker loop
- config: `queue.driver=rabbitmq`, `RABBITMQ_URL` (or host/user/pass/vhost), queue name prefix
- `plugins/core/rabbitmqqueue`: register when driver is rabbitmq; clear error if broker unreachable
- `docker-compose.yml`: `queue` profile adding `rabbitmq` service (management UI optional); example `.env` snippet in `RUNTIME_MODES.md`
- startup guard: reject config with more than one queue driver; document `postgres` | `redis` | `rabbitmq`
- tests: queue contract tests against RabbitMQ in integration tag or testcontainers; unit tests for message serialization

## Out Of Scope

- Kafka, SQS, or other brokers (remain deferred in roadmap)
- RabbitMQ for cache or search
- Federation / clustering guides

## Validation

- `queue.driver=postgres` (default): no RabbitMQ dependency
- `docker compose --profile queue up` + `queue.driver=rabbitmq`: worker consumes enqueued `email.send` job successfully
- retry and permanent failure behavior matches Postgres queue semantics
- `go test ./plugins/core/rabbitmqqueue -count=1` (and integration target if tagged)

## What changed

- **`internal/infrastructure/rabbitmq/`**: durable main + failed queues; JSON job messages; manual ack with in-flight tracking; retry via re-publish with per-message expiration (backoff); integration tests behind `integration` build tag
- **`plugins/core/rabbitmqqueue/`**: registers when `queue.driver=rabbitmq`; URL from config or `RABBITMQ_URL`
- **`plugins/core/register.go`**: if/else-if registers one queue plugin (postgres, redis, or rabbitmq)
- **`core_plugins.go`**: `CoreRabbitMQQueueEnabled()`
- **`config.go`**: `queue.rabbitmq.url`, `queue.rabbitmq.queue_prefix`; env overlays
- **`docker-compose.yml`**: `queue` profile with RabbitMQ 3 management image
- **`RUNTIME_MODES.md`**, config examples: RabbitMQ env overlay documented

## Retry strategy

On `Fail`, the claimed message is acked and either re-published to the main queue with a per-message TTL (exponential backoff aligned with postgres/redis) or published to `{prefix}.jobs.failed` when max retries are exhausted. `RunAt` delays on `Enqueue` use the same expiration mechanism.
