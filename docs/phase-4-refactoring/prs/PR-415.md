# PR-415 — Redis Queue Driver + Core Plugin (Track B)

Status: planned

## Summary

- implement `jobs.Queue` Redis backend (lists/streams with atomic claim, retry, `RunAt` delay)
- package as `plugins/core/redis-queue`; activate when `queue.driver=redis`
- Postgres job queue remains default

## Why

Background jobs today use only `postgres.JobQueue`. Redis is a common alternative for higher throughput job dispatch. It belongs in the core-plugins tier alongside RabbitMQ (PR-416), not as ad-hoc infrastructure in `main.go`.

## Scope

- Redis `jobs.Queue`: `Enqueue`, `Dequeue`, `Complete`, `Fail` with retry semantics aligned with `internal/infrastructure/postgres/job_queue.go`
- config: `queue.driver=redis`, Redis connection settings; mutual exclusivity — only one queue driver active
- `plugins/core/redis-queue`: register queue provider when driver is redis
- worker and scheduler commands unchanged in interface; they consume whatever `Queue` bootstrap provides
- tests: queue contract tests (enqueue/dequeue/complete/fail/retry) against Redis test instance or miniredis where feasible

## Out Of Scope

- RabbitMQ (PR-416)
- Dead-letter admin UI
- Priority queues beyond existing job model

## Validation

- `queue.driver=postgres`: worker processes jobs from Postgres table (unchanged)
- `queue.driver=redis`: email job enqueued on order event is dequeued and processed by worker
- `go test ./internal/infrastructure/redis ./plugins/core/redis-queue -count=1`
