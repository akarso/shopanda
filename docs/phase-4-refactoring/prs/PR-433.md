# PR-433 — Auth Email Normalization (Track D)

Status: planned

## Summary

- normalize email (lowercase, trim) at register, login, password reset, email change, and `FindByEmail` repository lookups
- prevent case-variant duplicate accounts and login mismatches

## Why

Deferred from PR-399 review: registering `User@Example.com` vs logging in as `user@example.com` can diverge. Email change flow added more surfaces that assume consistent lookup keys.

## Scope

- shared `normalizeEmail` in auth application layer (may already exist from PR-399 — extend to all entry points)
- apply on: `Register`, `Login`, `RequestPasswordReset`, `RequestEmailChange`, `ConfirmEmailChange`, and any admin customer email create/update if applicable
- repository: `FindByEmail` normalizes input before query (or store normalized only — pick one strategy, document migration if needed)
- optional one-time migration or login-time normalization for existing mixed-case rows (minimal: normalize on read + write going forward)
- tests: register with mixed case, login with different case succeeds; duplicate detection case-insensitive

## Out Of Scope

- Plus-address aliasing (`user+tag@`)
- Internationalized email local-parts beyond Unicode lowercasing
- Changing customer notification templates

## Validation

- register `Foo@Bar.com`, login `foo@bar.com` succeeds
- password reset email lookup case-insensitive
- `go test ./internal/application/auth -count=1`
