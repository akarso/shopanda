# PR-412 — Payment Core Plugins (Stripe, Manual) (Track B)

Status: done

## Summary

- extract Stripe and manual/flat-rate payment provider registration into `plugins/core/stripe` and `plugins/core/manualpay`
- preserve env-gated Stripe behavior (disabled when keys absent)

## Why

Payment providers are constructed inline in `main.go` (`stripepay.NewProvider`, manual provider). Moving them to core plugins aligns payments with the three-tier model and keeps Stripe optional without code changes.

## Scope

- `plugins/core/stripe`: registers Stripe provider when `STRIPE_SECRET_KEY` (or existing env) is set; no-op or failed init when absent
- `plugins/core/manualpay`: registers manual/offline payment method (always available as core fallback)
- bootstrap reads payment providers from plugin registration instead of direct `main.go` construction
- checkout and admin payment settings behavior unchanged
- tests: stripe plugin skipped without key; manual plugin always registers

## Out Of Scope

- New payment methods (PayPal, Klarna, etc.)
- Payment transaction ledger admin UI
- Webhook handling changes

## Validation

- default/manual checkout still completes with manual provider
- Stripe-enabled env: Stripe appears in payment methods; existing Stripe flow works
- `go test ./plugins/core/... -count=1`

## What changed

- **`plugins/core/manualpay/`**: always registered; provides manual payment when no other provider is active
- **`plugins/core/stripe/`**: registered when `payment.stripe.enabled`; registers Stripe provider only when `SHOPANDA_PAYMENT_STRIPE_SECRET_KEY` is set (warns and no-ops otherwise)
- **`plugins/core/register.go`**: stripe registers before manualpay so Stripe wins the single provider slot when configured
- **`cmd/api/providers.go`**: `resolvePaymentProvider` reads from plugin app with manual fallback
- **`cmd/api/main.go`**: removed inline Stripe/manual construction
- **Tests**: plugin init guards; register order; resolve payment provider integration
