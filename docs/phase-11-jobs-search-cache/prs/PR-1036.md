# PR-1036 — On-Save Incremental Indexing

Status: planned

## Summary

- Event bus subscribers on product/price/stock/category-assignment change events, enqueuing a small, debounced reindex job scoped to the affected product/category IDs — the search index stays fresh without a manual reindex.

## Why

This is the actual gap identified in prior research: the search index does not update automatically today. A product edit, price change, or stock update leaves the index stale until someone runs `search:reindex` by hand. Every piece needed to fix this cheaply already exists after PR-1033/1034/1035 — this PR is the wiring, following the exact same shape as `internal/application/cache/invalidation.go`'s existing subscriber.

## Scope

- `internal/application/search/invalidation.go` (new, deliberately named/shaped to mirror `internal/application/cache/invalidation.go`) — `IndexUpdateSubscriber.Register(bus)`:
  - `bus.OnAsync(catalog.EventProductUpdated, s.HandleProductUpdated)` → enqueue `ScopeProducts{IDs: [productID]}`.
  - `bus.OnAsync(pricing.EventPriceUpserted, s.HandlePriceUpserted)` → enqueue `ScopeProducts{IDs: [productID]}`.
  - `bus.OnAsync(inventory.EventStockUpdated, s.HandleStockUpdated)` (confirm this event exists; if stock changes don't currently publish an event, adding one is in scope here since it's the direct blocker) → enqueue `ScopeProducts{IDs: [productID]}`.
  - Category-assignment change (new event needed, or reuse `catalog.EventProductUpdated` if category assignment already publishes through it — confirm during implementation) → enqueue `ScopeProducts{IDs: [productID]}` (the product's own document needs its `CategoryIDs` refreshed) **and** nothing for the category document itself unless category metadata changed, not just its product membership.
- **Debouncing:** a burst of edits to the same product within a short window (e.g. a bulk price import touching one SKU multiple times) should not enqueue one reindex job per event. Coalesce via a short in-memory debounce window per product ID (a few seconds) before enqueueing — document the exact mechanism chosen (e.g. a small TTL-based dedupe set) and why it's safe to lose at most one debounce window's worth of coalescing on a process restart (the next save still triggers reindexing; nothing is permanently lost, only delayed).
- These enqueued jobs go through the same `search.reindex` job type and `ScopeProducts` path PR-1034 already built — no new job type, no new execution path.

## Out Of Scope

- Synchronous (request-blocking) on-save indexing — always async via the queue, consistent with every other side-effect-on-event pattern in this codebase (cache invalidation, webhook dispatch). A product save should not get slower because the search engine is momentarily slow.
- Debouncing across a distributed multi-instance deployment (each instance debounces independently) — acceptable over-triggering in the multi-instance case (a few extra small reindex jobs, not a correctness problem) versus the complexity of a distributed debounce; document this tradeoff explicitly.

## Validation (planned — run when implementing)

- `go test ./internal/application/search/... -run Invalidation -count=1` — each event triggers the right scope, debounce coalesces a rapid burst into one enqueue.
- Integration test: update a product via the admin API, assert (with a short poll/wait) that the search index reflects the change without calling `search:reindex`.
- `go build ./...`
