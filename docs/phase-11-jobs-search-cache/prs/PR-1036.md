# PR-1036 — On-Save Incremental Indexing

Status: done

## Summary

- Event bus subscribers on product/price/stock/category-assignment change events, enqueuing a small, debounced reindex job scoped to the affected product/category IDs — the search index stays fresh without a manual reindex.

## Why

This is the actual gap identified in prior research: the search index does not update automatically today. A product edit, price change, or stock update leaves the index stale until someone runs `search:reindex` by hand. Every piece needed to fix this cheaply already exists after PR-1033/1034/1035 — this PR is the wiring, following the exact same shape as `internal/application/cache/invalidation.go`'s existing subscriber.

## Scope

- `internal/application/search/invalidation.go` (new) — `IndexUpdateSubscriber.Register(bus)`:
  - `bus.OnAsync(catalog.EventProductCreated, s.HandleProductCreated)` and `bus.OnAsync(catalog.EventProductUpdated, s.HandleProductUpdated)` → enqueue `ScopeProducts{IDs: [productID]}`.
  - `bus.OnAsync(pricing.EventPriceUpserted, s.HandlePriceUpserted)` → enqueue `ScopeProducts{IDs: [productID]}`.
  - `bus.OnAsync(inventory.EventStockUpdated, s.HandleStockUpdated)` — this event didn't exist; added it (`internal/domain/inventory/events.go`) and the publish call at the admin stock-adjustment path.
  - Category-assignment change — reuses `catalog.EventProductUpdated` (no new event); wired a publish call into `category_product_assignment_admin.go`'s `Assign`/`Unassign`, which previously published nothing at all.
- **Debouncing:** a 5-second in-memory, per-product-ID debounce (`IndexUpdateSubscriber.allow`, a mutex-guarded map with opportunistic pruning) coalesces a burst of edits to the same product into one enqueue. Per-process, not distributed — see "Design decisions."
- These enqueued jobs go through the same `search.reindex` job type and `ScopeProducts` path PR-1034 already built — no new job type, no new execution path.

## Out Of Scope

- Synchronous (request-blocking) on-save indexing — always async via the queue, consistent with every other side-effect-on-event pattern in this codebase (cache invalidation, webhook dispatch).
- Debouncing across a distributed multi-instance deployment — each instance debounces independently; accepted over-triggering (a few extra small reindex jobs), not a correctness problem.
- Wiring `inventory.EventStockUpdated` from the bulk ERP stock-sync importer (`StockSyncService.UpsertBySKU`) — only the interactive admin stock-adjustment endpoint publishes it. See "Design decisions."
- `IndexCategory`-based category-document indexing — still blocked on PR-1037, unrelated to this PR's product-side `CategoryIDs` refresh.

## Design decisions made during implementation

- **Category-assignment changes reuse `catalog.EventProductUpdated`, not a new event.** `category_product_assignment_admin.go`'s `Assign`/`Unassign` published nothing before this PR. Adding a dedicated `catalog.EventCategoryAssignmentChanged` would mean every future consumer needs to remember to subscribe to *two* "this product might need reindexing" events instead of one. Reusing `EventProductUpdated` (with only `ProductID` populated — no consumer, old or new, reads `ProductUpdatedData`'s other fields; every consumer re-fetches fresh data by ID) means `IndexUpdateSubscriber.HandleProductUpdated` covers this for free, and — a genuine side benefit — `cache.InvalidationSubscriber` (already subscribed to this event) now correctly invalidates the product's cache on a category-assignment change too, which it never did before.
- **`inventory.EventStockUpdated` is published only from the interactive admin `PUT /api/v1/admin/inventory/{variantId}` path, not from the bulk ERP stock-sync importer.** `StockSyncService` (used by `wireIntegrationStockSyncer`, called from `serve`, `worker`, and CLI schedule-trigger entry points) doesn't have an `event.Bus` available at several of those call sites, and threading one through all of them was a materially larger, more invasive change than this PR's actual scope justified. A bulk stock import via ERP sync doesn't trigger on-save indexing as a result — an accepted, documented gap (manual/scheduled `search:reindex` remains the fallback), not an oversight.
- **The two pre-existing inline `bus.OnAsync(catalog.EventProduct*, ...)` handlers in `wire_services.go` were removed, not kept alongside the new subscriber.** They called `searchEngine.IndexProduct` directly and synchronously (relative to the event) on every product create/update, bypassing the job queue and `search_index_runs` entirely — no retry, no debounce, no progress tracking. Keeping both would double-index every product edit (once immediately via the old path, once again a few seconds later via the new debounced job) and add a one-row `search_index_runs` entry for every ordinary product edit. Removed in favor of `IndexUpdateSubscriber` handling `EventProductCreated`/`EventProductUpdated` too — this is a deliberate architectural replacement this PR's own "Out Of Scope" section already implied ("synchronous... on-save indexing" being exactly what's being replaced), not an unplanned scope expansion. The trade-off: a product edit now takes up to ~5s (the debounce window) to reflect in search instead of near-immediately, in exchange for queue durability/retry and one consistent code path.
- **`catalog.EventProductCreated` is subscribed even though the plan's own Scope section only names "product/price/stock/category-assignment change events."** Necessary precisely because of the previous point — removing the old inline handlers without also covering `EventProductCreated` in the new subscriber would silently stop indexing brand-new products until the next scheduled full reindex, a real regression the plan didn't intend.
- **The debounce map is bounded via opportunistic pruning on every `allow` call, not a periodic sweep goroutine.** A background goroutine would need its own shutdown/leak handling this subscriber (unlike, say, the job worker) has no natural lifecycle hook for. Pruning stale entries inline — every call scans and evicts anything older than the debounce window before checking/recording the current key — keeps `lastFire` bounded to "product IDs edited within roughly the last debounce window," with no goroutine to manage.
- **`IndexUpdateSubscriber` and `ReindexService` both add `bus`/event wiring to existing HTTP admin handlers via an optional `SetBus(bus *event.Bus)` setter, not a new required constructor parameter.** `InventoryAdminHandler`, `ProductPriceAdminHandler`, and `CategoryProductAssignmentAdminHandler` each have several existing constructors used across real wiring and many tests; adding a required `bus` parameter to all of them would touch every one of those call sites for a dependency most tests don't care about. `SetBus` (left unset, `nil`, publishing is skipped rather than erroring) mirrors `Auditor.SetAuditLogRepository`'s own established optional-wiring pattern in this codebase.

## Round 1 (code review)

- **Blocker — fixed.** `scheduleReindex` called `allow(productID, now)` — which reserves the debounce slot — *before* calling `reindex.Trigger`. If `Trigger` then failed (queue full, a transient DB error), the reservation was never released: every subsequent event for that product within the remaining debounce window was silently swallowed (`scheduleReindex` returns `nil` for a debounced call), even though no reindex had actually succeeded. The index would stay stale with no recovery path except an unrelated future edit to the same product or the next scheduled full reindex. Fixed by adding `evict(productID)`, called when `Trigger` fails, releasing the reservation so the very next event for that product is genuinely retried rather than falsely debounced. New test: `TestIndexUpdateSubscriber_TriggerFailure_EvictsDebounceEntry` — uses a `fakeQueue` with `enqueueErr` set, asserts a second same-product event still reaches `Trigger` (not silently dropped) even though it fails again for the same reason; confirmed to fail against the pre-fix code (second call returns `nil`, `queue.enqueued` stays at 1) and pass against the fix (`queue.enqueued` reaches 2).
- **Major — reviewed, not currently reachable, hardened defensively.** The concern: `pricing.EventPriceUpserted` is published once per row by the bulk price importer (`internal/application/importer/prices.go`), and since this PR now subscribes to that event, a large import could fire one `Trigger` call (one `search_index_runs` row, one queued job) per distinct product — thousands for a large CSV. Checked the actual wiring: `cmd/api/io_commands.go`'s `runImportPrices` (the only production construction of `PriceImporter`) passes `bus=nil` — `imp.bus != nil` is false, so this importer **does not currently publish the event at all**, and `IndexUpdateSubscriber` is never invoked from this path today. The concern is real *if* this importer is ever wired to a real bus, but not reachable in the shipped code as of this PR. Rather than leave that as an implicit, undocumented assumption someone could break by "helpfully" passing a real bus later, added a comment at the `nil` argument explaining why it must stay `nil` absent a batching fix for the search-index side.
- **Major — reviewed, scope confirmed and expanded, documented rather than fixed.** `inventory.EventStockUpdated` is published only from the admin single-variant "Adjust" endpoint; this PR's own "Out Of Scope" only named the ERP bulk-sync importer as a known gap. Investigation surfaced this list is longer, and the highest-frequency one wasn't called out at all:
  - **Checkout reservation/release** (`internal/application/checkout.ReserveInventoryStep`) — decrements/restores `stock.quantity` via raw SQL inside `postgres.ReservationRepo.Reserve`/`Release`, never through `StockRepository`, and has no `event.Bus` wired at all. This is the single highest-frequency stock-changing path in the system (every customer purchase) and it does not keep the index fresh today.
  - **Reservation-expiry release** (`ReservationExpiryHandler`/`ReleaseExpiredBefore`) — the interface only returns a count of released reservations, not which variants changed; publishing an event here requires widening that return type across the interface, the Postgres implementation, and its test doubles first, not just adding a bus.
  - **Returns restocking** (`returns.Service.Receive`) — already has a bus (required, not optional), but has no way to resolve a return item's `VariantID` to a `ProductID` yet (`domainReturns.Item` doesn't carry one, and the service has no `catalog.VariantRepository`).
  - **Bulk stock imports** — both `import:stock` (CLI/CSV, via `importer.NewStockImporter`, which has no event-publishing capability at all) and the ERP `StockSyncService.UpsertBySKU` (already documented as a gap before this round) process many variants per call; wiring either naively would reproduce the same one-event-per-row fan-out risk as the price-importer concern above.

  None of these are small, single-line additions like the three paths this PR already wired (each needed only a `SetBus` call and a nearby dependency already in scope) — the smallest (returns) needs a new constructor dependency across one production and two test call sites; the largest (reservation-expiry) needs a public interface signature change across three layers. Fixing all of this correctly, including the fan-out risk for the two bulk paths, is a meaningfully sized follow-up PR of its own, not a review-response patch. Documented explicitly and specifically (not just "there might be gaps") in `RUNBOOK.md` and below in "Follow-up", with checkout called out as the priority given it's the highest-frequency path.
- **Minor — fixed as part of the Blocker fix above.** New test `TestIndexUpdateSubscriber_TriggerFailure_EvictsDebounceEntry` pins exactly this — the review's ask.
- **Minor — reviewed, not changed.** Async `event.Bus` handler errors are logged only, never retried at the bus level — a pre-existing characteristic of the bus itself (see `internal/platform/event/bus.go`'s own doc comment: "async handler errors are logged and do not propagate"), not something `IndexUpdateSubscriber` introduced or can change unilaterally; changing it would be a bus-wide architectural change well outside this PR's scope. The Blocker fix above removes the specific compounding failure mode the review was actually worried about (a transient `Trigger` failure permanently — for the rest of the debounce window — masking itself as "handled"); a bare log-and-drop for a genuinely one-off transient failure, with the next real save retrying it, is the same accepted trade-off the rest of this codebase's async event handlers already make.

## Follow-up

- PR-1037 — category-entity indexing itself (this PR only refreshes a product's own `CategoryIDs` via reindex, not a separate category document).
- **Wire `inventory.EventStockUpdated` (or an equivalent) into checkout reservation/release — priority, given it's the highest-frequency stock-changing path in the system.** Needs: a `catalog.VariantRepository` (or similar) added to `ReserveInventoryStep` to resolve `ProductID`, and an `event.Bus` reference it currently lacks; the event should be published after a successful `Reserve`/`Release` call, not inside `postgres.ReservationRepo`'s own transaction.
- Wire the same event into reservation-expiry release, returns restocking, and the two bulk stock-import paths (CLI/CSV and ERP sync) — see Round 1's review notes above for what each specifically needs; the two bulk paths additionally need a batching strategy (a single `Trigger(ScopeProducts{IDs: [...]})` call per import, not one per row) to avoid the same job/run fan-out risk flagged for bulk price import.
