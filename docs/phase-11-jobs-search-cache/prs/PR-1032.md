# PR-1032 — Jobs/Scheduler CLI

Status: done

## Summary

- `app jobs:list`, `jobs:show <id>`, `jobs:retry <id>`, `jobs:cancel <id>`, `schedule:list`, `schedule:trigger <name>`, `schedule:enable <name>`, `schedule:disable <name>`.

## Why

Ops/deploy scripts and CI shouldn't need to script against HTTP + auth to do something as simple as "retry this job" or "trigger a reindex now" — a CLI command is the natural interface for that, and this repo already has a CLI command registry (`internal/platform/cli`) other features use the same way.

## Scope

- New commands registered via the existing `cli.Registry`/`app.RegisterCommand` pattern (core commands, not plugin-registered — these belong to the platform itself, same tier as `migrate`, `search:reindex`).
- Each command is a thin wrapper calling the same `internal/application/jobs.Service` / `internal/domain/scheduler` methods the HTTP handlers call — no separate business logic path, so CLI and API can never drift in behavior.
- Output format: human-readable table by default (matching other CLI list commands' style, if one exists to mirror — check `migrate`'s output style), machine-readable via a `--json` flag for scripting.
- Exit codes: non-zero on any failure (job not found, retry on non-failed job, etc.) — scriptable, not just human-readable success/failure text.

## Out Of Scope

- Interactive/TUI mode — plain argument-driven commands only, matching every other CLI command in this repo.

## Design corrections made during implementation

The original spec (kept above for history) got two factual details wrong, both caught by reading the actual CLI infrastructure before writing code:

- **"Registered via the existing `cli.Registry`/`app.RegisterCommand` pattern"** — that type/method pair is the **plugin**-tier CLI API (`internal/platform/plugin/cli.go`), used by plugin-registered commands only. Core/platform commands (`migrate`, `search:reindex`, `scheduler`, etc.) are dispatched via a hand-written `switch os.Args[1]` in `cmd/api/main.go`'s `run()`, each case calling a `runXxx(cfg, log)` helper — confirmed by `docs/guides/DEVELOPER.md`'s own instruction for core commands ("add a `case` in the subcommand switch and a `runXxx` helper"). Using `cli.Registry.Register` for `jobs:*`/`schedule:*` would have made them plugin commands, contradicting the spec's own "same tier as `migrate`, `search:reindex`" — so these commands use the switch+`runXxx` pattern instead, matching every other core command.
- **"Check `migrate`'s output style"** for the human-readable table format — `migrate` produces **no table at all**, only structured JSON log lines (`log.Info(...)`); it has nothing to mirror for tabular output. The actual closest existing convention is `internal/application/pluginreport/format.go`'s hand-rolled `fmt.Fprintf`-with-`%-*s`-padding table (used by `plugins report`) — no table library exists anywhere in this codebase. `cli_format.go`'s `columnWriter` mirrors that style instead.

One more design decision, not a correction of the spec but worth stating explicitly: **`schedule:trigger` does not call `schedulerApp.Service.Trigger`** (the same method `schedule_admin.go`'s HTTP handler calls) — see `runScheduleTrigger`'s doc comment in `schedule_cli.go` for the full reasoning. Short version: that path requires a live scheduler embedded in the calling process (PR-1030's cross-process design), which a standalone CLI invocation never has, so it would always return `CodeConflict` — architecturally correct for `serve` without an embedded scheduler, but useless for the CLI's actual purpose (firing a task on demand from a script). Instead, `schedule:trigger` builds its own short-lived local scheduler (mirroring `./app scheduler`'s exact registration set, including plugin-registered cron jobs) and calls `TriggerLocal` directly, then waits for the fired task to finish (`sched.Stop()`, which blocks on the same `wg.Wait()` `TriggerLocal` participates in) before exiting.

## What changed

- `cmd/api/cli_format.go` (new) — `writeJSON` (indented JSON, matches `pluginreport.FormatJSON`'s convention), `formatCLITimestamp`/`formatCLITimestampJSON` (RFC3339; `"-"` vs. `""` for a zero time, matching table vs. JSON conventions respectively — the latter matches the HTTP admin API's own `toJobSummaryResponses`/`toScheduleResponses` exactly), `parseSingleIDArg`/`parseSingleIDArgs` (usage-error helpers), `columnWriter` (hand-rolled padded-column table, see "Design corrections" above).
- `cmd/api/jobs_cli.go` (new) — `runJobsList`/`runJobsShow`/`runJobsRetry`/`runJobsCancel`, each a thin wrapper opening a standalone DB connection, constructing the same `jobsApp.Service` the HTTP admin API uses (Postgres-queue-only, `postgres.NewJobQueue(conn)` directly — matching `runScheduler`'s existing standalone construction, not `wireServeRuntime`'s plugin-override-aware `resolveJobQueue`), and calling the identical `List`/`Get`/`Retry`/`Cancel` methods `job_admin.go` calls. `jobSummaryToJSON` mirrors `toJobSummaryResponses` field-for-field (duplicated, not imported — the CLI and HTTP interface adapters each own their own presentation, per hexagonal boundaries) so `--json` output stays script-compatible with the REST API's JSON shape.
- `cmd/api/schedule_cli.go` (new) — `runScheduleList`/`runScheduleEnable`/`runScheduleDisable` (thin wrappers over `schedulerApp.Service`, same pattern as jobs); `runScheduleTrigger` (the local-scheduler-registration path — see "Design corrections" above).
- `cmd/api/main.go` — 8 new `case` entries in `run()`'s subcommand switch; 8 new lines in `printHelp`'s usage text (core commands aren't auto-discovered by `app help` — confirmed only plugin commands are, via `appendPluginCLIHelp`).

- `README.md` — 8 new rows in the "CLI commands" table (the actual command reference table in this repo — `docs/guides/DEVELOPER.md` has no such table to update, only a one-line instruction on the core-command pattern; see "Design corrections").
- `RUNBOOK.md` — added a "CLI equivalents" bullet to both the existing "Admin jobs (retry/cancel)" and "Admin schedules" sections, including the `schedule:trigger`-always-works-where-HTTP-trigger-doesn't distinction. Left the "Rollback (deploy / migration / plugin config)" table untouched — verified it contains no "no CLI exists for job retry" sentence (the spec's premise for that edit doesn't match the current file), and job/schedule state correction isn't really a "rollback" in that table's sense (deploy/migration/plugin-config), so no row was a natural fit there either.

## Round 2 (code review)

- **Blocker — fixed.** `jobs:retry`, `jobs:cancel`, `schedule:enable`, `schedule:disable`, `schedule:trigger` called `jobsApp.Service`/`schedulerApp.Service` directly with no `adminapp.Auditor` involved, so a CLI-initiated mutation left zero forensic trail — contradicting RUNBOOK.md's own stated guarantee ("every ... call is written to the admin audit log") for what was, until this fix, an HTTP-only claim. Added `auditCLIAction` (`cli_format.go`) — builds an `adminApp.Auditor` off the command's already-open DB connection and logs the same `AuditAction` constants the HTTP handlers use (`AuditJobRetry`/`AuditJobCancel`/`AuditScheduleEnable`/`AuditScheduleDisable`/`AuditScheduleTrigger`), for both the success and error outcome (matching the HTTP handlers' own both-paths-audited convention). Since a CLI invocation has no authenticated admin session, `AdminID` is `cli:<os-user>` (`cliActor()`, via `os/user.Current()`) — a real, if different, forensic identifier rather than the HTTP path's `"system"` fallback (which is a different, pre-existing convention for "no identifiable admin," not something CLI mutations should silently reuse and be indistinguishable from). All 5 mutating commands now audit; `jobs:list`/`jobs:show`/`schedule:list` (read-only) don't, matching the finding's own explicit scope.
- **Major — fixed.** `jobs:list` hardcoded `Limit: 100, Offset: 0` with no flags and no truncation indicator, unlike the HTTP endpoint's full `offset`/`limit` support. Added `--limit=N`/`--offset=N`, clamped client-side to the same `jobsApp.Service`-internal caps (`jobsListDefaultLimit=20`, `jobsListMaxLimit=100` — duplicated as small stable constants, not re-derived from the unexported service internals) so a full page can be detected reliably; `formatJobsList` now prints `"(showing N job(s) — there may be more; re-run with --offset=M ...)"` when the page came back full, instead of silently truncating.
- **Major — fixed.** `runScheduleTrigger` duplicated `runScheduler`'s entire 5-call registration block inline, with nothing enforcing the two stay in sync — a task added to one and forgotten in the other would make `schedule:trigger <name>` return a misleading "no such task" for a task that plainly exists in `schedule:list`. Extracted `registerSchedulerTasks(pluginApp, jobQueue, log, sched) error` (`schedule_cli.go`) as the single source of truth; both `runScheduler` (`main.go`) and `runScheduleTrigger` now call it. A new task added to the registration set going forward can't silently diverge between the two call sites — there's only one to edit.
- **Major — documented, not re-architected.** `schedule:trigger` runs the full plugin bootstrap (`registry.InitAll`, permission registry freeze, stock syncer wiring) to fire one named task, so any plugin's `Init()` side effects (webhook registration, background goroutines, external calls) fire on every invocation regardless of which task was targeted. This mirrors `runScheduler`'s own construction (not a new pattern — it's required for `schedule:trigger` to be able to reach a plugin-registered cron task at all, the same reason `runScheduler` itself pays this cost at startup) and re-architecting it (e.g. skipping plugin init unless the target task is plugin-registered) is a real, separate change with its own risk (how would the command know *before* registering whether the target is plugin-owned, without already having done the registration?) — out of scope for a review-fix round. Documented explicitly in `runScheduleTrigger`'s doc comment and in RUNBOOK.md's "Admin schedules" section, including the specific caution against wiring `schedule:trigger` into a tight automated loop if an installed plugin does non-idempotent `Init()` work.
- **Minor — fixed.** `formatCLITimestampJSON`'s doc comment claimed to match the HTTP admin API "exactly," which is only true for schedules (`schedule_admin.go`'s `toScheduleResponses` also special-cases a zero time as `""`) — `job_admin.go`'s `toJobSummaryResponses`/`toJobDetailResponse` never check `IsZero()` and would render a zero time as `"0001-01-01T00:00:00Z"` instead. Practically unreachable (a job row's timestamp columns are always populated), so left the HTTP handlers unchanged rather than touching already-shipped, tested PR-1029 code for a purely documentation-driven reason — corrected the comment to state the known divergence instead of overclaiming parity.
- **Minor — fixed.** `--status=` accepted any string with no validation, so a typo (`--status=faild`) silently produced `"No jobs found."` — indistinguishable from a correct query that legitimately found nothing. Added `validJobStatuses` (checked against the same five `domainjobs.Status` constants the domain type defines) and a clear usage error naming the valid values on a mismatch.
- **Minor — subsumed by the Major-1 fix above.** The "no `--limit` validation, filter struct already supports it" note is resolved by the same change that added `--limit`/`--offset` flags with their own validation (positive/non-negative integer checks).
