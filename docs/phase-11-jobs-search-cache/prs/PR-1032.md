# PR-1032 — Jobs/Scheduler CLI

Status: planned

## Summary

- `app jobs:list`, `jobs:show <id>`, `jobs:retry <id>`, `jobs:cancel <id>`, `schedule:list`, `schedule:trigger <name>`, `schedule:enable <name>`, `schedule:disable <name>`.

## Why

Ops/deploy scripts and CI shouldn't need to script against HTTP + auth to do something as simple as "retry this job" or "trigger a reindex now" — a CLI command is the natural interface for that, and this repo already has a CLI command registry (`internal/platform/cli`) other features use the same way.

## Scope

- New commands registered via the existing `cli.Registry`/`app.RegisterCommand` pattern (core commands, not plugin-registered — these belong to the platform itself, same tier as `migrate`, `search:reindex`).
- Each command is a thin wrapper calling the same `internal/application/jobs.Service` / `internal/domain/scheduler` methods the HTTP handlers call — no separate business logic path, so CLI and API can never drift in behavior.
- Output format: human-readable table by default (matching other CLI list commands' style, if one exists to mirror — check `migrate`'s output style), machine-readable via a `--json` flag for scripting.
- Exit codes: non-zero on any failure (job not found, retry on non-failed job, etc.) — scriptable, not just human-readable success/failure text.

## Out Of Scope

- Interactive/TUI mode — plain argument-driven commands only, matching every other CLI command in this repo.
