# PR-1046 — Invalidation Wiring + Stampede Guard

Status: planned

## Summary

- Event subscribers (product/category/price/stock/CMS change events) call `DeleteByTag` (PR-1039) with the changed entity's ID, purging every cached page that rendered it.
- Admin/CLI purge-by-URL escape hatch for anything a tag missed.
- A per-key in-flight lock on cache miss so a popular page invalidated under load is re-rendered once, not once per concurrent request (cache stampede / thundering herd protection).

## Why

PR-1044 writes tags; nothing invalidates by them yet without this PR — a product price change would leave every cached page showing that product serving the stale price until TTL expiry (the safety-net TTL from PR-1044, by design bounds the damage but doesn't eliminate it). Separately, any cache has a well-known failure mode under load: a popular, expensive-to-render page gets invalidated, and the next N concurrent requests for it all miss the cache simultaneously and all try to re-render at once — exactly when the origin is least able to absorb N times the normal render cost. Both are real, both are expected in a "real caching for key areas" deliverable, so both ship together in this PR.

## Scope

**Invalidation wiring:**
- `internal/interfaces/http/storefront/cache_invalidation.go` (new, same shape as `internal/application/cache/invalidation.go` and Track B's `internal/application/search/invalidation.go`) — subscribes to `catalog.EventProductUpdated`, `pricing.EventPriceUpserted`, category-assignment/category-metadata events, CMS content-change events (whatever events those already publish, or need to publish — audit during implementation, same as Track B's PR-1036 had to for stock events).
- Each handler calls `cache.DeleteByTag(ctx, "product:"+id)` / `"category:"+id` / `"cms:"+id` as appropriate — this purges every cached page tagged with that ID, regardless of which route template rendered it (a product's PDP *and* every PLP page it appears on *and* any CMS page featuring it all get purged together, correctly, because they all carry the same tag).
- Async (`bus.OnAsync`), matching every other invalidation subscriber in this codebase — a product save should not get slower because full-page-cache purge is momentarily slow.

**Escape hatch:**
- `POST /admin/cache/purge-url` (`{"path": "/products/some-slug"}`) — computes the cache key(s) for that path across the vary dimensions (store/language/currency × auth-state — a handful of concrete keys, not a wildcard scan) and deletes them directly. For the case a tag genuinely missed (a bug, or content that doesn't cleanly map to a taggable entity), an operator has a manual out that doesn't require guessing at internal tag names.
- New `cache.purge_url` permission (distinct from PR-1042's general `cache.write` — this is full-page-cache-specific).
- CLI: `app cache:purge-url <path>`.

**Stampede guard:**
- Per-key in-flight lock on cache miss, checked before rendering: the first request for a missed key acquires the lock and renders; concurrent requests for the *same* key block briefly (bounded wait, with a fallback to render-anyway past a short timeout rather than hang indefinitely — never let a lock-acquisition failure turn into a hung request) and then read the now-populated cache entry instead of independently re-rendering.
- Implementation: reuse PR-1040's L1 tier's process-local locking for the common single-instance-hot-key case (cheapest, no network round trip), with a documented note that true cross-instance stampede protection (all instances coordinating on the same lock) would need a distributed lock (e.g. a Postgres advisory lock, or a Redis `SETNX`-based lock) — flagged as the natural escalation if per-instance-only locking proves insufficient in practice, not built preemptively without evidence it's needed.

## Out Of Scope

- Cross-instance distributed locking for the stampede guard, as noted above — per-instance locking ships first; escalate only if warranted.
- Predictive/proactive re-render (warming a about-to-expire entry before it's actually requested) — this PR is reactive (invalidate on change, guard on miss), not predictive; predictive warming is real but explicitly deferred per the ROADMAP's "Out of scope" (cache warming).

## Validation (planned — run when implementing)

- `go test ./internal/interfaces/http/storefront/... -run CacheInvalidation -count=1` — a product price change purges every cached page tagged with that product ID and no others; the purge-by-URL escape hatch removes exactly the vary-dimension keys for that path.
- `go test ./internal/interfaces/http/storefront/... -run Stampede -count=1` — N concurrent requests for a missed key result in exactly one render call (assert via a call counter on a test render function), all N requests still get a correct response.
- `go build ./...`
