# PR-1040 — In-Memory (L1) Cache Tier

Status: done

## Summary

- A bounded, TTL+LRU process-local cache sitting in front of the existing `cache.Cache` backend (now "L2"), scoped explicitly to low-churn, read-heavy, bounded-staleness-tolerant data.
- Invalidation propagates within the same process via a broadcast over the existing event bus, backed by a short L1 TTL as the safety net — see "Design decisions" below for why "propagates across instances" from the original spec doesn't literally hold given how that bus actually works, and why the TTL, not the broadcast, is the real cross-replica staleness bound.

## Why

Some reads happen repeatedly and change rarely — the RBAC permission catalog and the storefront category tree, both re-derived from scratch on every call today. This was the highest-judgment PR in the phase: getting the boundary of "safe to serve slightly stale, in-process" wrong turns into a correctness bug, not just a performance one.

## Scope

- `internal/infrastructure/localcache` (new) — `Store[T]`, a generic bounded LRU (fixed max entries, evict-oldest) with per-entry TTL, safe for concurrent use. `GetOrLoad(key, loader)` is the check-then-populate helper most call sites use.
- **Not a new `cache.Cache` implementation** — `Store[T]` satisfies no domain port. It's a narrower, opt-in wrapper a specific caller reaches for explicitly, not a drop-in cache-backend swap — making L1 look like a general-purpose `Cache` would make it too easy to accidentally put invalidation-sensitive data in it.
- **Allowlist actually wired in this PR:** `adminrole.Service.Catalog()` (the RBAC permission catalog) and `storefront.StorefrontHandler.cachedCategories` (the category tree, replacing its own pre-existing ad-hoc single-entry TTL cache). Both documented with their TTL and invalidation story — see "Design decisions" for why the third originally-named candidate, "active plugin config snapshot," is not wired here.
- **Invalidation propagation:** `internal/domain/cache.EventInvalidated`, published by both `cache.Cache` backends' `DeleteByTag`/`DeleteByPrefix` (once `SetBus` is wired — `cacheApp.BusSetter`) on the existing `event.Bus`. `localcache.InvalidateOnTag`/`InvalidateOnPrefix` subscribe a `Store` to it. Neither allowlisted use site above actually routes through `cache.Cache` at all, so both instead use the more direct `localcache.InvalidateOnEvent`, wired to the domain event that already fires on the real mutation (`catalog.EventCategoryCreated/Updated/Deleted` for the category tree; nothing at all for the permission catalog, which never mutates post-freeze). The generic broadcast mechanism is still built and tested as real infrastructure for a future L1 consumer that does sit in front of L2 tag/prefix-invalidated data.
- **Denylist, stated as a design rule:** nothing gated by per-request RBAC context, nothing with a tag that changes more than a few times a minute, nothing containing customer/session/cart data (Track D's fragment territory, never L1). See `docs/guides/DEVELOPER.md`'s new "When it's safe to use the L1 (in-process) cache" section — every future L1 call site must justify itself against that rule in its own comment.

## Out Of Scope

- Using L1 for the full-page cache itself (Track D) — unchanged from the original spec; still reads through L2 directly.
- A generic "cache anything in L1" API — deliberately narrow and allowlisted.
- Making `event.Bus` cross-process (e.g. Redis pub/sub) so invalidation genuinely reaches other replicas — see "Design decisions" below. That would be its own PR, not a fix folded into this one.
- Wrapping "active plugin config snapshot" in L1 — see "Design decisions" below for why investigating it found no actual computation to cache.

## Validation

- `go test ./internal/infrastructure/localcache/... -count=1` — TTL expiry, LRU eviction at capacity, `GetOrLoad` hit/miss/error-not-cached, `Clear`/`Delete`, and a concurrent-access race check. Plus a dedicated broadcast test suite: `InvalidateOnTag`/`InvalidateOnPrefix`/`InvalidateOnEvent` each evict correctly and ignore non-matching tags/prefixes, including a two-`Store`-instances-on-one-bus test standing in for "two separate replicas" (the closest honest simulation given `event.Bus` has no real cross-process delivery — see "Design decisions").
- `go test ./internal/infrastructure/postgres/... ./internal/infrastructure/redis/... -count=1` (with `SHOPANDA_TEST_DSN` set to a real Postgres) — `SetBus` wiring: a successful `DeleteByTag`/`DeleteByPrefix` publishes `cache.EventInvalidated` with the right `Tag`/`Prefix`, including on a partial failure (some batch deleted before a later one errored); unset `SetBus` leaves both methods working exactly as before.
- `go test ./internal/application/adminrole/... -count=1` — `Catalog()` serves from L1 within the TTL window, returns an independent copy each call (mutating one caller's result, including an element of an entry's own `Defaults` slice, must not corrupt what a later call returns), and every existing test (including ones using a non-frozen test registry) still passes unchanged.

Full existing black-box suite for the package still passes unchanged.

## Retrospective

### What changed

- `internal/infrastructure/localcache/store.go` (new) — `Store[T]`: `New`, `Get`, `Set`, `GetOrLoad`, `Delete`, `Clear`, `Len`. Generic bounded LRU (`container/list` + map) with per-entry TTL reset on `Set`, not on `Get` (a write-through freshness bound, not a sliding idle timer).
- `internal/infrastructure/localcache/broadcast.go` (new) — `Evictor` (satisfied by `*Store[T]` for any `T`), `InvalidateOnTag`, `InvalidateOnPrefix` (both async, subscribing to `cache.EventInvalidated`), `InvalidateOnEvent` (synchronous, subscribing to an arbitrary existing domain event).
- `internal/domain/cache/events.go` (new) — `EventInvalidated` constant, `InvalidatedData{Tag, Prefix}`.
- `internal/infrastructure/postgres/cache_store.go` / `internal/infrastructure/redis/cache_store.go` — new optional `SetBus(*event.Bus)`; `DeleteByTag`/`DeleteByPrefix` publish `cache.EventInvalidated` via `PublishAsync` (not `Publish` — see "Design decisions") on success when a bus is set.
- `internal/application/cache/handler.go` — new `BusSetter` interface (`SetBus(*event.Bus)`), the optional-capability type this PR's `cmd/api` wiring asserts against.
- `internal/application/adminrole/service.go` — `Catalog()` now serves from a `localcache.Store[[]PermissionCatalogEntry]` (1 entry, 30s TTL); the original computation moved to `computeCatalog()`, called only on a cache miss.
- `internal/interfaces/http/storefront/storefront.go` — replaced the ad-hoc `storefrontCategoryCache` struct/field with `catNav *localcache.Store[[]catalog.Category]` (same `storefrontCategoryCacheTTL`, unchanged at 45s); new `WithBus(*event.Bus)` wires immediate, same-process eviction on category create/update/delete.
- `cmd/api/main.go` — `setupWorker` asserts the resolved `cache.Cache` against `cacheApp.BusSetter` and wires `app.Bus` when both are non-nil, covering `serve` and `worker` identically (the same shared function, same pattern PR-1049 already established for this cache-store-setup site).
- `cmd/api/wire_routes.go` — `storefront.NewStorefrontHandler(...).WithBus(rt.bus)` added to the existing builder chain.

### Design decisions

- **"Invalidation propagates across instances via a broadcast over the existing event bus" (the original spec's own words) does not literally hold, and this PR does not pretend otherwise.** `internal/platform/event.Bus` is a plain in-process pub/sub — no Redis pub/sub, no network I/O — and every server process (`serve`, `worker`, and each scaled-out replica of either) constructs its own independent `*event.Bus` (confirmed by PR-1049's own finding for `runWorker` vs `wireServeRuntime`). Publishing `cache.EventInvalidated` therefore reaches only subscribers within the SAME OS process; it cannot and does not reach other replicas. `cache.EventInvalidated`'s own doc comment states this explicitly, as does `docs/guides/DEVELOPER.md`'s new section and this PR's own validation test names. The short L1 TTL (30s/45s, "seconds, not minutes" per the original spec's own denylist rule) is therefore not just a safety net alongside the broadcast — it is the *entire* cross-replica staleness bound; the broadcast only shortens same-process staleness (typically to sub-millisecond). Making the bus genuinely cross-process is out of scope (see "Out Of Scope") — a materially larger, separately-reviewable change.
- **Only two of the three originally-named allowlist candidates are actually wired: the RBAC permission catalog and the category tree. "Active plugin config snapshot" is not.** Investigating it found no expensive computation to cache in the first place: plugin config values are read via direct, already-O(1) struct-field access (`ConfigField.Get`/`ValueFromConfig` against the shared `*config.Config`), not a query or a derived computation like `Registry.CatalogPermissions()` or `CategoryRepository.FindAll()`. Wrapping an already-cheap read in a cache adds real complexity (the underlying struct has no synchronization of its own today, so an L1 snapshot would need to decide what "atomic enough" means across its several plugin-owned fields) for no measurable benefit. Revisit only if a genuinely expensive plugin-config-derived computation appears later — the allowlist is additive, not a checklist to complete for its own sake.
- **The permission catalog needs no invalidation trigger, not even the generic broadcast — it is TTL-only by design, not by oversight.** `rbac.Registry.Register` is only ever called from plugin `Init()`, before `Freeze()`, before `sealPermissionRegistry` runs (confirmed: `wire_services.go` freezes before constructing `adminRoleService`) — by the time `Catalog()` is ever called in production, the registry it reads cannot mutate again for the life of the process. The 30s TTL exists purely for uniform L1 policy (every use site gets one, so nobody has to remember which is the exception), not because this specific cache can ever actually go stale.
- **The category tree's own invalidation uses `localcache.InvalidateOnEvent` (a direct subscription to `catalog.EventCategoryCreated/Updated/Deleted`), not the generic `cache.EventInvalidated`/`InvalidateOnTag` mechanism** — because category writes don't go through `cache.Cache`'s tag/prefix mechanism at all today (`category_admin.go` publishes those catalog events directly; nothing calls `DeleteByTag`/`DeleteByPrefix` for a category change). Routing this through the generic mechanism would have meant inventing a cache tag nobody else needs, purely to reuse infrastructure that doesn't actually fit. `InvalidateOnEvent` is registered synchronously (`bus.On`, not `bus.OnAsync`) specifically so the process that handled the admin write has already evicted its own L1 copy by the time that same request's response goes out — it can never observe its own stale write; other processes still rely solely on the TTL.
- **`SetBus`/`publishInvalidated` use `PublishAsync`, not `Publish`, even though `PublishAsync`'s own doc comment frames it as a fallback for "after a Publish call has already failed."** Mechanically it does exactly what's needed here — dispatch straight to async handlers, no sync phase, never returns an error — and that last property is the actual reason for choosing it: `cache.EventInvalidated` is a fire-and-forget coherence signal for an in-process cache tier, not a domain event meant to carry request-blocking listeners, and a future misbehaving sync subscriber must never be able to make an otherwise-successful cache deletion itself fail. Both backends' `SetBus` doc comments spell this out.
- **The "two simulated instances" validation scenario in the original spec (`RegisterPermission` on one instance evicting a second instance's L1) doesn't translate literally**, for the same reason above: `Register` never runs after `Freeze()`, so there is no real "change a permission at runtime" event to broadcast for the RBAC catalog specifically. `internal/infrastructure/localcache/broadcast_test.go`'s `TestInvalidateOnTag_EvictsAcrossSimulatedInstances` demonstrates the actual, honest limit instead: two independent `Store` instances (standing in for two replicas) both subscribed to ONE shared bus (the closest a same-process test can get to "another subscriber reacting to the same invalidation," since a real second replica's bus is categorically unreachable from here) — publishing once evicts both. This proves the mechanism works; it does not and cannot prove cross-process delivery, because that delivery doesn't exist.
- **A prior draft of the category-tree migration return the L1-cached slice directly to callers.** Both `adminrole.Service.Catalog()` and `storefront.cachedCategories` instead return a fresh `append([]T(nil), cached...)` copy on every call (hit or miss) — matching the discipline the pre-existing ad-hoc `storefrontCategoryCache` already had (clone on write AND read) — so a caller mutating its own result in place can never corrupt the cached entry or another caller's copy. Regression tests for both (`TestService_Catalog_MutatingResultDoesNotCorruptCache`, `TestCachedCategories_ReturnsIndependentCopies`) mutate via index assignment specifically, not `append` — `append` onto a slice with no spare capacity silently allocates a new backing array and would pass even against an aliased, uncopied cache entry, so it doesn't actually exercise the bug either fix guards against.
- **A first draft of the `SetBus`/broadcast tests raced**: a bare `var captured []event.Event` written by `bus.OnAsync`'s own goroutine and polled by the test's `waitForCaptured` helper from the main test goroutine, with no synchronization between the two. `go test -race` caught it. Fixed with a small mutex-guarded `eventCollector` in both `cache_store_test.go` (Redis) and `cache_store_integration_test.go` (Postgres) — a test-only bug, not a production one; `redis.CacheStore`/`postgres.CacheStore`/`event.Bus` themselves were never at fault.
