# PR-1040 — In-Memory (L1) Cache Tier

Status: planned

## Summary

- A bounded, TTL+LRU process-local cache sitting in front of the existing `cache.Cache` backend (now "L2"), scoped explicitly to low-churn, read-heavy, bounded-staleness-tolerant data.
- Invalidation propagates across instances via a broadcast over the existing event bus, backed by a short L1 TTL as the safety net.

## Why

Some reads happen on every request (permission catalog, category tree for nav, active promotion rule set, plugin config) and change rarely — a network round trip to Postgres/Redis for data that changes a few times a day is pure overhead. This is the highest-judgment PR in the phase: get the boundary of "safe to serve slightly stale, in-process" wrong and it becomes a correctness bug (a permission change or a disabled promotion staying live for one instance's TTL window after every other part of the system has already moved on).

## Scope

- `internal/infrastructure/localcache` (new) — a generic `Store[T]` wrapping a bounded LRU (fixed max entries, evict-oldest) with per-entry TTL, safe for concurrent use.
- **Not a new `cache.Cache` implementation** — this does not satisfy the `Cache` port. It's a narrower, opt-in wrapper a specific caller reaches for explicitly (`localcache.Cached(loader func() (T, error), ttl time.Duration)`-style helper), not a drop-in cache-backend swap. This is a deliberate design choice: making L1 look like a general-purpose `Cache` implementation would make it too easy to accidentally put invalidation-sensitive data in it.
- **Explicit allowlist of what may use L1 in this PR:** `rbac.Registry` permission catalog (read-only after `FreezePermissionRegistry`, already effectively immutable per-process — L1 here is closer to a formalization of an existing implicit cache than a new risk), category tree (nav rendering), active plugin config snapshot. Each documented with its TTL (seconds, not minutes) and its invalidation story.
- **Invalidation propagation:** `PR-1039`'s `DeleteByTag`/`DeleteByPrefix` calls also publish an async event (`cache.invalidated`, payload = tag or prefix) on the existing `event.Bus`; every instance's L1 layer subscribes and evicts matching local entries. This bounds cross-instance staleness to "however long the async event takes to arrive" (typically sub-second, same-process-cluster) rather than relying solely on TTL expiry.
- **Explicit denylist, stated as a design rule, not just an implementation detail:** nothing gated by per-request RBAC context, nothing with a tag that changes more than a few times a minute, nothing containing customer/session/cart data (that's Track D's fragment territory, never L1). A code-review checklist item for this PR: every L1 use site must justify itself against this rule in its own comment, not just exist because it was convenient.

## Out Of Scope

- Using L1 for the full-page cache itself (Track D) — full-page cache entries are large, per-route+vary-key (high cardinality, low reuse-per-entry benefit relative to memory cost), and need tag invalidation with the multi-instance guarantee that a broadcast-plus-short-TTL model gives L2 but L1 only approximates. Track D reads through L2 directly.
- A generic "cache anything in L1" API — deliberately narrow and allowlisted, not a general facility, per the reasoning above.

## Validation (planned — run when implementing)

- `go test ./internal/infrastructure/localcache/... -count=1` — TTL expiry, LRU eviction at capacity, concurrent access race-free (`-race`).
- Integration test: change a permission via `RegisterPermission` on one simulated instance, assert the invalidation broadcast evicts the local cache on a second simulated instance within a bounded time.
- `go build ./...`
