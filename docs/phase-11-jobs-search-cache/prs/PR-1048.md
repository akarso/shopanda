# PR-1048 — Fix Search Reindex Stuck-Run Gap

Status: done

## Summary

- Add an automatic reconciliation sweep (`search.reindex.reconcile`, a scheduled job like `audit.retention`/`inventory.reservation_expiry`) that corrects a `search_index_runs` row stuck `processing` once its underlying `search.reindex` job has itself reached a terminal status.
- Add a CLI mutation (`app search:reindex-runs:reconcile <run-id> --reason=<text>`) for the ambiguous case the sweep can't safely resolve on its own — an operator-confirmed orphaned run whose job is also still `processing`/`pending` or missing.

## Why

PR-1033's own "Out Of Scope" section named two ways a `search_index_runs` row can be left `processing` forever with nothing left to ever change it — a worker crash before `Finish` is ever called, and every retry of the terminal `Finish` write itself failing on the job's last allowed attempt — and said the row "just needs to be reconciled with the job's outcome." That reconciliation was never built: RUNBOOK.md documented the gap (`grep` for `` left `processing` forever ``) but the only fix on offer was `UPDATE search_index_runs` by hand. This PR closes that gap for real.

## Scope

- `internal/domain/search/reindex.go`: `RunStore.FindStaleProcessing(ctx, olderThan, limit)` (new port method, `limit`-bounded) and a new `ReindexJobLookup` port (`FindReindexJobByRunID`) returning a `ReindexJobStatus` — deliberately not `domain/jobs.Detail`, keeping `domain/search` decoupled from the jobs bounded context (the same principle `ProductSource`'s doc comment applies to the catalog domain). `RunStore.Finish` is now a **conditional** update (only a currently-`processing` run is changed) and reports a run that's already terminal via `ErrRunNotProcessing`, distinct from "not found" — see "Design decisions."
- `internal/infrastructure/postgres/search_index_run_repo.go`: `SearchIndexRunRepo.FindStaleProcessing` — `SELECT ... WHERE status = 'processing' AND started_at < $1 ORDER BY started_at ASC LIMIT $2`. `Finish` — `UPDATE ... WHERE id = $1 AND status = 'processing'`, with a follow-up existence check on a zero-row update to distinguish "not found" from "found but no longer processing."
- `internal/infrastructure/postgres/search_reindex_job_finder.go` (new): `ReindexJobFinder`, a narrow type (not a method on `JobQueue` — see its doc comment for why, mirroring `SearchProductSource`'s own reasoning) that queries `jobs` by `type = 'search.reindex' AND payload->>'run_id' = $1`.
- `migrations/070_add_jobs_reindex_run_id_index.sql` (new): a partial index (`WHERE type = 'search.reindex'`) backing that `payload->>'run_id'` lookup — unindexed otherwise past `idx_jobs_type` (066) narrowing to the type.
- `internal/application/search/reindex_reconcile.go` (new):
  - `ReconcileHandler` (`jobs.Handler`, type `search.reindex.reconcile`) — sweeps up to `reconcileBatchLimit` (500) runs stuck `processing` past `staleAfter` (2 hours), within a `reconcileSweepTimeout` (5 minutes) budget, and for each checks `ReindexJobLookup`. A job found and terminal (`done`/`failed`/`cancelled`), or no job found at all, is safe to correct automatically — nothing will ever call `Finish` for that run again either way — so the run is marked `failed` with an explanatory `last_error` via the now-conditional `Finish` (a concurrently-finished run is skipped, not clobbered). A job still `pending`/`processing` is left alone: status alone can't tell a genuinely orphaned job apart from one still legitimately running. `Handle` returns an error when any run's job-lookup or `Finish` call hits a genuine failure (not the benign already-terminal case), so a persistent problem surfaces as a retried/failed job rather than a silent `done`.
  - `ReconcileRunManually(ctx, runs, runID, reason)` — the manual counterpart the CLI calls: validates the run is currently `processing` (`apperror.Conflict` otherwise) and exists (`apperror.NotFound` otherwise) as a friendly up-front check, then `Finish`es it `failed` with the given reason — `Finish`'s own conditional update is the actual guard against the run finishing concurrently between that check and this write (mapped to `apperror.Conflict` too).
  - `NewReconcileHandler` panics on a nil dependency, matching `inventory.NewReservationExpiryHandler`'s convention.
- `internal/platform/runtime/reindex_reconcile.go` (new): `RegisterReindexReconcile(jobQueue, log, sched)`, cron `*/30 * * * *`, registered alongside the other three `Register*` calls in both `runServe`'s embedded scheduler and `registerSchedulerTasks` (`cmd/api/schedule_cli.go`, shared by `runScheduler` and `schedule:trigger`) — both call sites gated on `queue.driver=postgres` (Round 3).
- `cmd/api/main.go`: `setupWorker` constructs `ReindexJobFinder` and registers `ReconcileHandler` right after `ReindexHandler`, also gated on `queue.driver=postgres` (Round 3).
- `cmd/api/search_reindex_runs_cli.go` (new): `app search:reindex-runs:reconcile <run-id> --reason=<text>`, audited as `search_reindex_run.reconcile` (new `AuditAction`, `internal/application/admin/audit.go`) via the same `auditCLIAction` helper `jobs:retry`/`jobs:cancel` use.
- `internal/application/search/reindex_handler.go`: `finishWithRetry` treats `ErrRunNotProcessing` from its own `Finish` calls as success, not a transient failure to retry — see "Design decisions."

## Design decisions

- **The automatic sweep only acts when the underlying job is unambiguously done for good.** A worker crash mid-`Handle` leaves not just the run row but the *job* row stuck `processing` too — this codebase's `jobs` table has no lease/heartbeat column and no reaper, so nothing ever requeues or fails an orphaned job on its own (confirmed by reading `internal/domain/jobs/worker.go` and the `017_create_jobs.sql` schema: `Dequeue` sets `processing` and increments `attempts`; only the same process instance's own `Complete`/`Fail` call ever moves it again). Guessing "processing for a long time == crashed" from status alone risks failing a run that a slow-but-alive worker is still genuinely processing — there is no signal that changes during a long batch scan to tell the two apart. Rather than guess, the sweep only auto-corrects the unambiguous case (job reached `done`/`failed`/`cancelled`, or no job exists at all), and surfaces the ambiguous case (job also stuck `processing`/`pending`) for an operator to judge via the manual CLI. This means a raw worker-process-crash-mid-scan, by itself, is *not* fully closed by the automatic sweep — see "Out of scope" below.
- **A terminal job always corrects the run to `failed`, never `completed`,** even when the job's own status is `done`. There is no way to trust a `processed_count`/`total_count` as genuinely "complete" when `ReindexHandler` itself never got to confirm it (the whole point of the gap is that its own `Finish(completed)` call never landed) — a false `completed` would hide that a reindex silently never finished writing its own outcome. `failed` with an explanatory `last_error` is the honest state; an operator who wants the data reindexed for real re-runs `search:reindex`.
- **`ReconcileHandler`/`ReconcileRunManually` reuse `RunStore.Finish` rather than a new "reconcile" write path**, and `Finish` itself is now a conditional update (`WHERE status = 'processing'`) rather than the unconditional-by-id write it started as — see Round 2 below for why that changed.
- **The manual CLI never touches the `jobs` table**, only `search_index_runs` — matching `jobs.Admin`'s existing, deliberate absence of a "force-fail a processing job" action (`Cancel` only works on `pending`; see its doc comment on why there's no in-flight cancellation). An operator judging a job dead doesn't need — and per that existing constraint, can't get — a matching mutation on the job row itself; RUNBOOK.md's crashed-job caveat stays a separately documented, orthogonal limitation of the job queue itself (affects every job type, not just `search.reindex`), not something this PR's scope covers.
- **`staleAfter = 2 hours`, sweep every 30 minutes**, both plain constants (not config-overridable like PR-1034's `search.reindex_full_scan_threshold`) — this is an internal operational threshold with no merchant-facing tuning need, matching `sweepTimeout`/`reindexBatchSize`'s existing precedent in `reindex_handler.go` rather than PR-1034's user-facing scope-threshold precedent. `ReindexHandler` indexes one product at a time with no batching/concurrency, so an unusually slow `SearchEngine` could in principle push a legitimate run past 2 hours — functionally harmless (its job still reads as non-terminal, so the sweep just logs `job_not_terminal` and leaves it alone), just a reminder this is a heuristic, not a hard proof of "stuck."

## Out of scope

- **A general job-queue lease/heartbeat/reaper mechanism** for a worker that crashes mid-`Handle`, leaving the job row itself (not just the run row) stuck `processing` forever. This is a pre-existing gap in `internal/domain/jobs`/`postgres.JobQueue` affecting every job type, not something specific to `search.reindex` — a real fix (a claimed-at/heartbeat column, a reaper sweep requeuing jobs whose claim looks stale) is a job-queue-level design decision well beyond "fix the search-reindex stuck-run gap," and is exactly the residual scenario `search:reindex-runs:reconcile`'s manual path exists for today. Flagged as a natural follow-up, not attempted here.
- Admin HTTP API exposure of `search:reindex-runs:reconcile` — CLI-only in this PR, matching PR-1029's job admin API scope boundary (retry/cancel exist as both HTTP and CLI, but this fix predates and is independent of PR-1035's admin API work). Revisit alongside PR-1035 if a GUI action is wanted.

## Round 2 (code review)

- **Blocker — fixed.** `RunStore.Finish` wrote unconditionally by `id`, with no `WHERE status = 'processing'` guard. Both new callers decide to call `Finish` based on an earlier, separate read (the stale-run scan, or `ReconcileRunManually`'s own `Get`) with no re-check at write time — concretely: the sweep reads a run as stale with its job `failed` (terminal) → in parallel an operator runs `jobs:retry` on that same job (`internal/infrastructure/postgres/job_queue.go`'s `Retry`) and it goes on to complete, calling `Finish(run, completed)` → the sweep's now-stale decision still fires `Finish(run, failed, "...")` afterward and silently overwrites a run that just legitimately completed, with a misleading `last_error`. `ReconcileRunManually` had the same TOCTOU independently (`Get` then `Finish` as two round trips with no lock between them). Fixed using the same conditional-`UPDATE` pattern `job_queue.go`'s `Retry`/`Cancel` (via `transitionStatus`) already use for exactly this class of bug: `Finish` is now `UPDATE ... WHERE id = $1 AND status = 'processing'`; a zero-row update triggers a follow-up existence check to distinguish "run doesn't exist" (still a plain error) from "run exists but is no longer processing" (new `domainsearch.ErrRunNotProcessing`, via `errors.Is`). `ReconcileHandler` treats that error as a skip (`already_terminal` counter, logged, not an error), `ReconcileRunManually` maps it to `apperror.Conflict`, and `ReindexHandler.finishWithRetry` (which shares the same port method for its own, non-racy-in-the-common-case completion path) treats it as success rather than something to retry. New tests: `TestSearchIndexRunRepo_Finish_AlreadyTerminalIsNoop`/`_NotFoundErrors` (integration, against real Postgres), `TestReconcileHandler_Handle_ConcurrentlyFinishedRunIsSkippedNotErrored`, `TestReconcileRunManually_ConcurrentlyFinishedRunReturnsConflict`.
- **Major — fixed.** `ReconcileHandler.Handle` never returned an error for per-run failures — a `FindReindexJobByRunID`/`Finish` failure on every stale run (e.g. a permissions or connectivity issue scoped to those tables) still returned `nil` overall, so the Jobs Admin GUI would always show the job `done` with no operator-visible signal that reconciliation was silently doing nothing (unlike `inventory.ReservationExpiryHandler`, which does propagate its own genuine failures). Fixed: `Handle` now returns an aggregate error when one or more stale runs hit a real failure (excluding the benign already-terminal case above), so a persistent problem surfaces as a retried/failed `search.reindex.reconcile` job like any other genuine failure. Updated `TestReconcileHandler_Handle_JobLookupErrorSkipsRunWithoutFailingJob` (renamed to `..._LeavesRunUntouchedButFailsJob`) to assert the new behavior.
- **Major — fixed.** No bound on iteration count or time: `FindStaleProcessing` had no `LIMIT` and `Handle`'s loop had no timeout (unlike `reservation_expiry_handler.go`'s explicit `sweepTimeout`) — a mass-orphan event (e.g. a bad deploy crashing many workers) would make one sweep tick sequentially process an unbounded number of runs with no time cap. Fixed: `FindStaleProcessing` gained a `limit` parameter (`SearchIndexRunRepo` implements it as `LIMIT $2`), `ReconcileHandler` calls it with `reconcileBatchLimit = 500`, and `Handle` wraps its work in a `reconcileSweepTimeout = 5 * time.Minute` deadline, breaking the loop cleanly (and logging `more_remaining`) if it fires mid-batch — mirroring `reservation_expiry_handler.go`'s own pattern exactly. A run left over a full batch or past the deadline stays `processing` and so stays a match for the next 30-minute tick, draining a large backlog across ticks the same way reservation expiry does. New tests: `TestSearchIndexRunRepo_FindStaleProcessing_RespectsLimit` (integration), `TestReconcileHandler_Handle_BoundsFindStaleProcessingQuery`.
- **Minor — fixed.** `FindReindexJobByRunID`'s query relied on `idx_jobs_type` to narrow rows and then filtered `payload->>'run_id'` unindexed — fine at current volume, but no index backs the `run_id` lookup itself. Added `migrations/070_add_jobs_reindex_run_id_index.sql`, a partial index scoped to `type = 'search.reindex'` (same `CREATE INDEX IF NOT EXISTS` + no-`CONCURRENTLY`-inside-a-transaction caveat as `066_add_jobs_introspection_indexes.sql`).
- **Minor — fixed.** `NewReconcileHandler` had no nil-checks on its dependencies, unlike `NewReservationExpiryHandler`'s explicit panics — inconsistent defensive style for a job handler with no meaningful degraded mode. Added matching panics for `runs`/`jobLookup`/`log`. New test: `TestNewReconcileHandler_PanicsOnNilDeps`.
- **Reviewed, not changed:** the `staleAfter = 2h` throughput justification is a documented heuristic, not a proof — noted explicitly in "Design decisions" above rather than changed, since a slow-but-alive run reading as non-terminal (and thus being left alone) is the correct, harmless outcome of that heuristic being wrong in the conservative direction.

## Round 3 (code review)

- **Blocker — fixed.** `ReindexJobFinder.FindReindexJobByRunID` queries the Postgres `jobs` table directly, bypassing the `jobs.Queue` port entirely. That's only meaningful when Postgres is actually the queue backend: on `queue.driver=redis`/`rabbitmq`/`kafka`/`sqs` (each a real, plugin-provided `jobs.Queue` implementation — see `plugins/core/{redisqueue,rabbitmqqueue,kafkaqueue,sqsqueue}` and `cmd/api/providers.go`'s `resolveJobQueue`), that table is never populated regardless of what's really running. Left as-is, the sweep would report `Found: false` for every live broker-backed job once its run passed `staleAfter`, mark the run `failed`, and then — thanks to Round 2's own conditional-`Finish` fix — correctly *reject* the job's later legitimate completion as `ErrRunNotProcessing`, leaving a successfully-reindexed run permanently misreported `failed`. This is exactly the class of gap `jobs.Reader`/`jobs.Admin` already document as Postgres-queue-only (see `jobs_cli.go`'s `newJobsService`, which refuses `jobs:*` commands outright under a non-Postgres driver, the same reasoning). Fixed the same way: `setupWorker` (`cmd/api/main.go`) only constructs `ReindexJobFinder`/registers `ReconcileHandler` under `cfg.Queue.Driver == "postgres"` (logging `search.reindex.reconcile.disabled` otherwise); both scheduler registration sites (`runServe`'s embedded scheduler, and `registerSchedulerTasks` shared by `runScheduler`/`schedule:trigger`, via `pluginApp.Config.Queue.Driver`) skip `RegisterReindexReconcile` under the same condition, so a broker-backed worker never gets a `search.reindex.reconcile` job it has no handler for either. `search:reindex-runs:reconcile` (the manual CLI) is unaffected — it only ever touches `search_index_runs`, never the `jobs` table — and remains the supported recovery path on every queue driver.
- **Minor — fixed.** The new `search:reindex-runs:reconcile` command was missing from `README.md`'s "CLI commands" table (the repository's primary command reference, which does enumerate `jobs:*`/`schedule:*` alongside `search:reindex`) — an operator working from that table alone had no way to discover the manual recovery path. Added a row directly under `search:reindex`.
