# PR-1028 — Job Introspection

Status: planned

## Summary

- Add a read-only application service over the `jobs` table: list (filtered by type/status), get by ID, status counts by type.
- No HTTP surface in this PR — this is the foundation PR-1029 (jobs admin API), PR-1035 (reindex progress), and PR-1046 (cache-purge job tracking) all build on.

## Why

Job state today is visible only via logs or direct SQL against the `jobs` table. Every later PR in this phase that needs "what's the status of this background thing" (reindex progress, async cache purge) would otherwise reinvent this query layer. Building it once, generically, first, is what keeps the rest of the phase from accumulating parallel ad-hoc status-tracking code.

## Scope

- `internal/application/jobs` (new package): `Service` with `List(ctx, filter ListFilter) ([]JobSummary, error)`, `Get(ctx, id string) (*JobDetail, error)`, `CountsByStatus(ctx) (map[string]int, error)`.
- `ListFilter{Type string; Status string; Limit, Offset int}` — both fields optional (empty = no filter on that dimension).
- `JobSummary` / `JobDetail` are read models over `jobs.Job` — `JobDetail` additionally exposes attempt history if the queue implementation tracks it (Postgres implementation does not currently retain per-attempt error history beyond the last one; document this as a known limitation, not silently pretend richer history exists).
- Repository method additions on the Postgres `jobs.Queue` implementation (or a new narrower read-only port, `jobs.Reader`, if adding read methods to the write-oriented `Queue` interface would violate its existing single-responsibility shape — decide during implementation, document the choice in "What changed").
- Pagination: `Limit` capped at the same `maxListLimit`-style bound used elsewhere in the admin repos (100), default page size documented.

## Out Of Scope

- Any HTTP or CLI surface — PR-1029 and PR-1032.
- Non-Postgres queue drivers (Redis/RabbitMQ/Kafka/SQS) gaining the same introspection — those are broker-backed and don't have a queryable `jobs` table; document this as a real limitation: **job introspection is Postgres-queue-only in this phase.** A broker-backed deployment loses admin visibility into job state, which is a real regression a future PR would need to address (e.g. a shadow status table written by the worker regardless of which queue backend is active) — flagged here, not solved here.

## Validation (planned — run when implementing)

- `go test ./internal/application/jobs/... -count=1` — list filtering, pagination bounds, counts-by-status against a real Postgres test DB.
- `go build ./...`
