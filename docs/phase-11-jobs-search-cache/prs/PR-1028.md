# PR-1028 — Job Introspection

Status: done

## Summary

- Add a read-only application service over the `jobs` table: list (filtered by type/status), get by ID, status counts by type.
- No HTTP surface in this PR — this is the foundation PR-1029 (jobs admin API), PR-1035 (reindex progress), and PR-1046 (cache-purge job tracking) all build on.

## Why

Job state today is visible only via logs or direct SQL against the `jobs` table. Every later PR in this phase that needs "what's the status of this background thing" (reindex progress, async cache purge) would otherwise reinvent this query layer. Building it once, generically, first, is what keeps the rest of the phase from accumulating parallel ad-hoc status-tracking code.

## Scope

- `internal/application/jobs` (new package): `Service` with `List(ctx, filter ListFilter) ([]JobSummary, error)`, `Get(ctx, id string) (*JobDetail, error)`, `CountsByStatus(ctx) (map[string]int, error)`.
- `ListFilter{Type string; Status string; Limit, Offset int}` — both fields optional (empty = no filter on that dimension).
- `JobSummary` / `JobDetail` are read models over `jobs.Job` — `JobDetail` additionally exposes attempt history if the queue implementation tracks it (Postgres implementation does not currently retain per-attempt error history beyond the last one; document this as a known limitation, not silently pretend richer history exists).
- Repository method additions on the Postgres `jobs.Queue` implementation (or a new narrower read-only port, `jobs.Reader`, if adding read methods to the write-oriented `Queue` interface would violate its existing single-responsibility shape — decide during implementation, document the choice in "What changed").
- Pagination: `Limit` capped at the same `maxListLimit`-style bound used elsewhere in the admin repos (100), default page size documented.

## What changed

Verified against source before implementing: the spec assumed the Postgres queue "does not currently retain per-attempt error history beyond the last one." That was optimistic — `job_queue.go`'s `Fail` never persisted `jobErr` anywhere at all; a failed job's `status='failed'` carried no reason whatsoever. Since the entire point of a "detail" read model is showing why a job failed, closing that specific gap (last error only, not full history — matching what the spec actually asked for) was in scope here rather than deferred to a later PR discovering the same thing.

| Area | Change |
| --- | --- |
| `migrations/065_add_jobs_last_error.sql` | New nullable `jobs.last_error TEXT` column. |
| `internal/infrastructure/postgres/job_queue.go` | `Fail(ctx, id, jobErr)` now persists `jobErr.Error()` into `last_error` on both the permanent-fail and re-queue-for-retry paths (`last_error = COALESCE($n, last_error)`, so a nil `jobErr` — the worker's "no handler registered" path — leaves whatever was already there instead of clobbering it with an invented message). Added `List`, `Get`, `CountsByStatus` to the same `*JobQueue` type, satisfying the new `jobs.Reader` port below — one Postgres-backed type naturally satisfies both the write-oriented `Queue` port and the read-only `Reader` port, since it's the same table either way. |
| `internal/domain/jobs/reader.go` (new) | `ListFilter`, `Summary` (list read model, no `Payload`), `Detail` (`Summary` + `Payload` + `LastError`), and the `Reader` port itself — kept separate from `Queue` deliberately: a future broker-backed `Queue` (Redis/RabbitMQ/Kafka/SQS) has no queryable job table and structurally can't implement introspection, so folding `List`/`Get`/`CountsByStatus` into `Queue` would force every implementation to either fake it or leave methods unimplemented against an interface claiming to support them. This mirrors `internal/domain/admin`'s existing `AuditLogFilter`/`AuditLogRepository` split (filter type + read methods live in the domain package, not the application layer) rather than the spec's original literal package placement (`internal/application/jobs`) — followed the codebase's own established convention over the spec's first draft. |
| `internal/application/jobs/service.go` (new) | `Service` wraps `domainjobs.Reader`, owning pagination policy centrally (`defaultListLimit = 20`, `maxListLimit = 100`, negative offset floored to 0) rather than trusting every future `Reader` implementation to enforce it consistently — the reader itself just trusts `filter.Limit`/`Offset` as given. `List`/`Get`/`CountsByStatus` are thin pass-throughs otherwise; `Get("")` and a nil reader at construction both reject early. |
| `internal/infrastructure/postgres/job_queue_test.go` | New integration tests: `last_error` persisted on both `Fail` paths, nil `jobErr` leaves it unchanged, `List` (unfiltered/by-type/by-status/paginated), `Get` (not-found → `nil, nil`; payload round-trips), `CountsByStatus` (a status with zero jobs is absent from the map, not zero-valued). |
| `internal/application/jobs/service_test.go` (new) | Unit tests against a fake `Reader`: limit defaulting/capping, offset flooring, filter/error pass-through, `Get`'s empty-id guard and not-found pass-through. |

### Round 2 — code review response

One major finding undercut the whole point of this PR; the other was a real, if lower-severity, performance gap. Both fixed:

- **The most diagnostically useful failure case still recorded no reason.** `worker.go`'s "no handler registered" branch called `recordFail(ctx, job.ID, nil)` — a misconfigured or typo'd job type, exactly the case an operator most needs `last_error` for. `Fail`'s `COALESCE($n, last_error)` only records something when `jobErr` is non-nil, so this specific path left `last_error` blank forever, contradicting this PR's own stated rationale. Fixed: the worker now passes `fmt.Errorf("no handler registered for job type %q", job.Type)` instead of `nil`. New test: `TestWorker_FailsUnknownType` extended to assert the recorded error's exact message (required teaching `mockQueue.Fail` to actually capture `jobErr` — it previously discarded it).
- **No index backs any of the new read queries.** `idx_jobs_dequeue` (migration 017) is a partial index scoped to `status = 'pending'` for the dequeue hot path only — it does nothing for `List`'s `ORDER BY created_at DESC` (every call) plus optional type/status filters, or `CountsByStatus`'s unconditional `GROUP BY status`, both of which degrade as the table grows (and there is no pruning/retention job for `jobs` itself — flagged as a separate, real follow-up, not fixed here since it's a bigger, undiscussed policy decision: how long to keep done/failed rows, whether that's even wanted for audit purposes). Fixed: `migrations/066_add_jobs_introspection_indexes.sql` adds plain indexes on `created_at DESC`, `type`, and `status`.

Three minor findings, all fixed:

- **`ListFilter.Status` was a bare `string`** while `Summary.Status`/`Detail.Status` are the typed `Status` — a typo silently matched zero rows instead of failing to compile. Changed to `Status Status` (same pattern `jobs.Job.Status` already uses), with an explicit `string(filter.Status)` cast at the one place it binds to a SQL query arg.
- **`Offset` was floored at 0 but never capped**, so an arbitrarily large value would force a full scan-and-discard for a request returning nothing. Added `maxListOffset = 100_000` in `Service.List`, documented as a stopgap — real deep pagination should move to a keyset (`created_at`/`id` cursor) design once PR-1029 actually exposes `Offset` to an untrusted caller, not just raise this ceiling further.
- **`Detail.Payload`'s nil-guard in `Get` was dead code** — `jobs.payload` is `NOT NULL DEFAULT '{}'`, so `payloadJSON` is never empty and `Unmarshal` never leaves `Payload` nil. Removed. (The identical dead-code shape also pre-exists in `Dequeue`, unrelated to this PR and not touched — noted here rather than silently left for a future reader to wonder why one copy was cleaned up and its twin wasn't.)

**Reviewed, not changed:** `List`/`Get`/`CountsByStatus` trusting `filter.Limit`/`Offset` as given (rather than each independently validating) — this is the deliberate design already documented in `Service`'s own doc comment (pagination policy lives once, centrally, not duplicated per `Reader` implementation). The review called this "fine today since there's exactly one caller path" and flagged it as a footgun for a future second caller bypassing `Service` — a real, correctly-scoped concern to revisit if/when a second caller actually appears, not something to defensively re-validate at every layer preemptively.

### Round 3 — code review response

**Unstable pagination.** `List`'s `ORDER BY created_at DESC` alone leaves ties undefined across separate queries — two jobs enqueued in the same instant (plausible: a bulk enqueue, or just coarse timestamp resolution under load) could appear on neither page, or on both, depending on how Postgres happens to break the tie each time. Fixed: `ORDER BY created_at DESC, id DESC` (id is the primary key, so this fully determines order). Also updated `migrations/066_add_jobs_introspection_indexes.sql` — not yet shipped, so edited in place rather than adding a new migration — so `idx_jobs_created_at` covers `(created_at DESC, id DESC)` and can satisfy the full sort, not just the first key. New test: `TestJobQueue_List_StableOrderOnEqualCreatedAt` — seeds several jobs sharing one `created_at` (verified via a `count(DISTINCT created_at)` sanity check rather than assumed), pages through them one at a time, and confirms every job is visited exactly once with a repeatable order across two independent runs of the same pagination sequence.

## Out Of Scope

- Any HTTP or CLI surface — PR-1029 and PR-1032.
- Non-Postgres queue drivers (Redis/RabbitMQ/Kafka/SQS) gaining the same introspection — those are broker-backed and don't have a queryable `jobs` table; document this as a real limitation: **job introspection is Postgres-queue-only in this phase.** A broker-backed deployment loses admin visibility into job state, which is a real regression a future PR would need to address (e.g. a shadow status table written by the worker regardless of which queue backend is active) — flagged here, not solved here.
