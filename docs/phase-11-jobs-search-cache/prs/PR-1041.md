# PR-1041 — Rate Limiting Hardening

Status: done

## Summary

- Added a Redis-backed sliding-window rate limiter as an opt-in alternative to the in-process token bucket (`rate_limit.driver: memory|redis`, default `memory`).
- HTTP middleware talks to `ratelimit.Allow` / `ratelimit.Factory` — same interface for both backends.
- Documented sliding-window vs fixed-window, optional auth `per_route` (not in `defaults()`), and probe/webhook policy.

## Why

`ratelimit.Limiter` is correct for one instance and silently wrong for more than one — each process gets its own bucket, so the effective limit scales with instance count. This PR makes a shared ceiling opt-in without forcing Redis on single-instance or gateway-fronted deployments.

## Scope

- `internal/platform/ratelimit` — `Allow(ctx, key) Decision` (`Canceled` marks a gone client), `Factory.New(Spec)`, `Window` as exact `burst/rate` duration (µs floor), `MemoryRetryAfter`, `on_error` open/closed/local. Injected `now` on the memory limiter (tests freeze time). Memory `Allow` ignores `ctx`.
- `internal/infrastructure/redis` — dedicated limiter client (`NewLimiterClient`: 200ms I/O, retries disabled, pool `min(10*GOMAXPROCS, 64)` or `rate_limit.redis.pool_size`). ZSET sliding window using Redis `TIME` (Redis 5+) and Lua with **microsecond** scores. Window = `burst/rate` seconds (floor 1µs); `rate > burst` is valid (2000/s burst 1 → 500µs). Circuit: ≥20 requests with ≥50% errors in 2s (20×100ms atomic buckets), **or** ≥5 all-error requests when the window is quieter → 5s hold; a failed probe re-arms the hold; `defer` always releases `probing`. Already-cancelled contexts set `Decision.Canceled` without recording. Redis I/O uses `context.WithoutCancel`. `on_error: local` builds an in-process limiter only when requested. Keys under `<prefix>-rl:`.
- `rate_limit.driver`, `rate_limit.on_error`, `rate_limit.redis.url`, `rate_limit.redis.key_prefix`, `rate_limit.redis.pool_size`, env overlays. Limiter URL is `rate_limit.redis.url` / `SHOPANDA_RATE_LIMIT_REDIS_URL`, else `cache.redis.url` / `REDIS_URL`. `enabled: false` does not dial Redis. Startup PING failure with global `on_error` other than `closed` logs a warning (`fail_closed_routes` when a `per_route` is `closed`) and opens the circuit instead of exiting.
- `/readyz` is always in-process. Example auth prefixes: login, login/mfa, register, password-reset with `on_error: local`. Not in `defaults()`.
- `ClientIP` joins every `X-Forwarded-For` line, walks from the right, accepts `ip:port` / `[v6]:port`, stops at the first invalid hop. No `X-Real-Ip` fallback when XFF is present.

## Out of scope

- Auth-lockout mechanism (`internal/application/auth/lockout.go`) — already shared via cache `Incr`.
- Rate-limit admin UI/API — infrastructure config only.
- Redis Cluster / Sentinel (same limit as the cache plugin).
- Capping the cache client's go-redis pool (still `10*GOMAXPROCS`).
- Applying cancel-deny to the memory limiter (documented driver difference).

## Design decisions

- **Dedicated limiter client.** Production never reuses the cache pool. Short timeouts and no retries bound a hung Redis at ~200ms without leaking eval goroutines or starving cache connections. Default pool is `min(10*GOMAXPROCS, 64)` (at least 8); YAML `pool_size` can raise the cap. Fleet math is limiter pool + cache pool per instance — see RUNBOOK.
- **Cancelled request = drop, uncounted.** Redis `Allow` sets `Decision.Canceled` if the parent context is already done **or** finishes after Redis returns (no fail-open admit, no local-fallback consume, no 429, no `ratelimit.rejected`). A Redis **error** after RST_STREAM does not `recordError` (no circuit trip, no backend-error metric). A Redis **success** still `recordSuccess`, so a half-open probe closes the circuit for live traffic even if that client is gone. Middleware writes status 499 so HTTP metrics record 4xx instead of the default 2xx. Redis runs on `WithoutCancel` so a disconnect cannot abort the script. `defer releaseProbe()` so a probe cannot stick open. The memory driver ignores `ctx` (HTTP/1.1 half-close is counted there, dropped on redis).
- **Fail-open by default; auth uses `local`.** A Redis outage must not 429 the whole API or `/readyz`. Auth example routes use `on_error: local` so logins keep a per-process ceiling (N instances → N× budget during an outage). `closed` is still available. Circuit: ≥20 req and ≥50% errors in 2s, **or** ≥5 all-error reqs **within those 2s** when the window has fewer than 20 samples (quiet instances / staging). Slower than five errors per 2s just pays 200ms each. A short `BGSAVE` stall at high RPS does not open the circuit (successes in the same window). At ~3–9 req/s a 300ms stall with no successes in the same 2s can trip; that is the trade-off for covering quiet instances. Failed probes re-arm the 5s hold. `shopanda_ratelimit_backend_errors_total` keeps incrementing while the circuit is open (`reason=circuit_open`). Sum over `limiter` for a factory-wide outage. `pool_timeout` uses `errors.Is(err, goredis.ErrPoolTimeout)` only.
- **Startup.** Unreachable Redis at boot does not crash serve unless **global** `on_error=closed`. The circuit starts open and a probe recovers it. Per-route `closed` still 429s for the 5s hold (`fail_closed_routes` on the warning). This does **not** apply when `cache.driver=redis`: `ConnectURL` still PINGs and fails startup.
- **`/readyz` stays in-process.** Protects this instance's DB pool.
- **Microsecond window; `rate` may exceed `burst`.** Lua scores Redis `TIME` in microseconds so a window shorter than 1ms is not rounded up (2000/s burst 1 is 500µs, not a 1ms window that halves the rate). `Window` is the exact `burst/rate` duration. PEXPIRE is still millisecond-only and is rounded up so TTL cannot reap an in-progress window. Switching `memory` → `redis` with the same rate/burst does **not** preserve burst-recovery timing: the token bucket refills continuously (~100ms at 10/20); the sliding window waits for the oldest entry to age out (~2s at 10/20).
- **No default auth `per_route`.** `/login/mfa` has its own example entry (burst 5) so MFA does not share login's burst of 2. Replaces the previous example's `/api/v1/auth` 5/s burst 10: login is tighter (1/s burst 2; two rapid attempts then 429); `/auth/me` and `/logout` use default 10/20. Regenerating from the example is a real policy change.
- **Rightmost-untrusted `ClientIP` across all header lines.** HAProxy-style second `X-Forwarded-For` line is joined before the walk. `host:port` hops are stripped. Invalid hop → peer. `trusted_proxies` must include CDN/edge ranges (also keys auth lockout).
- **Limiter Redis URL.** `rate_limit.redis.url` / `SHOPANDA_RATE_LIMIT_REDIS_URL` wins; otherwise `cache.redis.url` / `REDIS_URL`. A dedicated limiter URL is never ignored in favor of cache Redis.
- **Key prefix.** `rate_limit.redis.key_prefix` (else cache prefix, else `shopanda`). When `cache.driver=redis`, `cache.redis.key_prefix` must be non-empty so `DeleteByPrefix("")` cannot SCAN `*` over limiter keys.
- **Metrics interface.** `RateLimitBackendError(limiter, reason string)` is a breaking change for any out-of-repo recorder (none in this repo). `limiter` is `default` or `route:<path_prefix>` (not CR1's `per_route` umbrella). `reason` is `error`, `circuit_open`, or `pool_timeout`.
