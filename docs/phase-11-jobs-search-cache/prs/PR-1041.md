# PR-1041 — Rate Limiting Hardening

Status: done

## Summary

- Add a Redis-backed sliding-window rate limiter as an opt-in alternative to the existing in-process token bucket (`rate_limit.driver: memory|redis`, default `memory` — no new dependency for the common single-instance/behind-a-gateway case).
- Document TTL/window best practices and bring the general HTTP limiter's design in line with the reasoning the existing auth-lockout limiter already gets right.

## Why

Today's `ratelimit.Limiter` is correct for one instance and silently wrong for more than one — each process gets its own independent bucket, so the *effective* limit scales with instance count instead of staying fixed, without anyone configuring that on purpose. This has been true since rate limiting shipped in Phase 10 and RUNBOOK.md already discloses it ("Limits are not shared across instances — use a gateway or WAF for a global HTTP ceiling"), but a documented limitation is still a real gap for anyone running multiple instances without a gateway-level limiter in front.

## Scope

- `internal/infrastructure/redis/ratelimit.go` (new) — sliding-window counter using Redis sorted sets (timestamp-scored entries, `ZREMRANGEBYSCORE` to expire the window, `ZCARD` to check the count, `ZADD` to record) — avoids the fixed-window "burst at the boundary" problem a naive `INCR`+`EXPIRE` fixed-window counter has (a client can send 2x the limit by timing requests around a window edge).
- `rate_limit.driver` config key, `memory` (default, current `ratelimit.Limiter` behavior, unchanged) or `redis` (new). Both satisfy a new, narrow `RateLimiter` interface (`Allow(key string) bool`) introduced in `internal/interfaces/http/shared` at the middleware's own point of use — the middleware previously depended on the concrete `*ratelimit.Limiter` type directly, so this PR also had to extract that interface, not just add a second implementation of a pre-existing one. `RateLimitMiddleware` takes a `LimiterFactory` (nil defaults to the in-process bucket); the redis-backed factory is constructed at the composition root (`cmd/api`), since the interfaces layer must not import `internal/infrastructure/redis` directly (AGENTS.md's dependency-direction rule).
- **Documented policy, not just code** (this is as much a RUNBOOK/DEVELOPER.md deliverable as a code one):
  - Sliding window over fixed window, and why (boundary-burst avoidance, as above).
  - Auth endpoints get a distinct, tighter budget from general API traffic — already true for login lockout; this PR extends the same reasoning explicitly to the general HTTP limiter's config (a documented recommended split, e.g. auth routes at 1/10th the general API rate), not a new enforced mechanism beyond what `rate_limit.trusted_proxies`-scoped, per-route limiter configuration already technically allows.
  - Probe/automated-traffic endpoints need their own budget — already true for `/readyz`; this PR's docs audit whether any other automated-traffic path (webhook delivery callbacks, integration inbound routes) should get the same treatment, and either applies it or explicitly documents why not.

## Out Of Scope

- Changing the auth-lockout mechanism itself (`internal/application/auth/lockout.go`) — it already does sliding-window-correct atomic counting via `Incr`/`CompareAndSubtract`; this PR is about bringing the *general* HTTP limiter up to the same standard, not touching what's already correct.
- A distributed rate-limit admin UI/API — rate limiting is infrastructure-level config (`rate_limit.driver`, thresholds), not a runtime-adjustable-per-request admin surface; no GUI/API deliverable in this PR.

## Validation

- `go test ./internal/infrastructure/redis/... -run RateLimit -count=1` — burst admitted then rejected, independent keys/scopes, a deterministic (injected clock, no real sleeping) sliding-window test proving an entry is admitted again as soon as the OLDEST entry ages out of the window rather than waiting for a fixed-window reset, fail-open on a broken Redis connection, and constructor argument validation.
- `go test -race -count=3 ./internal/infrastructure/redis/... -run RateLimiter_ConcurrentRequestsNearLimitDoNotOverAdmit` — 100 goroutines racing one key with burst=20 admit exactly 20, not more; regression-proofed by temporarily swapping the atomic Lua script for a naive two-round-trip ZREMRANGEBYSCORE+ZCARD-then-ZADD check, which reliably over-admitted (23–39 out of a burst of 20 across 10 runs) before the fix was restored.
- `go test ./internal/infrastructure/redis/... -run TestRateLimiter_CrossReplicaMembersDoNotCollide -count=1` — two real `RateLimiter` instances (standing in for two replicas) against one Redis backend, same scope, same client key, same frozen clock: a shared burst of 2 is enforced combined, not doubled. Regression-proofed by reverting to the pre-fix counter-only member scheme and confirming it over-admits (3 of 2) before the fix was restored — see "Design decisions" for the bug this closes.
- `go test ./internal/interfaces/http/shared/... -run RateLimit -count=1` — `RateLimitMiddleware` uses a provided `LimiterFactory` (scope names passed correctly), propagates a factory error, and — standing in for the spec's planned "memory vs redis across two simulated instances" comparison, since this package cannot import `internal/infrastructure/redis` — two independent `RateLimitMiddleware` instances built from factories sharing one fake limiter's budget map enforce a *combined* limit across both, exactly what a shared Redis backend does and a per-process memory bucket cannot.
- `go test ./internal/platform/config/... -run RateLimit -count=1` — `rate_limit.driver`/`rate_limit.redis.*` YAML parsing, env overlay (including the generic `REDIS_URL` fallback and the dedicated env var winning over it), and flatten entries.
- `go test ./cmd/api/... -run ResolveRateLimiterFactory -count=1` — driver switch: `memory`/empty/case-insensitive returns a nil factory, `redis` without a URL or with an unreachable one errors, an unsupported driver value errors.
- `go build ./...`, `go vet ./...`, `gofmt -l .` — clean except the pre-existing, unrelated `internal/application/auth/lockout_test.go` formatting diff.

## Retrospective

### What changed

- `internal/infrastructure/redis/ratelimit.go` (new) — `RateLimiter`: `NewRateLimiter(client, keyPrefix, scope, rate, burst, log)`, `Allow(key string) bool`. One atomic Lua script (`ZREMRANGEBYSCORE` + `ZCARD` + conditional `ZADD` + `PEXPIRE`) per check — a sliding-window LOG, not a fixed-window counter. Fails open (logs, returns `true`) on any Redis error, including a check that now hits an explicit `checkTimeout` (250ms) deadline rather than relying solely on the go-redis client's own implicit default. Each `Allow` call's ZSET member embeds a per-`RateLimiter`, `crypto/rand`-generated instance ID (fixed after code review — see "Design decisions") alongside the timestamp and an intra-instance sequence counter.
- `internal/interfaces/http/shared/ratelimit_middleware.go` — extracted `RateLimiter` (`Allow(key string) bool`) and `LimiterFactory` (`func(scope string, rate float64, burst int) (RateLimiter, error)`); `RateLimitMiddleware` now takes a `LimiterFactory` (nil → the in-process bucket, scope ignored) and returns `(Middleware, error)` instead of just `Middleware`, since constructing a redis-backed limiter can fail.
- `internal/interfaces/http/shared_compat.go` — re-exports `RateLimiter`/`LimiterFactory` and the updated `RateLimitMiddleware` signature, same shim pattern PR-1021 established for every other shared primitive.
- `internal/platform/config/config.go` — `RateLimitConfig.Driver`/`.Redis` (`RedisRateLimitConfig{URL, KeyPrefix}`), defaulting to `"memory"`; env overlay (`SHOPANDA_RATE_LIMIT_DRIVER`/`_REDIS_URL`/`_REDIS_KEY_PREFIX`, plus the generic `REDIS_URL` fallback already used by `cache.redis.url`/`queue.redis.url`); flatten entries.
- `cmd/api/wire_routes.go` — `resolveRateLimiterFactory(cfg, log)`: `memory`/empty → `nil` (default); `redis` → connects via `redis.ConnectURL` and returns a factory wrapping `redis.NewRateLimiter`; anything else → error. `buildServeHandler` now propagates that error instead of unconditionally wiring the memory limiter.

### Design decisions

- **The middleware did not already depend on an interface — the spec's "both satisfy the same internal limiter interface the middleware already depends on" wasn't quite accurate.** `RateLimitMiddleware` held `*ratelimit.Limiter` (the concrete struct) directly. Extracting `RateLimiter` was itself part of this PR's work, not a pre-existing seam the redis backend could just plug into.
- **The `RateLimiter`/`LimiterFactory` interface lives in `internal/interfaces/http/shared` (the consumer), not in `internal/platform/ratelimit` (the existing concrete type's package) or in `internal/infrastructure/redis`.** AGENTS.md's dependency direction is `interfaces → application → domain`, with infrastructure wired in from the composition root — the interfaces layer must not import `internal/infrastructure/redis` directly. Defining the interface at the point of use (a well-known Go idiom, reinforced here by an actual architectural constraint, not just style) lets both the memory and redis implementations satisfy it structurally with zero import from `shared` back into either.
- **Rate/Burst (the existing token-bucket shape) maps onto the sliding-window log as: admit up to Burst requests in any Burst/Rate-second window.** This preserves the same peak burst size and long-run average rate a token bucket of that capacity/refill-rate allows, so switching `rate_limit.driver` needs no config reshaping — the existing `default`/`per_route` rate/burst values carry over unchanged.
- **One Lua script, not separate `ZREMRANGEBYSCORE`/`ZCARD`/`ZADD` calls.** Two round trips would let two concurrent `Allow` calls for the same key both read a `ZCARD` below the limit before either writes, over-admitting past the burst under load — confirmed by deliberately reverting to that shape during regression-proofing (see Validation): it reliably over-admitted (23–39 instead of 20) under 100 concurrent goroutines. A single atomic script closes the race entirely.
- **Millisecond-epoch scores, not nanosecond.** A Redis ZSET score is a double-precision float. Nanosecond epoch timestamps (~1.7×10¹⁸ as of 2026) exceed a float64's exact-integer range (2^53 ≈ 9×10¹⁵) and would silently lose precision, risking misordering or same-score collisions. Millisecond epoch (~1.7×10¹²) fits exactly for centuries.
- **The ZSET member embeds a per-`RateLimiter` random instance ID, not just a timestamp and a process-local counter.** An earlier version of this code used only `"<ms>-<seq>"`, with `seq` a plain `atomic.Int64` starting at 0 — the code review round below caught that this was a real, not theoretical, cross-replica bug: every replica's own `seq` starts at 0, so two replicas' Nth call to the same scope at the same millisecond produced the *identical* member string, and the second `ZADD` silently overwrote the first entry's score instead of adding a new one — undercounting real admitted traffic and letting more through than the shared burst allows, in exactly the multi-instance scenario this whole PR exists to fix. Fixed by generating an 8-byte `crypto/rand` instance ID once per `RateLimiter` (`NewRateLimiter`) and folding it into every member (`"<ms>-<instanceID>-<seq>"`) — `seq` still disambiguates same-millisecond calls *within* one instance, but cross-replica uniqueness now comes from randomness, not from an assumption that never held. Regression-proofed: `TestRateLimiter_CrossReplicaMembersDoNotCollide` constructs two real `RateLimiter`s against one Redis backend with a frozen, identical clock on both (reproducing the worst case deterministically) and confirms a shared burst is enforced combined, not doubled; reverting to the counter-only member scheme reliably over-admits (3 of a burst of 2) and fails the test.
- **Fail open on a Redis error, matching `auth.Service.reserveLockoutAttempt`'s own established reasoning, not a new policy invented for this PR.** A rate limiter that fails closed turns a transient Redis blip into a full API outage for every request — a strictly worse availability failure than the theoretical, temporary abuse window an open-fail leaves. Deliberately regression-proofed the same way: temporarily flipping the fail-open branch to `false` and confirming the dedicated test catches it.
- **`Allow`'s script call now runs under an explicit `checkTimeout` (250ms), not just the go-redis client's own implicit default read/write timeouts.** A code review round flagged that relying solely on client defaults leaves the "fail open, don't take down the request path" guarantee dependent on those defaults never being overridden (e.g. via the connection URL) — without an explicit deadline, a genuine hang (not just an explicit error) could block the request path for however long an overridden or misconfigured client timeout allowed, or indefinitely with none. An explicit, code-owned timeout removes that dependency.
- **The `/api/v1/auth` per-route example in `configs/config.example.yaml` keeps its original `rate: 5.0`/`burst: 10` values, not the initially-drafted `1.0`/`2`.** A code review round caught that silently tightening a shipped example 5x, framed as rate-limiter infrastructure hardening, is an undocumented behavior change for any deployment that regenerates its config from this file — `burst: 2` on login is aggressive (two attempts total, including retries after a typo or a 2FA step) for something no one asked to change. The ~1/10th-of-default recommendation stays in prose (this doc, RUNBOOK.md) as guidance to tune deliberately, not baked into the example's actual numbers.
- **An independent Redis client, not a reuse of `cache.Cache`'s Redis connection, despite an earlier ROADMAP.md planning note suggesting the latter.** `cache.driver` and `rate_limit.driver` are independent config keys — a deployment can run `cache.driver=postgres` with `rate_limit.driver=redis` (no cache Redis client would exist to reuse) or the reverse. Sharing a connection only when both happen to be `redis` would add real coupling between two independently-configured features for a marginal connection-count saving, and there is no existing precedent for it either: `cache.driver=redis` and `queue.driver=redis` already each open their own independent client today. Matching that established, simpler pattern won out over the planning note's aspiration.
- **`internal/interfaces/http/shared`'s own tests cannot exercise a real `redis.RateLimiter`** (that package must not import `internal/infrastructure/redis`), so the spec's planned "load-style test comparing memory vs redis driver behavior... across two simulated instances" is instead demonstrated with a fake `RateLimiter` sharing one budget map across two independently-constructed `RateLimitMiddleware` instances — proving the *mechanism* (a shared backend enforces a combined limit no per-process memory bucket can) without needing a live Redis connection in a package that architecturally can't have one. The real Redis atomicity/correctness guarantees are covered separately, with a live `miniredis` backend, in `internal/infrastructure/redis`'s own tests.
