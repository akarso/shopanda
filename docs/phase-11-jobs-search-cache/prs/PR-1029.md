# PR-1029 — Jobs Admin API

Status: done

## Summary

- `GET /api/v1/admin/jobs` (list, filter by type/status, paginated), `GET /api/v1/admin/jobs/{id}` (detail), `POST /api/v1/admin/jobs/{id}/retry`, `POST /api/v1/admin/jobs/{id}/cancel`.
- New `jobs.read` / `jobs.write` RBAC permissions.

## Why

This is the first point in the codebase where an operator can see or act on job state without SQL. It's also a direct, scoped answer to a question that's come up in prior work: "how do I retry a failed job?" — today the only answer is "manually flip its status/run_at/attempts in the database."

## Scope

- `internal/interfaces/http/admin/job_admin.go` — `JobAdminHandler`, constructor takes the PR-1028 `jobs.Service` plus an `Auditor`, methods return `http.HandlerFunc` (matching the existing `*_admin.go` convention, e.g. `store_credit_admin.go`).
- `retry`: only valid on a `failed` job — resets `attempts` to 0 and `status` to `pending`, `run_at` to now. Returns `409 conflict` if the job isn't currently `failed` (retrying a `pending` or `processing` job is a no-op error, not silently ignored).
- `cancel`: only valid on a `pending` job — flips status to `cancelled` (new terminal status, migration needed). **No in-flight cancellation** — a `processing` job cannot be cancelled; document this clearly in the API response (`409` with a message explaining why, not a generic error) since it's the most likely point of operator confusion.
- Permissions: `jobs.read` gates list/detail; `jobs.write` gates retry/cancel (mirrors the `customers.read`/`customers.store_credit.write` split pattern from Phase 10). Add both to `internal/domain/rbac/permission.go` and `CorePermissions()` in `catalog.go`.
- Audit log entries for retry/cancel (`ResourceType: "job"`), matching the store-credit-issuance audit pattern — every retry/cancel is who-did-what-when, same as payments/returns.
- Route registration in `cmd/api/wire_routes.go`, gated by `admin.RequirePermission(rbac.JobsRead)` / `RequirePermission(rbac.JobsWrite)`.

## Out Of Scope

- Bulk retry/cancel (retry-all-failed-of-type) — single-job actions only in this PR; revisit if operators actually hit a batch-retry need in practice.
- A `cancelled` job's downstream side effects (e.g. did a partially-processed handler leave inconsistent state) — cancellation is only meaningful for `pending` jobs precisely because they haven't started, so this isn't a real risk in this PR's scope, but worth stating explicitly since it would become one if cancellation were ever extended to `processing`.

## What changed

- `internal/domain/jobs/job.go` — new `StatusCancelled` status constant; `migrations/067_add_jobs_cancelled_status.sql` extends the `jobs_status_check` CHECK constraint.
- `internal/domain/jobs/admin.go` — new `Admin` port (`Retry`, `Cancel`), kept separate from `Queue` and `Reader` for the same ISP reasoning as PR-1028's `Reader`: a broker-backed queue has no updatable job table.
- `internal/infrastructure/postgres/job_queue.go` — `Retry`/`Cancel` implemented via a shared `transitionStatus` helper: look up current status first (so a 409 can name the actual status), then an atomic conditional `UPDATE ... WHERE status = <expected>` + `RowsAffected()` check, the same race-safe shape as the worker's own `Complete`/`Fail`.
- `internal/application/jobs/service.go` — `Service` now also holds an `admin` port; `NewService` takes both `reader` and `admin` (both required); added `Retry`/`Cancel` (empty-id validation, then delegate).
- `internal/domain/rbac/{permission.go,catalog.go,role_permissions.go}` — new `jobs.read`/`jobs.write` permissions, admin-only (mirrors `audit.read`).
- `internal/interfaces/http/admin/job_admin.go` — `JobAdminHandler` (`List`, `Get`, `Retry`, `Cancel`), matching the `store_credit_admin.go` convention: audit-logs every call (`ResourceType: "job"`), reuses `httpshared.JSON`/`JSONError`/`ParsePagination`.
- `internal/application/admin/audit.go` — `AuditJobList`/`AuditJobRead`/`AuditJobRetry`/`AuditJobCancel` actions.
- `cmd/api/wire_services.go` — type-asserts the resolved `jobQueue` to `jobs.Reader` and `jobs.Admin` and fails startup with a clear error if the configured queue driver doesn't support them (same pattern as `resolveCache`'s `ExpiredDeleter` assertion) — Postgres-queue-only for now, consistent with PR-1028.
- `cmd/api/wire_routes.go` — 4 routes gated by `jobs.read` (list/get) and `jobs.write` (retry/cancel).
- `openapi.yaml` — documents the 4 routes; adds a new `Conflict` (409) response component (didn't exist before this PR).
- `docs/guides/DEVELOPER.md` — new "Jobs admin API" section (there's no admin GUI for this yet, so it's documented as a direct API, not a UI walkthrough).
- `docs/diagrams/c4-component.md` — new `JobAdminHandler` component + a `Rel` to `PostgresJobQueue` via the `jobs.Reader`/`jobs.Admin` ports.
- `docs/guides/MERCHANT.md` — **No change.** That guide walks through the admin *UI*; there is no jobs admin GUI yet (that's PR-1031), so documenting retry/cancel there would describe a screen that doesn't exist. The API itself is documented in `docs/guides/DEVELOPER.md` instead.
- `docs/diagrams/c4-container.md`, `docs/diagrams/c4-code.md` — **No change.** `c4-container.md` is container-grained (API server / worker / scheduler / Postgres) and doesn't enumerate individual HTTP handlers; `JobAdminHandler` runs in the existing API Server container, so there's nothing new to draw at that level. `c4-code.md` is a representative class-diagram excerpt (e.g. `StoreAdminHandler`), not an enumeration of every `*_admin.go` handler — `store_credit_admin.go`, `webhook_endpoint_admin.go`, etc. aren't there either, and `job_admin.go` doesn't need to be the exception.

- Reviewed and skipped: collapsing `transitionStatus`'s lookup+conditional-UPDATE into a single `UPDATE ... RETURNING` — the current two-step shape is already race-safe (`RowsAffected() == 0` catches a concurrent status change between the lookup and the UPDATE), so this is a minor round-trip optimization, not a correctness fix. Not worth the added complexity unless this endpoint becomes hot.
