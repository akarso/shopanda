# PR-1030 — Scheduler Admin

Status: done

## Summary

- Expose the cron scheduler's registered tasks (name, spec, next run time, enabled state) as a queryable catalog.
- `GET /api/v1/admin/schedules`, `POST /api/v1/admin/schedules/{name}/trigger` (fire now), `POST /api/v1/admin/schedules/{name}/enable` / `.../disable` (persisted override).
- Reuses PR-1029's `jobs.read`/`jobs.write` permissions — no new permission pair.

## Why

`cron.Scheduler` only exposed `Register`/`Start`/`Stop` — there was no way to ask it "what's registered and when does it next fire" without reading source code, and no way to fire a scheduled task on demand.

## Design correction made during implementation

The original spec (see the "Scope" section below, kept for history) assumed an in-process `Scheduler.Catalog()`/`TriggerNow()` pair would be enough, with "trigger now and the real tick fired are indistinguishable to the fn itself — no special-casing needed." That assumption only holds when the admin API and the running scheduler are the same OS process.

They aren't, in the deployment topology this codebase already documents: per `docs/phase-4-refactoring/specs/RUNTIME_MODES.md`, **`serve` (which hosts the admin API) only embeds a scheduler in dev/opt-in mode** — the standalone `./app scheduler` command is a **separate process** in production, with no HTTP surface of its own. An admin handler that only reads an in-process `*cron.Scheduler` would return an empty catalog in the normal production deployment, and "trigger now" would have no live registrations to invoke at all.

Corrected design, discovered by tracing where `sched := cron.New(log)` actually gets constructed (`cmd/api/main.go`'s `runServe`, conditional on `embedScheduler`, and separately in `runScheduler`) before writing any admin code:

- **`List` and `SetEnabled` are Postgres-backed**, not read from any one process's memory — a new `scheduler_tasks(name, spec, enabled, updated_at)` table (migration 068). Whichever process actually runs a scheduler (the standalone `scheduler` command in production, or `serve` with `embedScheduler=true` in dev) upserts its registrations into this table once at `Start`, and checks the `enabled` column on every tick before firing a task. This makes List and enable/disable work correctly and consistently regardless of which process is asking — the same reason job introspection (PR-1028) reads the `jobs` table instead of the in-process `Worker`.
- **`Trigger` still needs a live registered task's `fn`**, which only exists in a process that actually embeds a running scheduler. It now returns a precise `404` (unknown task — checked against the Postgres catalog, so this works even without a local scheduler) or `409 conflict` ("this server process has no embedded scheduler to trigger from") instead of either silently no-op'ing or crashing. It works immediately in `dev` mode or any `serve` deployment that opts into embedding.
- New domain ports: `scheduler.Catalog` (admin-facing: List/Trigger/SetEnabled) and `scheduler.Store` + `scheduler.LocalTrigger` (consumed by `cron.Scheduler` itself) — kept separate from the existing `scheduler.Scheduler` interface (Register/Start/Stop) for the same ISP reasoning as `jobs.Reader`/`jobs.Admin` vs. `jobs.Queue`: only one concrete implementation needs introspection, and `Scheduler`'s existing callers (every `Register*` helper, and `internal/platform/runtime/scheduler_test.go`'s `stubScheduler` fake) have no reason to grow these methods.

## Scope (original spec, for history)

- `internal/domain/scheduler/catalog.go` (new) — `CatalogEntry{Name, Spec string; NextRun time.Time; Enabled bool}`, `Scheduler.Catalog() []CatalogEntry` — computing `NextRun` requires the cron parser to expose a "next occurrence after t" function (`internal/infrastructure/cron`'s expression parser likely already computes this internally for tick alignment; expose it as a standalone function rather than duplicating the logic).
- `internal/domain/scheduler/overrides.go` — a small persisted table, `scheduler_overrides(name TEXT PRIMARY KEY, enabled BOOLEAN NOT NULL DEFAULT true, updated_at TIMESTAMPTZ)`. `Scheduler.run` (the internal tick-fire path) checks this before invoking a registered fn; absence of a row means enabled (default-on, matching today's behavior for anyone who never touches this feature).
- `GET /api/v1/admin/schedules` — list catalog entries with enabled state.
- `POST /api/v1/admin/schedules/{name}/trigger` — invokes the registered fn immediately, out-of-band from the normal tick (same function, so "trigger now" and "the real tick fired" are indistinguishable to the fn itself — no special-casing needed in individual task implementations).
- `POST /api/v1/admin/schedules/{name}/enable` / `.../disable` — writes to `scheduler_overrides`.
- Same `jobs.read`/`jobs.write` permissions from PR-1029 gate this (schedules and jobs are the same conceptual surface — no new permission pair needed).

## Out Of Scope

- Changing a schedule's cron spec at runtime (only enable/disable) — spec changes stay code-level, matching the existing "schedules are code-registered" model.
- Any change to the scheduler process's single-instance assumption — distributed scheduler/leader election is explicitly out of scope for this phase.
- A cross-process trigger mechanism (e.g. a trigger-request queue the standalone `scheduler` process polls) for the case where the admin API's process has no embedded scheduler — the honest `409 conflict` is the deliberate scope boundary for this PR; revisit only if operators actually hit this in practice (they can already achieve the same effect by running `serve` with the scheduler embedded, or waiting for the next real tick after re-enabling).

## Round 2 (code review)

- **Blocker — fixed.** `tick()`'s override check called `store.IsEnabled(context.Background(), ...)` with no timeout. The tick loop is single-threaded (one `Start` goroutine evaluates every entry in sequence each minute), so a hung Postgres call would block the entire loop indefinitely — silently stopping *every* scheduled task, including reservation-expiry cleanup, until process restart. Fixed by bounding the check with a 500ms `context.WithTimeout`; a timeout now hits the existing fail-open branch (log and fire anyway) instead of hanging.
- **Major — fixed.** `SchedulerStore.Trigger` checked existence against the shared `scheduler_tasks` table but fired via the calling process's own in-memory entries (`TriggerLocal`). If more than one process embeds a scheduler with a divergent task set, a task that legitimately exists elsewhere returned a misleading `CodeNotFound` — indistinguishable from "this task doesn't exist anywhere." Fixed: `Trigger` now recognizes when `TriggerLocal` returns not-found *after* the shared-registry check already confirmed the task exists, and translates that specific case into a `CodeConflict` naming the real cause (divergent embedded task sets), rather than passing the misleading not-found straight through. Running more than one embedded scheduler with different task sets remains unsupported (already discouraged — it double-fires every tick, per `RUNTIME_MODES.md`), so this is a diagnosis improvement, not a new feature.
- **Major — fixed.** `wg.Add(1)` in both `tick()`'s fire path and the new `TriggerLocal` could race with `Stop()`'s `close(s.stop)` → `s.wg.Wait()` — a documented `sync.WaitGroup` misuse (`Add` concurrent with `Wait`) that can panic the process. Pre-existing risk for `tick()`, but `TriggerLocal` made it reachable from an external HTTP request for the first time. Fixed with a `stopMu sync.RWMutex` + `stopped bool` pair: `Stop()` marks `stopped = true` under the write lock *before* closing `stop`/calling `Wait()`; both fire paths now go through a new `tryAdd()` that checks `stopped` under the read lock before calling `wg.Add` — once `Stop` has flipped the flag, no further `Add` can happen, closing the race window. `TriggerLocal` returns `CodeConflict` ("scheduler is shutting down") if it loses the race instead of proceeding.
- **Minor — fixed.** `IsEnabled` did one DB round-trip per matching task per tick. Replaced with `IsEnabledBatch(ctx, names) (map[string]bool, error)` on both the `scheduler.Store` domain port and `SchedulerStore`'s implementation (`WHERE name = ANY($1)`) — `tick()` now collects every matching entry first and does one query per tick regardless of how many tasks matched that minute. Folded into the same change as the timeout fix since both touch the same call site.
- **Minor — reviewed, skipped.** `scheduler_tasks` rows are never pruned, and `List()` has no pagination. Both are genuinely low-priority at this codebase's scale: unlike `jobs` (unbounded, customer/order-driven row growth), `scheduler_tasks` only grows from code-registered tasks — a handful of static `Register*` helpers plus one row per installed plugin's cron-triggered sync job — realistically staying well under 100 rows even in a heavily-plugin-laden deployment. Building a cleanup job is a real, separate feature (needs its own staleness/retention policy decision, e.g. "unregistered by any process for N days"), not a one-line fix; not worth the added complexity until a concrete deployment actually accumulates enough stale rows to matter. Revisit if that changes.
