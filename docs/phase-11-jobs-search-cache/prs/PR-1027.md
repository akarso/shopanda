# PR-1027 — Fix Reservation Expiry Gap

Status: planned

## Summary

- Wire the already-implemented `inventory.ReservationRepository.ReleaseExpiredBefore` into a scheduled job — today it exists and is fully implemented but is never called from anywhere in the codebase.

## Why

Expired inventory reservations currently only stop counting against availability implicitly (stock queries filter `expires_at > now()` at read time). Their rows never flip to `released` status and are never purged. This is invisible in normal operation (availability is still correct) but leaves an unbounded, ever-growing set of stale `active`-status reservation rows, and means anything that later wants to report on or clean up reservation history has no reliable signal — an `active` row does not mean "still valid."

## Scope

- New job handler `inventory.ReservationExpiryHandler` (job type `inventory.reservation_expiry`), calling `ReleaseExpiredBefore(ctx, time.Now())`.
- Register the job type in `setupWorker` (`cmd/api/main.go`), alongside the existing handler set.
- Cron registration in `internal/platform/runtime/scheduler.go`: `RegisterReservationExpiry`, spec `*/15 * * * *` — matches the existing 15-minute reservation TTL already documented in RUNBOOK.md's "Checkout cancel and timeouts" section, so expired reservations are cleaned up within one TTL window of expiring, not indefinitely.
- Log `job.reservation_expiry.released` with the count `ReleaseExpiredBefore` returns.
- Metric: increment the existing job-failure counter on handler error (no new metric needed — this reuses `shopanda_job_failures_total{job_type="inventory.reservation_expiry"}`).

## Out Of Scope

- Admin API/CLI visibility into this job specifically — it's a generic job like any other once Track A (PR-1028–1032) ships; no bespoke surface needed here.
- Backfilling/cleaning up the historical backlog of already-expired-but-never-released rows as part of this PR's automated path — call out in the migration notes whether a one-time manual cleanup query is needed for existing deployments, but don't script it as part of the recurring job (a recurring job only needs to keep up with new expirations, not necessarily catch up a large historical backlog in one run).

## Validation (planned — run when implementing)

- `go test ./internal/domain/jobs/... ./internal/platform/runtime/... -run ReservationExpiry -count=1`
- Integration test: create a reservation with a past `expires_at` directly in the DB, run the handler, assert status flips and `ReleaseExpiredBefore`'s count matches.
- `go build ./...`
