# PR-1027 — Fix Reservation Expiry Gap

Status: done

## Summary

- Wire the already-implemented `inventory.ReservationRepository.ReleaseExpiredBefore` into a scheduled job — today it exists and is fully implemented but is never called from anywhere in the codebase.

## Why

Expired inventory reservations currently only stop counting against availability implicitly (stock queries filter `expires_at > now()` at read time). Their rows never flip to `released` status and are never purged. This is invisible in normal operation (availability is still correct) but leaves an unbounded, ever-growing set of stale `active`-status reservation rows, and means anything that later wants to report on or clean up reservation history has no reliable signal — an `active` row does not mean "still valid."

## Scope

- New job handler `inventory.ReservationExpiryHandler` (job type `inventory.reservation_expiry`), calling `ReleaseExpiredBefore(ctx, time.Now())`.
- Register the job type in `setupWorker` (`cmd/api/main.go`), alongside the existing handler set.
- Cron registration in `internal/platform/runtime/scheduler.go`: `RegisterReservationExpiry`, spec `*/15 * * * *` — matches the existing 15-minute reservation TTL already documented in RUNBOOK.md's "Checkout cancel and timeouts" section, so expired reservations are cleaned up within one TTL window of expiring, not indefinitely.
- Log `job.reservation_expiry.released` with the count `ReleaseExpiredBefore` returns.
- Metric: increment the existing job-failure counter on handler error (no new metric needed — this reuses `shopanda_job_failures_total{job_type="inventory.reservation_expiry"}`).

### Round 2 — code review response

A review round on the first cut found the sweep itself was unsafe at scale: `ReleaseExpiredBefore` ran the entire expired set as one unbatched transaction, with no statement timeout, no per-job execution deadline, and no guard against overlapping runs — on the large first-run backlog this job is explicitly expected to handle, that combination could hold locks on `stock` rows (blocking concurrent checkout `Reserve` calls) for however long the whole backlog took, with no bound. Verified against source and fixed:

| Area | Change |
| --- | --- |
| `internal/infrastructure/postgres/reservation_repo.go` | `ReleaseExpiredBefore` now loops over bounded batches (`reservationExpiryBatchSize = 500` rows/transaction, `SELECT ... FOR UPDATE SKIP LOCKED`) instead of one unbatched transaction over the whole expired set. Each batch transaction sets `SET LOCAL statement_timeout = '30s'` as a backstop. `SKIP LOCKED` also makes concurrent invocations (e.g. two `worker` processes both processing the job during a large sweep) safe — they partition the work instead of blocking on each other. Stops early and returns cleanly (nil error) if `ctx` is cancelled/deadline-exceeded mid-loop, since the caller's next invocation picks up the remainder. A per-row stock-restore `RowsAffected` check now catches an orphaned reservation (variant deleted after the reservation was created) instead of silently dropping the quantity — reported via a new `*inventory.OrphanedStockRestoreError`, not a hard failure (the release itself still committed). Batch size is a `var`, not `const`, with a `SetReservationExpiryBatchSizeForTest` test seam so tests can exercise the multi-batch loop without seeding 500+ rows. |
| `internal/domain/inventory/reservation_expiry_error.go` | New `OrphanedStockRestoreError` type — the domain-level vocabulary for the case above, shared between the postgres implementation and the application-layer handler without either depending on a concrete logger in the repo layer (this codebase's repos consistently return data/errors and never log directly; kept that convention rather than bolting a logger onto `ReservationRepo`). |
| `internal/application/inventory/reservation_expiry_handler.go` | `Handle` now wraps a `sweepTimeout = 10 * time.Minute` deadline around the ctx it passes to `ReleaseExpiredBefore` (well under the 15-minute cron interval, but enough for many batches) — the previous version handed through the worker's poll-loop context unmodified, which only ever ends at process shutdown. An `*inventory.OrphanedStockRestoreError` back from the releaser is logged as a warning (`job.reservation_expiry.orphaned_stock_restore`) and does **not** fail the job — the release succeeded; retrying would just re-find nothing to do. The success log now also reports `duration` and `more_remaining` (true if the sweep's own deadline fired before the backlog was fully drained, detected via `sweepCtx.Err()` after the call — same context object, so a deadline that fired is still observable) so a long first-run backlog is visible across consecutive ticks in the logs, not a silent black box. |
| `internal/infrastructure/postgres/reservation_repo_test.go` | Three new integration tests: multi-batch draining (7 rows against an overridden batch size of 3), orphaned-stock-restore reporting (delete the stock row out from under an active reservation, assert the error type/contents and that the release still committed), graceful stop on an already-cancelled context. |
| `internal/application/inventory/reservation_expiry_handler_test.go` | Two new unit tests: the orphan-warning path logs but doesn't fail the job, and the ctx handed to the releaser actually carries a bounded deadline (not just trusting the wiring by inspection). |
| `RUNBOOK.md` | The "first run sweeps the backlog in one pass" note corrected — it's now bounded batches across possibly several ticks (`more_remaining: true` in the logs when a tick runs out of time), with concurrent checkout no longer blocked for the sweep's full duration. |

**Reviewed, not changed** (confirmed against source, not just asserted):

- **Enqueue-timeout drift (5s in `RegisterReservationExpiry` vs. 30s in `RegisterAuditRetention`)** — checked all four `runtime.Register*` functions: `cache.cleanup` and `cart.recovery` both already use 5s: `audit.retention`'s 30s is the actual outlier, not this PR's 5s. Left as-is; matches the majority precedent.
- **Local `Logger`/`ExpiredReservationReleaser` interfaces "redefined" instead of reusing a shared type** — `internal/application/cache/handler.go` already defines an identical narrow local `Logger` interface (2 of `internal/platform/logger.Logger`'s 3 methods) for the same reason: accept the minimal interface a package actually needs rather than depending on the full concrete logger type. `internal/domain/jobs/worker.go` does the same. This is established, consistent convention in this codebase, not duplication introduced by this PR.

## Out Of Scope

- Admin API/CLI visibility into this job specifically — it's a generic job like any other once Track A (PR-1028–1032) ships; no bespoke surface needed here.
- A separate one-time backfill script for the historical backlog: unnecessary. `ReleaseExpiredBefore(ctx, cutoff)` has no "only newly-expired" filter — `WHERE status = 'active' AND expires_at < cutoff` matches everything expired as of `cutoff`, so the job's regular batched sweep naturally drains the pre-existing backlog across however many ticks it takes, same mechanism as ongoing operation. See RUNBOOK.md's caveat about a large backlog taking several ticks.
- A persisted/pollable progress mechanism (row counts mid-sweep, visible via an API) — deferred to Track A's job-introspection work (PR-1028), consistent with this PR's original scope boundary. This round's fix is log-based visibility (duration + `more_remaining` per tick), not a new observability system.
