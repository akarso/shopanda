# PR-1039 — Tag-Based Invalidation

Status: planned

## Summary

- Extend `cache.Cache`: `SetWithTags(key string, value any, ttl time.Duration, tags ...string) error`, `DeleteByTag(ctx context.Context, tag string) error`.
- Implement for both the Postgres and Redis backends. `DeleteByPrefix`/`Delete`/`Get`/`Set` stay unchanged — tags are additive, not a replacement for the existing simple case.

## Why

Prefix-based invalidation only works when everything that needs invalidating together shares a key prefix by construction (today's one real example: all of one product's cached variants under `product:<id>:`). It can't express "invalidate every cached page that happens to include CMS block #7" or "invalidate every cached page that rendered category #12" — the whole premise of Track D's full-page cache. Tags are the standard answer (this is exactly what Magento's cache tag system solves, and the user explicitly asked for it "if only for future integrations" even before Track D's concrete need existed).

## Scope

- `internal/domain/cache/cache.go`: add the two methods to the `Cache` interface.
- **Postgres implementation** (`internal/infrastructure/postgres/cache_store.go`): new `cache_tags(tag TEXT, key TEXT, PRIMARY KEY (tag, key))` table, FK-less by design (cache rows are transient and already have their own TTL-expiry path; a tag row pointing at an expired/deleted cache key is harmless — `DeleteByTag` just deletes zero rows for it, and the existing `DeleteExpired` cleanup job gets a small addition to also sweep orphaned tag rows). `SetWithTags` writes the cache row then the tag rows in one transaction. `DeleteByTag` is `DELETE FROM cache WHERE key IN (SELECT key FROM cache_tags WHERE tag = $1)` followed by `DELETE FROM cache_tags WHERE tag = $1`.
- **Redis implementation** (`internal/infrastructure/redis/cache_store.go`): a `SET` per tag (key `tag:<name>`, members = tagged cache keys). `SetWithTags` does the value `SET` plus a pipelined `SADD` per tag. `DeleteByTag` does `SMEMBERS` then pipelined `DEL` of the members plus the tag set itself. Tag-set entries for since-expired cache keys are cleaned up lazily on the next `DeleteByTag` call for that tag (a `DEL` on an already-gone key is a harmless no-op) — no separate sweep needed, unlike Postgres, since Redis doesn't need an explicit expiry-sweep job at all.
- `internal/application/cache/invalidation.go`'s existing subscriber is **not required to switch to tags in this PR** — it keeps using `DeleteByPrefix`, which still works. This PR ships the capability; Track D (PR-1046) is what actually needs and uses tags for real invalidation wiring.

## Out Of Scope

- Retrofitting the existing product-cache invalidation path onto tags — no functional need to change working code in this PR; if a future need arises to tag product cache entries too (e.g. "invalidate every cache entry that mentions this product, not just its own prefix"), that's a small follow-up, not blocked by anything here.
- Tag cardinality limits/monitoring (e.g. a tag with 100k members) — flagged as a real operational risk worth watching once Track D is in production use (a popular category tag could end up with a very large member set), but not a concern this PR's scope needs to solve preemptively without real usage data.

## Validation (planned — run when implementing)

- `go test ./internal/infrastructure/postgres/... ./internal/infrastructure/redis/... -run Tag -count=1` — set with multiple tags, delete by one tag leaves entries under other tags intact, delete by tag on a key that was already separately deleted/expired is a safe no-op.
- Both backends tested against the same interface-level test suite (table-driven, run against both implementations) to guarantee behavioral parity — the same pattern likely already used for the existing `Cache` backend tests; follow it.
- `go build ./...`
