# PR-1039 — Tag-Based Invalidation

Status: done

## Summary

- Extend `cache.Cache`: `SetWithTags(ctx context.Context, key string, value any, ttl time.Duration, tags ...string) error`, `DeleteByTag(ctx context.Context, tag string) (int64, error)`.
- Implement for both the Postgres and Redis backends. `Get`/`Set` stay; tags are additive across `SetWithTags` calls, not a replacement for prefix invalidation.

## Why

Prefix-based invalidation only works when everything that needs invalidating together shares a key prefix by construction (today's one real example: all of one product's cached variants under `product:<id>:`). It can't express "invalidate every cached page that happens to include CMS block #7" or "invalidate every cached page that rendered category #12" — the whole premise of Track D's full-page cache. Tags are the standard answer (this is exactly what Magento's cache tag system solves, and the user explicitly asked for it "if only for future integrations" even before Track D's concrete need existed).

## Scope

- `internal/domain/cache/cache.go`: add the two methods to the `Cache` interface (`SetWithTags` takes `ctx`; `DeleteByTag` returns the snapshot key count).
- `internal/domain/cache/tags.go`: `UniqueTags` — shared empty/whitespace/duplicate filtering used by both backends.
- `internal/domain/cache/tagtest`: shared contract suite (`tagtest.Run`) covering SetWithTags + DeleteByTag, including additive re-save and concurrent SetWithTags vs DeleteByTag.
- **Postgres implementation** (`internal/infrastructure/postgres/cache_store.go`): new `cache_tags(tag TEXT, key TEXT, PRIMARY KEY (tag, key))` table plus `idx_cache_tags_key` (`migrations/078_create_cache_tags.sql`), UNLOGGED and FK-less by design. `SetWithTags` writes the cache row and a single batched `INSERT … SELECT unnest($1::text[])` of tag rows in one transaction; a cancelled `ctx` is honoured even when UniqueTags leaves no tags. `DeleteByTag` trims via `NormalizeTag`, then one statement: `WITH doomed AS (DELETE FROM cache_tags WHERE tag = $1 RETURNING key), gone AS (DELETE FROM cache WHERE key IN (SELECT key FROM doomed)) SELECT count(*) FROM doomed` — snapshot size, not `RowsAffected` of the cache delete. `Delete` is the same CTE pattern (`WITH gone AS (DELETE FROM cache WHERE key = $1) DELETE FROM cache_tags WHERE key = $1`), one round trip. `DeleteByPrefix` likewise. `DeleteExpired` deletes expired cache rows, then (separate statement) sweeps orphaned tag rows.
- **Redis implementation** (`internal/infrastructure/redis/cache_store.go`): a `SET` per tag (key `tag:<name>` after the store's key prefix, members = logical cache keys). `SetWithTags` does the value `SET` plus a pipelined `SADD` per tag; a cancelled/deadline `ctx` is honoured even when UniqueTags leaves no tags (the write uses that ctx, not `Set`'s `context.Background()`). `DeleteByTag` trims via `NormalizeTag` then `RENAME`s the tag set to a unique `__purge:tag:…` key (O(1) snapshot — concurrent `SADD` creates a new set at the original key), `EXPIRE`s that purge key (1h safety net), then `SSCAN`s and batched-`DEL`s members. On any error after the rename, remaining members are `SUNIONSTORE`d back onto the live tag key (fresh timeout, not the cancelled caller ctx) and the purge key is deleted, so a retry can still invalidate. EXPIRE/restore failures are logged (`redis.cache.purge_expire_failed` / `redis.cache.purge_restore_failed`). `DeleteExpired` `SCAN`s tag sets, then for each batch of members a Lua script `EXISTS`+conditional `SREM` so a concurrent `SetWithTags` cannot have its fresh membership stripped. Empty sets are deleted with a Lua `SCARD==0` then `DEL`. A prune failure on one tag key is logged (`redis.cache.prune_tag_skipped`) and skipped; the rest of the scan still runs.
- Test doubles that implement `cache.Cache` (`stubCache` / `mockCache` in auth, invalidation, plugin, postgres unit tests) gained the two methods.
- `internal/application/cache/invalidation.go`'s existing subscriber is **not** switched to tags — it keeps using `DeleteByPrefix`, which still works. This PR ships the capability; Track D (PR-1046) is what actually needs and uses tags for real invalidation wiring.

## Design decisions

- **Tags are additive on re-save.** `SetWithTags` unions the new tags onto the key; it does not drop previous tag memberships. Re-saving the same tags is idempotent (Postgres `ON CONFLICT DO NOTHING`, Redis `SADD`). Conservative over-invalidation (an old tag still points at the key) rather than replace-on-write.
- **`DeleteByTag` snapshots membership in one step.** Postgres deletes tag rows `RETURNING key` and deletes those cache keys in the same statement. Redis `RENAME`s the tag set off to a purge key before scanning members. A concurrent `SetWithTags` that commits after the snapshot keeps its association.
- **Empty / whitespace tag names are ignored** (`UniqueTags`); `DeleteByTag("")` is a no-op. Tags are case-sensitive opaque strings.
- **Redis tag-set keys use the existing store prefix plus `tag:`.** Application cache keys should not use the `tag:` prefix — it is reserved for membership sets. Members stored in the set are logical cache keys (not prefix-expanded).
- **Postgres `Delete`/`DeleteByPrefix` drop matching `cache_tags` rows.** Redis has no reverse index; stale tag-set members (TTL expiry or `Delete`) are pruned by `DeleteExpired` (`cache.cleanup`), which now actually runs on the Redis backend instead of being a no-op.
- **`Set` does not untag.** A later untagged `Set` of the same key leaves membership in place (over-invalidation). Clearing tags on `Set` would need a reverse index on Redis; not taken in this PR.
- **`DeleteByTag` returns snapshot size**, not "how many value rows were physically deleted." Postgres `SELECT count(*) FROM doomed`; Redis counts `SSCAN` members. Members whose value is already gone still count.
- **Redis purge keys are recoverable.** After `RENAME`, the purge set gets a 1h `EXPIRE`. Any error after the rename merges remaining members back onto the live tag key (`SUNIONSTORE`) using a fresh timeout, not the caller's (possibly cancelled) context, then deletes the purge key. A retry of `DeleteByTag` can still invalidate. EXPIRE/restore failures are logged rather than swallowed.
- **Redis `DeleteExpired` skips a bad tag key.** A non-set (or otherwise failing) `tag:*` key is logged and skipped; the rest of that tick's scan still runs. A cancelled/deadline context still aborts the call.

## Out Of Scope

- Retrofitting the existing product-cache invalidation path onto tags — no functional need to change working code in this PR; if a future need arises to tag product cache entries too (e.g. "invalidate every cache entry that mentions this product, not just its own prefix"), that's a small follow-up, not blocked by anything here.
- Tag cardinality limits/monitoring (e.g. a tag with 100k members) — flagged as a real operational risk worth watching once Track D is in production use (a popular category tag could end up with a very large member set), but not a concern this PR's scope needs to solve preemptively without real usage data.

## Round 2 (code review)

Verified against the code, then fixed:

- **Blocker — fixed.** `DeleteByTag` collected members then deleted the tag association as a separate step. Under Postgres `READ COMMITTED`, a concurrent `SetWithTags` that committed between `DELETE FROM cache WHERE key IN (SELECT …)` and `DELETE FROM cache_tags WHERE tag = $1` lost its new membership while the value survived — a later `DeleteByTag` would never see it. Redis had the same window (`SMEMBERS` then `DEL` of the tag set). Postgres is now a single `WITH doomed AS (DELETE FROM cache_tags … RETURNING key) DELETE FROM cache WHERE key IN (SELECT key FROM doomed)`. Redis `RENAME`s the tag set to a unique purge key first (concurrent `SADD` creates a new set at the original key), then `SSCAN`s members. Contract test `ConcurrentSetWithTagsKeepsMembership` (20 interleaved rounds) asserts a follow-up `DeleteByTag` always removes a key written concurrently.
- **Major — fixed.** Redis `DeleteByTag` used `SMEMBERS` (one blocking O(N) command, full set in memory). It now `SSCAN`s the renamed set in 100-member cursors, matching `DeleteByPrefix`'s `SCAN` pattern.
- **Major — fixed.** Redis tag sets had no prune path for members whose value key expired or was `Delete`d (`DeleteExpired` was a no-op). `DeleteExpired` now `SCAN`s `tag:*` sets and `SREM`s members whose value key is gone; empty sets are deleted. Postgres `Delete`/`DeleteByPrefix` drop matching `cache_tags` rows immediately (backed by `idx_cache_tags_key`). A later untagged `Set` still does not drop membership (over-invalidation); that would need a Redis reverse index and is left as-is.
- **Major — fixed.** `uniqueTags` was copy-pasted in both adapters. Both now call `cache.UniqueTags`. Whitespace-only names are treated as empty; case is not folded (tags are opaque; documented in `DEVELOPER.md`).
- **Major — fixed.** Contract test `AdditiveAcrossSeparateSetWithTags`: `SetWithTags(k, v1, "A")` then `SetWithTags(k, v2, "B")` then `DeleteByTag("A")` must miss — replace-on-write would leave `v2` in place.
- **Minor — fixed.** Postgres tag inserts are one `INSERT … SELECT unnest($1::text[])` instead of N `Exec`s.
- **Minor — fixed.** `SetWithTags` takes `context.Context` (this was new API). `DeleteByTag` returns `(int64, error)` so callers can log invalidated-key counts.
- **Minor — fixed.** `DeleteExpired` no longer wraps the TTL delete and the orphan-tag sweep in one transaction. `idx_cache_tags_key` supports per-key tag deletes.
- **Minor — noted, not case-folded.** `"CMS:7"` and `"cms:7"` stay distinct; Track D should build tags from IDs, not free text. Documented.
- **Minor — fixed.** `tagtest` has a package doc comment; the directory is part of this change set (was untracked only because the PR is not committed yet).

## Round 3 (code review)

Verified against the code, then fixed:

- **Blocker — fixed.** Redis `DeleteByTag` `RENAME`d the tag set, then `SSCAN`/`DEL`. Any failure after the rename (cancelled ctx, network, OOM) returned an error and left members under an unreferenced `__purge:tag:…` key with no TTL. A retry saw "no such key" on the original tag key and returned `(0, nil)` — invalidation for that tag was permanently broken. After rename the purge key now gets a 1h `EXPIRE`; on any subsequent error, remaining members are `SUNIONSTORE`d back onto the live tag key (fresh 5s timeout, not the caller's ctx) and the purge key is deleted. Test `TestCacheStore_TagDeleteByTagRestoresOnFailureAfterRename` cancels ctx after rename, asserts the value survives, no purge key leaks, and a retry invalidates.
- **Blocker — fixed.** `DeleteByTag`'s count is snapshot size on both backends. Postgres was using `RowsAffected()` of the outer `DELETE FROM cache`, which skipped tag rows whose cache row was already gone. It now `SELECT count(*) FROM doomed`. Shared contract `DeleteByTagCountIsSnapshotSize` (two live keys → 2). Postgres `TestCacheStoreDB_TagDeleteByTagCountIncludesOrphans` (live + orphaned tag row → 2). Redis `TestCacheStore_TagDeleteByTagCountIncludesDeletedValues` (`Delete` one of two tagged keys → 2, because Redis has no reverse index).
- **Major — fixed.** Postgres `Delete` is one CTE statement (`WITH gone AS (DELETE FROM cache WHERE key = $1) DELETE FROM cache_tags WHERE key = $1`), matching `DeleteByPrefix`/`DeleteByTag`, not a four-round-trip transaction.
- **Major — fixed.** `pruneTagSet`'s empty-set delete is a Lua `if SCARD==0 then DEL` so a concurrent `SADD` between check and delete cannot be wiped.
- **Major — fixed.** `EXISTS` checks in `pruneTagSet` are pipelined in 100-member batches instead of one round trip per member.
- **Minor — fixed.** Purge-key TTL (see blocker). `isWrongType` substring matching is gone; non-set keys under `tag:*` return an explicit error (reserved-prefix collision). `isNoSuchKey` uses `errors.Is(Nil)` and `redis.HasErrorPrefix` for the `RENAME` missing-key case only.
- **Minor — fixed.** RUNBOOK documents that Redis `cache.cleanup` is O(total tag members), not a no-op.

## Round 4 (code review)

Verified against the code, then fixed:

- **Major — fixed.** `DeleteExpired` aborted the whole tag-prune pass on the first `pruneTagSet` error. A single non-set key under the reserved `tag:*` prefix (the `TYPE` check added in round 3) would fail every future tick and skip every subsequent tag. Per-tag failures are now logged (`redis.cache.prune_tag_skipped`) and skipped; only a cancelled/deadline context or a `SCAN` iterator error still abort. Test `TestCacheStore_TagDeleteExpiredSkipsBadKey` seeds a string key next to a real tag set and asserts the good tag is still pruned. The Redis cache plugin passes `app.Logger` so those events are visible in production.
- **Minor — fixed.** `afterTagRename` is a field on `*CacheStore`, set via `SetAfterTagRename` in `export_test.go`. The previous package-level function pointer would leak across instances the moment any test in this package used `t.Parallel()`.
- **Minor — fixed.** `Delete` and `DeleteByTag` have comments stating that the unreferenced data-modifying `gone` CTE is intentional (Postgres still executes it).
- **Minor — fixed.** `expirePurge` / `restorePurge` log `redis.cache.purge_expire_failed` and `redis.cache.purge_restore_failed` (and a leftover-purge-key `DEL` failure) instead of swallowing Redis errors.
- **Minor — fixed.** RUNBOOK no longer implies `idx_cache_tags_key` makes the `DeleteExpired` orphan sweep cheap; that index is for per-key deletes. Redis cleanup notes the skip-and-log behaviour for a poisoned `tag:*` key.

## Round 5 (code review)

Verified against the code, then fixed:

- **Issue 1 — fixed.** Redis `pruneStaleBatch` pipelined `EXISTS` then a separate `SREM`. A `SetWithTags` that recreated the value in that window lost its tag membership, so a later `DeleteByTag` could not invalidate it. Prune is now one Lua script (`EXISTS` then conditional `SREM` per member). Test `TestCacheStore_TagPruneDoesNotDropRecreatedMembership` races `DeleteExpired` against `SetWithTags` after TTL expiry and asserts a follow-up `DeleteByTag` still hits.
- **Issue 2 — fixed.** `SetWithTags` with no tags (or whitespace-only) delegated to context-free `Set`. Both backends now write through an internal `set(ctx, …)` and reject an already-cancelled ctx. Shared contract `SetWithTagsHonorsCancelledContext`.
- **Issue 3 — fixed.** `DeleteByTag` looked up the raw argument while `SetWithTags` stored `UniqueTags` (trimmed) names. Both backends (and the stub) call `cache.NormalizeTag`. Shared contract `DeleteByTagTrimsLikeSetWithTags` covers padded write + padded delete and unpadded write + padded delete.
