# PR-1045 — Fragment Mechanism (ESI-Equivalent)

Status: planned

## Summary

- An app-level "hole" mechanism for customer-specific content embedded in an otherwise-cacheable page: a template placeholder renders an htmx-loaded fragment endpoint that is always `Cache-Control: no-store` and always reads real session/cart state.
- Explicitly documented as the ESI-equivalent for this architecture, and why an app-level hole is the right fit here instead of literal ESI.

## Why

Real ESI (Edge Side Includes) is resolved by an edge cache (Varnish, a CDN) that fetches the cached page, sees `<esi:include>` tags, and does the sub-request substitution *before* the response leaves the edge — the origin server never even sees most of those requests. Shopanda has no edge/CDN layer in front of it (confirmed: nothing in this repo's deployment docs or architecture describes one), so there's nothing to resolve an ESI tag. The equivalent effect — a mostly-cached page with small always-fresh regions — is achievable at the app level instead: the cached HTML (PR-1044) contains a placeholder, the browser (already running htmx per the existing theme) fetches the real content client-side after the shell loads. Same outcome for the shopper (fast page, correct personalized bits), different place the substitution happens, and no new infrastructure dependency.

## Scope

- Template helper (`{{fragment "minicart"}}`-style, wired into the existing `html/template` pipeline) that renders a placeholder element: `<div hx-get="/fragment/minicart" hx-trigger="load" hx-swap="outerHTML">...skeleton/loading state...</div>`.
- `/fragment/{name}` routes (`internal/interfaces/http/storefront/fragment.go`, new file, in the *uncacheable* handler package from PR-1044's package-boundary structure) — each fragment handler:
  - Always sets `Cache-Control: no-store`.
  - Reads real request-scoped session/cart/customer state (exactly the state PR-1044's cached shell must never contain).
  - Returns a small HTML snippet (not a full page) — htmx swaps it into the placeholder.
- **Fragments shipped in this PR** (the concrete personalized-content cases identified as needing this mechanism):
  - Mini-cart (item count + quick summary).
  - CSRF token (rendered into forms on otherwise-cached pages — the non-negotiable requirement from PR-1044).
  - Personalized greeting ("Welcome back, {name}" on an otherwise-cached PDP/PLP header, if the theme renders one there).
  - Wishlist indicator, if the theme has one.
  - "Recently viewed" — this one is the most complex (needs real per-customer history, not just auth-state), documented as the reference example for *how* to add a new fragment (data source, endpoint, template placement) since it's the least trivial of the set.
- **A skeleton/loading state is required for every fragment placeholder**, not optional — an empty `<div>` that pops content in after load is a worse UX than a static page; the placeholder must render something reasonable (e.g. a `0`-count mini-cart icon) so the page doesn't visibly shift/flash for the common case.

## Out Of Scope

- Server-side fragment caching (each fragment call is always live) — fragments are by definition the parts that must never be stale; caching them defeats the purpose. If a specific fragment turns out to be expensive to compute (unlikely for the initial set — mini-cart count and CSRF token generation are both cheap), that's a targeted follow-up for that one fragment, not a general fragment-caching layer.
- A generic "any plugin can register a fragment" extension point — the ROADMAP's design notes call this out as a natural Track A/B/C-style follow-up if plugin authors need it (mirrors the `RegisterCompositionStep`/slots pattern), but this PR ships the concrete fragments the platform itself needs, not a new plugin extension mechanism (avoid scope creep into "Extension Points" territory — see Phase 10's `EXTENSION_POINTS.md` for why a new mechanism needs its own deliberate design pass, not a rider on this PR).

## Validation (planned — run when implementing)

- `go test ./internal/interfaces/http/storefront/... -run Fragment -count=1` — every fragment endpoint returns `Cache-Control: no-store`, correctly reflects real per-request state (two different simulated sessions get different mini-cart counts from the same fragment endpoint), CSRF fragment returns a genuinely per-request token (not a cached/stale one).
- Manual QA: load a cached PDP twice from two different "customers" (per PR-1044's test setup), confirm the shell is identical but the mini-cart fragment differs correctly for each.
- `go build ./...`
