# PR-1034 — Partial & Scoped Reindex

Status: done

## Summary

- Scope a reindex run to explicit product IDs, explicit category IDs, or "changed since `<timestamp>`" (using `products.updated_at`).
- Document and implement a threshold heuristic: past a certain fraction of the catalog, a full scan is cheaper than a scoped run, and the reindex service picks full-scan automatically rather than trusting the caller's scope.

## Why

The whole point of partial reindex is to make "I changed 12 products" cheap. But a naive per-ID lookup implementation is *not* automatically cheaper than a full scan once the scoped set gets large — each scoped product still costs one lookup + one index write, and a full scan has a fixed per-run overhead (opening the transaction, listing) that partial reindex also pays, just per-batch instead of once. Below some fraction of the catalog, scoped wins; above it, the fixed overhead of full-scan-in-one-pass wins over N individual round trips. Getting this backwards would make partial reindex a trap: someone reindexes "since yesterday" after a large price-import job touched 80% of products, and it ends up slower and more DB-load-intensive than just reindexing everything.

## Scope

- `internal/application/search.Scope` — `ScopeAll{}`, `ScopeProducts{IDs []string}`, `ScopeCategories{IDs []string}`, `ScopeSince{Since time.Time}`.
- `ScopeSince` resolves to a concrete product ID list via `productRepo.ListUpdatedSince(ctx, since) ([]string, error)` (new repository method) at job-run time, then follows the same path as `ScopeProducts`.
- **Threshold heuristic:** before enqueueing, `ReindexService.Trigger` compares the resolved scope's product count against total catalog size (`productRepo.Count(ctx)`, new or existing method). If the scope covers more than **20%** of the catalog, the job is enqueued as `ScopeAll` instead of the caller's requested partial scope — the run record's `scope_params` still records what was *requested*, but `scope` reflects what actually ran, so this substitution is visible, not silent. The 20% figure is a documented starting point, not empirically tuned in this PR (no production traffic to tune against yet) — flag it as a config-overridable constant (`search.reindex_full_scan_threshold`, default `0.2`) so it can be adjusted post-launch without a code change.
- `ScopeCategories{IDs}` resolves to the product IDs assigned to those categories via the existing `ProductCategoryAssignmentRepository`/`ListCategoryIDsByProduct`-adjacent query (needs the inverse: products-by-category — check whether this already exists before adding it; `FindByCategoryID` on `ProductRepo` already exists per Phase 10 work, likely reusable directly).

## Out Of Scope

- A UI/API for adjusting the threshold constant beyond the config key — no admin screen for "reindex tuning," just a documented config value.
- Scoping by store — no `store_id` on products/categories (see ROADMAP's "Out of scope"); nothing to scope by here.
- A CLI flag or admin endpoint to actually *request* a partial reindex — `search:reindex` still only ever triggers `ScopeAll`. Wiring an external caller to the new `Scope` types is explicitly PR-1035's job ("exposes scope selection through the admin API"); this PR only builds the application-layer mechanism PR-1035 will call into.

## Design decisions made during implementation

- **`domainsearch.ReindexScope{Name, Params}` (the original PR-1033 placeholder) was removed, not extended.** The plan's own note that "Params exists so PR-1034's partial/scoped values ... don't need a schema or port change" was true for the `search_index_runs` table (its `scope`/`scope_params` columns are still a bare `TEXT`/`JSONB` pair, untouched) but not for `ReindexService.Trigger`'s own input type: a stringly-typed `Name`/`Params` pair gives no compile-time guarantee that, say, a `"categories"` scope actually carries a `category_ids` key of the right shape. Replaced it with the planned `Scope` interface (`ScopeAll`/`ScopeProducts`/`ScopeCategories`/`ScopeSince`, an unexported-method "sealed interface" so only these four types satisfy it) as `Trigger`'s new parameter type; `Run.Scope`/`Run.ScopeParams` themselves are unchanged, still populated as a plain string + map by `Trigger` after resolution. The only caller affected, `cmd/api/main.go`'s `search:reindex`, moved from `search.ReindexScope{Name: "all"}` to `searchApp.ScopeAll{}` — one line.
- **`domainsearch.ProductSource` gained three new methods (`ListByIDs`, `ProductIDsByCategory`, `ProductIDsUpdatedSince`) instead of a separate resolver port.** The plan named `productRepo.ListUpdatedSince`/`productRepo.Count` as new methods on `catalog.ProductRepository`, but `ReindexService`/`ReindexHandler` deliberately never import `catalog` (see `ProductSource`'s own doc comment, and PR-1033's "Design decisions" on the same point for `SearchProductSource`) — routing scope resolution through `catalog.ProductRepository` would have broken that boundary just for this PR. `ProductSource` already had `CountAll` (reused directly for the threshold check, no new `Count` method needed); added `ListByIDs` (the scoped equivalent of `ListAll`'s paging, for `ReindexHandler`'s actual scan), `ProductIDsByCategory`, and `ProductIDsUpdatedSince` (both resolve a partial scope to concrete IDs, for `ReindexService.Trigger`) to the same port, implemented by the same `postgres.SearchProductSource` that already backs `CountAll`/`ListAll` — reading `products`/`product_categories` directly, not through `catalog.ProductRepository`'s own `FindByCategoryID` (confirmed to already exist, per the plan's own note, but going through it would have meant `SearchProductSource` depending on `ProductRepo`, the same layering break in a different shape).
- **A resolved scope collapses to exactly one job-level shape: `"products"` + a concrete ID list.** `ScopeProducts`, `ScopeCategories`, and `ScopeSince` all resolve to a product ID list before `Trigger` ever enqueues anything — `ReindexHandler` only ever needs to know "scan everything" (`scope: "all"`) or "scan exactly these IDs" (`scope: "products"`, `product_ids: [...]` on the job payload); it never re-resolves a category or since-timestamp itself. This matters for correctness, not just simplicity: resolving once, at trigger time, means the threshold check and the job's actual work always agree on the same ID list — re-resolving inside the handler (potentially much later, after a job requeue/retry) could return a different answer than what the threshold check saw (products added/removed from a category, or updated after the "since" cutoff), silently invalidating the substitution decision.
- **The threshold check is skipped entirely for an empty resolved scope** (`applyThreshold` returns early for `len(resolvedIDs) == 0`) — comparing zero against any catalog size can never exceed the threshold, so consulting `CountAll` would be a pure, guaranteed-pointless round trip. This also means a `ScopeCategories`/`ScopeSince` request that matches nothing doesn't require a working `CountAll` call at all.
- **`ReindexHandler.Handle` branches on whether the job payload carries a `product_ids` array, not by threading a new parameter through the existing full-scan loop.** A scoped run chunks the resolved ID list into `reindexBatchSize`-sized batches and calls the new `ListByIDs` once per batch (mirroring `ListAll`'s offset-paging loop structure exactly, including per-batch `UpdateProgress`); a full-scan run is untouched. The per-product index-and-progress-update step (`IndexProduct` + `UpdateProgress`) was factored into a small shared closure (`indexBatch`) used by both loops — real duplicated logic, not a new abstraction layered on top of working code.
- **`ListByIDs` assumes well-formed IDs, the same way `variant_repo.go`'s existing `WHERE product_id = ANY($1)` queries do** — `products.id` is a `UUID` column, and every ID flowing into this port comes from `id.New()` (all UUIDs) via `ScopeProducts`, or from `ProductIDsByCategory`/`ProductIDsUpdatedSince`'s own `SELECT`s (also always real column values). A syntactically invalid UUID string reaching this port would be a bug at the caller, not a "deleted product" case to tolerate — confirmed by an integration test that initially used a bare placeholder string and got a real `invalid input syntax for type uuid` error from Postgres, then was corrected to use a well-formed-but-nonexistent `id.New()` value (the actual "deleted between resolve and run" shape), which behaves exactly as documented (silently absent from the result).
- **`search.reindex_full_scan_threshold` lives in the static YAML/env config (`platform/config.SearchConfig`), not the admin-editable dynamic config table** (`admin.ConfigGetter`, the mechanism `audit.retention_days` uses to let an admin change it without a redeploy). The plan's own "Out Of Scope" note ("no admin screen for reindex tuning") already ruled out the admin-editable path; this is an infra-level tuning knob for whoever operates the deployment, not a merchant-facing setting. Follows `database.query_exec_mode`'s exact convention: a documented struct field + `DefaultSearchReindexFullScanThreshold` constant seeded in `defaults()`, an `f >= 0` env-override guard mirroring `tracing.sample_ratio`'s (0 is a deliberate "always substitute" value, not silently dropped), and `validateSearch` rejecting anything outside `[0, 1]` at startup (unlike `sample_ratio`, which *clamps* an above-1 value instead of rejecting it — rejected here instead, since a threshold above 1 has no "obviously what they meant" reading the way "sample more than 100% of traces" does, and is far more likely a typo, e.g. `20` meant as a percentage rather than a fraction).

## What changed

- `internal/domain/search/reindex.go` — removed `ReindexScope`; extended `ProductSource` with `ListByIDs`, `ProductIDsByCategory`, `ProductIDsUpdatedSince`.
- `internal/application/search/reindex_scope.go` (new) — `Scope` interface and the four concrete types.
- `internal/application/search/reindex_service.go` — `Trigger(ctx, scope Scope)` (was `domainsearch.ReindexScope`); `NewReindexService` gained `products domainsearch.ProductSource` and `fullScanThreshold float64` parameters; new `resolveScope`/`applyThreshold` methods implementing the resolution + threshold heuristic.
- `internal/application/search/reindex_handler.go` — `Handle` reads `job.Payload["scope"]`/`["product_ids"]` via new `scopedProductIDs`, branching between the existing full-scan `ListAll` loop and a new chunked `ListByIDs` loop (shared `indexBatch` closure for the per-product index-and-progress-update step).
- `internal/infrastructure/postgres/search_product_source.go` — `ListByIDs` (`WHERE id = ANY($1)`), `ProductIDsByCategory` (`SELECT DISTINCT product_id FROM product_categories WHERE category_id = ANY($1)`), `ProductIDsUpdatedSince` (`WHERE updated_at >= $1`); shared row-scanning extracted into `scanSearchProducts` (used by both `ListAll` and `ListByIDs`, same column set).
- `internal/platform/config/config.go` — `SearchConfig.ReindexFullScanThreshold` (`DefaultSearchReindexFullScanThreshold = 0.2`), env override (`SHOPANDA_SEARCH_REINDEX_FULL_SCAN_THRESHOLD`), `flatten()` entry.
- `internal/platform/config/validate.go` — `validateSearch`, rejecting a threshold outside `[0, 1]`.
- `cmd/api/main.go` — `newSearchReindexService` constructs a `SearchProductSource` and passes it plus `cfg.Search.ReindexFullScanThreshold` into `NewReindexService`; `runSearchReindex`'s `Trigger` call updated to `searchApp.ScopeAll{}`.
- `configs/config.example.yaml` — new `search.reindex_full_scan_threshold` entry.

No migration — `search_index_runs.scope`/`scope_params` were already a bare `TEXT`/`JSONB` pair (PR-1033), sufficient for whatever `Trigger` resolves a scope down to.
