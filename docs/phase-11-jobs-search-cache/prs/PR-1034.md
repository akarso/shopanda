# PR-1034 — Partial & Scoped Reindex

Status: done

## Summary

- Scope a reindex run to explicit product IDs, explicit category IDs, or "changed since `<timestamp>`" (using `products.updated_at`).
- Document and implement a threshold heuristic: past a certain fraction of the catalog, a full scan is cheaper than a scoped run, and the reindex service picks full-scan automatically rather than trusting the caller's scope.

## Why

The whole point of partial reindex is to make "I changed 12 products" cheap. But a naive per-ID lookup implementation is *not* automatically cheaper than a full scan once the scoped set gets large — each scoped product still costs one lookup + one index write, and a full scan has a fixed per-run overhead (opening the transaction, listing) that partial reindex also pays, just per-batch instead of once. Below some fraction of the catalog, scoped wins; above it, the fixed overhead of full-scan-in-one-pass wins over N individual round trips. Getting this backwards would make partial reindex a trap: someone reindexes "since yesterday" after a large price-import job touched 80% of products, and it ends up slower and more DB-load-intensive than just reindexing everything.

## Scope

- `internal/application/search.Scope` — `ScopeAll{}`, `ScopeProducts{IDs []string}`, `ScopeCategories{IDs []string}`, `ScopeSince{Since time.Time}`.
- `ScopeSince` resolves to a concrete product ID list via `domainsearch.ProductSource.ProductIDsUpdatedSince(ctx, since) ([]string, error)` at trigger time (`ReindexService.Trigger`, not job-run time — see "Design decisions" below for why resolving once, up front, matters), then follows the same path as `ScopeProducts`.
- **Threshold heuristic:** before enqueueing, `ReindexService.Trigger` compares the resolved scope's product count against total catalog size (`domainsearch.ProductSource.CountAll(ctx)`, already existing from PR-1033). If the scope covers more than **20%** of the catalog, the job is enqueued as `ScopeAll` instead of the caller's requested partial scope — the run record's `scope_params` still records what was *requested*, but `scope` reflects what actually ran, so this substitution is visible, not silent. The 20% figure is a documented starting point, not empirically tuned in this PR (no production traffic to tune against yet) — flag it as a config-overridable constant (`search.reindex_full_scan_threshold`, default `0.2`) so it can be adjusted post-launch without a code change.
- `ScopeCategories{IDs}` resolves at trigger time via `domainsearch.ProductSource.ProductIDsByCategory(ctx, categoryIDs) ([]string, error)` — the inverse of `ListCategoryIDsByProduct`, reading `product_categories` directly rather than through `catalog.ProductRepository`/`ProductCategoryAssignmentRepository` (keeping the same catalog-decoupling boundary `ProductSource` already has — see "Design decisions").

## Out Of Scope

- A UI/API for adjusting the threshold constant beyond the config key — no admin screen for "reindex tuning," just a documented config value.
- Scoping by store — no `store_id` on products/categories (see ROADMAP's "Out of scope"); nothing to scope by here.
- A CLI flag or admin endpoint to actually *request* a partial reindex — `search:reindex` still only ever triggers `ScopeAll`. Wiring an external caller to the new `Scope` types is explicitly PR-1035's job ("exposes scope selection through the admin API"); this PR only builds the application-layer mechanism PR-1035 will call into.

## Design decisions made during implementation

- **`domainsearch.ReindexScope{Name, Params}` (the original PR-1033 placeholder) was removed, not extended.** The plan's own note that "Params exists so PR-1034's partial/scoped values ... don't need a schema or port change" was true for the `search_index_runs` table (its `scope`/`scope_params` columns are still a bare `TEXT`/`JSONB` pair, untouched) but not for `ReindexService.Trigger`'s own input type: a stringly-typed `Name`/`Params` pair gives no compile-time guarantee that, say, a `"categories"` scope actually carries a `category_ids` key of the right shape. Replaced it with the planned `Scope` interface (`ScopeAll`/`ScopeProducts`/`ScopeCategories`/`ScopeSince`, an unexported-method "sealed interface" so only these four types satisfy it) as `Trigger`'s new parameter type; `Run.Scope`/`Run.ScopeParams` themselves are unchanged, still populated as a plain string + map by `Trigger` after resolution. The only caller affected, `cmd/api/main.go`'s `search:reindex`, moved from `search.ReindexScope{Name: "all"}` to `searchApp.ScopeAll{}` — one line.
- **`domainsearch.ProductSource` gained three new methods (`ListByIDs`, `ProductIDsByCategory`, `ProductIDsUpdatedSince`) instead of a separate resolver port.** The plan named `productRepo.ListUpdatedSince`/`productRepo.Count` as new methods on `catalog.ProductRepository`, but `ReindexService`/`ReindexHandler` deliberately never import `catalog` (see `ProductSource`'s own doc comment, and PR-1033's "Design decisions" on the same point for `SearchProductSource`) — routing scope resolution through `catalog.ProductRepository` would have broken that boundary just for this PR. `ProductSource` already had `CountAll` (reused directly for the threshold check, no new `Count` method needed); added `ListByIDs` (the scoped equivalent of `ListAll`'s paging, for `ReindexHandler`'s actual scan), `ProductIDsByCategory`, and `ProductIDsUpdatedSince` (both resolve a partial scope to concrete IDs, for `ReindexService.Trigger`) to the same port, implemented by the same `postgres.SearchProductSource` that already backs `CountAll`/`ListAll` — reading `products`/`product_categories` directly, not through `catalog.ProductRepository`'s own `FindByCategoryID` (confirmed to already exist, per the plan's own note, but going through it would have meant `SearchProductSource` depending on `ProductRepo`, the same layering break in a different shape).
- **A resolved scope collapses to exactly one job-level shape: `"products"` + a concrete ID list.** `ScopeProducts`, `ScopeCategories`, and `ScopeSince` all resolve to a product ID list before `Trigger` ever enqueues anything — `ReindexHandler` only ever needs to know "scan everything" (`scope: "all"`) or "scan exactly these IDs" (`scope: "products"`, `product_ids: [...]` on the job payload); it never re-resolves a category or since-timestamp itself. This matters for correctness, not just simplicity: resolving once, at trigger time, means the threshold check and the job's actual work always agree on the same ID list — re-resolving inside the handler (potentially much later, after a job requeue/retry) could return a different answer than what the threshold check saw (products added/removed from a category, or updated after the "since" cutoff), silently invalidating the substitution decision.
- **The threshold check is skipped entirely for an empty resolved scope** (`applyThreshold` returns early for `len(resolvedIDs) == 0`) — comparing zero against any catalog size can never exceed the threshold, so consulting `CountAll` would be a pure, guaranteed-pointless round trip. This also means a `ScopeCategories`/`ScopeSince` request that matches nothing doesn't require a working `CountAll` call at all.
- **`ReindexHandler.Handle` branches on whether the job payload carries a `product_ids` array, not by threading a new parameter through the existing full-scan loop.** A scoped run chunks the resolved ID list into `reindexBatchSize`-sized batches and calls the new `ListByIDs` once per batch (mirroring `ListAll`'s offset-paging loop structure exactly, including per-batch `UpdateProgress`); a full-scan run is untouched. The per-product index-and-progress-update step (`IndexProduct` + `UpdateProgress`) was factored into a small shared closure (`indexBatch`) used by both loops — real duplicated logic, not a new abstraction layered on top of working code.
- **`ListByIDs` assumes well-formed IDs, the same way `variant_repo.go`'s existing `WHERE product_id = ANY($1)` queries do** — `products.id` is a `UUID` column, and every ID flowing into this port comes from `id.New()` (all UUIDs) via `ScopeProducts`, or from `ProductIDsByCategory`/`ProductIDsUpdatedSince`'s own `SELECT`s (also always real column values). A syntactically invalid UUID string reaching this port would be a bug at the caller, not a "deleted product" case to tolerate — confirmed by an integration test that initially used a bare placeholder string and got a real `invalid input syntax for type uuid` error from Postgres, then was corrected to use a well-formed-but-nonexistent `id.New()` value (the actual "deleted between resolve and run" shape), which behaves exactly as documented (silently absent from the result).
- **`search.reindex_full_scan_threshold` lives in the static YAML/env config (`platform/config.SearchConfig`), not the admin-editable dynamic config table** (`admin.ConfigGetter`, the mechanism `audit.retention_days` uses to let an admin change it without a redeploy). The plan's own "Out Of Scope" note ("no admin screen for reindex tuning") already ruled out the admin-editable path; this is an infra-level tuning knob for whoever operates the deployment, not a merchant-facing setting. Follows `database.query_exec_mode`'s exact convention: a documented struct field + `DefaultSearchReindexFullScanThreshold` constant seeded in `defaults()`, an `f >= 0` env-override guard mirroring `tracing.sample_ratio`'s (0 is a deliberate "always substitute" value, not silently dropped), and `validateSearch` rejecting anything outside `[0, 1]` at startup (unlike `sample_ratio`, which *clamps* an above-1 value instead of rejecting it — rejected here instead, since a threshold above 1 has no "obviously what they meant" reading the way "sample more than 100% of traces" does, and is far more likely a typo, e.g. `20` meant as a percentage rather than a fraction).

## What changed

- `internal/domain/search/reindex.go` — removed `ReindexScope`; extended `ProductSource` with `ListByIDs`, `ProductIDsByCategory`, `ProductIDsUpdatedSince`.
- `internal/application/search/reindex_scope.go` (new) — `Scope` interface and the four concrete types.

- `internal/application/search/reindex_handler.go` — `Handle` reads `job.Payload["scope"]`/`["product_ids"]` via new `scopedProductIDs`, branching between the existing full-scan `ListAll` loop and a new chunked `ListByIDs` loop (shared `indexBatch` closure for the per-product index-and-progress-update step).
- `internal/infrastructure/postgres/search_product_source.go` — `ListByIDs` (`WHERE id = ANY($1)`), `ProductIDsByCategory` (`SELECT DISTINCT product_id FROM product_categories WHERE category_id = ANY($1)`), `ProductIDsUpdatedSince` (`WHERE updated_at >= $1`); shared row-scanning extracted into `scanSearchProducts` (used by both `ListAll` and `ListByIDs`, same column set).
- `internal/platform/config/config.go` — `SearchConfig.ReindexFullScanThreshold` (`DefaultSearchReindexFullScanThreshold = 0.2`), env override (`SHOPANDA_SEARCH_REINDEX_FULL_SCAN_THRESHOLD`), `flatten()` entry.
- `internal/platform/config/validate.go` — `validateSearch`, rejecting a threshold outside `[0, 1]`.
- `cmd/api/main.go` — `newSearchReindexService` constructs a `SearchProductSource` and passes it plus `cfg.Search.ReindexFullScanThreshold` into `NewReindexService`; `runSearchReindex`'s `Trigger` call updated to `searchApp.ScopeAll{}`.
- `configs/config.example.yaml` — new `search.reindex_full_scan_threshold` entry.

No migration for `search_index_runs` — `scope`/`scope_params` were already a bare `TEXT`/`JSONB` pair (PR-1033), sufficient for whatever `Trigger` resolves a scope down to. `migrations/071_add_products_updated_at_index.sql` (new, Round 2) adds the index `ProductIDsUpdatedSince` needs — see Round 2 below.

## Round 2 (code review)

- **Major — fixed.** `ProductIDsUpdatedSince`'s `WHERE updated_at >= $1` had no supporting index — `products.updated_at` was only ever indirectly touched by `idx_products_status`, not indexed itself — meaning every `ScopeSince` trigger was a full sequential scan, the exact "changed since yesterday" scenario this PR exists to make cheap becoming its own most expensive resolution path on a large catalog. Added `migrations/071_add_products_updated_at_index.sql` (`CREATE INDEX idx_products_updated_at ON products (updated_at)`), same `CREATE INDEX IF NOT EXISTS` + no-`CONCURRENTLY`-inside-a-transaction caveat as `066_add_jobs_introspection_indexes.sql`/`070_add_jobs_reindex_run_id_index.sql`. Confirmed present via `pg_indexes` after running migrations against a real Postgres instance in this session (a throwaway local container, torn down after) — `EXPLAIN` still picks a sequential scan on the tiny test table, which is Postgres correctly favoring it at that size, not evidence the index goes unused; it applies once the table is large enough for an index scan to actually win, which is the case that matters.
- **Major — fixed.** A resolved scope's product ID list was serialized whole into `job.Payload["product_ids"]` (persisted as JSONB on the `jobs` row, reloaded on every dequeue/retry) with only `fullScanThreshold`'s *percentage* bounding it — on a catalog of a few million products, 20% is hundreds of thousands of UUIDs, tens of MB in one JSONB column. Added `maxScopedReindexProductIDs` (10,000), an absolute cap `applyThreshold` checks before ever consulting `CountAll` — a scope resolving to more IDs than that substitutes a full scan regardless of what fraction of the catalog it actually represents (the byte size of the payload doesn't care about the fraction). Chose a hard cap over the reviewer's other suggested option (storing the ID list separately from the job row): a new storage mechanism is a real architectural addition for a case the cap already closes at essentially zero cost, and 10,000 IDs (~a few hundred KB of JSONB) is comfortably above any "reindex the batch I just changed" partial run — a genuinely bulk change is exactly what the percentage threshold already exists to redirect. New test: `TestReindexService_Trigger_ScopeThreshold_HardCapSubstitutesFullScan` (proves the cap trips without ever calling `CountAll`, the same technique `TestReindexService_Trigger_EmptyResolutionSkipsCountAll` already used).
- **Minor — fixed.** `ScopeProducts.IDs` fed `applyThreshold`'s ratio and the run's `total_count` with no deduplication, while `ListByIDs`' own `= ANY($1)` naturally deduplicates on the read side — a caller-supplied list with repeats could leave a genuinely `completed` run permanently showing e.g. `1/2` instead of `1/1`. New `normalizeProductIDs`/`normalizeCategoryIDs` (in `reindex_service.go`) validate and deduplicate `ScopeProducts.IDs`/`ScopeCategories.IDs` before either is used, preserving first-seen order. Confirmed the existing threshold-boundary tests were themselves exhibiting exactly this gap (repeated placeholder `"p"` values, which the fix's own deduplication would have silently collapsed the intended 20%/21% down to a single ID) — fixed by switching every test to distinct real `id.New()` values, and added `TestReindexService_Trigger_ScopeProducts_DeduplicatesAndValidatesIDs` to pin the dedup behavior directly.
- **Minor — fixed.** `normalizeProductIDs` also closes a related gap: a blank or non-UUID entry in `ScopeProducts.IDs` previously passed straight through `resolveScope`'s `len(sc.IDs) == 0` guard and only surfaced as a Postgres `invalid input syntax for type uuid` error once the job actually ran — after being enqueued, and potentially retried to exhaustion. Every ID is now validated as non-blank and UUID-shaped (`platform/id.IsValid`, matching `products.id`'s actual column type) synchronously in `Trigger`, before any DB/queue work happens. `ScopeCategories.IDs` gets the non-blank check only (`normalizeCategoryIDs`, no UUID-shape requirement) since `categories.id` is a plain `TEXT` column, not UUID-typed.
- **Minor — fixed.** `ReindexHandler.scopedProductIDs` treated any scope value other than exactly `"products"` as a full scan — a typo'd scope string, a future scope kind added here without updating this function, or outright payload corruption would silently rescan the entire catalog instead of failing, inconsistent with `resolveScope`'s own `default: return error` symmetry on the trigger side. Changed to an explicit `switch`: `""`/`"all"` → full scan (unchanged, preserves every pre-PR-1034 and legacy payload), `"products"` → scoped (unchanged), anything else → a real error. New test: `TestReindexHandler_Handle_UnrecognizedScopeErrors`.
- **Minor — reviewed, documented, not changed.** `applyThreshold` compares two independent reads (the already-resolved ID count, then a separate `CountAll` call) with no shared snapshot — the catalog can change in between, occasionally flipping the threshold decision right at the margin. Left as-is (the reviewer's own note called this "acceptable... worth a one-line mention"): the cost of being wrong is bounded either way (a scoped run slightly over/under the intended fraction, or an unnecessarily-thorough full scan), the same trade-off `SearchProductSource.ListAll`'s own doc comment already accepts for its per-batch scan. Added that one-line mention directly in `applyThreshold`'s doc comment.

## Round 3 (code review)

- **Blocker — fixed.** A product deleted between `ReindexService.Trigger` resolving a scope and the job actually running (`ListByIDs` simply omits it, per its own doc comment) left `total` — set once, upfront, to the *requested* ID count — permanently ahead of `processed` even on a genuinely successful run, e.g. a `completed` run reporting `11/12 products indexed`. `Handle`'s scoped-scan loop now shrinks `total` by exactly how many of each batch's requested IDs came back missing from `ListByIDs`, right before that batch's own `UpdateProgress` call — so `processed == total` once the run actually completes, regardless of how many requested IDs no longer existed by the time the scan ran. New test: `TestReindexHandler_Handle_ScopedRun_DeletedProductShrinksTotal` — confirmed to fail against the pre-fix code (`processed=1 total=2`) and pass against the fix.
- **Blocker — fixed.** `applyThreshold`'s empty-resolution branch returned `resolvedIDs` itself as the job's product ID list — which can be a `nil` `[]string` (e.g. `ProductIDsByCategory` matching nothing). A `nil` slice marshals to JSON `null`; decoding `null` back into a job payload's generic `map[string]interface{}` (exactly what happens once the payload round-trips through a real Postgres JSONB column) gives an untyped `nil`, not an empty `[]interface{}` — so `scopedProductIDs`' own `.([]interface{})` type assertion would fail, and a legitimate, if trivial, 0-match scoped run would error with `requires a "product_ids" array` instead of completing as a 0/0 run. Now returns an allocated `[]string{}`, which round-trips through JSON correctly. New test: `TestReindexService_Trigger_EmptyResolvedScope_ProductIDsSurvivesJSONRoundTrip` — actually round-trips the enqueued payload through `encoding/json` (the same transformation JSONB applies) rather than relying on `fakeQueue`'s in-memory `Enqueue`, which never serializes anything and so could never have caught this; confirmed to fail against the pre-fix code (`product_ids decoded as <nil>`) and pass against the fix.
- **Minor — fixed.** `SHOPANDA_SEARCH_REINDEX_FULL_SCAN_THRESHOLD`'s env-override parsing had an `f >= 0` guard that silently dropped a negative value (leaving whatever YAML/default was already set) instead of surfacing `validateSearch`'s error the way a negative *YAML* value already does — the same source-dependent inconsistency `SHOPANDA_STORE_CREDIT_MAX_ISSUE_AMOUNT`'s own env parsing deliberately avoids. Removed the guard: every successfully parsed value is now assigned, and `validateSearch` (which runs after `applyEnv`) enforces `[0, 1]` identically regardless of source. New test: `TestSearchConfig_ReindexFullScanThresholdNegativeEnvOverlayRejected`.
- **Minor — fixed.** `validateSearch`'s range check (`< 0 || > 1`) silently passed a `NaN` threshold through — every IEEE 754 comparison with `NaN` is `false`, so neither branch of that check ever fires for it, and `applyThreshold`'s own `ratio > fullScanThreshold` comparison would then also always be `false` against a `NaN` threshold, disabling the entire heuristic with no error anywhere. Added an explicit `math.IsNaN` check ahead of the range comparison. New test: `TestSearchConfig_ReindexFullScanThresholdNaNRejected`, using YAML's real `.nan` literal (confirmed this repo's YAML parser actually produces a NaN `float64` from it, not just a theoretical concern) — confirmed to fail against the pre-fix `validateSearch` and pass against the fix.
- **Documentation — fixed.** This spec's own `## Scope` section still named `productRepo.ListUpdatedSince`/`productRepo.Count`/`ProductCategoryAssignmentRepository`-adjacent methods that were never built — the planning-time approach, superseded by what "Design decisions" above already correctly describes (`domainsearch.ProductSource.ProductIDsUpdatedSince`/`ProductIDsByCategory`/`CountAll`, resolved at `Trigger` time). Updated `## Scope` in place to match, rather than leaving it to whoever reads that section without also cross-referencing "Design decisions."
- **Documentation — fixed.** `ROADMAP.md`'s "PR index (quick reference)" table still had a single `1034–1038 | B | planned` row — stale now that PR-1034 is done. Split into `1034 | B | done` and `1035–1038 | B | planned`, matching the existing per-PR-row convention every other completed PR in that table already uses.
