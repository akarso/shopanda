# PR-1042 — Cache Admin API + CLI

Status: planned

## Summary

- `GET /api/v1/admin/cache/stats` (per cache-tier/type visibility — L1 vs L2, approximate key counts), `POST /api/v1/admin/cache/clear` (by prefix, tag, key, or all).
- CLI parity: `app cache:stats`, `cache:clear --prefix|--tag|--key|--all`.

## Why

There is currently no admin visibility into the cache at all — not stats, not manual clearing. This is the same gap Track A closed for jobs, applied to cache.

## Scope

- `internal/interfaces/http/admin/cache_admin.go` — `CacheAdminHandler`.
- `GET /admin/cache/stats` — per-backend approximate stats: Postgres backend via `SELECT count(*) FROM cache` (and `cache_tags` row count as a proxy for tag cardinality — flagged in PR-1039 as worth watching), Redis via `DBSIZE`/`INFO memory`; L1 (PR-1040) reports its own entry count and hit/miss counters directly from the in-process store, no backend round trip needed for that part.
- `POST /admin/cache/clear` — body `{"prefix": "..."}` \| `{"tag": "..."}` \| `{"key": "..."}` \| `{"all": true}`. The `all` case is gated behind a **distinct** permission (`cache.clear_all`, separate from `cache.write` for prefix/tag/key) — full cache flush is a materially bigger blast radius (every cache consumer pays a cold-cache penalty simultaneously, including Track D's full-page cache once it ships) than a targeted clear, and the permission split reflects that. Every clear operation, including targeted ones, is audit-logged with what was cleared.
- New `cache.read`/`cache.write`/`cache.clear_all` permissions.
- CLI commands wrapping the same service calls the HTTP handler uses (no separate logic path, matching PR-1032's pattern).

## Out Of Scope

- Real hit/miss rate tracking for L2 (Postgres/Redis) — L1 gets this cheaply (in-process counters), but instrumenting L2 hit/miss would mean threading counters through every `Get` call site or wrapping the backend, which is a bigger change than "expose what's already computable." If this turns out to matter operationally, Track D's PR-1047 (full-page cache observability) is a natural place to add Prometheus-based hit/miss metrics with proper labels, superseding a one-off admin-stats-endpoint approach.

## Validation (planned — run when implementing)

- `go test ./internal/interfaces/http/admin/... -run CacheAdmin -count=1` — stats reflect actual backend state (seed known keys, assert count), each clear variant (prefix/tag/key/all) only removes what it should, `all` requires the distinct permission.
- `go build ./cmd/api/`
