# PR-1047 — Observability + Rollup

Status: planned

## Summary

- Full-page cache hit/miss/bypass Prometheus counters, matching Phase 10's existing metrics conventions.
- RUNBOOK.md incident-response entries in the established symptom → check → fix style.
- Cache admin GUI page for full-page-cache-specific stats (hit rate by route template, current cached-page count).

## Why

Everything in Track D up to this point is correct-by-design but invisible in production — an operator has no way to see the cache is actually working (or actually not working) without this. This is the same "close the observability gap" pattern Phase 10 applied to metrics/tracing generally, applied here to the one subsystem this phase adds that didn't exist before (jobs/search/cache-clearing all got their own observability earlier in this phase; full-page cache is new enough to need its own pass).

## Scope

- New Prometheus metrics (bounded labels, matching Phase 10's label-cardinality discipline — `route_template`, not raw path):
  - `shopanda_fpc_requests_total{route, outcome}` — `outcome` ∈ `hit`/`miss`/`bypass` (bypass = a route not on the allowlist, or a request that structurally can't be cached — e.g. non-GET).
  - `shopanda_fpc_render_duration_seconds{route}` — histogram, render time on miss (what the cache is saving on hit).
  - `shopanda_fpc_purge_total{trigger}` — `trigger` ∈ `tag_invalidation`/`manual_url`/`ttl_expiry` (counts, not which key — no cardinality risk).
- RUNBOOK.md entries, Phase 10 incident-response format:
  - "Full-page cache hit rate unexpectedly low" → check: vary-key cardinality blowup (are `store`/`language`/`currency` combinations actually as narrow as expected, or did something start sending unexpected values), TTL too short, allowlist coverage.
  - "A cacheable-looking page never gets cached" → check: is the route actually on the allowlist (PR-1044's fail-closed design means "forgot to add it" looks identical to "deliberately excluded" from the outside — this entry exists specifically to distinguish them).
  - "Stale content despite tag invalidation" → check: did the triggering event actually fire (same class of check as Track B's on-save indexing troubleshooting), is the entity's tag actually attached to the stale cached page (a rendering bug that omits a tag is silent until this exact symptom appears).
- Cache admin GUI (extends PR-1043's cache screen): a "Full-page cache" tab — hit rate by route template (derived from the metrics above, queried via whatever the admin panel's existing pattern is for surfacing metrics, if any exists — otherwise this may need its own lightweight stats endpoint rather than a live PromQL query from the admin API, since the admin backend shouldn't take a runtime dependency on the Prometheus server being reachable).

## Out Of Scope

- Grafana dashboards — Phase 10's precedent is "document example PromQL queries, don't ship dashboards" (see RUNBOOK.md's existing metrics section); this PR follows the same precedent rather than introducing dashboard-as-code for the first time in this repo.
- Alerting rules — same reasoning; out of scope for a metrics-and-docs PR, and alerting thresholds need real production traffic data this phase can't have yet.
