# PR-1033 — Reindex as a Job

Status: done

## Summary

- Model `search:reindex` as a queued `search.reindex` job processed by the existing `jobs.Worker`, with a persisted `search_index_runs` row tracking scope/progress/counts/errors as the worker processes it.
- The `search:reindex` CLI command becomes a thin enqueue wrapper (optionally `--wait` to block until the run finishes, for scripts/CI that want synchronous behavior) instead of doing the scan-and-index work inline in the CLI process itself.

## Why

Today's `runSearchReindex` does the entire full-table-scan-and-index loop inline in the CLI process — no progress is persisted anywhere, an interrupted run (SIGINT, or the CLI process dying) leaves no record of how far it got, and there's no way to build an admin-facing progress endpoint (PR-1035) against a process that isn't even running inside the queue's worker model. Moving it onto the job queue fixes all three at once, and is consistent with this phase's principle that background work goes through the existing queue.

## Scope

- New migration: `search_index_runs(id UUID PK, scope TEXT, scope_params JSONB, status TEXT, total_count INT, processed_count INT, error_count INT, started_at, finished_at, last_error TEXT)`.
- `internal/application/search` (new package): `ReindexHandler` (job type `search.reindex`) — reads `scope`/`scope_params` from the job payload, updates the `search_index_runs` row's `processed_count` incrementally as it works (not just at the end — this is what makes a progress endpoint meaningful in PR-1035), sets `status` to `completed`/`failed` on exit.
- `internal/application/search.ReindexService.Trigger(ctx, scope Scope) (runID string, error)` — creates the `search_index_runs` row, enqueues the job, returns the run ID immediately (the caller doesn't wait for it to finish).
- `runSearchReindex` (`cmd/api/main.go`) rewritten to call `ReindexService.Trigger`, then either exit immediately (default) or poll the run row until terminal (`--wait`).
- This PR ships **full-scope reindex only** — the same behavior as today's CLI command, just running through the queue. Scoping (partial reindex) is PR-1034.

## Out Of Scope

- Partial/scoped reindex logic — PR-1034.
- The admin HTTP API / progress endpoint — PR-1035.
- Resumability of an interrupted run (if the worker process crashes mid-run, the run row is left `processing` with a partial `processed_count`, not automatically resumed or retried) — a `search_index_runs` row stuck in `processing` past some threshold is a signal an operator can act on via the jobs admin API (PR-1029) since the underlying job itself gets the queue's normal retry/failure handling; the run row's own state just needs to be reconciled with the job's outcome. Document this interaction explicitly during implementation rather than leaving it as an implicit assumption.

## Design decisions made during implementation

- **A dedicated `search.ProductSource` port, not `catalog.ProductRepository`.** `search.Product` already avoids importing the `catalog` package (see its own doc comment — search intentionally stays decoupled from the wider catalog domain); routing `ReindexHandler` through `catalog.ProductRepository` would have broken that boundary just to reuse `List`. Added a narrow `search.ProductSource` (`CountAll`, `ListAll`) instead, implemented by a new `postgres.SearchProductSource` that reads the `products` table directly and maps straight into `search.Product` — no `catalog.Product` intermediate.
- **`total_count` needed a real count, so `ProductSource.CountAll` was added** — not in the original spec's schema description, but `search_index_runs.total_count` is meaningless without one, and none of `catalog.ProductRepository`'s existing methods return a bare count.
- **Fail the current attempt on the first indexing error, not per-item tolerance.** The spec's "not a behavior change" principle means this PR preserves the inline CLI loop's exact failure behavior: one failed `IndexProduct` call stops the scan (returns an error to the job worker) rather than skipping the bad product and continuing. Whether the *run row* is marked failed for that error depends on whether the job has any retries left — see "Round 2" below; `error_count` exists in the schema for forward compatibility but is always `0` in this PR either way — per-item error tolerance is a real design decision for a later PR (arguably PR-1034), not an oversight here.
- **`runSearchReindex` still goes through the same plugin-bootstrap-then-`resolveJobQueue` path `runScheduleTrigger` uses**, not the Postgres-only fail-fast shortcut `jobs_cli.go`/`schedule_cli.go`'s *admin* commands use — `ReindexService.Trigger` only needs `Enqueue`, which every queue driver supports, so there's no reason to require Postgres here the way job/schedule *introspection* legitimately does.
- **`--wait` polls every 500ms** rather than using a push notification — matches this codebase's existing "no new infra dependency for a CLI convenience" bias (no pub/sub exists for this signal), and 500ms is fine for a reindex run that takes seconds to minutes, not a latency-sensitive path.
- **The worker registers `ReindexHandler` in `setupWorker`** (shared by both `runWorker` and `runServe`'s embedded worker, via `wire_services.go`), the same place every other job handler is registered — `search:reindex` now requires a running worker process to actually do anything, a real behavioral change from before (when the CLI process did the work itself) that's called out explicitly in RUNBOOK.md's new "Search reindex" section and in `docs/phase-4-refactoring/specs/RUNTIME_MODES.md`'s failure-signature table.

## What changed

- `migrations/069_create_search_index_runs.sql` (new) — `search_index_runs` table per the planned schema.
- `internal/domain/search/reindex.go` (new) — `RunStatus`, `Run`, `ReindexScope`, and the two new ports: `RunStore` (persistence) and `ProductSource` (the narrow product-scan source; see "Design decisions").
- `internal/application/search` (new package):
  - `reindex_service.go` — `ReindexService.Trigger(ctx, scope)`: creates the run row (`RunStatusProcessing`), enqueues a `search.reindex` job carrying `run_id`/`scope` in its payload, returns the run ID.
  - `reindex_handler.go` — `ReindexHandler` (`jobs.Handler`, type `search.reindex`): reads `run_id` from the job payload, counts total products, then scans in batches of 100 via `ProductSource.ListAll`, calling `SearchEngine.IndexProduct` per product and `RunStore.UpdateProgress` after every batch; `RunStore.Finish` marks the run `completed` or `failed` (with `LastError`) on exit. Fails the whole run (and returns the error, so the job itself fails/retries) on the first error from either `CountAll`, `ListAll`, or `IndexProduct` — see "Design decisions."
- `internal/infrastructure/postgres/search_index_run_repo.go` (new) — `SearchIndexRunRepo` implementing `RunStore` over `search_index_runs`.
- `internal/infrastructure/postgres/search_product_source.go` (new) — `SearchProductSource` implementing `ProductSource`, reading `id, name, slug, description, attributes, created_at` directly off `products` (same fields the old inline CLI loop indexed — no behavior change).
- `cmd/api/main.go`:
  - `runSearchReindex` rewritten: parses `[--wait]`, opens a standalone connection (`newSearchReindexService`, mirroring `runScheduleTrigger`'s plugin-bootstrap-then-`resolveJobQueue` path — see "Design decisions"), calls `ReindexService.Trigger`, then either returns immediately or polls `RunStore.Get` every 500ms until the run is `completed`/`failed`. Dispatch changed from `runSearchReindex(cfg, log)` to `runSearchReindex(os.Stdout, cfg, log, os.Args[2:])`, matching the `w io.Writer, args []string` convention Track A's `jobs:*`/`schedule:*` commands already use.
  - `setupWorker` now also resolves the search engine, constructs `SearchIndexRunRepo`/`SearchProductSource`, and registers `ReindexHandler` on the worker — covers both `runWorker` and `runServe`'s embedded worker (`wire_services.go` calls the same `setupWorker`).
  - `printHelp`'s `search:reindex` line updated to mention `[--wait]`.
- `docs/diagrams/c4-component.md` — new `ReindexHandler` component (Application Layer, alongside the other job handlers), plus two Infrastructure Layer components alongside `PostgresJobQueue`: `SearchIndexRunRepo` and `SearchProductSource` (its own component, not folded into the generic `PostgreSQL Repositories` box — that box's own description is catalog/cart/order/etc. via `catalog.ProductRepository`, which `SearchProductSource` explicitly does not go through). `Rel` lines mirror the existing job-handler pattern: `jobWorker` dispatches to `reindexHandler`, which reads products via `searchProductSource`, indexes via `postgresSearch`, and updates progress via `searchIndexRunRepo`.

## Round 2 (code review)

- **Blocker — fixed.** `ReindexHandler.Handle`'s `fail()` marked the run row `failed` on the *first* error from any attempt, but the job queue auto-retries up to `MaxRetries` (default 3) with backoff — a single transient `IndexProduct` failure permanently marked the run failed while the underlying job kept retrying and could still go on to succeed, silently flipping the same row back to `completed` later. `--wait`/any progress view would report a false failure mid-retry. Replaced `fail()` with `failIfTerminal(ctx, runID, job, cause)`, which only calls `RunStore.Finish(failed)` when `job.Attempts >= job.MaxRetries` — the exact condition `jobs.Queue`'s own `Fail` implementation uses to decide a permanent failure vs. a requeue (`postgres/job_queue.go`). A non-terminal failure is logged (`search.reindex.attempt_failed_will_retry`) and the run is left `processing` for the next attempt. Added `TestReindexHandler_Handle_TransientFailureLeavesRunProcessing` and `TestReindexHandler_Handle_TransientFailureThenRetrySucceeds` (attempt 1 fails and leaves the run processing, attempt 2 on the same job succeeds and completes it — the exact scenario the bug mishandled); the three existing `...FailsRun` tests were updated to use an explicit terminal attempt (`Attempts: 3, MaxRetries: 3`, via a new `finalAttemptJob` helper) instead of relying on a zero-value `Job{}`'s `0 >= 0` coincidentally reading as terminal.
- **Major — fixed.** `ReindexService.Trigger`'s `Create` (run row) and `Enqueue` (job) were two independent, non-transactional steps — if `Enqueue` failed after `Create` succeeded, the run row was stuck at `processing` forever with no job ever created to finish it, indistinguishable from a crashed worker but with nothing to reconcile against (a crashed worker's job row is still there for the queue's own retry/fail machinery; an unenqueued run has no such row). A real cross-system transaction isn't feasible here — `domainjobs.Queue` is a port with broker-backed implementations (Redis/RabbitMQ/Kafka/SQS) alongside the Postgres one, so `Create` and `Enqueue` can't share a single DB transaction in general, and this codebase doesn't have (and this PR isn't the place to add) an outbox pattern for that. Added a compensating call instead: on `Enqueue` error, `Trigger` now calls `s.store.Finish(runID, RunStatusFailed, ...)` before returning, so the failure is immediately visible (`jobs:list`, a future admin progress view) instead of silently orphaning the row. `ReindexService` gained a `Logger` dependency (`NewReindexService`'s new third parameter) to log the rare case where the compensating `Finish` call itself also fails — best-effort, matching this codebase's existing best-effort audit/compensation conventions elsewhere. Renamed the existing enqueue-error test to `TestReindexService_Trigger_QueueEnqueueErrorPropagates_MarksRunFailed` and added the run-status assertion the bug had zero coverage for.
- **Major — documented, not re-architected.** `SearchProductSource.ListAll` offset-pages the live `products` table with no snapshot isolation, unlike the old inline CLI loop's `REPEATABLE READ` transaction wrapping the whole scan — a product created or deleted concurrently during a reindex can now be skipped or (less likely) double-indexed. Restoring snapshot isolation would mean holding one transaction open for an entire catalog scan, which — now that this runs inside a long-lived worker process handling many other job types, not a short-lived one-shot CLI invocation — is its own operational risk (blocks autovacuum, holds a snapshot for however long the whole reindex takes). Chose to document this as an accepted, deliberate trade-off rather than reintroduce a long transaction: doc comment on `SearchProductSource.ListAll`, and a new paragraph in RUNBOOK.md's "Search reindex" section advising a low-write window for reindexes where this matters. Revisit if concurrent-write correctness during reindex turns out to matter in practice.
- **Minor — fixed (documentation only).** `Run.ErrorCount` is hardcoded to `0` in every `UpdateProgress`/`Finish` call and can never be non-zero under this PR's fail-the-whole-run-on-first-error design — flagged as a dead/misleading field. Added an explicit doc comment on the field itself (`internal/domain/search/reindex.go`) stating it's always `0` as of this PR and explaining why the column exists anyway (forward compatibility for a later per-item-tolerance PR), rather than leaving that context only in this PR doc's "Design decisions" section where the field's own definition doesn't surface it.
- **Minor — fixed.** `docs/diagrams/c4-component.md`'s `Rel(reindexHandler, postgresRepos, ...)` routed through the generic "PostgreSQL Repositories" (catalog/cart/order/...) component, but `SearchProductSource`'s own source comment says it deliberately does *not* go through `catalog.ProductRepository` — the diagram edge contradicted the code it documented. Added a dedicated `SearchProductSource` component (Infrastructure Layer, alongside `SearchIndexRunRepo`) and repointed the relationship at it instead of `postgresRepos`.

## Round 3 (code review)

- **Fixed — run could stay `processing` forever if the terminal `RunStore.Finish` write itself failed.** Round 2's `failIfTerminal` correctly decided *when* to mark a run failed, but neither terminal `Finish` call (the success path's `Finish(completed)` at what was line 92, and `failIfTerminal`'s own `Finish(failed)`) handled its *own* write failing: on the success path, a failed `Finish(completed)` was logged and swallowed, and `Handle` still returned `nil` — the worker then marked the **job** `done` while the **run** row stayed `processing` forever, with no future job attempt ever able to touch it again. Added `finishWithRetry` (3 attempts, 50ms apart) and use it at both call sites. Critically, on the success path, if `finishWithRetry(completed)` still fails after retrying, `Handle` no longer returns `nil` — it wraps the error and calls `failIfTerminal` (reusing the same terminal-vs-retry logic Round 2 added), then returns the wrapped error, so the worker retries/fails the **job** instead of silently completing it over a stuck run. Added 4 tests: retry actually recovers a transient `Finish` failure on both the completed and failed paths (`TestReindexHandler_Handle_FinishCompletedRetriesThenSucceeds`, `TestReindexHandler_Handle_FailIfTerminalFinishRetriesThenSucceeds`), and the two "every retry still fails" cases on the completed path — non-terminal attempt (job must still be retried, not completed) and terminal attempt (store is down entirely; `Handle` still returns an error and doesn't panic, even though the run row itself ends up unable to reach any terminal status in that worst case).
  - Deliberately did not change `UpdateProgress`'s error handling (still logged and swallowed) — the review's own structured fix instructions scoped this to "both `RunStore.Finish` calls," not the progress updates; a stale `processed_count` mid-run is a materially smaller problem than the run never reaching a terminal status at all, and mid-run progress is naturally overwritten by the next successful `UpdateProgress` call, unlike a missed terminal write.
- **Fixed — phase PR index left PR-1033 `planned`.** `docs/phase-11-jobs-search-cache/prs/README.md` (a separate index file from the phase `README.md`/`ROADMAP.md` already updated after Round 1 — missed entirely in that pass) still listed PR-1033 as `planned`. Updated to `done`.
- **Fixed — misleading CLI guidance.** `runSearchReindex`'s non-`--wait` success message told the operator to "Check jobs:show" — but `ReindexService.Trigger` only returns the run ID, never the underlying job's own ID, so `jobs:show <id>` has no ID to actually check without some other lookup first. Changed to `jobs:list --type=search.reindex`, which needs no ID and is exactly what RUNBOOK.md's own "Search reindex" section already recommends for the same situation.
- **Fixed — RUNBOOK.md conflated job status with reindex progress.** The "Progress is visible the same way any other job's is" line implied `jobs:list`/`jobs:show`/the jobs admin API expose the reindex's actual progress; they only expose the underlying job's queue status (pending/processing/done/failed, attempts) — `search_index_runs.processed_count`/`total_count` isn't surfaced there at all. Reworded to state that distinction explicitly: those surfaces show queue status only, `--wait` prints the final indexed/total count on completion (not live progress), and a dedicated progress endpoint is PR-1035.
