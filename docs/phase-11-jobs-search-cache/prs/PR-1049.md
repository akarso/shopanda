# PR-1049 — Stock-Change Event Coverage for On-Save Indexing

Status: done

## Summary

- Publish `inventory.EventStockUpdated` (added in PR-1036) from every stock-mutating path that isn't already covered — checkout reservation/release (**priority** — the highest-frequency stock-changing path in the system), reservation-expiry release, and returns restocking — so PR-1036's on-save search reindex subscriber actually stays fresh for real stock changes, not just admin-panel adjustments.
- Give the two bulk stock-mutation paths (CLI/CSV `import:stock`, and the ERP `StockSyncService.UpsertBySKU` sync) a batching strategy before wiring them, so doing so doesn't reproduce the per-row job/run fan-out risk already flagged (and avoided) for bulk price import in PR-1036's review.

## Why

PR-1036 wired on-save search indexing to react to stock changes, but only ever wired the *publish* side for the interactive admin single-variant "Adjust" endpoint. Its own code review surfaced that this leaves the actual highest-frequency stock-changing path — checkout reservation on every customer purchase — completely uncovered: the search index's stock-derived fields go stale for real sales traffic, not just admin edits. Two more paths (reservation-expiry release, returns restocking) have the same gap for lower-frequency reasons, and the two bulk paths were deliberately left unwired specifically because wiring them naively would reintroduce the exact one-job-per-row fan-out problem PR-1036 caught and avoided for bulk price import. This PR closes all of it.

## Scope

- **Checkout reservation/release** (`internal/application/checkout.ReserveInventoryStep`) — priority.
  - Add a `catalog.VariantRepository` (or a narrower interface) dependency to resolve a reserved/released `VariantID` to its `ProductID`/`SKU`.
  - Add an `*event.Bus` dependency (currently absent from this step entirely).
  - Publish `inventory.EventStockUpdated` after each successful `Reserve`/`Release` call into `postgres.ReservationRepo` — post-commit, matching how every other publish site in this codebase fires after (not inside) the write's own transaction; the stock decrement/restore happens via raw SQL inside that repo, not through `StockRepository`, so the event can't be published from inside the same transaction without also changing `ReservationRepo` itself.
  - Update wiring at `cmd/api/wire_services.go` (already constructs both `repos.variantRepo` and `bus` right next to where this step is built) and `NewReserveInventoryStep`'s call sites/tests.
- **Reservation-expiry release** (`ReservationExpiryHandler` / `ExpiredReservationReleaser.ReleaseExpiredBefore`).
  - Widen `ReleaseExpiredBefore`'s return type to report which variants (and quantities) were actually released, not just a total count — touches the interface (`internal/domain/inventory`), the Postgres implementation (`releaseExpiredBatch`, which already has this data locally but doesn't return it), and existing test doubles across all three layers.
  - Add a `catalog.VariantRepository` dependency to `ReservationExpiryHandler` (currently absent) to resolve each released variant's `ProductID`, and publish `inventory.EventStockUpdated` per release once that data is available.
- **Returns restocking** (`returns.Service.Receive`).
  - Add a `catalog.VariantRepository` dependency (the service already has a required `*event.Bus`, so no new bus wiring needed here).
  - Publish `inventory.EventStockUpdated` per restocked item, alongside the existing `EventReturnReceived`.
- **Bulk stock imports — batch, don't publish per row.**
  - `import:stock` (CLI/CSV, `importer.NewStockImporter`, which currently has no event-publishing capability at all) and `StockSyncService.UpsertBySKU` (ERP sync): instead of publishing `inventory.EventStockUpdated` once per row — which would reproduce the exact fan-out risk PR-1036 identified and deliberately avoided for bulk price import (thousands of `search_index_runs` rows and queued jobs from one large import) — each importer collects the set of touched product IDs during its run and, once, after the batch completes, calls `ReindexService.Trigger(ctx, search.ScopeProducts{IDs: [...]})` directly. This bypasses the event-driven subscriber for the bulk case entirely, the same way an explicit admin-triggered scoped reindex already works (PR-1035), and lets `ReindexService`'s own existing full-scan-threshold/hard-cap logic (PR-1034) take over automatically if the touched set is large. Needs a `*searchApp.ReindexService` (or a narrow interface over just `Trigger`) threaded into both importers as an **optional** dependency (nil skips triggering, matching the `SetBus`/optional-wiring pattern PR-1036 already established) so existing call sites/tests that don't care about this aren't forced to supply one.

## Out Of Scope

- A general job-queue lease/heartbeat/reaper mechanism, or any other change to `internal/domain/jobs` itself.
- Changing `ReleaseExpiredBefore`'s release semantics beyond widening its return type — the release logic itself (batch size, `FOR UPDATE SKIP LOCKED`) is unchanged.
- `IndexCategory`-based category-document indexing (PR-1037, unrelated to this PR's stock-event scope).
- Splitting into multiple smaller PRs is explicitly allowed during implementation if bundling all four sub-fixes here turns out to exceed this phase's own "one PR = one responsibility, reviewable in ~10–20 minutes" convention — checkout is the one piece that must not slip if it does get split, since it's the only one addressing the actual highest-frequency gap.

## Retrospective

### What changed

- `internal/application/checkout/reserve_inventory_step.go` — new `WithStockEventPublishing(variants, bus) ReserveOption` (the existing functional-options mechanism this file already had, not a required constructor param — see "Design decisions"). Publishes after each successful `Reserve` and after each rollback `Release`. Round 3: panics on a nil variants repository or bus.
- `internal/application/checkout/validate_cart_step.go` — `Execute` now stores every resolved variant in `cctx.Meta["cart_variants"]` (round 2 review fix — see below).
- `internal/domain/inventory/events.go` — `StockUpdatedData` is `OnHand` (resulting absolute) and `Delta` (signed change), not a mixed-meaning `Quantity` (round 3).
- `internal/domain/inventory/reservation_repository.go` — `ReleaseExpiredBefore` now returns `[]ReleasedReservation` (new type: `VariantID`, `Quantity`) instead of a bare `int`.
- `internal/infrastructure/postgres/reservation_repo.go` — `ReleaseExpiredBefore`/`releaseExpiredBatch` build and return that slice instead of just counting; the batched-loop/orphan-tracking logic itself is unchanged.
- `internal/application/inventory/reservation_expiry_handler.go` — new `SetEventPublishing(variants, bus)` (mirrors `InventoryAdminHandler.SetBus`'s optional-wiring convention exactly). `Handle` publishes once per element of the widened `ReleaseExpiredBefore` result, including committed releases returned alongside a later non-orphan error (round 3), using a short-lived publish context that does not reuse a deadline-expired sweep ctx.
- `internal/application/returns/service.go` — `NewService` gained a required `variants catalog.VariantRepository` param. `Receive` publishes per restocked item using the quantity it already computes (`entry.Quantity`, post-restock absolute — see "Design decisions").
- `internal/application/inventory/stock_sync_service.go` — new `SetReindexService(*searchApp.ReindexService)`. `UpsertBySKU` records touched product IDs only after each `SetStocks` chunk succeeds and fires one `Trigger(ScopeProducts{...})` afterward (round 3: independent context, Trigger errors returned).
- `internal/application/importer/stock.go` — new `WithReindex(*searchApp.ReindexService)` (mirrors the existing `WithRowHooks` builder). Same batch-then-trigger-once shape as `StockSyncService`.
- `cmd/api/integration_wiring.go` — `wireIntegrationStockSyncer`/`wireIntegrationStockSyncerFromDB` now return the constructed `*inventoryApp.StockSyncService` so a caller can wire `SetReindexService` on it later in its own setup sequence (see "Design decisions").
- `cmd/api/wire_services.go` — `reserveInventoryStep` built with `WithStockEventPublishing(repos.variantRepo, bus)`; `returnService` built with the new `variants` param; `stockSyncSvc.SetReindexService(reindexService)` called once `reindexService` exists.
- `cmd/api/main.go` — `setupWorker`'s `ReservationExpiryHandler` registration calls `SetEventPublishing` when `app.Bus != nil`. `runWorker` now constructs its own `*event.Bus` (previously had none at all) and, after `setupWorker` returns a real `jobQueue`, builds a `ReindexService` via new helper `newWorkerReindexService` and wires it into the ERP stock syncer **and** registers `IndexUpdateSubscriber` on that bus (round 3) so reservation-expiry events in the standalone worker enqueue a reindex. `runSetup`/`schedule_cli.go`'s stock-syncer wiring discards the returned service (see "Design decisions" for why).
- `cmd/api/io_commands.go` — `import:stock` builds its own `ReindexService` via the existing `newSearchReindexService` helper and calls `WithReindex` on the importer; a construction failure there is logged and the import proceeds without reindex triggering, not aborted.

### Design decisions

- **Checkout's new dependencies are a `ReserveOption`, not required constructor params.** `ReserveInventoryStep` already had a functional-options mechanism (`WithTTL`); adding `WithStockEventPublishing(variants, bus)` to it, rather than widening `NewReserveInventoryStep`'s arity, meant the ~10 existing test call sites across three files (`order_inventory_steps_test.go`, `context_cancel_test.go`, three storefront checkout test files) needed zero changes — only the one real production wiring site (`wire_services.go`) and the new tests that specifically exercise event publishing touch it at all. Both arguments must be non-nil (round 3: a nil variants repository or bus panics) so there is no partial-wiring state at publish time.
- **`StockUpdatedData` no longer uses a mixed-meaning `Quantity` field (round 3).** Round 2 documented the inconsistency (admin/returns = on-hand total; checkout/expiry = delta) and left it. Round 3 splits it into explicit optional `OnHand` and `Delta` pointer fields: producers set whichever they already have without extra queries (admin Adjust and returns restocking set both; checkout reserve/release and reservation-expiry set `Delta` only). `IndexUpdateSubscriber.HandleStockUpdated` still reads only `ProductID`.
- **`wireIntegrationStockSyncer` now returns the concrete `*inventoryApp.StockSyncService`**, instead of only registering it on the plugin app, so `SetReindexService` can be called on it later — `ReindexService` needs a `jobQueue` that doesn't exist yet at the point the plugin app requires its stock syncer wired (before `registry.InitAll`), in both `serve` (`wireServeRuntime`) and the standalone `worker` process (`runWorker`). This mirrors the exact reordering constraint PR-1036's own retrospective already named for the event bus, one level further: it's not just "no bus yet," it's "no queue yet either."
- **`runWorker` previously had no event bus at all — it now does, for real production reasons, not just to satisfy this PR.** The reservation-expiry sweep this PR wires into events runs in whichever process registers `ReservationExpiryHandler` via `setupWorker` — which includes the standalone `worker` process, a real, commonly-used deployment topology for scaling web and background work independently. Leaving `runWorker` bus-less would have meant this fix only actually worked for the embedded-worker (`serve`, no separate `worker` process) topology.
- **`runSetup` and `schedule:trigger`'s stock-syncer wiring deliberately do not get a `ReindexService`.** Both discard the newly-returned `*inventoryApp.StockSyncService` (`_, err := wireIntegrationStockSyncerFromDB(...)`). `runSetup` is a one-time bootstrap that doesn't process real ERP sync traffic. `schedule:trigger` fires one *named* schedule — any plugin-registered cron task, not specifically ERP sync — and is already documented (RUNBOOK.md) as an expensive, low-frequency, manual-trigger path; its own construction sequence doesn't build a `ReindexService` anywhere else either. Matches PR-1036's own established precedent for exactly this kind of call-site-completeness tradeoff (see ROADMAP.md's "Design notes" for that PR).
- **The CLI `import:stock` command builds its own `ReindexService` via the existing `newSearchReindexService` helper** (already used by `search:reindex`/`search:reindex-runs:reconcile`) rather than plumbing one through `runIOCommand`'s shared scaffold. That helper opens its own DB connection and does its own full plugin bootstrap — a real, but accepted, extra cost for a CLI command that already reads and processes a whole file in one shot. A failure *constructing* it is logged and the import still proceeds (without reindex triggering). A failure *calling* `Trigger` after stock has committed is now returned (round 3) — a queue/scope/database error after a successful write must be actionable, not silent.

### Code review fixes (round 2)

- **Major, confirmed — both bulk paths silently reintroduced the exact gap this PR exists to close, on their own error path.** `StockSyncService.UpsertBySKU` and `StockImporter.Import` only called `triggerReindex` after their whole run succeeded. `SetStocks` writes in chunks of 100 (`UpsertBySKU`) and `Import` writes one row at a time — if a later chunk/row failed, the function returned the error immediately, but earlier chunks/rows had already committed real stock changes for products that were then never reindexed: no event, no retry, nothing but a manual full-scan `search:reindex` to notice. Fixed by triggering the reindex via `defer` in both functions instead of a plain call before the final `return`, so it always fires — including on every early-return error path — covering whatever was actually committed before the failure. For `UpsertBySKU` specifically, the deferred call's `touchedProductIDs` map is built from ALL resolved entries before any `SetStocks` chunk runs, so a mid-run failure's deferred trigger can include a few products whose own chunk was never reached — accepted as harmless over-inclusion (a redundant reindex of already-correct state), never under-inclusion (the actual bug). `Import`'s per-row accumulation doesn't have this imprecision: a row's product is only added to the set after its own `SetStock` call succeeds. Added `TestStockSyncService_UpsertBySKU_ReindexesProductsCommittedBeforeALaterChunkFails` and `TestStockImport_ReindexesRowsCommittedBeforeALaterRowFails`, both confirmed to fail against the pre-fix (call-only-on-success) code.
- **Major, confirmed — checkout's new stock-event publishing added a redundant `VariantRepository.FindByID` per cart item on the highest-frequency stock-changing path.** `ValidateCartStep.Execute` (a step or two earlier in the same checkout pipeline) already resolves and discards this exact variant per item, purely to confirm it still exists. `ReserveInventoryStep.publishStockUpdated` then queried it again. Fixed by having `ValidateCartStep` store every resolved variant in `cctx.Meta["cart_variants"]` (a `map[string]*catalog.Variant`, via new package-private helpers `cartVariantsMetaKey`/`cartVariantFromMeta`), and `publishStockUpdated` consults that cache first, falling back to its own `FindByID` only if the metadata is absent (e.g. a caller — some existing tests — wiring `ReserveInventoryStep` without `ValidateCartStep` ahead of it). Purely an optimization, never a correctness dependency: the fallback keeps every pre-existing call site working unchanged. `CreateOrderStep` has the same kind of pre-existing, separate duplicate lookup — out of scope here, since this PR didn't introduce it. Added `TestReserveInventoryStep_ReusesValidateCartStepResolvedVariant` (sabotages the shared variant repo to error after `ValidateCartStep` runs, proving `ReserveInventoryStep` still succeeds only via the cache), confirmed to fail without the fix.
- **Minor, confirmed — `StockUpdatedData.Quantity`'s cross-site inconsistency (see "Design decisions" above) wasn't documented anywhere a future consumer would actually see it.** Added a doc comment directly on the `Quantity` field itself (`internal/domain/inventory/events.go`) spelling out the two different meanings in use and warning that a future consumer needing a precise, consistent shape must query current state itself — not fixed structurally (see "Design decisions" for why splitting the field wasn't worth it given today's sole consumer ignores the value entirely).
- **Minor, confirmed — `ReleasedReservation`'s "may reference an orphaned (deleted) variant" contract lived only in `releaseExpiredBatch`'s implementation, not the type or `ReleaseExpiredBefore`'s own doc comment.** A caller resolving `VariantID` to a variant depended entirely on independently reinventing the same "handle not-found" dance `ReservationExpiryHandler.publishStockUpdated` already does. Strengthened both `ReleaseExpiredBefore`'s and `ReleasedReservation`'s doc comments in `internal/domain/inventory/reservation_repository.go` to state this explicitly — no code change, since the existing implementation already handles it correctly; this was a documentation gap, not a bug.
- **Minor, confirmed — no test exercised `returns.Service.publishStockUpdated`'s own swallowed-error paths** (a failed variant lookup, a failed `bus.Publish`), unlike the equivalent paths already tested for `ReservationExpiryHandler`. Added `TestService_Receive_SwallowsVariantLookupFailure` and `TestService_Receive_SwallowsStockEventPublishFailure`, asserting `Receive` still succeeds and the expected warning is logged (captured via `logger.NewWithWriter` into a buffer) in both cases.

### Code review fixes (round 3)

- **Major, confirmed — standalone `worker` published reservation-expiry stock events on a bus that had no `IndexUpdateSubscriber`.** `runWorker` constructed an `event.Bus` so `setupWorker` could `SetEventPublishing`, but the subscriber that turns `inventory.EventStockUpdated` into a queued reindex was only registered in `wireServeRuntime`. Expired reservations processed by a standalone worker restored stock without enqueueing a reindex. Fixed by constructing and registering `IndexUpdateSubscriber` in `runWorker` after `newWorkerReindexService` succeeds (same deps as `wireServeRuntime`), and draining that bus on worker shutdown so in-flight async handlers can enqueue.
- **Major, confirmed — `ReservationExpiryHandler` reused a canceled `sweepCtx` for variant lookup and publish.** `ReleaseExpiredBefore` returns already-committed releases when the sweep deadline fires; the publish loop then called `FindByID`/`Publish` on that canceled context, lookups failed, and `Handle` still returned success — later sweeps cannot select the released rows, so restored stock stayed unreindexed. Fixed: publish uses a short-lived timeout derived from the job's parent ctx (so a sweep-timeout still publishes, while a caller cancel still cancels). Also: `ReleaseExpiredBefore` may return committed releases alongside a later non-context batch error — `Handle` now publishes every returned release before propagating that error (context errors keep the existing immediate-return path). `ReleaseExpiredBefore`'s port doc states this contract. Tests: `TestReservationExpiryHandler_Handle_PublishesCommittedReleasesBeforeNonOrphanError`.
- **Major, confirmed — both bulk paths discarded `ReindexService.Trigger` errors and reused a possibly-canceled operation context.** A queue, scope-resolution, or database failure after stock had already committed produced no reindex and no actionable error. Fixed: `triggerReindex` uses a bounded independent context (canceled after completion) and `UpsertBySKU`/`Import` return a Trigger error when the stock write itself succeeded. Tests: `TestStockSyncService_UpsertBySKU_TriggerErrorIsReturned`, `TestStockImport_TriggerErrorIsReturned`.
- **Major, confirmed — `UpsertBySKU` counted `Updated` and touched product IDs before `SetStocks` committed.** A failed later chunk inflated the result and could reindex products whose write never landed. Fixed: bookkeeping happens only after each successful `SetStocks` chunk; SKUs are sorted so chunk membership is deterministic. `TestStockSyncService_UpsertBySKU_ReindexesProductsCommittedBeforeALaterChunkFails` now assigns `p1` to the successful chunk and `p2` to the failed chunk and asserts `Updated == stockSyncChunkSize` and `product_ids` contains only `p1`.
- **Major, confirmed — `StockUpdatedData.Quantity` still mixed on-hand totals and deltas** (round 2 only documented it). Split into explicit optional `OnHand` and `Delta` pointer fields so consumers do not have to branch on event source. Checkout reserve publishes negative `Delta`; rollback release and reservation-expiry publish positive `Delta`; admin Adjust and returns restocking publish both (values already in hand).
- **Minor, confirmed — `WithStockEventPublishing` accepted a nil variants repository**, leaving incomplete stock-event configuration that would panic or silently skip at publish time. The option now panics if `variants` or `bus` is nil. Test: `TestWithStockEventPublishing_NilVariantsPanics`.
- **Minor, confirmed — RUNBOOK overstated that each bulk run makes exactly one `Trigger` call.** Updated to: the trigger occurs when a `ReindexService` is successfully wired; `import:stock` may continue without reindexing when `newSearchReindexService` fails.
