# PR-1049 — Stock-Change Event Coverage for On-Save Indexing

Status: done

## Summary

- Publish `inventory.EventStockUpdated` (added in PR-1036) from every stock-mutating path that isn't already covered — checkout reservation/release (**priority** — the highest-frequency stock-changing path in the system), reservation-expiry release, and returns restocking — so PR-1036's on-save search reindex subscriber actually stays fresh for real stock changes, not just admin-panel adjustments.
- Give the two bulk stock-mutation paths (CLI/CSV `import:stock`, and the ERP `StockSyncService.UpsertBySKU` sync) a batching strategy before wiring them, so doing so doesn't reproduce the per-row job/run fan-out risk already flagged (and avoided) for bulk price import in PR-1036's review.

## Why

PR-1036 wired on-save search indexing to react to stock changes, but only ever wired the *publish* side for the interactive admin single-variant "Adjust" endpoint. Its own code review surfaced that this leaves the actual highest-frequency stock-changing path — checkout reservation on every customer purchase — completely uncovered: the search index's stock-derived fields go stale for real sales traffic, not just admin edits. Two more paths (reservation-expiry release, returns restocking) have the same gap for lower-frequency reasons, and the two bulk paths were deliberately left unwired specifically because wiring them naively would reintroduce the exact one-job-per-row fan-out problem PR-1036 caught and avoided for bulk price import. This PR closes all of it.

## Scope

- **Checkout reservation/release** (`internal/application/checkout.ReserveInventoryStep`) — priority.
  - Add a `catalog.VariantRepository` (or a narrower interface) dependency to resolve a reserved/released `VariantID` to its `ProductID`/`SKU`.
  - Add an `*event.Bus` dependency (currently absent from this step entirely).
  - Publish `inventory.EventStockUpdated` after each successful `Reserve`/`Release` call into `postgres.ReservationRepo` — post-commit, matching how every other publish site in this codebase fires after (not inside) the write's own transaction; the stock decrement/restore happens via raw SQL inside that repo, not through `StockRepository`, so the event can't be published from inside the same transaction without also changing `ReservationRepo` itself.
  - Update wiring at `cmd/api/wire_services.go` (already constructs both `repos.variantRepo` and `bus` right next to where this step is built) and `NewReserveInventoryStep`'s call sites/tests.
- **Reservation-expiry release** (`ReservationExpiryHandler` / `ExpiredReservationReleaser.ReleaseExpiredBefore`).
  - Widen `ReleaseExpiredBefore`'s return type to report which variants (and quantities) were actually released, not just a total count — touches the interface (`internal/domain/inventory`), the Postgres implementation (`releaseExpiredBatch`, which already has this data locally but doesn't return it), and existing test doubles across all three layers.
  - Add a `catalog.VariantRepository` dependency to `ReservationExpiryHandler` (currently absent) to resolve each released variant's `ProductID`, and publish `inventory.EventStockUpdated` per release once that data is available.
- **Returns restocking** (`returns.Service.Receive`).
  - Add a `catalog.VariantRepository` dependency (the service already has a required `*event.Bus`, so no new bus wiring needed here).
  - Publish `inventory.EventStockUpdated` per restocked item, alongside the existing `EventReturnReceived`.
- **Bulk stock imports — batch, don't publish per row.**
  - `import:stock` (CLI/CSV, `importer.NewStockImporter`, which currently has no event-publishing capability at all) and `StockSyncService.UpsertBySKU` (ERP sync): instead of publishing `inventory.EventStockUpdated` once per row — which would reproduce the exact fan-out risk PR-1036 identified and deliberately avoided for bulk price import (thousands of `search_index_runs` rows and queued jobs from one large import) — each importer collects the set of touched product IDs during its run and, once, after the batch completes, calls `ReindexService.Trigger(ctx, search.ScopeProducts{IDs: [...]})` directly. This bypasses the event-driven subscriber for the bulk case entirely, the same way an explicit admin-triggered scoped reindex already works (PR-1035), and lets `ReindexService`'s own existing full-scan-threshold/hard-cap logic (PR-1034) take over automatically if the touched set is large. Needs a `*searchApp.ReindexService` (or a narrow interface over just `Trigger`) threaded into both importers as an **optional** dependency (nil skips triggering, matching the `SetBus`/optional-wiring pattern PR-1036 already established) so existing call sites/tests that don't care about this aren't forced to supply one.

## Out Of Scope

- A general job-queue lease/heartbeat/reaper mechanism, or any other change to `internal/domain/jobs` itself.
- Changing `ReleaseExpiredBefore`'s release semantics beyond widening its return type — the release logic itself (batch size, `FOR UPDATE SKIP LOCKED`) is unchanged.
- `IndexCategory`-based category-document indexing (PR-1037, unrelated to this PR's stock-event scope).
- Splitting into multiple smaller PRs is explicitly allowed during implementation if bundling all four sub-fixes here turns out to exceed this phase's own "one PR = one responsibility, reviewable in ~10–20 minutes" convention — checkout is the one piece that must not slip if it does get split, since it's the only one addressing the actual highest-frequency gap.

## Retrospective

### What changed

- `internal/application/checkout/reserve_inventory_step.go` — new `WithStockEventPublishing(variants, bus) ReserveOption` (the existing functional-options mechanism this file already had, not a required constructor param — see "Design decisions"). Publishes after each successful `Reserve` and after each rollback `Release`.
- `internal/domain/inventory/reservation_repository.go` — `ReleaseExpiredBefore` now returns `[]ReleasedReservation` (new type: `VariantID`, `Quantity`) instead of a bare `int`.
- `internal/infrastructure/postgres/reservation_repo.go` — `ReleaseExpiredBefore`/`releaseExpiredBatch` build and return that slice instead of just counting; the batched-loop/orphan-tracking logic itself is unchanged.
- `internal/application/inventory/reservation_expiry_handler.go` — new `SetEventPublishing(variants, bus)` (mirrors `InventoryAdminHandler.SetBus`'s optional-wiring convention exactly). `Handle` publishes once per element of the widened `ReleaseExpiredBefore` result.
- `internal/application/returns/service.go` — `NewService` gained a required `variants catalog.VariantRepository` param. `Receive` publishes per restocked item using the quantity it already computes (`entry.Quantity`, post-restock absolute — see "Design decisions").
- `internal/application/inventory/stock_sync_service.go` — new `SetReindexService(*searchApp.ReindexService)`. `UpsertBySKU` collects touched `ProductID`s while building its per-SKU entries and fires one `Trigger(ScopeProducts{...})` after `SetStocks` completes.
- `internal/application/importer/stock.go` — new `WithReindex(*searchApp.ReindexService)` (mirrors the existing `WithRowHooks` builder). Same batch-then-trigger-once shape as `StockSyncService`.
- `cmd/api/integration_wiring.go` — `wireIntegrationStockSyncer`/`wireIntegrationStockSyncerFromDB` now return the constructed `*inventoryApp.StockSyncService` so a caller can wire `SetReindexService` on it later in its own setup sequence (see "Design decisions").
- `cmd/api/wire_services.go` — `reserveInventoryStep` built with `WithStockEventPublishing(repos.variantRepo, bus)`; `returnService` built with the new `variants` param; `stockSyncSvc.SetReindexService(reindexService)` called once `reindexService` exists.
- `cmd/api/main.go` — `setupWorker`'s `ReservationExpiryHandler` registration calls `SetEventPublishing` when `app.Bus != nil`. `runWorker` now constructs its own `*event.Bus` (previously had none at all) and, after `setupWorker` returns a real `jobQueue`, builds a `ReindexService` via new helper `newWorkerReindexService` and wires it into the ERP stock syncer. `runSetup`/`schedule_cli.go`'s stock-syncer wiring discards the returned service (see "Design decisions" for why).
- `cmd/api/io_commands.go` — `import:stock` builds its own `ReindexService` via the existing `newSearchReindexService` helper and calls `WithReindex` on the importer; a construction failure there is logged and the import proceeds without reindex triggering, not aborted.

### Design decisions

- **Checkout's new dependencies are a `ReserveOption`, not required constructor params.** `ReserveInventoryStep` already had a functional-options mechanism (`WithTTL`); adding `WithStockEventPublishing(variants, bus)` to it, rather than widening `NewReserveInventoryStep`'s arity, meant the ~10 existing test call sites across three files (`order_inventory_steps_test.go`, `context_cancel_test.go`, three storefront checkout test files) needed zero changes — only the one real production wiring site (`wire_services.go`) and the new tests that specifically exercise event publishing touch it at all. `variants` and `bus` are set only together (one option sets both), so there's no partial-wiring state to guard against at publish time.
- **`StockUpdatedData.Quantity`'s meaning is genuinely inconsistent across publish sites, and that's accepted, not fixed here.** `InventoryAdminHandler.Adjust` (PR-1036) publishes the post-change *absolute* on-hand quantity, because it already has that value from its own `SetStock` call. Checkout's Reserve/Release and the reservation-expiry sweep publish the reservation's own quantity instead — the size of the *change*, not the resulting total — because getting the absolute total would cost an extra `StockRepository.GetStock` call per item/release that today's sole consumer, `IndexUpdateSubscriber.HandleStockUpdated`, doesn't need: it reads only `ProductID` and schedules a full reindex of that product, which re-fetches the product's real current stock independently. Returns restocking publishes the absolute quantity (`entry.Quantity`), simply because that value is already sitting in a local variable there — not for consistency with the admin path. No call site was made to fetch data solely to normalize this field's semantics; a future consumer that actually needs a precise, consistently-shaped quantity should query current state itself rather than trust this field's shape.
- **`wireIntegrationStockSyncer` now returns the concrete `*inventoryApp.StockSyncService`**, instead of only registering it on the plugin app, so `SetReindexService` can be called on it later — `ReindexService` needs a `jobQueue` that doesn't exist yet at the point the plugin app requires its stock syncer wired (before `registry.InitAll`), in both `serve` (`wireServeRuntime`) and the standalone `worker` process (`runWorker`). This mirrors the exact reordering constraint PR-1036's own retrospective already named for the event bus, one level further: it's not just "no bus yet," it's "no queue yet either."
- **`runWorker` previously had no event bus at all — it now does, for real production reasons, not just to satisfy this PR.** The reservation-expiry sweep this PR wires into events runs in whichever process registers `ReservationExpiryHandler` via `setupWorker` — which includes the standalone `worker` process, a real, commonly-used deployment topology for scaling web and background work independently. Leaving `runWorker` bus-less would have meant this fix only actually worked for the embedded-worker (`serve`, no separate `worker` process) topology.
- **`runSetup` and `schedule:trigger`'s stock-syncer wiring deliberately do not get a `ReindexService`.** Both discard the newly-returned `*inventoryApp.StockSyncService` (`_, err := wireIntegrationStockSyncerFromDB(...)`). `runSetup` is a one-time bootstrap that doesn't process real ERP sync traffic. `schedule:trigger` fires one *named* schedule — any plugin-registered cron task, not specifically ERP sync — and is already documented (RUNBOOK.md) as an expensive, low-frequency, manual-trigger path; its own construction sequence doesn't build a `ReindexService` anywhere else either. Matches PR-1036's own established precedent for exactly this kind of call-site-completeness tradeoff (see ROADMAP.md's "Design notes" for that PR).
- **The CLI `import:stock` command builds its own `ReindexService` via the existing `newSearchReindexService` helper** (already used by `search:reindex`/`search:reindex-runs:reconcile`) rather than plumbing one through `runIOCommand`'s shared scaffold. That helper opens its own DB connection and does its own full plugin bootstrap — a real, but accepted, extra cost for a CLI command that already reads and processes a whole file in one shot; a failure constructing it is logged and the import still proceeds (without reindex triggering), matching this PR's "best-effort, never turn a successful stock write into a reported failure over a stale search index" principle used everywhere else in this PR.
