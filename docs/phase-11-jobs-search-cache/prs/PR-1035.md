# PR-1035 — Reindex Admin API + Progress

Status: planned

## Summary

- `POST /api/v1/admin/search/reindex` to trigger a full, category-scoped, product-scoped, or since-timestamp reindex.
- `GET /api/v1/admin/search/reindex/{runID}` for progress, reusing PR-1028's job-status shape.
- A single explicit ID (one product or one category) skips the queue and indexes synchronously — genuinely "reindex this one now," not "queued, poll for it."

## Why

This is the actual "admin API to trigger a reindex, with a progress endpoint" the phase set out to deliver — everything in PR-1033/1034 exists to make this endpoint meaningful rather than a thin wrapper around a black box.

## Scope

- `internal/interfaces/http/admin/search_admin.go` — `SearchAdminHandler`.
- Request body: `{"scope": "all"}` \| `{"scope": "products", "ids": [...]}` \| `{"scope": "categories", "ids": [...]}` \| `{"scope": "since", "since": "<RFC3339>"}`. Validates `ids` non-empty for `products`/`categories`, `since` parseable and not in the future.
- **Synchronous single-item path:** when `scope=products` or `scope=categories` with exactly one ID, call `SearchEngine.IndexProduct`/`IndexCategory` (PR-1037) directly in the request handler instead of enqueueing — bounded by a short request timeout (a few seconds; single-document indexing is fast), returns `200` with the result inline, not a run ID to poll. This is a deliberate UX distinction from the bulk path: "reindex this one now" should feel instant, not like kicking off a background job you then have to check on.
- **Bulk path** (`all`, multi-ID `products`/`categories`, or `since`): enqueues via `ReindexService.Trigger`, returns `202 Accepted` with `{"run_id": "..."}`.
- `GET /api/v1/admin/search/reindex/{runID}` — returns `search_index_runs` row (status, total/processed/error counts, timestamps). Reuses the same JSON shape conventions as PR-1029's job detail response where the fields overlap (status/counts), for GUI consistency in PR-1038.
- Permissions: new `search.reindex` permission (not reusing `jobs.write` — reindexing is a catalog-adjacent operation an operator might grant separately from general job control).
- Audit log entry per trigger (`ResourceType: "search_reindex"`), recording the requested scope.

## Out Of Scope

- Cancelling an in-progress bulk reindex run — the underlying job follows PR-1029's existing job-cancel semantics (pending-only), so an already-`processing` reindex can't be stopped mid-run in this PR; revisit only if this becomes a real operational pain point.

## Validation (planned — run when implementing)

- `go test ./internal/interfaces/http/admin/... -run SearchAdmin -count=1` — all four scope request shapes, the synchronous-single-item vs enqueued-bulk branch, progress polling against a seeded `search_index_runs` row, permission gating.
- `openapi.yaml` documents both routes and all four scope body shapes.
- `go build ./cmd/api/`
