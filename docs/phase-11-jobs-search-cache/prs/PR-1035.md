# PR-1035 — Reindex Admin API + Progress

Status: done

## Summary

- `POST /api/v1/admin/search/reindex` to trigger a full, category-scoped, product-scoped, or since-timestamp reindex.
- `GET /api/v1/admin/search/reindex/{runID}` for progress.
- A single explicit product ID skips the queue and indexes synchronously — genuinely "reindex this one now," not "queued, poll for it."

## Why

This is the actual "admin API to trigger a reindex, with a progress endpoint" the phase set out to deliver — everything in PR-1033/1034 exists to make this endpoint meaningful rather than a thin wrapper around a black box.

## Scope

- `internal/interfaces/http/admin/search_admin.go` — `SearchAdminHandler`, built on top of `application/search.ReindexService` (bulk, queued path), `domainsearch.RunStore` (progress reads), `domainsearch.ProductSource` and `domainsearch.SearchEngine` (the synchronous single-product path).
- Request body: `{"scope": "all"}` \| `{"scope": "products", "ids": [...]}` \| `{"scope": "categories", "ids": [...]}` \| `{"scope": "since", "since": "<RFC3339>"}`. `ids` required non-empty for `products`/`categories`; `since` required, RFC3339-parseable, and not in the future.
- **Synchronous single-item path:** `scope=products` with exactly one ID fetches that product (`ProductSource.ListByIDs`) and calls `SearchEngine.IndexProduct` directly in the request handler instead of enqueueing, returning `200` with the result inline. See "Design decisions" for why `scope=categories` does **not** get this treatment, even for a single ID.
- **Bulk path** (`all`, multi-ID `products`/`categories`, or `since`, and — per the above — every `categories` request regardless of ID count): enqueues via `ReindexService.Trigger`, returns `202 Accepted` with `{"run_id": "..."}`.
- `GET /api/v1/admin/search/reindex/{runID}` — returns the `search_index_runs` row: `id`, `scope`, `scope_params`, `status`, `total_count`/`processed_count`/`error_count`, `started_at`, and `finished_at`/`last_error` when set.
- New `search.reindex` permission, admin-role-only (not `jobs.write` — reindexing is a catalog-adjacent operation an operator might grant separately from general job control).
- Audit log entry per trigger and per progress read (`ResourceType: "search_reindex"`, actions `search_reindex.trigger`/`search_reindex.read`), recording the requested scope and whether it took the synchronous or queued path.

## Out Of Scope

- Cancelling an in-progress bulk reindex run — the underlying job follows PR-1029's existing job-cancel semantics (pending-only), so an already-`processing` reindex can't be stopped mid-run in this PR; revisit only if this becomes a real operational pain point.
- `scope=categories`'s synchronous single-item path — blocked on PR-1037's `SearchEngine.IndexCategory`, which doesn't exist yet. See "Design decisions."

## Design decisions made during implementation

- **`scope=categories` never takes the synchronous path, even for exactly one ID — deferred to PR-1037.** The original plan described `IndexProduct`/`IndexCategory` symmetrically for the single-item shortcut. `IndexCategory` doesn't exist on `domainsearch.SearchEngine` (only `IndexProduct`/`RemoveProduct`/`Search`/`Suggest` do); adding it is PR-1037's own scope, and a non-trivial one — it also fixes `Product.CategoryID` (singular) → `CategoryIDs []string`, a real behavior change to the indexed document shape, not just a new method signature. Blocking this PR's actual deliverable (the admin API + progress endpoint) on that independent, still-planned PR would have been the wrong trade — instead, every `scope=categories` request goes through the queued bulk path (`ReindexService.Trigger(ScopeCategories{...})`), which already works correctly today: it resolves the category to product IDs via `ProductSource.ProductIDsByCategory` and indexes those products through the existing `IndexProduct`-based `ReindexHandler`. A single category ID just means a queued run with one (or a few) product IDs in it — slower than the "instant" UX the synchronous path gives products, but correct, and no dependency on PR-1037. Revisit once PR-1037 ships.
- **The single-product synchronous path re-fetches the product via `ProductSource.ListByIDs`, not through `catalog.ProductRepository`.** Same catalog-decoupling boundary `ReindexHandler`/`ReindexService` already keep (see PR-1033/1034's own notes on this) — the admin HTTP layer for search stays on the same narrow `domainsearch.ProductSource` port the bulk reindex path uses, rather than introducing a second product-lookup dependency with a different field set. This also means the synchronously-indexed document has exactly the same fields (`id`, `name`, `slug`, `description`, `attributes`, `created_at`) a bulk run would have indexed for it — no behavioral difference between "reindexed via a queued run" and "reindexed via the single-item shortcut" beyond timing.
- **A malformed product ID on the single-item path is rejected before any DB call**, via `platform/id.IsValid` — the same UUID-shape check `ReindexService`'s own `normalizeProductIDs` applies on the bulk path (PR-1034), duplicated here specifically because the synchronous path calls `ProductSource.ListByIDs` directly and bypasses `ReindexService`/`normalizeProductIDs` entirely. Without it, a bad ID would surface as a raw Postgres `invalid input syntax for type uuid` error, reported as a `500`, instead of a clean `422` validation error. Category IDs get no such check (`categories.id` is plain `TEXT`), matching `normalizeCategoryIDs`' own asymmetry.
- **`GET /reindex/{runID}` reads `RunStore.Get` directly, not through `ReindexService`.** `ReindexService` has no read method — it only ever creates and enqueues (`Trigger`) — so `SearchAdminHandler` takes `domainsearch.RunStore` as its own dependency, the same store instance `ReindexService` was constructed with. Simpler than adding a pass-through `Get` method to `ReindexService` for a single caller.
- **No new named response schema in `openapi.yaml`.** The response shape (`run_id` on `202`, the run detail fields on `GET`) is small enough, and specific enough to these two endpoints, that an inline schema in each response was clearer than a shared named component only these two paths would ever reference.

## Round 1 (code review)

- **Major — fixed.** A multi-ID `scope=products` request with a malformed UUID (e.g. `["not-a-uuid","also-bad"]`) returned `500 internal server error` instead of `422`. The single-ID path validates with `id.IsValid` before dispatch, but the multi-ID path skipped that check and let `ReindexService.Trigger` → `resolveScope` → `normalizeProductIDs` reject it deep inside the service — and `normalizeProductIDs`/`resolveScope`'s own validation branches returned plain `fmt.Errorf` values, not typed errors, so `triggerBulk` had no way to tell a caller mistake from a genuine internal failure and force-wrapped every `Trigger` error as `apperror.CodeInternal`. Fixed by having `normalizeProductIDs`, `normalizeCategoryIDs`, and `resolveScope`'s own "at least one id is required"/"a non-zero timestamp is required" checks return `apperror.Validation(...)` (already the established pattern in this same package — `reindex_reconcile.go`, PR-1048, already returns `apperror.NotFound`/`apperror.Conflict` directly), and changing `triggerBulk` to forward `Trigger`'s error straight to `JSONError` instead of re-wrapping it — the same pattern `JobAdminHandler.Retry`/`Cancel` already use for a service that can return either a typed or a generic error. `JSONError`'s own `errors.As` unwrapping (already used by the rest of this codebase) now correctly resolves a validation failure to `422` and everything else to `500`, regardless of how many `fmt.Errorf("...: %w", ...)` layers wrap it on the way up. New test: `TestSearchAdminHandler_Trigger_ScopeProducts_MultipleIDs_InvalidUUID_Rejected` — confirmed to fail against the pre-fix code (`500`) and pass against the fix.
- **Minor — reviewed, not changed.** The claim that request bodies have no size guard is inaccurate: `cmd/api/wire_routes.go` already applies `shophttp.BodyLimitMiddleware` globally to every body-bearing route, `/admin/search/reindex` included — the same default cap every other admin write endpoint in this codebase relies on (only a few, e.g. media uploads, override it with a different limit). No change needed here.
- **Minor — fixed.** Added an explicit `maxReindexRequestIDs` (10,000) cap on the incoming `ids` array, checked in `cleanIDs` before any per-ID validation loop runs — cheaper defense-in-depth than relying solely on the global body-size limit (which bounds total bytes, not array length) or on `ReindexService`'s own `maxScopedReindexProductIDs` (which only applies after normalization/resolution). New test: `TestSearchAdminHandler_Trigger_ScopeProducts_TooManyIDs_Rejected`.
- **Minor — addressed as a side effect of the Major fix, not separately.** The review noted validation logic was split across `cleanIDs` (handler, blank-check only) and `normalizeProductIDs`/`normalizeCategoryIDs` (service, blank+UUID-shape+dedup), with UUID-shape checking only happening on the single-ID handler shortcut — "exactly what produced the [500-vs-422] bug." That specific consequence (a validation failure surfacing as 500) is what the Major fix resolves; the duplication itself (both layers blank-checking) is retained deliberately — `cleanIDs` needs a clean, non-blank list before it can decide whether to take the single-ID synchronous path at all, so some trimming has to happen in the handler regardless of what the service re-validates.
- Additional test beyond the review's own ask: `TestSearchAdminHandler_Trigger_ScopeProducts_SingleID_ListByIDsError`, exercising `triggerSingleProduct`'s DB-failure branch (previously untested — only the not-found and invalid-UUID branches had coverage).

## Round 2 (code review)

- **Major — fixed.** `triggerSingleProduct` passed `r.Context()` directly to both `ProductSource.ListByIDs` and `SearchEngine.IndexProduct`. `r.Context()` is only cancelled by client disconnect or server shutdown — a slow Postgres query or a stalled search engine could hold the request (and a DB connection) open indefinitely, directly contradicting the synchronous path's own promise of feeling "instant." Added `singleProductIndexTimeout` (5s) and derive `ctx, cancel := context.WithTimeout(r.Context(), singleProductIndexTimeout)` at the top of `triggerSingleProduct`, passed to both calls. New test: `TestSearchAdminHandler_Trigger_ScopeProducts_SingleID_BoundedContext`, asserting both fakes receive a context with a deadline — confirmed to fail against the pre-fix code (no deadline on either call) and pass against the fix.
- **Major — fixed.** `Trigger` decoded only the first JSON value (`dec.Decode(&req)`) without requiring the body be exhausted — `json.Decoder.Decode` reads exactly one value and silently leaves anything after it unread, so a body like `{"scope":"all"}{"scope":"products"}` decoded the first object successfully and went on to enqueue a real reindex, silently discarding (with no record) whatever malformed content followed. Added `requireSingleJSONValue`, decoding into a throwaway `json.RawMessage` and requiring `io.EOF`; called right after the first `Decode` succeeds. New test: `TestSearchAdminHandler_Trigger_TrailingJSONValue_Rejected` — confirmed to fail against the pre-fix code (`202`, a real run enqueued) and pass against the fix (`422`).
- **Minor — fixed.** Every validation rejection in `Trigger` (malformed JSON, unknown scope, empty/invalid ids, a bad `since`) previously produced **no audit entry at all** — only a request that passed every check ever reached `triggerBulk`/`triggerSingleProduct`, the only two places that called `h.audit`. Refactored `Trigger` around a local `reject` closure that both audits (`AuditSearchReindexTrigger`, `Result: "error"`) and responds for every rejection branch; `triggerBulk`/`triggerSingleProduct` are untouched, and since a request either gets rejected by `Trigger` itself or reaches one of those two (never both), this produces exactly one audit entry per request, not a duplicate. New test: `TestSearchAdminHandler_Trigger_RejectedRequest_IsAudited` (using a `fakeAuditLogRepository` attached via `Auditor.SetAuditLogRepository` to inspect persisted records) — confirmed to fail against the pre-fix code (0 records) and pass against the fix (1 record).
- **Documentation — fixed.** `docs/guides/MERCHANT.md`'s "Reindexing the catalog" section conflated two different 10,000-ID limits: the new request-shape cap (`maxReindexRequestIDs`, Round 1 — an oversized raw `ids` array is rejected outright with `422`) and the pre-existing resolved-scope full-scan substitution (`ReindexService`'s `maxScopedReindexProductIDs` — a large *resolved* ID list silently runs as a full scan instead). Reworded to describe both, distinctly. Also added `maxItems: 10000` to `openapi.yaml`'s `ids` schema so clients can pre-validate the same limit client-side, with a description distinguishing it from the full-scan heuristic.
- **Suggestion — reviewed, not changed.** The review asked for concrete named response schemas (`data.status`/`data.product_id` on the sync `200`, `data.run_id` on the `202`, and the full run shape with nullable/optional `finished_at`/`last_error` on `GET`) instead of `Envelope` + inline examples. Every other endpoint in this ~2,000-line spec documents its response the same way this PR already does — `$ref: Envelope` plus an `example:` block, no typed `data` schema anywhere — so adding named schemas only here would reduce consistency with the rest of the file, not improve it (a decision already recorded in "Design decisions" above, under "No new named response schema"). Left as-is; a repo-wide move to typed response schemas is out of scope for a review-response commit on one PR.

## Round 3 (code review)

- **Major — fixed.** Round 2's `singleProductIndexTimeout` fix bounded `ListByIDs`/`IndexProduct`, but `audit` — called at the end of every `triggerSingleProduct` branch, success or failure — still logged via `h.auditor.LogAction(r.Context(), ...)` unconditionally, and `LogAction` synchronously persists to `AuditLogRepository.Insert` using that same context. A slow audit-log write (its own Postgres insert, independent of the reindex work already completed) could therefore still hold the "supposedly bounded" single-product request open past its 5-second deadline, defeating the point of Round 2's fix and continuing to retain the request goroutine and a DB connection. Changed `audit`'s signature to take an explicit `ctx context.Context` parameter (previously it always derived one internally from `r.Context()`); `triggerSingleProduct`'s three call sites now pass the same `singleProductIndexTimeout`-bounded `ctx` its `ListByIDs`/`IndexProduct` calls already use, so the audit write shares the same deadline instead of getting an unbounded one of its own. Every other call site (`Trigger`'s `reject`, `triggerBulk`, `Get`) still passes `r.Context()` — unchanged, since only the synchronous single-item path makes a bounded-latency promise. If the shared deadline is already exhausted by the time `audit` runs, the insert fails fast with a context error instead of blocking — a strictly better outcome than before, and consistent with `Auditor`'s own documented "best-effort persistence" contract (the action is still logged via the logger regardless, synchronously and without a context dependency). New test: `TestSearchAdminHandler_Trigger_ScopeProducts_SingleID_AuditUsesBoundedContext`, asserting the audit repository's `Insert` receives a context with a deadline — confirmed to fail against the pre-fix code (no deadline) and pass against the fix.
