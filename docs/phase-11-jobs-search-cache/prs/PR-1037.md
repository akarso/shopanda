# PR-1037 — Category Indexing + Relationship Fix

Status: done

## Summary

- Add `IndexCategory`/`RemoveCategory` to the `SearchEngine` port (both Postgres and Meilisearch implementations); index categories as their own searchable/filterable entity.
- Fix `search.Product.CategoryID` (singular) → `CategoryIDs []string` — the catalog domain already supports many-to-many product↔category assignment; the search index has never been able to represent that correctly.

## Why

Two related, previously-unaddressed gaps:

1. **The relationship fix is a correctness bug, not a feature request.** `internal/domain/catalog`'s `ProductRepo` already has `AssignCategory`/`RemoveCategory`/`ListCategoryIDsByProduct` — a product can belong to multiple categories today, and that's used elsewhere (category listing pages, admin category assignment UI). The search index silently drops every category assignment past the first for any multi-category product, which means category-filtered search results have been wrong for every such product since the search feature shipped. **As implemented:** this only ever bit the Meilisearch backend — the Postgres `SearchEngine` never stored category data on the indexed product document at all (see "Retrospective" below), so Postgres-backed deployments were never actually affected by this bug in practice, even though the fix (the domain type becoming `CategoryIDs []string`) still applies to both backends.
2. **Categories themselves aren't indexed.** There's no way to search for a category by name/description, and no way to build a "browse categories" search-backed feature — everything category-related today goes through direct Postgres queries against `internal/domain/catalog`'s category repo, not through `SearchEngine`.

## Scope

- `internal/domain/search/search.go`: `Product.CategoryID string` → `Product.CategoryIDs []string`. This is a breaking change to the `Product` struct — every caller that builds a `search.Product` (the reindex loop, PR-1035's synchronous single-item path, PR-1036's event-triggered path) and every caller that reads `CategoryID` off a search result needs updating in the same PR, not left half-migrated.
- New `search.Category{ID, Name, Slug, Description, ParentID string, ProductCount int}` type, `SearchEngine.IndexCategory(ctx, c Category) error` / `RemoveCategory(ctx, categoryID string) error`.
- Postgres implementation: category documents live in the same full-text-search infrastructure as products (separate table/tsvector column, or a `doc_type` discriminator column on a shared table — decide based on whether the existing Postgres search schema is more naturally extended or duplicated; document the choice). **As implemented:** a `search_vector` column on `categories` itself (migration `072_add_categories_search_vector.sql`) — net-new storage, not a data migration, since Postgres never had a `category_id`/`category_ids` column on the product document to change.
- Meilisearch implementation: a separate index (`categories`, alongside the existing `products` index).
- **Migration for existing indexed data:** a data migration path for the `CategoryID` → `CategoryIDs` schema change on the Postgres search backend (column type change + backfill from `product_categories`), and a note that Meilisearch-backed deployments need a one-time full reindex after this PR ships (schema of the indexed document changed) — call this out explicitly as a deployment step, not just a code change. **As implemented:** the Postgres column-type-change-and-backfill described here is **not applicable** — there was no such column to begin with (see above); only the Meilisearch full-reindex note applies, and is documented in `docs/guides/DEPLOYMENT.md`'s "Search Index Maintenance" section. Standard migrations (including `072`, needed for Postgres category-document indexing) still run for every deployment via the normal `shopanda migrate` step, unrelated to this bullet's now-inapplicable rename backfill.
- Wire category create/update/delete (admin API) to call `IndexCategory`/`RemoveCategory`, and to PR-1036's event subscriber pattern for on-save category indexing.

## Out Of Scope

- Faceted search UI changes on the storefront to actually surface multi-category filtering — this PR fixes the index's ability to represent the relationship correctly; consuming that correctly in storefront search UI is a separate, storefront-facing PR if/when there's a concrete need (this phase is about admin reachability and index correctness, not new storefront search UX).
- Indexing CMS pages or other content types (see ROADMAP's "Design notes" — deliberately deferred).

## Validation (planned — run when implementing)

- `go test ./internal/domain/search/... ./internal/infrastructure/postgres/... ./internal/infrastructure/meili/... -count=1` — a product assigned to 3 categories round-trips correctly through index/search; category CRUD indexes/removes correctly.
- Migration test: seed a product with multiple category assignments under the old single-`CategoryID` schema, run the migration, confirm `CategoryIDs` reflects the full assignment set from `product_categories`, not just whatever the old single column happened to hold. **As implemented: not applicable** — there was no old `CategoryID`/`category_id` column on the Postgres side to seed data under or migrate (see "Scope" above); the actual Postgres-side test coverage added instead (`TestSearchProductSource_ListAll_PopulatesCategoryIDs`) verifies the real behavior change — `CategoryIDs` correctly reflecting all of a product's `product_categories` assignments when read for indexing, regardless of engine.
- `go build ./...`

## Follow-up

- PR-1038 — GUI reindex-trigger row action extends to categories, not just products.
- `internal/interfaces/http/admin/search_admin.go`'s `scope=categories` path still always goes through the queued/bulk `ReindexService.Trigger`, even for a single explicit category ID — unlike `scope=products`, which shortcuts a single ID to a synchronous `IndexProduct` call. Wiring the same shortcut to `IndexCategory` (which now exists) wasn't in this PR's own Scope and would have added constructor-signature churn to `SearchAdminHandler` for a convenience path, not a correctness fix — left as an easy follow-up, not bundled in opportunistically. See `ROADMAP.md`'s "Design notes: PR-1035 shipped ahead of PR-1037".
- `meili.Engine.IndexProduct`/`RemoveProduct`/`IndexCategory`/`RemoveCategory` all return success as soon as Meilisearch accepts the HTTP submission, without waiting for or checking the resulting async task's outcome (unlike `New()`'s own index-configuration calls, which do `waitForTask`). This predates PR-1037 for the product side; `IndexCategory`/`RemoveCategory` were written to match it for consistency. Worth revisiting for all four together — it would make PR-1037's category retry mechanism (and any future product-side retry) actually catch async-task-level failures, not just HTTP-level ones — but changes real indexing latency/behavior and deserves its own PR, not a drive-by fix to only the newer two methods.

## Retrospective

### Design decisions

- **The relationship bug only ever affected Meilisearch.** Investigating before writing any code found that the Postgres `SearchEngine` never stored category data on the indexed product document at all — `IndexProduct`/`RemoveProduct` only ever touch `products.search_vector` (name/description), and `Search()`'s category filtering/faceting is a live `JOIN` against `product_categories`/`categories`. So `Product.CategoryID`'s single-value limitation was real, but concentrated entirely in the Meilisearch adapter (which stores category data directly on the product document and filters against it). This didn't change the fix (the domain type still needed to become `CategoryIDs []string`, correctly populated for whichever engine is configured) but it did change the migration story below.
- **No Postgres data migration for the rename** — because there was no persisted `category_id` column to migrate on that side (see above), PR-1037.md's originally planned "migration test" (seed under the old schema, migrate, verify) doesn't apply there. The only new Postgres schema change is migration `072_add_categories_search_vector.sql`, which is net-new category-document storage (a `search_vector` column + GIN index + trigger on `categories`, mirroring `016_add_search_vector.sql`'s pattern for `products`), not a backfill.
- **Category documents live in the `categories` table itself** (a new `search_vector` column), not a separate table or a `doc_type` discriminator on a shared table — categories already have their own table and there's exactly one non-product entity type to support, so a discriminator column would add complexity with no present benefit.
- **Meilisearch gets a second index** (`categories`, config key `search.meilisearch.categories_index`, default `"categories"`), configured with its own settings (`SearchableAttributes: name/slug/description`, `FilterableAttributes: parent_id`, `SortableAttributes: name/product_count`). `meili.Engine` now holds a second `meiliAPI` client/index pair internally.
- **The product-document field renamed `category_id` → `category_ids`** (a JSON array) in the Meilisearch document, not left as `category_id` for backward compatibility — this is exactly the field this PR fixes, and Meilisearch's `=` filter operator matches membership against an array attribute the same way it matches a scalar, so `category_ids = "cat-1"` works unchanged as a filter. The storefront facet-merging code (`internal/interfaces/http/storefront/storefront.go`'s `storefrontCategoryFilterGroup`) and the reserved-facet-key set (`internal/domain/search/facets.go`) were updated to match.
- **A new narrow `domainsearch.CategorySource` port** (mirroring the existing `ProductSource`), implemented by `postgres.SearchCategorySource`, fetches fresh category data (including a live-computed `ProductCount`) for `IndexUpdateSubscriber` — keeping `search` decoupled from `catalog.CategoryRepository`, the same principle enforced throughout this track.
- **A category document is indexed via a direct `SearchEngine.IndexCategory`/`RemoveCategory` call**, not through `ReindexService`/the job queue — `ScopeCategories` only ever resolves to member *product* IDs, never to the category document itself, so there's no existing scope/path to reuse. `IndexUpdateSubscriber` gained `HandleCategoryCreated`/`HandleCategoryUpdated`/`HandleCategoryDeleted`, wired to the category admin API's already-published `EventCategoryCreated`/`Updated`/`Deleted`.
- **No debounce for category events**, unlike PR-1036's per-product debounce — category writes go through a single synchronous admin request each, not a bulk-import path, so there's no burst to coalesce. Create/Update re-read the category's current state (`CategorySource.GetByID`) rather than trusting the event payload, so the indexed document always reflects the latest state even under rapid successive edits; Delete calls `RemoveCategory` directly since there's nothing left to read.
- **`catalog.Category` was not given a `Description` field** to populate `search.Category.Description` — that's a separate, unscoped catalog schema change. `search.Category.Description` is currently always empty; the field exists on the type so a future catalog change is additive, not another breaking rename.
- **The single-category synchronous admin-API shortcut was deliberately not added** (see Follow-up) — not in this PR's own Scope, and PR-1035.md's own prior deferral note only mentioned it informally.

### Code review fixes (round 1)

- **Blocker, confirmed partially valid — `Category.ProductCount` never refreshed on assignment change.** `CategoryProductAssignmentAdminHandler.Assign`/`Unassign` (PR-1036) already publish `catalog.EventProductUpdated`, which does correctly refresh the affected product's `CategoryIDs` through the existing on-save subscriber + this PR's `SearchProductSource` fix — so the review's headline claim ("`Product.CategoryIDs` ... never refreshed ... only a fresh reindex or an incidental product edit surfaces the fix") did not hold against current code. The category-count half did: neither `Assign` nor `Unassign` published anything category-side, so `ProductCount` only ever refreshed on the category's own next create/update. Fixed by also publishing `catalog.EventCategoryUpdated` (category's own current Name/Slug, empty `OldSlug`) alongside the existing product event — reuses `IndexUpdateSubscriber.HandleCategoryUpdated` and `PublishAsync`'s existing sync-failure fallback, no new dependencies.
- **Major, confirmed — category indexing had no durability/retry path.** `HandleCategoryCreated/Updated/Deleted` called `SearchEngine.IndexCategory`/`RemoveCategory` directly from a bare `bus.OnAsync` handler; per `event.Bus.Publish`, an async handler's error is only logged, never retried. Fixed with a small bounded in-process retry (`categoryIndexMaxAttempts` attempts, doubling backoff from `categoryIndexRetryBaseDelay`, aborting early on context cancellation) around both engine calls — absorbs a transient failure without needing job-queue infrastructure; a truly persistent failure still ultimately drops the update (recoverable via the category's next edit or a manual/full reindex), same trade-off as before, just a narrower window for it.
- **Major, confirmed — no test exercised assign/unassign → search-visible state.** Added `TestCategoryProductAssignmentAdminHandler_{Assign,Unassign}_EmitsCategoryUpdatedEvent` (asserts the new category event fires with the right payload) and `TestIndexUpdateSubscriber_HandleCategoryCreated_RetriesTransientFailure` (asserts the retry wiring, not just the retry helper in isolation) plus focused `retryCategoryEngineCall` unit tests.
- **Minor, confirmed — `ProductCount` doesn't aggregate child categories.** Documented explicitly as a decision (not a gap) on `search.Category.ProductCount` and `SearchCategorySource.GetByID`: it counts only directly-assigned products, matching how `product_categories` assignment already works.
- **Minor, skipped — no test for `meili.New()` failing on the second (categories) index setup.** Low value given the symmetric, already-tested error-handling shape of the first (products) index setup in the same function; not adding test surface for a straightforward, unchanged failure path.
- **Minor, skipped — `search_admin.go`'s `scope=categories` still bulk-only for a single ID.** Already an explicitly documented, deliberate follow-up (see this doc's own "Follow-up" section and `ROADMAP.md`'s "Design notes"), not a new finding — no action beyond what's already tracked there.

### Code review fixes (round 3)

- **Confirmed — Update/Delete race could resurrect a deleted category.** `HandleCategoryUpdated` and `HandleCategoryDeleted` are two independent async event handlers with no ordering guarantee between them. Before this fix, an Update handler whose `CategorySource.GetByID` read ran before a concurrent Delete actually removed the category could still push that now-stale data to `IndexCategory` *after* the Delete handler's `RemoveCategory` had already run — permanently resurrecting a deleted category as searchable (nothing else would ever remove it again, since deleting it already happened). Fixed with a per-category `sync.Mutex` (lazily created via a `sync.Map`, keyed by category ID) held across both `indexCategory`'s `{GetByID read, engine call}` and `HandleCategoryDeleted`'s engine call — whichever of the two starts first now fully completes (including its live read) before the other begins, so the last one to run always determines the correct final state: a `RemoveCategory` that runs after a racing `IndexCategory` still correctly clears it, and an `IndexCategory` that runs after a racing `RemoveCategory` re-reads live state and correctly no-ops (`found=false`). New test `TestIndexUpdateSubscriber_HandleCategoryUpdatedAndDeleted_SerializedNoResurrection` deterministically forces the race (pauses `IndexCategory` mid-flight via a blocking fake engine, starts `HandleCategoryDeleted` concurrently, asserts it cannot complete until the lock is released) — confirmed to fail against the pre-fix code (`HandleCategoryDeleted` completed while `HandleCategoryUpdated` was still in `IndexCategory`) and pass against the fix.
- **Confirmed — C4 diagrams left stale.** `docs/diagrams/c4-component.md`'s `Rel(coreMeilisearch, meilisearch, "Indexes and queries products", "HTTP")` no longer fully described the relationship once this PR added a second (categories) Meilisearch index — corrected to `"Indexes/queries products; indexes categories in a second index"`. The new `SearchCategorySource` component and the category-handling additions to `IndexUpdateSubscriber` were deliberately **not** added as new diagram boxes: this diagram has never modeled event-subscriber-shaped components at all — `application/cache.InvalidationSubscriber` and `application/rewrite.Subscriber` are equally absent, and PR-1036 itself (which introduced `IndexUpdateSubscriber`) never added it either. Adding only PR-1037's slice of that already-undiagrammed subsystem would create a new, arbitrary inconsistency rather than fix one; representing it properly is a pre-existing gap spanning at least PR-1036 and this PR, better addressed as one deliberate pass across all three subscribers than opportunistically half-done here.

### Code review fixes (round 4)

- **Confirmed — `DEPLOYMENT.md`'s "nothing to migrate" wording was ambiguous.** Could be misread as "no migrations at all for Postgres," when the actual claim is narrower: no product-document backfill/full-reindex for the `category_id`→`category_ids` rename specifically. Standard migrations (including `072_add_categories_search_vector.sql`) still apply to every deployment via the normal `shopanda migrate` step regardless of `search.engine` — reworded to state both halves explicitly.
- **Confirmed — the original spec's Why/Scope/Validation sections read as if a Postgres migration/backfill/migration-test had been implemented.** Annotated each with "**As implemented:**" notes pointing at the actual Postgres-vs-Meilisearch finding, without deleting the original planned text — matches this doc's own established convention of treating the top-level sections as the historical plan and layering findings on top, rather than rewriting history.
- **Confirmed — the Validation section's `<touched packages>` was a placeholder, not the actual command.** Replaced with the exact `go test`/`go build`/`go vet`/`gofmt` invocations run, the exact Docker/`SHOPANDA_TEST_DSN` setup, and an explicit split between the default suite (green, no unrelated failures — those tests skip without a DSN) and the unfiltered Postgres integration run (where the two pre-existing, unrelated failures appear).
- **Confirmed — `meili.New()` silently accepted `CategoriesIndex == Index`.** Both indexes would collide onto the same physical Meilisearch index, and the categories `updateSettings` call (running second) would silently overwrite the product index's `FilterableAttributes`/`SearchableAttributes`, breaking product search with no startup error. Fixed with an equality check alongside the existing empty-index checks; new `TestNew_Validation` table test covers all four `New()` config-validation branches (confirmed to fail — falls through to a real network dial — against the pre-fix code).
- **Confirmed — `New()`'s two sequential index-setup steps shared one 10-second context.** A slow product-index `updateSettings`/`waitForTask` round trip could leave little to no budget for the categories step, causing a spurious startup failure unrelated to the categories index itself. Fixed with a second, independent `context.WithTimeout(..., httpTimeout)` created after the product step completes, so each step gets its own full budget.
- **Not valid anymore — `indexCategory`'s retry callback reuses the value from a single `GetByID` call across all retry attempts, instead of re-reading (or falling back to `RemoveCategory`) on each attempt.** True as stated, but round 3's per-category lock already closes the specific failure mode this describes (a deleted category getting resurrected): `indexCategory` holds that lock for its *entire* call, including every retry attempt, so a concurrent `HandleCategoryDeleted` for the same category cannot run until `indexCategory` (successful or not) has fully finished and released the lock — meaning `RemoveCategory` can never land before `IndexCategory` for the same category, only strictly after, and a `RemoveCategory` that runs after an `IndexCategory` using slightly-stale-but-then-still-current data still correctly clears it. Re-fetching per attempt would only avoid writing that already-corrected-a-moment-later staleness — not fix a persistent-state bug, since none remains. Implementing it anyway would be redundant belt-and-suspenders on top of an already-sufficient fix. No change made.
- **Legitimate but out of scope — `IndexCategory`/`RemoveCategory` don't wait for/check the Meilisearch async task's outcome, only the HTTP submit.** True, and it does mean this PR's new retry mechanism only catches HTTP-level failures, not deeper async-task failures (a malformed document rejected during processing, etc.). But this is a pre-existing pattern shared identically by `IndexProduct`/`RemoveProduct` (unchanged by this PR) — `IndexCategory`/`RemoveCategory` were deliberately written to mirror that exact shape. Fixing only the category side would create a new inconsistency between the two; fixing both would add a real latency/behavior change to already-live, unrelated product-indexing calls (blocking on `waitForTask`'s polling, up to `httpTimeout`) — a meaningful decision deserving its own PR and review, not a drive-by bundled into this one. Flagged as a follow-up below.

### Code review fixes (round 5)

- **Confirmed — round 3's per-category lock was process-local, not distributed.** `categoryLocks sync.Map` (a `*sync.Mutex` per category ID) only provides mutual exclusion between goroutines within *one* API server process. In a horizontally-scaled deployment, an Update event for a category handled by instance A and a Delete for the same category handled by instance B each get their own independent, unrelated mutex — no protection between them at all. This is exactly the resurrection scenario round 3 fixed for a single process, still fully open across instances, and unlike the accepted per-process debounce trade-off (documented on `productReindexDebounceWindow`, worst case "a few extra reindex jobs" — self-healing, low severity), this one produces a *permanent* wrong state, which is a materially different severity and worth an actual fix rather than a documented trade-off.
- Fixed with a new `domainsearch.CategoryLock` port (`internal/domain/search/reindex.go`) and a Postgres implementation, `postgres.AdvisoryLock` (`internal/infrastructure/postgres/category_lock.go`), using `pg_advisory_xact_lock(hashtextextended(key, 0))` inside a dedicated transaction per `Lock` call — transaction-scoped (not session-scoped) specifically to avoid the classic "acquired on one pooled connection, released from another" advisory-lock pitfall with `database/sql`: a transaction pins one physical connection for its duration, and the lock releases automatically on commit (what the returned `unlock` does). This is visible to, and mutually exclusive across, every connection to the same database — i.e. every API server instance — not just goroutines in one process.
- `IndexUpdateSubscriber`'s old in-process `categoryLocks`/`lockCategory` are gone entirely, replaced by the new `categoryLock domainsearch.CategoryLock` dependency (`NewIndexUpdateSubscriber` gained a required parameter, nil-checked like the others). `indexCategory`/`HandleCategoryDeleted` now call `s.categoryLock.Lock(ctx, categoryID)`, which can itself fail (e.g. DB unavailable) — handled by returning an error rather than proceeding unlocked.
- New `postgres.AdvisoryLock` integration test (`category_lock_test.go`) proves cross-connection serialization specifically — the whole point this round exists to fix — using *two independent* `*sql.DB` pools against the same test database (standing in for two API server instances), asserting a `Lock` on one pool genuinely blocks a `Lock` for the same key on the other until the first unlocks; a second test confirms different keys don't serialize against each other. Revert-tested: swapping the real `pg_advisory_xact_lock` call for a no-op makes the serialization test fail, confirming it actually exercises the lock.
- Round 3's own `TestIndexUpdateSubscriber_HandleCategoryUpdatedAndDeleted_SerializedNoResurrection` (an in-process fake-lock test) still holds real value post-fix: it verifies `IndexUpdateSubscriber` calls and holds the `CategoryLock` port correctly (across the right critical section, for the right duration) independent of which concrete lock implementation is plugged in — kept, now running against a `fakeInternalCategoryLock`/`fakeCategoryLock` implementing the new port instead of exercising the subscriber's own removed mutex map directly.
