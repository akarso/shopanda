# PR-1044 — Full-Page Cache Core + Cacheability Policy

Status: planned

## Summary

- Cache fully-rendered storefront HTML (post-`html/template` execution) in the `cache.Cache` backend, keyed by route template + a deliberately coarse vary key.
- A hard, fail-closed cacheability policy: an explicit allowlist of cacheable route templates, checked on top of (not instead of) a denylist — a new route defaults to **uncached** until someone deliberately adds it to the allowlist.

## Why

This is the actual "full-page cache" deliverable — and the one PR in this phase where a design mistake has the worst possible failure mode: serving one shopper's private data (cart contents, account details, a CSRF token) to a different shopper. Every decision below is made with that failure mode as the thing to design against, not just "make it fast."

## Scope

**Cache key:** `route_template + vary`, where `vary = {store, language, currency, auth_state}`.
- `auth_state` is `guest` or `authenticated` — **never** a session ID or customer ID. This is the single most important constraint in this PR: varying by anything customer-identifying defeats the entire purpose of the cache (key space explosion, ~0% hit rate reuse) and is *also* exactly how you'd accidentally build a per-customer cache that then gets served to the wrong customer if the key derivation has any bug. Personalized content never lives in the cached body at all — it's always a fragment (PR-1045).

**Cacheable (allowlist, route template, not path — matches how metrics already bucket routes in Phase 10):**
- PDP (`/products/{slug}`)
- PLP / category listing (`/categories/{slug}`, search results pages)
- CMS pages
- Home page

**Never cached — enforced by two independent mechanisms, not one:**
1. The allowlist above is checked first — anything not on it is never cached, full stop, regardless of what the denylist says. This is the fail-closed backstop: a new route added to the storefront router with no cache-policy decision made yet is uncached by default.
2. An explicit denylist double-check on the allowlisted set itself, for routes that *look* cacheable by template but carry response-specific state — e.g. a PDP response that happens to include real-time stock-out messaging tied to reservation state needs to either exclude that fragment (PR-1045) or be pulled off the allowlist; this check exists so "PDP is allowlisted" doesn't become "therefore never re-examined."
- Cart, mini-cart, checkout (every step), account pages, order history/detail, admin — **structurally excluded**: these route groups are never on the allowlist, and their handlers are in separate packages (`interfaces/http/storefront` cart/checkout/account handlers vs. the cacheable PDP/PLP/CMS handlers) from Phase 10's HTTP package split, so there's an existing package boundary to lean on, not just a runtime check.
- **CSRF tokens never enter cached HTML.** A CSRF token baked into a cached page is served identically to every visitor who hits the cache — either breaking legitimate submissions (token mismatch) or, worse, becoming a predictable/shared token. The cached page renders a placeholder; the real token is a PR-1045 fragment, full stop, non-negotiable for any allowlisted route that contains a form.

**Tagging:** every cached entry is written via `SetWithTags` (PR-1039), tagged with the IDs of everything it rendered — a PDP is tagged with its product ID (and its category IDs, since breadcrumbs/related-category data render into the page); a PLP is tagged with its category ID and every product ID on that page; a CMS page is tagged with its own block ID and any product/category IDs it references. This is what makes PR-1046's invalidation precise instead of "clear everything on any change."

**TTL:** a safety-net TTL even with tag invalidation wired (defense in depth — if an event is ever missed, PR-1039's `DeleteByTag`/PR-1046's subscriber has a bug, or a plugin mutates data through a path that doesn't publish the right event, a bounded TTL caps the damage). Default a few minutes, configurable per route template.

**Response headers:** cached responses get `Cache-Control: public, max-age=<remaining TTL>` (extending, not replacing, the existing `CacheControlMiddleware` header-setting logic from Phase 10) plus an internal `X-Shopanda-Cache: HIT|MISS` header for debugging (stripped or gated behind dev-mode in production — this is diagnostic, not something to expose to every client by default).

## Out Of Scope

- The fragment/hole mechanism for personalized content within an otherwise-cacheable page — PR-1045.
- Invalidation wiring (events → `DeleteByTag`) and the stampede guard — PR-1046.
- Admin/observability — PR-1047.
- Any change to admin pages' cacheability — admin is never on the allowlist and stays that way; not revisited by this phase (matches the user's own instinct that admin shouldn't be cached).

## Validation (planned — run when implementing)

- `go test ./internal/interfaces/http/storefront/... -run FullPageCache -count=1` — allowlist enforcement (a route not on the allowlist is never cached even if it superficially resembles a cacheable one), vary-key correctness (two requests differing only in store/language/currency/auth-state get distinct cache entries; two requests differing only in session/customer ID with identical store/language/currency/auth-state hit the *same* entry, which is the point), CSRF token never appears in a cached body (grep the cached bytes for the token pattern in the test).
- **Security-focused test explicitly modeling the failure mode this PR exists to prevent:** two simulated "different customers," both `guest`, hit the same cacheable PDP — assert the served bytes are byte-identical and contain no customer-identifying data; then one authenticates and the other doesn't — assert they now get different cache entries only if `auth_state` actually changes the rendered content (if it doesn't, document why `auth_state` is still part of the key regardless, as a conservative default).
- `go build ./...`
