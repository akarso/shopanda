Status: done

## Summary

- Reindex trigger screen: scope picker (all / products / categories / since-date), progress bar, run history table.
- Per-row "reindex now" action on the product and category admin grids.

## Why

Closes out Track B's "admin API to trigger and progress endpoint" and "manual mode: reindex this one now" requirements with an actual UI, not just curl.

## Scope

- New "Search" screen in the admin SPA: scope picker form → `POST /admin/search/reindex` (PR-1035) → for the bulk path, a progress bar polling `GET /admin/search/reindex/{runID}` until terminal; for the synchronous single-item path, an inline success/failure result with no polling.

- Product admin grid and category admin grid each get a row-level "Reindex now" action, calling the same synchronous single-item endpoint PR-1035 exposes.
- Navigation entry alongside PR-1031's jobs/schedules entries.

## Out Of Scope

- Anything not already covered by PR-1035's API surface — this PR is UI only, no new backend behavior. **As implemented:** two small, minimal backend additions turned out to be genuine prerequisites for this PR's own Scope, not scope creep — see "Design decisions" below.

## Retrospective

### Design decisions

- **The category single-item synchronous shortcut was a genuine prerequisite, not scope creep.** PR-1038's own spec says the category grid's row action calls "the same synchronous single-item endpoint" the product grid uses — but `search_admin.go`'s `Trigger` never actually wired that for categories (deliberately deferred by PR-1037, which added `SearchEngine.IndexCategory` but left the admin-API shortcut for later — see that PR's own Follow-up section and `ROADMAP.md`'s "Design notes: PR-1035 shipped ahead of PR-1037"). Building the category row action against the spec's literal words required closing that gap first: `SearchAdminHandler` gained a `categories domainsearch.CategorySource` dependency (reusing the existing `postgres.SearchCategorySource` from PR-1037, already available in `wire_services.go`) and a `triggerSingleCategory` method mirroring `triggerSingleProduct` exactly. `Trigger`'s `scope=categories` case now takes the same length-1-ids synchronous branch the product case does.
- **A run-history list endpoint was also a genuine prerequisite, not scope creep.** The spec's own Scope explicitly requires a "read-only run history table: past `search_index_runs` rows," but `domainsearch.RunStore` had no `List` — only `Get` (by ID), `FindStaleProcessing` (the reconciliation sweep's own narrow query), and the write methods. Added `RunStore.List(ctx, limit, offset) ([]Run, error)` (mirroring `domain/jobs.Reader.List`'s shape — no separate total count, ordered most-recently-started-first) with a Postgres implementation, and `GET /api/v1/admin/search/reindex` (same path as the existing `POST`, different method — no route conflict, same pattern as `GET`/`POST /api/v1/admin/jobs`) gated by the same `search.reindex` permission as the other two reindex endpoints.
- **No client-side polling pattern existed anywhere in `admin.js` to copy** (confirmed by inspection before writing any code) — the progress bar's poll loop (`setTimeout`-based, 2s interval, stops on a terminal status) is new. Since `admin.js` also has no route-teardown/unmount hook for any screen, `pollRun` checks `location.pathname` against its own route before each poll and before acting on a response, so a stray timer doesn't keep hitting the API forever after the user navigates away (the only failure mode this omission could cause, given a detached DOM write is otherwise harmless).
- **`search.reindex` added to the frontend's client-side `adminRoleDefinitions()`** (admin role only, matching `role_permissions.go`) — this is a hand-maintained mirror of the backend's compiled-in permission set (already true for `jobs.read`/`jobs.write` since PR-1029/1031); without it, `userHasPermission("search.reindex")` would always return `false` and the Search nav link/screen/row actions would be permanently hidden even for an admin.
- **Products grid and Categories page each get their own row-action wiring**, not a single shared component — matching this codebase's existing pattern (Products is schema-driven, Categories is a hand-coded tree; PR-1031 already established that "one generic schema-driven grid" isn't this codebase's actual convention, just an occasional appearance).

### Code review fixes (round 1)

- **Major, confirmed — no index on `search_index_runs` beyond the PK.** `SearchIndexRunRepo.List`'s `ORDER BY started_at DESC LIMIT/OFFSET` was a full table scan + sort on every open of the Search screen and every history refresh — fine today, worse as the table grows (one row per triggered reindex, retained indefinitely). Fixed with migration `073_add_search_index_runs_started_at_index.sql` (plain index on `started_at`, not a composite with `status` — `List` is deliberately unfiltered by status, unlike `FindStaleProcessing`'s narrower query, so the plain column index is what actually serves it).
- **Major, confirmed — the synchronous single-item engine-error path was untested for both product and category.** `fakeSearchEngine` already had `indexErr`/`indexCategoryErr` fields from this PR's own first round, but no test ever set them — a real production path (the "Reindex now" row action when the search engine itself is unreachable, as opposed to the product/category lookup failing, already covered) had no regression coverage. Added `TestSearchAdminHandler_Trigger_ScopeProducts_SingleID_IndexProductError` and `..._ScopeCategories_SingleID_IndexCategoryError` — the handler code was already correct (both branches already wrapped the error as `apperror.CodeInternal` → 500), so this closes a test-coverage gap, not a bug.
- **Minor, confirmed — `pollRun`'s stale-poll guard used `location.pathname` alone.** Leaving the Search screen and returning before a pending `setTimeout` fired would make the path check pass again even though the DOM it was writing into was long gone, letting a stale poll resume and keep hitting the API in the background (invisibly, until that old run reached a terminal status). Replaced with a per-render generation counter (`searchReindexGeneration`, bumped once per `renderSearchReindexPage` call; each render's `pollRun` closure captures its own `myGeneration` and compares) — correctly invalidates a stale loop on any fresh render of the screen, not just a path change.
- **Minor, confirmed — the progress bar had no ARIA semantics.** `role="progressbar"` + `aria-valuemin`/`aria-valuemax`/`aria-valuenow` + `aria-live="polite"` added to the track element, matching the `aria-live` convention already used elsewhere in this file for status messages.
- **Minor, confirmed but not a code change — the run-history table doesn't auto-refresh for a run triggered elsewhere** (another admin, `search:reindex` CLI). Only this screen's own trigger or a manual page reload updates it. This matches the PR's own scope (no cross-client live-update mechanism exists anywhere in this admin panel), but is worth naming explicitly as a known UX gap rather than leaving it merely implicit — noted here for that reason.
