# PR-1031 — Jobs + Scheduler Admin GUI

Status: done

## Summary

- New screens in the existing bundled admin SPA (`internal/interfaces/http/admin/dist`): job list/detail/retry/cancel, schedule list/trigger-now/enable-disable.
- Same schema-driven forms-and-grids pattern as the rest of the admin panel — no new frontend framework, no new build tooling.

## Why

PR-1029/PR-1030 ship the API; without a GUI, "admin reachability" is still CLI/curl-only for anyone who isn't comfortable scripting against the REST API. The rest of the admin panel already has this pattern solved (schema-driven forms/grids) — this PR is applying it, not inventing a new UI approach.

## Scope

- Jobs list screen: filterable grid (type, status), row actions (retry on `failed`, cancel on `pending`), links to detail view.
- Job detail screen: full `JobDetail` payload, attempt count, last error.
- Schedules list screen: grid of catalog entries (name, spec in human-readable form if feasible, next run, enabled toggle), row action "trigger now" with a confirmation step (this fires real work immediately — a misclick shouldn't be free).
- Navigation entry added to the admin panel's existing nav structure.

## Out Of Scope

- Real-time updates (polling only, matching the rest of the admin panel's existing pattern — no new websocket/SSE infrastructure for this one screen).
- Bulk actions in the GUI (matches PR-1029's API scope — no bulk retry/cancel).

## Validation (planned — run when implementing)

- Manual QA pass against a running `dev` instance: trigger a schedule, retry a failed job (seed one), cancel a pending job.
- No automated frontend test suite exists in this repo today for the bundled SPA — confirm that's still true at implementation time; if a test harness has been added since, follow it, otherwise this PR doesn't introduce one on its own (out of scope for a single-feature PR).

## What changed

The bundled admin SPA (`internal/interfaces/http/admin/dist/`) is hand-authored vanilla JS with no build step and no separate source directory — `admin.js`/`admin.css`/`index.html` are edited directly and served via `//go:embed`. Only one existing screen (Products) actually fetches a dynamic grid schema; every other grid hardcodes its HTML as a string template. That's the pattern this PR mirrors, not a generic schema renderer.

- `internal/interfaces/http/admin/dist/admin.js`:
  - `renderJobsGrid`/`renderJobsTable` — list screen at `/admin/operations/jobs`, filter form (type free-text + status `<select>`, submit-based like the existing bulk-price/inventory search forms, not filter-on-keystroke), row actions Retry (`status === "failed"`) / Cancel (`status === "pending"`), gated by `jobs.write`.
  - `renderJobDetail`/`renderJobDetailPanel` — detail screen at `/admin/operations/jobs/:id` (new regex route in `resolveRoute`), `<dl>` of id/type/status/attempts/timestamps, `<pre>` blocks for `last_error` and the JSON payload, same conditional Retry/Cancel actions as the grid.
  - `renderSchedulesGrid`/`renderSchedulesTable` — list screen at `/admin/operations/schedules` (no pagination/filter — `ScheduleAdminHandler.List` isn't paginated), row actions Trigger now (`window.confirm(...)` first, matching the existing refund/delete confirmation precedent — "this fires real work immediately"), Enable/Disable (no confirmation, matches spec).
  - `describeCronSpec` — best-effort plain-English translation for the handful of cron shapes this codebase's own registered tasks actually use (`*/N * * * *`, `H M * * *`, `M * * * *`, `* * * * *`); anything else falls back to the raw spec string rather than guessing.
  - `JOB_STATUS_OPTIONS`, `formatJobTimestamp` — small shared helpers.
  - `routes` gained `/admin/operations/jobs` and `/admin/operations/schedules`; `resolveRoute` gained the job-detail regex block, following the exact structure of the existing `orderMatch`/`returnMatch`/`customerMatch` blocks.
  - `adminRoleDefinitions()` — added `jobs.read`/`jobs.write` to the `admin` role's permission list (previously absent client-side even though the backend has gated on them since PR-1029/1030), so `userHasPermission('jobs.write')`-gated action buttons actually show for an admin instead of silently disappearing.
- `internal/interfaces/http/admin/dist/admin.css` — added `.badge-processing`/`.badge-done` (job statuses with no existing badge color; `pending`/`failed`/`cancelled` already had one).
- `internal/interfaces/http/admin/dist/index.html` — two new `<li>` nav links under the existing "Operations" nav group, alongside Inventory/Shipping/Payments.
- `docs/guides/MERCHANT.md` — new "Jobs" and "Schedules" subsections under Operations (text walkthrough, not a screenshot — no way to capture one in this environment; see Validation), plus two new rows in the admin-map route table.

## Round 2 (code review)

- **Fixed — nav not permission-gated.** Jobs/Schedules nav links were always shown regardless of role, even though `jobs.read` is admin-only (`role_permissions.go`) — a manager/editor/support admin would always see a dead link that only ever renders "Your account does not have jobs access." Matched an existing pattern in the file (`refreshCustomerGroupsNavVisibility`) but for a different reason (license probe vs. a plain role check) — added `refreshJobsNavVisibility()`, a synchronous client-side `userHasPermission("jobs.read")` check that hides both `<li>`s via the same `parentElement.style.display` technique, called alongside the existing customer-groups visibility refresh in `init()`.
- **Fixed — no double-submit guard.** None of the five action buttons (job retry/cancel in the grid and detail view, schedule trigger/enable/disable) disabled themselves during their in-flight `api()` call, so a fast double-click could fire the same POST twice — the backend's status guard rejects the second as a conflict, which would've shown as a spurious error for what was actually a successful first click. Added `withButtonBusy(btn, busyLabel, startAction)`: disables the button and swaps its label ("Retrying…"/"Cancelling…"/"Triggering…"/"Enabling…"/"Disabling…") for the duration of the call, re-enabling regardless of outcome (`.then(restore, restore)`, no `.finally` — matches this file's existing promise style, which uses none anywhere). All five action call sites now go through it.
- **Fixed — error banners stacked instead of replacing.** Only the jobs grid's row-action failure path had this bug (`grid.insertAdjacentHTML("afterbegin", ...)` on every failed click, no clearing) — the job detail and schedules screens already wrote into a single fixed message `<div>` via `msg.innerHTML =` (replace), so they were unaffected. Added a `#jobs-grid-msg` slot to the jobs grid, matching the pattern the other two screens already used, and pointed the row-action handler at it instead of `insertAdjacentHTML` on the grid itself.
- **Fixed — no pagination UI on the jobs grid.** `GET /admin/jobs` supports `offset`/`limit`, but the grid hardcoded `limit=50` with no way to see anything past the first page — a store with more than 50 jobs matching a filter silently truncated. No pagination pattern exists anywhere else in `admin.js` to copy, so introduced the minimal version: a "Load more" button that appends the next page (shown only when the last fetched page came back full — a short page means nothing further to fetch), resetting on a new filter submit.
- **Fixed — `describeCronSpec` missing the hourly case.** `"0 * * * *"` (`cart.recovery`'s actual registered spec) matched neither `everyMinutesMatch` (`*/N` step syntax) nor `dailyAtMatch` (requires both a numeric minute *and* hour field) — it fell back to the raw cron string, the only one of this codebase's four registered tasks to do so. Added an `hourlyAtMatch` branch (`/^(\d+) \* \* \* \*$/` → `"hourly at :" + mm`), verified against all four real registered specs plus the wildcard and an intentionally-unmatched case.
- **Fixed — schedule "Trigger now" didn't reload.** Enable/Disable already called `reload()` on success; Trigger didn't, leaving the grid stale relative to Enable/Disable's own behavior. Added the same `reload()` call after a successful trigger for consistency, even though no currently-displayed column actually changes value from a manual trigger today (`next_run` is a pure function of the cron spec, unaffected by firing) — cheap, and matches the established convention for every other successful write action on this screen.
- **Reviewed, not acted on.** No JS test coverage exists for any of the new render functions — the CR itself notes this isn't a regression (no test harness exists for `admin.js` anywhere in this codebase) and flags it as worth doing, not required. Introducing a JS test harness from scratch is a much larger, separate decision (framework choice, CI wiring) than appropriate for a review-fix round on top of an already-large PR; left as-is, consistent with every other screen in this file.

## Round 3 (code review)

- **Fixed — nav stays hidden after login.** `refreshJobsNavVisibility()` (added in Round 2) only ran from `init()`. An unauthenticated visitor loading the SPA gets the links hidden (`currentUser` is `null` at that point); after signing in without a full page reload, nothing called it again, so the links stayed hidden until a manual refresh. Added a call right after `loadContextSwitcherData()` resolves in the login success handler, alongside the existing `navigateTo("/admin/dashboard")`.
- **Spotted, not fixed (out of scope of this finding): the mirror-image gap on logout.** `handleLogout()` doesn't call `refreshJobsNavVisibility()` either, so a link visible before logout stays visible after — cosmetic only (the route itself still requires auth server-side and redirects to login), but the same root cause as the fix above. Not part of what was reported here; flagging for a follow-up rather than expanding this round's scope unprompted.
