# PR-621 — Order Invoice Admin UI (Track C, OSS)

Status: done

## Summary

- Order detail: list invoices and download/open PDF when available
- Thin admin HTTP wiring for invoice metadata + PDF download

## Why

MERCHANT.md states invoices are email-first with no admin viewer. Support teams need PDF access from the order screen. Invoices are persisted via `invoice.InvoiceRepository` and PDFs stored at `invoices/{invoiceId}/invoice-{number}.pdf`, but admin had no invoice routes despite `invoices.read` in RBAC.

## Scope

- `internal/interfaces/http/invoice_admin.go` — list + PDF stream handlers wired in `cmd/api/main.go`
- `admin.js` — invoices panel on order detail
- **List (metadata):** `GET /api/v1/admin/orders/{orderId}/invoices` — invoice id, number, created_at (`invoices.read`)
- **Download:** `GET /api/v1/admin/invoices/{invoiceId}/pdf` — admin-proxied PDF bytes (`Content-Type: application/pdf`); loads from local storage when available, otherwise re-renders via `invoicepdf.Renderer`

## Out Of Scope

- Regenerate invoice from admin
- Credit note editor
- Peppol/e-invoice dispatch

## Validation

- Paid order with invoice shows download link via admin PDF route
- PDF downloads through admin-proxied endpoint (not direct storage URL)
- Orders without invoice show clear empty state
- User without `invoices.read` sees forbidden state

## What changed

- `invoice_admin.go` — `ListByOrder` and `DownloadPDF` handlers with `invoices.read` guard
- `localfs.Storage.Read` — optional read path for stored invoice PDFs before re-render fallback
- `cmd/api/main.go` — shared `invoicePDFRenderer`, admin routes for list + PDF
- Order detail **Invoices** panel with metadata table and **Download PDF** (blob download via authenticated fetch)
- `invoice_admin_test.go` and `admin_handler_test.go` wiring assertions
