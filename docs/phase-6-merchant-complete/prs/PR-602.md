# PR-602 — Block Placement Admin UI (Track A, OSS)

Status: done

## Summary

- Assign ordered content blocks to home layout and CMS pages
- Wire PR-512 target placement API

## Why

Creating blocks (PR-601) is not enough — merchants must attach blocks to `/` and `/pages/{slug}` without API calls.

## Scope

- `admin.js` — placement UI on home settings and/or page edit
- Wire PR-512 target placement API (`content_block_admin.go`, `parseContentBlockTarget`, routes in `cmd/api/main.go`):
  - `GET /api/v1/admin/content-block-targets/{targetType}/{targetKey}` — load current placements (`content.read`)
  - `PUT /api/v1/admin/content-block-targets/{targetType}/{targetKey}` — save ordered block IDs (`content.write`)
- Home: `targetType=layout`, `targetKey=home` (e.g. `.../layout/home`)
- CMS page: `targetType=page`, `targetKey={page-id}` (page UUID from admin page record; not slug — matches how placements are stored)
- Ordered multi-select or list reorder matching API `block_ids` array semantics

## Out Of Scope

- New layout targets beyond `home` and CMS pages
- Live storefront preview iframe
- New block types

## Validation

- Assign two blocks to home; storefront `/` renders them in order
- Assign blocks to a CMS page; `/pages/{slug}` renders blocks + legacy content
- Removing a block from target updates storefront after save

## What changed

- Reusable `mountBlockPlacementsPanel` — load placements, reorder (move up/down), add/remove blocks, save via `PUT` with `block_ids`
- `/admin/content/home-blocks` — home layout placement editor (`layout` / `home`)
- Blocks grid link: **Home page blocks**
- Page edit form includes **Content blocks** section (`page` / `{page-id}`)
- `admin_handler_test.go` — placement route and wiring assertions
