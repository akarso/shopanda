# PR-903 — Installation UX

Status: done

## Summary

- Browser setup wizard at `/setup` for first-time merchant installation
- Public setup API: status check + install (migrate, seed, create admin)
- `/admin` redirects to `/setup` until an active admin account exists

## Why

CLI `install.sh` + `app setup` worked for operators but not merchants hosting their own store. WordPress-style first-run UX closes the gap without runtime `.so` plugin loading — configuration still comes from `.env`, and plugins remain compile-time registered.

## Scope

- `internal/application/setup/service.go` — status + install orchestration
- `internal/platform/migrate/pending.go` — pending migration count for wizard UI
- `internal/infrastructure/postgres/customer_repo.go` — `HasActiveAdmin`
- `internal/interfaces/http/setup.go` — wizard page, API, admin gate
- `cmd/api/main.go` — route registration
- Tests: setup HTTP handlers, migrate pending count

## Out Of Scope

- Interactive database / JWT configuration in the browser (still `install.sh` / `.env`)
- Plugin marketplace or runtime plugin loading
- Storefront setup wizard (admin-only first boot)
- Replacing CLI `app setup` (both paths coexist)

## Routes

| Route | Purpose |
| --- | --- |
| `GET /setup` | HTML setup wizard |
| `GET /api/v1/setup/status` | `{ needs_setup, database_ok, pending_migrations, has_admin }` |
| `POST /api/v1/setup/install` | Migrate + seed + create first admin |

## Install flow

1. Merchant configures `.env` (or runs `./install.sh`)
2. Starts server (`app dev` / `app serve`)
3. Opens `/setup` (or is redirected from `/admin`)
4. Submits admin email/password (+ optional store name)
5. Server runs migrations, default seeders, creates admin if none exists (serialized via PostgreSQL advisory lock)
6. Redirect to `/admin` login

## Validation

- `go test ./internal/interfaces/http/... -run Setup`
- `go test ./internal/platform/migrate/... -run PendingCount`
- `go build ./cmd/api/`
- Fresh DB + `.env` → visit `/setup` → install → sign in at `/admin`
