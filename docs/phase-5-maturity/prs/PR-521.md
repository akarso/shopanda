# PR-521 — Custom Roles Editor (Track C, OSS)

Status: done

## Summary

- DB-backed permission assignments for the four fixed admin roles
- Permission catalog API covering core and plugin permissions
- Runtime RBAC resolution loads from Postgres at startup and after updates

## Why

PR-520 added admin user CRUD but roles still used a compiled-in permission matrix. Merchants need to tailor manager/editor/support capabilities without code changes while staying within the core and plugin permission catalog.

## Scope

- `migrations/058_create_role_permissions.sql` — `role_permissions` table seeded with core defaults
- `internal/domain/rbac/` — catalog helpers, effective permission store, repository port
- `internal/infrastructure/postgres/role_permission_repo.go` — list/replace/ensure persistence
- `internal/application/adminrole/service.go` — catalog, list/get/update, startup sync
- `internal/interfaces/http/admin_role.go` — REST handlers + audit logging
- `internal/application/admin/audit.go` — role/permission audit actions
- `cmd/api/main.go` — startup sync after plugin init, routes under `settings.read` / `settings.write`

## Out Of Scope

- Admin SPA matrix editor UI (API only)
- Creating new role slugs (still admin/manager/editor/support only)
- Per-user permission overrides
- MFA (PR-522)

## Validation

- `GET /api/v1/admin/permissions` lists assignable core and plugin permissions
- `GET /api/v1/admin/roles` returns all four roles with effective permissions
- `GET /api/v1/admin/roles/{role}` returns a single role
- `PUT /api/v1/admin/roles/{role}` replaces permissions after catalog validation
- Plugin default grants are inserted on startup when missing
- `rbac.HasPermission` and admin context use DB-backed assignments after startup
- Endpoints require `settings.read` / `settings.write`
