# PR-535 — Omnibus Listing Batch Reads (Track D)

Status: planned

## Summary

- add batch repository methods for variants, current prices, and 30-day lowest history
- refactor `ListingPriceIndicationStep` to fetch once per PLP page instead of per product (N+1)

## Why

PR-530 renders Omnibus disclosures on listing cards by calling `ListByProductID`, `FindByVariantCurrencyAndStore`, and `LowestSince` inside a per-product loop. That is correct but scales poorly on large PLPs. Batch reads keep the same lowest-price-variant semantics while reducing query count.

## Scope

- domain ports: batch methods on `catalog.VariantRepository`, `pricing.PriceRepository`, and `pricing.PriceHistoryRepository` (names TBD, e.g. `ListByProductIDs`, `FindByVariantsCurrencyAndStore`, `LowestSinceByVariants`)
- postgres adapters implementing the new methods
- `buildListingPriceIndicationBlock` / `ListingPriceIndicationStep` — prefetch for all `ctx.Products`, resolve lowest variant in memory, reuse existing block builder
- tests: repo batch queries + composition step still picks lowest-price variant and respects `legal.omnibus_enabled`

## Out Of Scope

- PDP `PriceIndicationStep` (single product; no batch need)
- Caching layer or search-index denormalization
- Changing Omnibus business rules or template output

## Validation

- PLP with multiple discounted products still shows correct lowest 30d price per card
- lowest-price variant selection matches PR-530 behavior (same variant as search display)
- disabled Omnibus config still skips all work
- batch implementation uses O(1) repo round-trips per resource type per page (not per product)

## Depends On

- PR-530 (done) — listing step and PLP templates
