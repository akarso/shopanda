# PR-502 — Returns Domain + Workflow (Track A)

Status: done

## Summary

- RMA entity with lifecycle: requested → approved → received → refunded
- return line items linked to order variants
- application workflow service with inventory restock and optional provider refund

## Why

Merchants need traceable post-sale returns without external OMS tools. PR-502 establishes the domain model and workflow; admin and account UI follow in PR-503.

## Scope

- `internal/domain/returns/` — `Return`, `Item`, status transitions, repository port, events
- `migrations/048_create_order_returns.sql` — `order_returns`, `order_return_items`
- `internal/infrastructure/postgres/return_repo.go` — persistence
- `internal/application/returns/service.go` — RequestReturn, Approve, Reject, Cancel, Receive (restock), Refund
- wiring in `cmd/api/main.go` (service only; no HTTP yet)
- tests: domain, application workflow, postgres repo

## Out Of Scope

- Admin list/detail UI and customer account "request return" (PR-503)
- Credit note auto-generation on refund
- Partial payment status updates (provider refund only; payment row unchanged for partial returns)
- Store credit / gift cards (PR-505 stretch)

## Validation

- paid order → request return → approve → receive restocks stock → refund completes
- unpaid order rejected; return qty cannot exceed ordered qty minus active returns
- rejected/cancelled returns do not consume returnable quantity
- domain status transitions enforce workflow order
