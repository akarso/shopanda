# PR-503 — Returns Admin + Account UI (Track A)

Status: done

## Summary

- Admin API and SPA for listing returns, viewing detail, and workflow actions (approve, reject, receive, refund)
- Customer REST API and storefront account pages to request returns on eligible paid orders and track status

## Why

PR-502 delivered the returns domain and workflow service without HTTP surfaces. Merchants and customers need UI to initiate and process returns without calling internal services directly.

## Scope

- `internal/domain/returns/repository.go` — `List`, `FindByCustomerID` ports
- `internal/infrastructure/postgres/return_repo.go` — list/customer queries; migration `049_order_returns_customer_index.sql`
- `internal/application/returns/service.go` — `List`, `Get`, `ListByCustomerID`, `ListByOrderForCustomer`, `ReturnableLines`
- `internal/interfaces/http/return_admin.go` — admin endpoints under `orders.read` / `orders.write`
- `internal/interfaces/http/return_account.go` — customer/account REST endpoints
- `internal/interfaces/http/storefront_account_returns.go` — SSR return request + returns list
- Admin SPA: `/admin/sales/returns` grid + detail with action buttons
- Storefront: `/account/returns`, return form on paid order detail
- wiring in `cmd/api/main.go`
- tests: admin/account HTTP, existing domain/application/postgres suites

## Out Of Scope

- Payment transaction ledger admin (PR-504)
- Credit note auto-generation on refund
- Store credit (PR-505 stretch)
- Email notifications on return status changes

## Validation

- customer requests return on paid order from account order detail → appears in `/account/returns`
- admin lists return at `/admin/sales/returns` → approve → receive → refund completes workflow
- return qty cannot exceed remaining returnable quantity (service validation from PR-502)
- RBAC: support role can list; write actions require `orders.write`
