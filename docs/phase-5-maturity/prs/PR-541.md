# PR-541 — Plugin CLI Registration (Track E, OSS)

Status: done

## Summary

- Plugins register CLI subcommands during `Init` via `plugin.App.RegisterCommand`
- `cmd/api` dispatches unknown core commands to the plugin CLI registry
- Example plugin ships `example:ping` as a reference command

## Why

Operational commands (reindex, import/export) lived only in `main.go`. Integrators need a stable hook to add plugin-owned maintenance commands without editing core dispatch for every extension.

## Scope

- `internal/platform/cli/` — `Command`, `Context`, `Registry`
- `internal/platform/plugin/` — `RegisterCommand`, registry wiring in `InitAll`
- `cmd/api/cli_plugins.go` — plugin command dispatch + help listing
- `plugins/example/cli.go` — `example:ping` demo command
- Docs: PR spec, README, PLUGINS.md, DEVELOPER.md, C4 diagram note

## Out Of Scope

- Cobra/urfave-style CLI framework migration
- Dynamic command discovery (commands register only during plugin `Init`)
- Core built-in commands moving to plugins

## Contract

- Command names use `domain:action` (e.g. `example:ping`)
- Names must be unique; duplicate registration panics at init
- Handler signature: `func(ctx cli.Context, args []string) error`
- `cli.Context` exposes config, logger, and DB (opened by dispatcher when command runs)

## Validation

- With `plugins.example.enabled=true`, `app help` lists `example:ping`
- `app example:ping` prints `example plugin ok` and logs `example.ping`
- Unknown commands still return `unknown command` after plugin lookup
- `go test ./internal/platform/cli/... ./internal/platform/plugin/... ./plugins/example/... ./cmd/api/...`
