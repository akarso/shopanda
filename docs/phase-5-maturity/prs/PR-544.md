# PR-544 — Dynamic Plugin Loading Research (Track E, OSS)

Status: done

## Summary

- Research spike evaluating Go `.so` dynamic plugin loading for Shopanda
- **Verdict:** defer implementation; compile-time registration remains the supported model
- Published decision record: [`specs/DYNAMIC_PLUGIN_LOADING.md`](../specs/DYNAMIC_PLUGIN_LOADING.md)

## Why

Phase 4 deferred plugin `.so` hot-loading. Phase 5 required an explicit research gate (PR-544) before investing in a loader, ABI packages, or marketplace assumptions. Integrators need a clear answer: “can I drop in a `.so` without rebuilding?”

## Scope

- `docs/phase-5-maturity/specs/DYNAMIC_PLUGIN_LOADING.md` — options, constraints, decision matrix, integrator guidance
- `docs/phase-5-maturity/prs/PR-544.md` — this spec
- `docs/phase-5-maturity/README.md` — phase index (Phase 5 complete)
- Update root `README.md`, `PLUGINS.md`, `DEVELOPER.md`, `RUNBOOK.md`, C4 diagrams, Phase 5/6 roadmaps

## Out Of Scope

- `plugin.Open` loader implementation
- Plugin marketplace or version resolver
- Hot reload of plugins without process restart
- WASM or out-of-process plugin runtime

## Verdict (short)

| Option | Decision |
| --- | --- |
| Compile-time `register_plugins.go` | **Keep** (current) |
| Go `.so` via `plugin` package | **Defer** — toolchain/OS/GPL friction; little ops win vs rebuild |
| Out-of-process / WASM | **Future** — separate product decisions |

## Validation

- Research doc lists Go `plugin` constraints and maps them to Shopanda's single-binary model
- All public docs point integrators to compile-time registration, not `.so` loading
- Phase 5 roadmap and PR index mark PR-544 **done**; Phase 5 marked **complete**
- No new runtime loader code in `internal/` or `cmd/`
