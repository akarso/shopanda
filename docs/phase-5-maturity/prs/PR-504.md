# PR-504 — Payment Transaction Ledger Admin (Track A)

Status: done

## Summary

- Read-only admin API and SPA grid over stored payment records with order links and status filtering
- Merchants can reconcile captures and refunds (`completed`, `refunded`, etc.) without shell access

## Why

Payments exist in Postgres and flow through checkout/webhooks, but admin had no ledger view. PR-504 closes the operational gap called out in Phase 4 deferrals and MERCHANT.md.

## Scope

- `internal/domain/payment/repository.go` — `ListFilter`, `List` port
- `internal/infrastructure/postgres/payment_repo.go` — paginated list with optional status filter
- `internal/interfaces/http/payment_admin.go` — `GET /api/v1/admin/payments`, `GET /api/v1/admin/payments/{paymentId}`
- Admin SPA: `/admin/sales/transactions` read-only grid with status filter and order links
- RBAC: `orders.read` (same as orders/returns read surfaces)
- Audit: `payment.list`, `payment.read`
- wiring in `cmd/api/main.go`
- tests: HTTP handler, postgres repo list

## Out Of Scope

- Separate chargeback/dispute entity (no provider data model yet; refunded payments cover refund visibility)
- Provider webhook replay or manual refund actions (existing refund endpoint unchanged)
- Per-order payment timeline UI beyond order detail link
- Store credit / gift cards (PR-505 stretch)

## Validation

- completed and refunded payments appear in admin transactions grid
- status filter returns matching rows only
- each row links to the related order detail
- support role can list; editor role cannot (`orders.read` required)
