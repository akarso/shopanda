# PR-312 — Storefront Fresh-Session Step-Up Bypass

## Summary

Continued Track 4 with the next smallest account-security slice on top of PR-311.

This PR keeps the step-up checkpoint for sensitive storefront account routes, but avoids asking for the password twice when the shopper has only just authenticated. A recent storefront session can open `/account/security` directly, while older sessions still redirect through `/account/security/verify` before password-change or account-deletion controls are shown.

## Scope

### Fresh-session storefront identity

- updated `internal/domain/identity/identity.go`
- added `AuthenticatedAt` to request identity so downstream HTTP flows can tell when the current session was issued
- added `WithAuthenticatedAt(...)` helper for parsed identities and focused tests
- updated `internal/application/auth/token_parser.go`
- now carries JWT `iat` into the authenticated request identity instead of dropping it after token validation

### Step-up gate refinement

- updated `internal/interfaces/http/storefront_account_security.go`
- added a fresh-session grace window ahead of the existing signed verification-cookie check
- keeps the existing redirect to `/account/security/verify` for stale sessions and unverified direct access
- leaves the existing verification cookie flow intact for older sessions and sensitive POST retries

### Regression coverage

- updated `internal/domain/identity/identity_test.go`
- added focused coverage for storing authenticated-at timestamps on identities
- updated `internal/application/auth/token_parser_test.go`
- added coverage proving parsed customer identities now preserve the JWT issue time
- updated `internal/interfaces/http/storefront_account_test.go`
- added focused storefront coverage for:
  - allowing direct access to `/account/security` from a fresh session without a verification cookie
  - continuing to redirect stale sessions through the verification page
  - preserving the earlier redirect behavior for sessions without either freshness or verification

## Notes

- this is intentionally narrower than email verification or registration-time 2FA; it improves the current account-security UX without widening the auth surface
- the next Track 4 slice can build on this by replacing or complementing password step-up with email-code verification for older sessions and higher-risk account changes
