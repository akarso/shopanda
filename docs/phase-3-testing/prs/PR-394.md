# PR-394 — Guest Order Claim End-To-End (Track 2)

Status: implemented

## Summary

- persist customer linking on guest orders in Postgres so claiming actually transfers ownership in production
- wire the claim-search endpoint to real guest order discovery with a constant response shape
- add the SSR storefront claim page (`/account/orders/claim`) that the claim email already links to, including registration, linking, and immediate sign-in
- remove the `ClaimOrder` stub so the claim flow has no dead ends

## Why

PR-320/321 shipped claim tokens, endpoints, and a register-and-link service, but the flow did not work end to end outside unit tests:

- `internal/infrastructure/postgres/order_repo.go`: `UpdateStatus` writes only `status` and `updated_at`, so `LinkOrderService.RegisterAndLink` never persisted the new `customer_id`; mock-based tests hid this because the in-memory repo cloned the whole order
- `internal/interfaces/http/storefront_order_claim.go`: `ClaimOrderSearch` never called `ClaimService.SearchGuestOrders` — it emailed a token unconditionally without discovering orders; `ClaimOrder` was an explicit stub that verified ownership and returned a message without changing any state
- the claim email built in `cmd/api/main.go` links to `/account/orders/claim?claim_token=...`, but no such route or template existed; the token carries only `contact_email` while the claim endpoints required an `order_id` the guest had no way to discover

## Changes

### Repository

- `order.OrderRepository` gains `LinkToCustomer(ctx, order)` and `LinkToCustomerByContactEmail(ctx, contactEmail, customerID, updatedAt)`; `UpdateStatus` stays status-only
- `postgres.OrderRepo.LinkToCustomer` executes `UPDATE orders SET customer_id, updated_at WHERE id = $… AND customer_id = ''` — the guard ensures an already-linked order is never silently reassigned; zero rows affected is an error
- `postgres.OrderRepo.LinkToCustomerByContactEmail` links every unclaimed guest order for a contact email in a single UPDATE statement, so a multi-order claim is atomic and can never be partially persisted

### Application (`LinkOrderService`)

- `RegisterAndLink` persists via `LinkToCustomer` instead of the misused `UpdateStatus`; output now also carries the session `ExpiresAt`
- new `RegisterAndClaimByEmail(ctx, in)`: registers a customer under the verified guest contact email and links **all** guest orders carrying that email through the atomic by-email repository method; on failure (or when a concurrent claim left nothing to link) the just-registered customer is deleted so the claim can be retried

### HTTP / storefront

- `ClaimOrderSearch` (`POST /api/v1/orders/claim-search`) now calls `SearchGuestOrders` and sends the claim email only when at least one unclaimed guest order matches; the JSON response is identical either way, and token/send failures after the search are logged but still answered generically, so the endpoint cannot be used to enumerate emails
- new `AccountOrdersClaim` handles `GET`+`POST /account/orders/claim`:
  - `GET` verifies the `claim_token`, lists the guest's claimable orders, and renders a registration form (email fixed to the token's contact email)
  - `POST` registers via `RegisterAndClaimByEmail`, syncs any guest cart, sets the storefront session cookie, and redirects to `/account/orders`
  - invalid/expired tokens render a friendly error with HTTP 403
- `ClaimOrder` (`POST /api/v1/orders/claim`) removed along with its route and dead request/response types; `claim-register` (single-order JSON flow) stays
- template `themes/default/templates/account_orders_claim.html` added; routes wired in `cmd/api/main.go`
- structured logs: `storefront.order_claim.search`, `.page`, `.registered`, `.linked`, plus error events for token/email/register failures

## Out Of Scope

- guest notifications and confirmation messaging (PR-393)
- passwordless claim for existing accounts (explicit registration is the only claim path for now, per the Track 2 open question)
- marking the claimed email as verified (account email verification still runs through the standard flow)

## Validation

- a guest can: complete checkout → receive claim email → open `/account/orders/claim` → register → see the order under `/account/orders`
- the linked order row in Postgres carries the new `customer_id` (`TestOrderRepo_LinkToCustomer*` and `TestOrderRepo_LinkToCustomerByContactEmail`, require `SHOPANDA_TEST_DSN`)
- claim-search does not reveal whether orders exist — the match and no-match response bodies are asserted byte-identical (`TestStorefrontHandler_ClaimOrderSearch_NoMatches_SkipsEmail` / `_Matches_SendsEmailWithSameResponse`)
- claim page render, invalid token handling, and register-and-sign-in covered by `TestStorefrontHandler_AccountOrdersClaim_*`
- multi-order claim, no-orders, and cleanup-on-failure covered by `TestLinkOrderService_RegisterAndClaimByEmail_*`
- `go test ./internal/application/order ./internal/infrastructure/postgres ./internal/interfaces/http -count=1`
