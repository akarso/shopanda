# PR-394 — Guest Order Claim End-To-End (Track 2)

Status: planned

## Summary

- persist customer linking on guest orders in Postgres so `claim-register` actually transfers ownership in production
- wire the claim-search endpoint to real guest order discovery
- add the storefront claim page that the claim email already links to
- finish or remove the `ClaimOrder` stub so the claim flow has no dead ends

## Why

PR-320/321 shipped claim tokens, endpoints, and a register-and-link service, but the flow does not work end to end outside unit tests:

- `internal/infrastructure/postgres/order_repo.go`: `UpdateStatus` writes only `status` and `updated_at`, so `LinkOrderService.RegisterAndLink` never persists the new `customer_id`; mock-based tests hide this because the in-memory repo clones the whole order
- `internal/interfaces/http/storefront_order_claim.go`: `ClaimOrderSearch` never calls `ClaimService.SearchGuestOrders` — it emails a token unconditionally without discovering orders; `ClaimOrder` is an explicit stub that verifies ownership and returns a message without changing any state
- the claim email built in `cmd/api/main.go` links to `/account/orders/claim?claim_token=...`, but no such route or template exists; the token carries only `contact_email` while the claim endpoints require an `order_id` the guest has no way to discover

## Scope

- repository: add an explicit order-linking persistence method (e.g. `LinkToCustomer(ctx, orderID, customerID)` or a scoped `Update`) on `order.Repository` and `OrderRepo`; keep `UpdateStatus` status-only; cover with a Postgres integration test
- application: `LinkOrderService.RegisterAndLink` uses the new persistence method
- discovery: `ClaimOrderSearch` calls `SearchGuestOrders` and only sends a claim email when matching guest orders exist (constant-time response shape so the endpoint does not leak which emails have orders)
- storefront UI: add `GET /account/orders/claim` rendering the guest's claimable orders from a valid `claim_token`, with a registration form that posts to the existing `claim-register` endpoint; add the template under `themes/default/templates/`
- claim endpoint: either complete `ClaimOrder` (emit linking event / mark claimed) or remove it in favor of the search → page → register flow; no stubs left registered
- logging: structured logs on claim search, claim page render, and register-and-link, including order id and guest flag
- tests: HTTP tests for `claim-search` and the claim page, Postgres integration test proving `customer_id` is persisted after linking, and a flow test from claim token to linked order visible in account order history

## Out Of Scope

- guest notifications and confirmation messaging (PR-393)
- passwordless claim for existing accounts (explicit registration is the only claim path for now, per the Track 2 open question)

## Validation

- a guest can: complete checkout → receive claim email → open `/account/orders/claim` → register → see the order under `/account/orders`
- the linked order row in Postgres carries the new `customer_id`
- `go test ./internal/application/order ./internal/infrastructure/postgres ./internal/interfaces/http -count=1`
