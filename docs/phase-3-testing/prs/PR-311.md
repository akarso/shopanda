# PR-311 — Storefront Security Step-Up Verification

## Summary

Continued Track 4 with the first stronger-authentication slice for sensitive account access.

This PR adds a dedicated verification checkpoint in front of the storefront security surface so a signed-in shopper must re-enter their password before opening password-change and account-deletion controls. The step-up is scoped to `/account/security` and its sensitive POST actions rather than the entire account area.

## Scope

### Step-up verification model

- updated `internal/interfaces/http/storefront.go`
- added optional account-security verification support to the storefront handler via `WithAccountSecurity(...)`
- updated `cmd/api/main.go`
- enabled storefront account-security verification in production using the existing auth JWT secret plus a short-lived TTL
- added `internal/interfaces/http/storefront_account_security.go`
- implemented a short-lived, signed storefront verification cookie tied to the authenticated customer id
- added helpers to set, validate, and clear the verification cookie

### Verification page and route wiring

- updated `internal/interfaces/http/storefront_account.go`
- gated `GET /account/security` behind recent verification when step-up is enabled
- gated sensitive security POST routes behind the same verification check
- clears the verification cookie on successful logout, password change, and account deletion
- updated `cmd/api/main.go`
- added storefront verification routes:
  - `GET /account/security/verify`
  - `POST /account/security/verify`
- kept the existing password/delete POST aliases intact so stale tabs still land in the new verification flow rather than hard failing

### Password re-check in auth service

- updated `internal/application/auth/service.go`
- added `VerifyPassword(...)` so the storefront verify page can re-check the current signed-in user’s password without minting a new session token or overloading login semantics

### Storefront templates

- added `themes/default/templates/account_security_verify.html`
- created a dedicated verify page that asks the signed-in shopper to re-enter their password before continuing to the security area
- updated `themes/default/static/css/style.css`
- added a small width constraint for the verify panel so the checkpoint page stays compact and readable

### Regression coverage

- updated `internal/application/auth/service_test.go`
- added focused tests for successful and failed password verification
- updated `internal/interfaces/http/storefront_test.go`
- added the verify template and routes to the storefront test theme/router helper
- updated `internal/interfaces/http/storefront_account_test.go`
- added focused coverage for:
  - redirecting unverified access to the verify page
  - setting the short-lived verification cookie after password re-entry
  - rendering the security page only after verification
  - redirecting unverified password-change attempts back through verification
  - preserving the existing confirmation requirement on account deletion once verified

## Notes

- this is an intentionally small first step-up slice: profile and order-history pages remain available without reauthentication
- the next Track 4 security slice can widen from this checkpoint into stronger policies such as session-age checks, one-time email codes, or registration-time verification without redesigning the rest of the account area
