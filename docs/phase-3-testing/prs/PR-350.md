# PR-350 - Product Admin Permission Guard Coverage (Track 3)

Implemented the next small Track 3 hardening slice by aligning product-admin route tests with the real permission-based admin wiring used in the application.

## Summary

The app routes product-admin endpoints through `RequirePermission(...)`, but parts of the product-admin test suite were still using `RequireRole(admin)` helpers. That left the reported product-grid/product-endpoint 403 area under-validated at the actual boundary used in production.

This PR updates the tests to exercise the real permission model:

- `products.read` grants product list access
- `products.write` grants product create/update access
- guest and customer identities remain blocked

## Why This Slice

This keeps the change narrow and high-value:

- no production behavior changes
- no route changes
- no permission model changes
- direct coverage for the admin products access path that has been reported as fragile in Track 3

## Changes

### Tests

Updated ../../../internal/interfaces/http/product_admin_test.go:

- Refactored audit helper routers to use `RequirePermission(rbac.ProductsRead)` and `RequirePermission(rbac.ProductsWrite)` instead of `RequireRole(identity.RoleAdmin)`
- Refactored guarded admin route test helpers to mirror production permission wiring
- Added `TestAdminGuard_SupportListAllowed`
- Added `TestAdminGuard_EditorAllowed`
- Added `TestAdminGuard_Integration_SupportTokenListAllowed`
- Added `TestAdminGuard_Integration_EditorToken`
- Updated the integration helper to mount both read and write product routes through permission guards

The new coverage proves:

- support can access `GET /api/v1/admin/products` through `products.read`
- editor can access `POST /api/v1/admin/products` through `products.write`
- customer remains forbidden for protected product-admin writes
- guest remains unauthorized
- bearer-token integration flow preserves the same permission behavior through `AuthMiddleware`

### Existing Related Coverage

Schema permission tests in ../../../internal/interfaces/http/schema_handler_test.go already covered:

- `product.grid` granted via `products.read`
- `product.form` granted via `products.write`

This PR completes the matching route-level coverage for the product data endpoint.

## Notes

This is a permission-boundary hardening slice, not a permission-model rewrite. The goal is to ensure the product-admin tests fail if route wiring regresses back to admin-role-only access or otherwise drifts away from the production `RequirePermission(...)` model.
