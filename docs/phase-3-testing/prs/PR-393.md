# PR-393 — Guest Order Notification And Confirmation Parity (Track 2)

## Summary

- order lifecycle notifications now work for guest orders: when `customer_id` is empty, the recipient falls back to the order's `contact_email`
- guest orders can be invoiced: the invoice domain accepts an empty customer id (guest identity stays on the referenced order)
- the guest checkout confirmation page no longer shows a broken "View Order" link and instead tells the guest where the confirmation email goes and that the order can be claimed later
- removed the stale unreachable `RequiresAuth` branch with outdated "checkout is only available to signed-in customers" copy

## Scope

### Notification (`internal/application/notification/service.go`)

- new `resolveOrderRecipient`: authenticated orders resolve via the customer record (unchanged behavior); guest orders use `order.ContactEmail` with no customer lookup; a guest order without contact email is an error
- `HandleOrderPaid` and `HandleShipmentShipped` use the resolver instead of `customers.FindByID(o.CustomerID)`
- `HandleInvoiceCreated` now loads the invoice's order and resolves the recipient from it, so guest invoices email the contact address; the existing invoice/event mismatch checks are unchanged
- fallback templates render a neutral salutation when `FirstName` is empty; email data carries a `Guest` flag
- enqueue logs include `guest`

### Email templates (`templates/emails/`)

- `order_confirmed.html`, `order_shipped.html`, `invoice_created.html`: the "View Order" button linking to the auth-gated `/account/orders/{id}` page is hidden for guest orders
- `order_confirmed.html`: guests get a note to keep the email as their order reference for later claiming

### Invoice (`internal/domain/invoice/invoice.go`, `internal/application/invoice/service.go`)

- `NewInvoice` allows an empty `customerID` (guest order invoice); `invoices.customer_id` is `TEXT NOT NULL` without an FK, so empty-string persistence needs no migration
- recipient data is intentionally **not** copied onto the invoice; it is derived from the referenced order at notification time, keeping the invoice a pure financial snapshot
- `invoice.generated` log includes `guest`

### Storefront checkout (`internal/interfaces/http/storefront_checkout.go`, themes)

- `StorefrontCheckoutConfirmation`: `ViewOrderURL` is now only set for authenticated customers and points at the account order page (`/account/orders/{id}`) instead of the JSON API endpoint; new `GuestEmail` field carries the guest contact email
- `checkout_confirm.html`: "View Order" renders only when a URL exists; guest confirmations show "A confirmation email will be sent to {email}… you can use that email address later to claim this order"
- `checkout_address.html`: deleted the dead `RequiresAuth` branch; removed the unused `RequiresAuth` field from `StorefrontCheckoutPageData`

### Logging (`internal/application/checkout/service.go`)

- `checkout.started` now logs `guest` and `has_contact_email` so both checkout paths are observable

## Tests

- guest notification coverage: `TestHandleOrderPaid_GuestOrder`, `TestHandleOrderPaid_GuestOrderMissingContactEmail`, `TestHandleShipmentShipped_GuestOrder`, `TestHandleInvoiceCreated_GuestOrder` (customer repo lookups fail the test if called on guest paths)
- `TestNewInvoice_EmptyCustomerID_AllowsGuestInvoice` (domain), `TestGenerateFromOrder_GuestOrder` (application)
- storefront flow assertions: guest confirm page shows the contact-email notice and no view-order link; authenticated confirm page links `/account/orders/{id}` and shows no guest notice
