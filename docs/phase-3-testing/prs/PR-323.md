# PR-323 — Admin Context Middleware Foundation (Track 3)

## Summary

Implemented the next Track 3 slice by introducing runtime admin-context propagation in the HTTP middleware chain.

This closes a gap left by PR-322: audit and handler code could read admin context, but the context was not consistently populated in production requests.

## Scope

- internal/interfaces/http/auth_middleware.go
  - added AdminContextMiddleware()
- cmd/api/main.go
  - wired AdminContextMiddleware() after AuthMiddleware
- internal/interfaces/http/auth_middleware_test.go
  - added tests for authenticated and guest behavior

## Behavior

### New middleware: AdminContextMiddleware

For authenticated requests:
- reads identity from request context
- resolves role permissions via RBAC
- writes admin.AdminContext into request context with:
  - AdminID
  - Permissions

For guest requests:
- passes through unchanged
- does not inject admin context

### Middleware ordering

Wired after auth token parsing:
- AuthMiddleware(tokenParser)
- AdminContextMiddleware()

This ensures admin context is derived from the final authenticated identity and is available to downstream handlers (including admin audit paths).

## Why this slice

Track 3 requires permission and usability hardening in admin surfaces.

PR-322 added admin audit + validation primitives. PR-323 makes those primitives operational by ensuring context is available at runtime, without changing endpoint contracts.

## Validation

- go test ./internal/interfaces/http -run 'AuthMiddleware|Require|AdminContextMiddleware|OrderAdmin' -count=1
- go build ./cmd/api

Both pass.

## Notes

- No API contract changes.
- No permission model widening.
- This is a foundation slice for upcoming context-aware admin behavior in later Track 3 phases.
