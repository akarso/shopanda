# PR-399 — Account Email Change With Step-Up And Re-Verification (Track 4)

Status: done

## Summary

- let a customer change their account email from the security area, behind the existing step-up gate
- require verification of the new address before it becomes the active login/notification email
- complete the sensitive ("account") side of the Track 4 account/profile split

## Why

Email is the customer's login identifier and recovery channel, but it is display-only everywhere:

- the profile page renders email read-only and `UpdateProfileInput` in `internal/application/auth/service.go` only carries first/last name
- Track 4's scope requires "editable account management flows" for credentials/basic identity; password change shipped (PR-310/311), email change did not
- all the building blocks already exist: step-up verification (`requireStorefrontSecurityVerification` in `storefront_account_security.go`), signed email-link tokens, and `email_verified_at` semantics from PR-313/314

## Scope

- flow: from `/account/security`, the customer submits a new email (step-up gated, like password change); a verification link is sent to the new address; the email only switches after the link is confirmed; the old address receives a notification that a change was requested
- application: auth service methods to request and confirm an email change (`RequestEmailChange` / `ConfirmEmailChange`), with the pending new address carried in the signed token payload, consistent with the existing email-link machinery
- token invalidation: a new change request revokes all previously issued pending tokens — embed a nonce/`issued_at` in the token payload and record the latest value per customer (single column or equivalent); `ConfirmEmailChange` only applies the change when the token carries the latest nonce, so an older link can never overwrite a newer request
- uniqueness: validated twice — at request time (immediate validation error before any email is sent) and again at confirmation time (guards the race where the address was registered between request and confirm)
- session/JWT: after the change, the display name/email claims refresh on next token issuance; existing sessions stay valid
- guards: the change-request endpoint sits behind authenticated session + verified email + step-up, identical to `POST /account/security/password`; same email send cooldown as the existing link flows
- tests: full flow tests (request, confirm, conflict, expired token), step-up guard tests, notification-to-old-address test

## Out Of Scope

- phone numbers or additional identity fields (not on the `Customer` model; add only with a real requirement)
- login-time 2FA / TOTP (registration email verification plus step-up is the accepted Track 4 model; see deferred items in the ROADMAP)

## Validation

- a signed-in, step-up-verified customer can change their email and log in with the new address only after confirming the link
- an unconfirmed change leaves the old email fully functional
- the old address is notified about the change request
- an expired token is rejected cleanly and leaves the account unchanged
- a token from a superseded request (older nonce) is rejected after a newer request was made
- confirming fails with a clear error when the new address was registered by another customer after the request (race guard); requesting fails immediately when the address is already taken
- the change-request and confirm endpoints reject sessions without step-up verification (and unauthenticated requests)
- `go test ./internal/application/auth ./internal/interfaces/http -count=1`

## What Changed

- **domain** (`internal/domain/customer`): added `Customer.PendingEmailNonce` plus `SetPendingEmailNonce` / `ApplyEmailChange` helpers; new `EventEmailChangeRequested` / `EventEmailChangeNotified` events with `EmailChangeRequestedData` (carries `NewEmail` + `VerifyURL`) and `EmailChangeNotifiedData` (carries `OldEmail` + `NewEmail`).
- **persistence**: migration `045_add_customers_pending_email_nonce.sql` adds a single `pending_email_nonce TEXT NOT NULL DEFAULT ''` column; `postgres.CustomerRepo` reads/writes it in `FindByID`, `FindByEmail`, `Create`, and `Update`.
- **application** (`internal/application/auth`): `RequestEmailChange` validates/normalizes the address, rejects the current address and already-taken addresses (uniqueness at request time), records the latest nonce (invalidating older links), and publishes the verify-new-address + notify-old-address events; `ConfirmEmailChange` only applies the change when the token nonce matches the stored latest nonce and the address is still free (re-checked, plus unique-violation mapped to conflict), marks the new address verified, clears the nonce, and leaves token generation untouched so existing sessions stay valid.
- **signed token** (`storefront_account_security.go`): `account_email_change` purpose with a dedicated claims payload embedding the new email, nonce, and expiry; `emailChangeToken` / `verifyEmailChangeToken` / `newStorefrontEmailChangeNonce` reuse the existing HMAC email-link machinery.
- **storefront** (`storefront_account_email.go`): `POST /account/security/email` (step-up gated like password change, same email cooldown) requests a change; `GET /account/security/email/confirm` validates the link and applies the change from any device (no session required). The security page renders an email-change form plus success/error notices; `GET /account/security` shows a "check your new email" confirmation after a request.
- **notification**: `HandleEmailChangeRequested` sends the confirmation link to the new address (carried in the event, not the account's current email); `HandleEmailChangeNotified` alerts the current address. Two fallback templates registered (`email_change_verification`, `email_change_notice`).
- **wiring** (`cmd/api/main.go`): new routes registered and both events subscribed to the notification service.
- **tests**: auth service flow tests (request success, same/taken/invalid email, confirm success, superseded nonce, no-pending, race conflict); HTTP handler tests (request sends link + notice, step-up + auth guards, taken-email rejection, confirm applies/invalid/superseded/race); notification handler tests (verification to new address, notice to old address, invalid URL).
