# PR-328 — PR-E Scoped Editing UX For Settings (Track 3)

## Summary

Implemented the next Track 3 slice by exposing scope contracts directly in the admin Settings UI with explicit labels and edit affordances.

This builds on PR-327 backend contracts (`field_scopes`, `scope.store_id`) and makes scope visible to operators while editing settings.

## Scope

- internal/interfaces/http/admin/dist/admin.js
  - Settings page now consumes and uses config payload scope metadata (`field_scopes`, `scope.store_id`)
  - added a settings scope banner that shows whether edits are applied to:
    - global defaults, or
    - the active store override context
  - added explicit per-field scope badges:
    - Global
    - Store-scoped
    - Translatable (supported for future fields)
  - added scope notes on settings forms to clarify where edits apply
  - wired existing forms (Store, Email, Media, Currency, Tax) to render scope badges/notes from backend metadata
- internal/interfaces/http/admin/dist/admin.css
  - added styles for:
    - settings scope banner
    - scope badges
    - scope notes
- internal/interfaces/http/admin_handler_test.go
  - added static asset assertions for new scope UX markers in CSS/JS

## Behavior

### Explicit scope visibility in Settings

Operators now see the active settings scope immediately at the top of the page.

### Per-field scope cues

Each settings field now shows an explicit scope badge, reducing ambiguity between global and store-specific edits.

### Scope-aware editing affordances

Form-level notes explain whether current edits apply globally or as store overrides for the selected store context.

## Why this slice

PR-E requires scope to be obvious in page-level UI. This implementation keeps the UX simple and explicit while reusing the contract introduced in PR-327.
