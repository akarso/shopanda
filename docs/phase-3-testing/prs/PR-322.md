# PR-322 — Admin Order Hardening (Track 3, Phase A)

## Summary

Implement Track 3 admin hardening by adding audit logging, enhanced validation, and permission controls to admin order endpoints. This is the first concrete PR in Track 3: "Admin Bootstrap, Permissions, And Usability Hardening."

## Scope

- **internal/application/admin/audit.go**: new auditing service for logging admin actions with compliance context
- **internal/application/admin/validation.go**: validation helpers for admin operations (order ID validation, pagination safety)
- **internal/interfaces/http/order_admin.go**: updated order admin handler with Track 3 hardening (audit logging, enhanced validation, clearer error handling)

## Implementation Details

### 1. Admin Audit Service (`internal/application/admin/audit.go`)

Provides deterministic audit logging for admin actions:

- **AuditAction** enum: standardized action types (order.list, order.read, order.update, order.status_change)
- **AuditEntry** struct: represents a single audit log entry with admin ID, action, resource type, and details
- **Auditor** service: logs audit events with structured fields for downstream audit systems or SIEM integration

Benefits:
- All admin order operations are logged with the admin's ID, action type, and result
- Failed operations are logged at WARN level for immediate alertability
- Audit entries include contextual details (old/new status for transitions, pagination params for lists)
- Future extension: audit table persistence or event bus integration

### 2. Admin Validation (`internal/application/admin/validation.go`)

Provides input validation and context handling:

- **OrderValidator**: validates order IDs (not empty, max 255 chars) and pagination (min/max limits, offset bounds)
- **AdminContext**: carries admin ID, email, permissions, and optional store scope through request context
- **AdminContextKey**: safe context key for AdminContext retrieval

Benefits:
- Prevents resource exhaustion via pagination abuse (max 1000 items per page)
- Blocks injection via ID validation (length limits)
- Centralizes validation logic for reuse across admin endpoints
- Prepares for store-scoped operations (Track 3 later phases)

### 3. Enhanced Order Admin Handler (`internal/interfaces/http/order_admin.go`)

Updated handler with Track 3 hardening:

**List (`GET /api/v1/admin/orders`)**:
- Validates pagination parameters before querying database
- Logs list access with admin ID, offset, limit for audit trail
- Errors logged at WARN level with context

**Get (`GET /api/v1/admin/orders/{orderId}`)**:
- Validates order ID to prevent injection/resource exhaustion
- Logs successful reads with admin ID and order ID for compliance
- Does NOT log 404 events to prevent enumeration attacks
- Errors logged with admin context

**Update (`PUT /api/v1/admin/orders/{orderId}`)**:
- Enhanced validation: order ID, request body size limits, target status validation
- Logs old → new status transition with admin ID for audit trail
- Logs failed attempts with error reason for security investigation
- Does NOT log order-not-found to prevent enumeration

## Design Decisions

1. **Audit Logging Is Comprehensive**: Every admin operation logs action, admin ID, and result. Failed operations log at WARN level for alertability.

2. **Pagination Safety**: Max 1000 items enforced to prevent O(N) scans or DoS via large offset values.

3. **No Enumeration Leaks**: Order-not-found (404) does not audit to prevent an attacker from determining which order IDs exist via audit logs.

4. **AdminContext Extraction**: Optional (returns "system" if missing) to allow graceful degradation in tests and future context-aware phases.

5. **Minimal Breaking Changes**: Existing API contracts unchanged; audit logging is additive.

## Integration Notes

1. **Audit Logs**: Currently logged via structured logger (info/warn level). Future phases can:
   - Route to dedicated audit database table
   - Emit to event bus for downstream compliance systems
   - Export to SIEM/audit tools

2. **Admin Context**: Currently populated by auth middleware if admin is logged in; "system" used otherwise. Future phases will:
   - Ensure context is always populated by auth/permission middleware
   - Add store scope to context for store-scoped operations
   - Use context in all admin handlers

3. **Permissions**: OrderAdmin endpoints still use `requireOrdersRead` / `requireOrdersWrite` middleware. This PR lays groundwork; permission enforcement happens at middleware layer.
