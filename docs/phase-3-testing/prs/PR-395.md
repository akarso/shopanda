# PR-395 — Admin Scoped Product Editing (Track 3, PR-E Catalog)

Status: planned

## Summary

- deliver the catalog half of the deferred PR-E slice: product editing that distinguishes global, translatable, and store-scoped fields
- expose per-language product translations for editing in the admin, backed by the existing `content_translations` infrastructure
- surface store-scoped pricing in the product form using the existing pricing domain support
- make the global context switcher actually drive what the product form shows and saves

## Why

PR-328 shipped scoped editing for Settings only and explicitly deferred catalog/content ("catalog/content scoped editing will continue in follow-up slices", `docs/phase-3-testing/prs/PR-328.md`). Today:

- `internal/application/admin/product_schema.go` declares flat fields (name, slug, description, status) with no scope metadata
- the admin product form (`internal/interfaces/http/admin/dist/admin.js`, `renderProductForm` / `renderSchemaField`) has no scope banner or badges, unlike Settings
- `content_translations` exists and is consumed by storefront reads (`internal/infrastructure/postgres/content_translation_repo.go`), but there is no admin API or UI to write product translations
- the pricing domain supports store-scoped prices (`internal/domain/pricing/price.go`, `price_repo.go`), but the admin exposes no price editing per store
- the context switcher sends `X-Admin-Store-ID` / `X-Admin-Language` / `X-Admin-Currency` on every request, but `ProductAdminHandler` only uses them for audit metadata, never for data

## Scope

- schema: extend the product admin schema so each field declares its scope (`global` | `translatable` | `store`), mirroring the `field_scopes` model already used in `config_admin.go`
- translations API: admin endpoints to read/write product translations for the active language (reuse `content_translations`); writes go through the existing scoped audit logging in `product_admin.go`
- pricing API: admin endpoints to read/write the store-scoped price for the active store context, on top of the existing pricing repository
- UI: the product form shows the Settings-style scope banner and per-field scope badges; translatable fields load/save against the active language, store-scoped fields against the active store; global fields are clearly marked as affecting all stores
- behavior on context change: the product form reloads its scoped values for the new context (same re-route behavior the rest of the admin already uses)
- tests: handler tests for translation and scoped price read/write including partial-scope cases, plus the static JS guard updates in `admin_handler_test.go`

## Out Of Scope

- store-scoped product status/visibility (keep status global for now; note it as a follow-up only if a real need appears)
- category or page scoped editing (pages are PR-396; categories stay global)
- attribute management (placeholder nav section, deferred)

## Validation

- with language B selected, editing the product name changes only the language-B storefront rendering; the global name is untouched
- with store B selected, editing the price changes only store B's effective price
- audit log entries for translation and price writes include the full scope triad
- `go test ./internal/interfaces/http ./internal/application/admin -count=1`
