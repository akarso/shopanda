# PR-398 — Storefront Profile Completion: Addresses And Preferences (Track 4)

Status: done

## Summary

- add saved address management to the customer account area and prefill checkout from the default address
- add a preferences surface to the account area exposing the marketing consent that today exists only as an unlinked REST API
- complete the low-sensitivity ("profile") side of the Track 4 account/profile split

## Why

Track 4's split puts addresses and preferences on the profile side, but neither exists in the storefront:

- there is no `/account/addresses` route or template; addresses are only entered ad hoc during checkout (`checkout_address.html`) and never reusable
- marketing consent is implemented at `GET/PUT /api/v1/account/consent` (`internal/interfaces/http/account.go`) but has no storefront page and is not linked from account navigation
- the Track 4 open question "which fields belong in account versus profile" is unresolved for addresses, newsletter, and preferences

## Scope

- domain/persistence: a small saved-address model owned by the customer (label, recipient, street, city, postcode, country, default flag), repository, and migration; no overlap with the order address snapshot, which stays immutable on orders
- account UI: `GET /account/addresses` listing saved addresses with add/edit/delete and a default selection; linked from the account nav chips alongside Orders/Profile/Security
- checkout integration: when an authenticated customer has a default address, prefill the checkout address form with it; checkout continues to work unchanged with manual entry and for guests
- preferences UI: `GET/POST /account/preferences` rendering and saving marketing consent through the existing consent service; linked from the account nav
- gating: addresses and preferences are profile-side — authenticated session only, no step-up, consistent with `/account/profile`
- tests: handler tests for address CRUD and preferences, checkout prefill test, repo tests for the new repository

## Out Of Scope

- email/password/identity changes (account-side; email change is PR-399)
- per-customer locale preference (store-level locale stays the model for now)
- multiple address types beyond shipping default (no billing/shipping split until needed)

## Validation

- a signed-in customer can save addresses, mark one default, and see it prefilled at checkout
- a signed-in customer can view and toggle marketing consent from the account area
- profile-side pages remain accessible without step-up verification
- `go test ./internal/interfaces/http ./internal/infrastructure/postgres -count=1`

## What Changed

- domain: added `customer.Address` (with `Validate`/`Apply`) and `customer.AddressRepository` (`internal/domain/customer/address.go`, `address_repository.go`)
- persistence: `migrations/044_create_customer_addresses.sql` (FK to `customers` with `ON DELETE CASCADE`, partial unique index enforcing at most one default per customer) and `postgres.CustomerAddressRepo` with transactional default handling (`internal/infrastructure/postgres/customer_address_repo.go`)
- account UI: `GET /account/addresses` lists saved addresses with add/edit/delete and default selection; `GET/POST /account/preferences` reads and saves marketing consent through the existing `legal.ConsentRepository`, preserving the analytics flag. Handlers live in `internal/interfaces/http/storefront_account_profile.go` and are gated by `requireStorefrontAccount` (session only, no step-up)
- navigation: extended `StorefrontAccountNavData`/`storefrontAccountNav` with Addresses + Preferences chips and added them to every account template
- checkout: authenticated checkout address GET is prefilled best-effort from the customer's default saved address and account email (`prefillCheckoutFromDefaultAddress`); manual entry and guest checkout are unchanged
- templates: new `account_addresses.html` and `account_preferences.html`
- wiring: `customerAddressRepo` constructed in `cmd/api/main.go`, injected via `StorefrontHandler.WithAccountProfile(addresses, consents)`, and the new routes registered
- tests: handler tests for address CRUD, ownership enforcement, preferences, and checkout prefill (`storefront_account_profile_test.go`); Postgres repo tests for default exclusivity, update/delete, and ownership (`customer_address_repo_test.go`)
