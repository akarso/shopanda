# PR-313 — Storefront Email-Link Security Verification

## Summary

Continued Track 4 with the next step-up authentication slice on top of PR-312.

This PR keeps the existing password re-entry checkpoint for stale storefront sessions, but adds an email-link fallback on the same verification page. A shopper who does not want to type their password again can request a secure, time-limited verification link to their account email, click it while still signed in, and continue into `/account/security` with the same short-lived verification cookie flow used by the password path.

## Scope

### Security-verification notification event

- updated `internal/domain/customer/events.go`
- added a dedicated `customer.security_verification.requested` event and payload for storefront security-email delivery
- updated `internal/application/auth/service.go`
- added `RequestSecurityVerificationLink(...)` so the storefront security flow can request delivery without taking a direct dependency on notification infrastructure

### Email-link verification flow

- updated `internal/interfaces/http/storefront_account_security.go`
- added a stateless signed email token that encodes the current customer id, allowed redirect target, and expiry
- added absolute-link generation for `/account/security/verify?email_token=...`
- extended the existing verify page handler so it can:
  - request a security email link from the current signed-in session
  - accept a clicked email token
  - set the normal storefront security verification cookie after a valid email-link click

### Notification delivery

- updated `internal/application/notification/service.go`
- added a dedicated email template and notification handler for storefront security verification links
- updated `cmd/api/main.go`
- wired the new customer event into the existing async notification pipeline

### Storefront verify-page UX

- updated `themes/default/templates/account_security_verify.html`
- added a second action that sends a secure verification link to the signed-in account email
- added a success state after the request is accepted so the shopper understands the next step

- added focused storefront coverage for:

## Notes

- this PR deliberately complements the existing password-based checkpoint rather than replacing it; both step-up paths now terminate in the same short-lived storefront verification cookie
- the next Track 4 slice can widen this into registration-time email verification or stricter rules about which sensitive account surfaces require email-link verification versus password re-entry
