# PR-333: Order Admin Scoped Audit Logging

**Track 3 Admin Context Hardening — Slice 3 of N**

## Summary

Extends Track 3 scope-aware audit logging pattern to the Order Admin API. Admin scope context (`store_id`, `language`, `currency`) is now explicitly extracted from request headers, validated, and injected into all order admin audit entry Details maps. This ensures scope visibility for compliance and security auditing across all admin operations.

**Goal**: Order admin audit trail now includes full scope context alongside operation details.

---

## Changes

### Backend: `internal/interfaces/http/order_admin.go`

**Added Scope Detail Extraction**

- New helper: `adminScopeDetailsFromRequest(r *http.Request) map[string]interface{}`
  - Extracts AdminContext from request (populated by upstream middleware)
  - Safely includes non-empty `store_id`, `language`, `currency` in Details map
  - Returns empty map if admin context is missing or incomplete

**Updated Order Admin Handlers**

1. **List Handler**: 
   - Scope details injected into both success and error audit entries
   - Pagination context (offset, limit) merged with scope details

2. **Get Handler**:
   - Scope details injected into both success and error audit entries
   - Scope visible in read-access audit logs for compliance

3. **Update Handler**:
   - Scope details injected into all audit entry types (body parse errors, validation errors, success)
   - Consistent with PR-331 config admin pattern

**Audit Entry Pattern**

All order admin audit entries now follow:
```go
admin.AuditEntry{
    AdminID:      adminID,           // "admin-1" or "system"
    Action:       admin.AuditOrderXXX, // order.list, order.read, order.update
    ResourceType: "orders|order",
    ResourceID:   orderID,
    Result:       "success|error",
    Error:        errMsg,            // if Result == "error"
    Details: map[string]interface{}{
        "store_id":  "store-eu",      // Scope: store identifier
        "language":  "en",            // Scope: language context
        "currency":  "EUR",           // Scope: currency context
        // + operation-specific details (offset, limit, status, etc.)
    },
}
```

## Design Rationale

### Why Scope Context in Audit Details?

1. **Compliance**: Scope-scoped operations must be traceable by scope (multi-store audit trails)
2. **Security**: Anomaly detection across store/language/currency boundaries
3. **Consistency**: Matches PR-331 config admin pattern; aligns Track 3 audit hardening

### Why Not Query String?

- Scope is organizational metadata, not resource mutation parameter
- Request headers (X-Admin-*) are cleaner than querystring for metadata
- Follows hexagonal architecture: HTTP adapter receives/extracts; domain stays clean

### Why Separate Details Keys?

- `store_id` (not `scope_store`): Aligns with config admin Keys convention
- `language`, `currency`: Clear, flat structure for log parsing and alerting
