# PR-1554 — Optional customer identity on plugin public routes

Status: done

## Summary

Verified that core `AuthMiddleware` already runs on `RegisterPublicRoute`
handlers. The Metal Dogs gap was: a non-customer `Authorization` Bearer
(owner token) caused 401 before the storefront session cookie was read, so
product sites skipped JWT middleware and `EnsureStorefrontCart` wrote the
guest cart. Classify parser errors: opaque / malformed bearer
(`auth.ErrNotCustomerToken`) may use the session cookie or continue as guest;
expired/revoked/tampered customer JWTs stay hard 401 without consulting the
cookie.

## Scope

- `auth.ErrNotCustomerToken` + `jwt.ErrMalformedToken`; validating parser wraps
  malformed bearers
- `AuthMiddleware`: EqualFold `Bearer` + trim token; valid JWT wins; opaque
  bearer → session → guest; failed customer JWT → 401 (no cookie fallback)
- Staff Bearer defers to session on storefront/plugin paths only; `/api/v1/admin`
  and `/api/v1/auth` keep the Bearer. Staff-only identity still shops as that
  account (`StorefrontActorID` / `CustomerID` for any non-guest role)
- Opaque = malformed (not three JWT segments) only; JWT-shaped `a.b.c` stays 401
- `pkg/storefrontsession.SessionCookieName` / `SessionTokenFromRequest`
- Docs: EXTENSION_POINTS / ROADMAP follow-up → done

## Out of scope

- No C4 change — middleware behavior only
- Does not change RequireAuth or admin auth
- Product sites that fully omit AuthMiddleware still need to keep it (or an
  equivalent session parse) on customizer routes
