# PR-1546 — Declarative Needs

Status: done

## Summary

- `pluginsdk.Capability` (`CapCart`, `CapCatalog`, `CapOrders`, `CapDB`) aliases `plugin.Capability`.
- Optional `pluginsdk.NeedsDeclarer` and `plugin.NeedsDeclarer`; `Host.Require(cap)` during Init.
- `plugin.App` tracks required vs satisfied capabilities; `AssertNeedsMet()` fail-closed after binding.
- `CapCart` is late-bound in `serve` after `cart.Service` exists; other caps bind before InitAll.

## Why

Composition roots (serve, worker, CLIs) must refuse boot when a plugin declares a capability the process cannot provide.

## Scope

- `internal/platform/plugin/service_ports.go`, registry records `NeedsDeclarer` + `FreezePluginNeeds`.
- `pkg/pluginsdk/capability.go`, `adapt.go`, `Host.Require`.
- `AssertNeedsMet` at DB-backed entrypoints (worker/scheduler/CLIs without cart may fail if a plugin Needs `CapCart`) — **fixed in PR-1547 follow-up**: see `AssertNeedsMetExcept` below.
- `RecordNeeds` is a no-op once `FreezePluginNeeds` has run (a late `Host.Require` from code that outlived `Init`, e.g. an HTTP handler closure, must not poison the required-capability set after the gate already ran).
- `AssertNeedsMet`'s error names the plugin(s) that declared the unmet capability (`App.CurrentPluginName()` is tracked during `InitAllContext` and attributed per `RecordNeeds` call), e.g. `plugin: required capability "cart" not bound (needed by extref/reference)`.

## Out of scope

- Enforcing needs inside `InitAllContext` before late cart bind (callers invoke `AssertNeedsMet`).
