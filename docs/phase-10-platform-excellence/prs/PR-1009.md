# PR-1009 — Readiness Probe

Status: planned

## Summary

- Add `/readyz` that pings the database with a bounded timeout (503 on failure/timeout)
- Keep `/healthz` as process liveness; **Docker `HEALTHCHECK` stays on `/healthz`**
- Document `/readyz` as the traffic/readiness probe for orchestrators/load balancers

## Why

`/healthz` returns static 200. Containers with a dead DB can still pass a mis-aimed healthcheck if readiness is conflated with liveness. Preserve the distinction: process up vs ready for traffic.

## Scope

- `GET /readyz` → 200 if `db.PingContext` succeeds within a **finite timeout** (request context deadline or explicit timeout, e.g. 1–2s); else **503**
- Never wait indefinitely on a hung DB
- `GET /healthz` unchanged (process up)
- **Dockerfile `HEALTHCHECK` remains `/healthz`** (liveness)
- Update compose/docs: use `/readyz` for readiness/traffic control; `/healthz` for container liveness
- Tests:
  - fake ping success → 200
  - ping error → 503
  - slow/unreachable DB (blocked ping past timeout) → 503 without hanging the handler

## Out Of Scope

- Checking Redis/Meili/Rabbit in ready (optional later knobs)
