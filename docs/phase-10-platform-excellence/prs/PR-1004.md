# PR-1004 — Login Abuse Protection

Status: done

## Summary

- Enable HTTP rate limiting by default (`rate_limit.enabled=true`, default 10/s burst 20)
- Add failed-login lockout keyed by **IP + normalized email** for API and storefront login
- Default counter store: **`cache`** (shared via configured cache driver); `memory` allowed for single-instance only

## Why

Security audit High: unlimited credential stuffing against `/api/v1/auth/login` (and storefront `/account/login`) when rate limiting was off by default and no lockout existed.

## Scope

- Flip default `rate_limit.enabled` to `true` in `defaults()`, `configs/config.example.yaml`, `.env.example`
- Example stricter `per_route` for `/api/v1/auth`
- `auth.lockout` config: enabled, store (`cache`|`memory`), max_failures, window
- Application-layer lockout on `auth.Service.Login` (covers customer + admin password login)
- Handlers pass `ClientIP` using existing trusted-proxy helper
- Tests: lockout after N failures, reset on success, TTL expiry, IP+account keying, config defaults/env

## Out Of Scope

- No change — Captcha / external WAF
- No change — MFA attempt guard (already separate in MFA service)

## Counter store policy

| Mode | When to use | Strictness |
| --- | --- | --- |
| `cache` (default) | Multi-instance; counters in postgres/redis cache | Atomic `cache.Incr` under a healthy cache; check/increment/reset still **fail open** on store errors |
| `memory` | Single-instance only; bounded map (max 100k entries) + TTL; startup warning | Strict within one process only |
