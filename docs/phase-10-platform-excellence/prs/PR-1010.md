# PR-1010 — Release to GHCR

Status: done

## Summary

- On version tag, build and push container image to GHCR
- Deploy via **full commit-SHA tag or image digest** as the immutable identifier; version tags are convenience aliases only

## Why

Current "release" practice recommits `api`. Need immutable artifacts for deploys.

## Scope

- `.github/workflows/release.yml` on `v*` tags
- `docker build` + push:
  - **Immutable:** `ghcr.io/<org>/shopanda:sha-<full40gitsha>` and/or push-by-digest
  - **Alias only:** `ghcr.io/<org>/shopanda:<version-tag>` (mutable convenience; not the deploy pin)
- Do **not** describe short-SHA or version tags as immutable
- Permissions `packages: write`
- `DEPLOYMENT.md`: pin deploys to full SHA tag or digest; version tag optional alias
- `workflow_dispatch` dry-run (build+load, no push) for sandbox validation

## Out Of Scope

- Multi-cloud deploy automation
- SBOM signing (nice-to-have follow-up)

## Validation

- `go test ./...` — pass (no `.go` files touched by this PR; full suite run as a regression check)
- `go build ./cmd/api/` — pass
- `.github/workflows/release.yml` parses as YAML — pass
- Local `docker build` / smoke: blocked here (Docker daemon not running); covered by Release workflow smoke step (`test -x /usr/local/bin/shopanda`) on tag push or dry-run dispatch
- Live GHCR push requires a `v*` tag (or `workflow_dispatch` with dry_run=false) on the repo
- Re-releasing an already-published commit is rejected by the "Guard — sha tag must stay immutable" step (`docker buildx imagetools inspect` on the existing `sha-<sha>` tag) before any build/push happens, since Alpine packages are installed unpinned and a rebuild of the same commit is not guaranteed to be byte-identical
