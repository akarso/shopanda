## Summary

- Optional Prometheus `/metrics` (default **disabled**), served on a **dedicated listener** separate from the main app/worker port
- Instrument RED metrics for HTTP plus checkout/job/webhook counters with **bounded labels**

## Why

Zero metrics today. For commerce (orders, payments, queues) logs alone are insufficient for A+.

## Scope

### Exposure / defaults

- Default: metrics **disabled** (`metrics.enabled: false`)
- When enabled: `/metrics` is served on its own `http.Server` bound to `metrics.listen` (default `127.0.0.1:9090`, loopback-only) — **not** mounted on the public API/worker port and **not** behind any app middleware
- No built-in auth on `/metrics` itself; isolation is via bind address (loopback by default) and operator network policy (private scrape network / reverse-proxy auth) if `metrics.listen` is changed to a non-loopback address — documented in RUNBOOK/DEPLOYMENT
- Tests: disabled → recorder is a no-op and `newMetrics` returns a `nil` handler (no listener started); enabled → handler serves Prometheus text format on the configured address only

### Labels (bounded)

- HTTP: route **template** from `http.ServeMux`'s matched pattern (e.g. `/api/v1/products/{id}`) via `Router.RoutePattern`, not raw URL/query string; unmatched routes collapse to a fixed `"unmatched"` label
- Status is bucketed to `2xx/3xx/4xx/5xx` (`statusClass`), not exact codes
- Checkout/webhook outcome is a fixed two-value enum (`success`/`failed`)
- Job failures are labeled by `job.Type`, which is a small fixed set of registered job types (not user input)
- **Excluded** from all labels: raw URLs, query strings, user IDs, order IDs, webhook destination URLs, emails

### Instrumentation

- Client: `prometheus/client_golang` (added as a new dependency)
- `shopanda_http_requests_total{route,method,status_class}` (counter) + `shopanda_http_request_duration_seconds{route,method,status_class}` (histogram) — recorded by `MetricsMiddleware`, the **outermost** middleware in the chain
- `shopanda_checkout_result_total{outcome}` — recorded in `checkout.Workflow.Execute` via `defer`
- `shopanda_job_failures_total{job_type}` — recorded in `jobs.Worker` on handler error or unknown job type
- `shopanda_webhook_deliveries_total{outcome}` — recorded in `webhook.DeliverHandler.Handle` via `defer`, skipping deliveries that were never attempted (e.g. no matching subscription)

## Out Of Scope

- Full Grafana dashboards (example PromQL queries in docs only)
- OpenTelemetry (PR-1024)
- Auth/TLS on the metrics listener (bind-address isolation only; documented as an operator responsibility if exposed beyond loopback)

## Code review follow-ups, round 2 (applied — found during PR-1022 review)

The first round's webhook-skip fix only covered the missing-`endpoint_id`/`event_name` check; a second gap and two more issues surfaced in a later review pass:

| Finding | Action |
| --- | --- |
| `buildDeliveryBody` error (malformed `event_data_json`) still recorded as `OutcomeFailed` — the fix above only set `skipped` for the missing-field check, not this later return path, so a bad JSON payload still counted as a real delivery failure | Set `skipped = true` before returning the `buildDeliveryBody` error in `deliver_handler.go`; added `TestDeliverHandler_WithMetrics_MalformedEventDataJSONNotCounted` (the existing `MalformedPayloadNotCounted` test only exercised the missing-`endpoint_id` path, not this one) |
| `job.Type` passed straight through to `metrics.JobFailure` on the "handler not found" path — an unbounded Prometheus label in principle (only "bounded in practice" by the convention that enqueue sites use compile-time constants, per the old comment) | `worker.go`'s handler-not-found branch now records the fixed sentinel `"unknown"` instead of the raw dequeued `job.Type`; the registered-handler failure path is untouched (that `job.Type` is inherently bounded — it only reaches `metrics.JobFailure` after matching a registered handler). Strengthened `TestWorker_FailsUnknownType_RecordsMetric` to enqueue a distinctly bogus type instead of the literal string `"unknown"`, which had been passing regardless of whether the fix was applied |
| `runServe` leaked the worker goroutine if `startMetricsServer` failed: `workerCancel`/`workerDone` were never invoked on that early-return path (flagged directly by `go vet`, confirmed real) | `main.go`: on metrics startup failure, cancel and bounded-wait on the worker (and scheduler, if embedded) via the existing `runtime.ShutdownBackground` helper before returning the error |
