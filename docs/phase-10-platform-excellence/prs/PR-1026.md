# PR-1026 — Extension Guide + Runbook

Status: done

## Summary

- Add decision guide for events vs hooks vs pipelines vs workflows vs composition steps
- Expand `RUNBOOK.md` into a real ops playbook (DB down, bad migration, rollback, webhook SSRF rejects, rate-limit lockouts)

## Why

Thirteen registries and overlapping extension mechanisms create cognitive tax (architecture audit). `RUNBOOK.md` is currently a stub pointer page.

## Scope

- New `docs/guides/EXTENSION_POINTS.md` with examples pointing at real packages
- Expand root `RUNBOOK.md`: incident symptoms → checks → commands
- Link from `PLUGINS.md` and `DEVELOPER.md`
- **Approved docs-only exception** (see phase README): no production code change required; deliverable is operator/integrator documentation after Tracks A–E code has landed

## Out Of Scope

- Collapsing registries into one framework (explicitly not a goal)

## Implementation notes

- **`docs/guides/EXTENSION_POINTS.md`** (new) — a decision-first guide, distinct from `PLUGIN_COMPOSITION.md`: this one answers "which mechanism do I use and what exactly is it," `PLUGIN_COMPOSITION.md` answers "how do multiple plugins coordinate on the same seam" (ordering, precedence, task→mechanism table). They cross-link rather than duplicate content.
  - A decision tree at the top covering all five named mechanisms (events, hooks, pricing pipeline, checkout workflow, composition steps).
  - One section per mechanism with the real interface definition, file path, and a minimal real-package code snippet — verified against source directly (`internal/platform/event/bus.go`, `internal/application/hooks/registry.go`+`context.go`, `internal/domain/pricing/step.go`+`pipeline.go`, `internal/application/checkout/step.go`+`workflow.go`, `internal/application/composition/step.go`+`pipeline.go`), not paraphrased from memory.
  - Calls out two concrete gotchas the architecture audit's "cognitive tax" framing was really about: (1) `internal/domain/pricing.Pipeline` and `internal/application/composition.Pipeline[T]` share a name but are unrelated types with no common interface; (2) composition steps' `Apply(ctx *T) error` takes no `context.Context`, unlike every other mechanism, which is easy to miss when copying a pattern from checkout/pricing.
  - A registries table enumerating all 13 registries reachable from `plugin.App` (matching the audit's count) — name, file, what it registers, plugin-facing API — plus two registries found that exist but aren't currently exposed through `plugin.App` (`catalog.AttributeRegistry`, `admin.Registry`), flagged explicitly as unconfirmed/possibly-core-only rather than silently omitted or wrongly documented as plugin-reachable.
- **`RUNBOOK.md`** — added a new "Incident response" section (placed right after the intro links, before "Planning") with the 5 requested scenarios in symptom → check → fix style: database unreachable, bad migration, rollback (deploy/migration/plugin config — documents what rollback mechanism does and doesn't exist, rather than describing a scripted rollback that isn't real), webhook SSRF rejects, rate-limit/login lockouts. Each links back to the existing fuller reference section below it (e.g. "Outbound webhooks (SSRF)", "Rate limiting and login lockout") rather than duplicating detail. Also added a 4th line to the guide-links list at the top pointing to `EXTENSION_POINTS.md`.
- **Research discipline:** every fact used in both documents (log message strings, exact error prefixes, config defaults, env var names, what does/doesn't exist) was verified against current source — migration transaction-wrapping in `internal/platform/migrate/migrate.go`, SSRF blocklist and error strings in `internal/platform/ssrf/ssrf.go`, lockout store/key mechanics in `internal/application/auth/lockout.go`+`service.go`, liveness/readiness handlers in `internal/interfaces/http/health.go` — not assumed from the architecture-audit framing or written from memory. Where no remediation mechanism exists in code (webhook SSRF allowlist override, admin lockout-unlock endpoint, scripted deploy rollback), the runbook says so explicitly instead of inventing an operational procedure the code doesn't support.
- **Linking (scope item "Link from PLUGINS.md and DEVELOPER.md"):**
  - `PLUGINS.md` § Extension mechanisms: added a pointer to `EXTENSION_POINTS.md` at the top of the section, and added three missing rows to the mechanism table itself — **Hooks**, **Extension fields**, and **Import/export row hooks** were all absent from that table despite being shipped, first-class mechanisms (confirmed via grep — this predates this PR and wasn't something PR-1026 introduced). Leaving them out while publishing a new guide that treats hooks as a first-class mechanism would have made the two documents visibly contradict each other, so this was fixed as a minimal, directly-scoped correction rather than left as-is.
  - `DEVELOPER.md`: added `EXTENSION_POINTS.md` to the intro paragraph, the table of contents, and inline pointers at both the "Add Custom Pipeline Steps" and "Add Custom Event Listeners" section headers (the two places a reader is actively choosing a mechanism).
  - `PLUGIN_COMPOSITION.md`: added a reciprocal link to `EXTENSION_POINTS.md` in its own "Related" list, since `EXTENSION_POINTS.md` links into it heavily for the multi-plugin-coordination material it deliberately doesn't duplicate.
