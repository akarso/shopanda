# PR-1025 — pgx Driver Migration

Status: done

## Summary

- Replace maintenance-mode `lib/pq` with `jackc/pgx/v5` (stdlib `pgx/v5/stdlib` bridge acceptable)
- Keep SQL and repository behavior identical

## Why

`lib/pq` is in maintenance mode; pgx is the maintained driver and improves context/TLS ergonomics.

## Scope

- Swap driver import/registration in `platform/db`
- Fix any pq-specific error type switches → pgx/pgconn equivalents
- CI integration tests green
- Benchmark not required; smoke import/checkout paths

## Out Of Scope

- Rewriting repos to pgx-native APIs
- Connection pool redesign beyond pgx defaults

## Implementation notes

- Driver registered via the `pgx/v5/stdlib` `database/sql` compatibility bridge, under driver name `"pgx"` (was `"postgres"`) — `internal/platform/db/db.go` and every test file that opened its own `*sql.DB` for integration tests.
- `pq.Array(...)` wrapping on query *arguments* was removed outright (not replaced) — pgx's `stdlib.Conn.CheckNamedValue` passes Go values straight to pgx's own encoder, which natively encodes slices (`[]string`, `[]int`, `[]time.Time`) as Postgres arrays. Affected: `price_history_repo.go`, `price_repo.go`, `order_repo.go`, `return_repo.go`, `extension_value_repo.go`, `stock_repo.go`, `variant_repo.go`, `zone_repo.go`, `webhook_endpoint_repo.go`, `plugins/b2b/pricing/postgres_repo.go`.
- `pq.Array(&dest)` wrapping on *scan* destinations is NOT a drop-in removal — pgx's stdlib driver falls back to returning unrecognized column types (including arrays) as their raw text-literal wire form, which `database/sql` would then fail to assign to a `[]string`. Fixed via `pgTypeScanner(dest)` (`internal/infrastructure/postgres/zone_repo.go`), which builds a fresh `pgtype.NewMap()` per call and returns its `.SQLScanner(dest)` — used at each array-column scan site: `zone_repo.go` (`countries`) and `webhook_endpoint_repo.go` (`events`). See Round 2 below for why this is call-local rather than a shared package-level map.
- `pq.Error` → `pgconn.PgError`; the only fields actually used in this codebase besides `.Code` were `.Constraint` (renamed to `.ConstraintName`) — mechanical across ~14 repo files. All four sites that had used a raw `err.(*pgconn.PgError)` type assertion instead of `errors.As(err, &pgErr)` (silently failing to match if the error is ever wrapped) were brought in line with the rest of the migration: `content_block_repo.go`, `store_credit_repo.go`, `plugins/b2b/groups/postgres_repo.go`, `plugins/b2b/pricing/postgres_repo.go`. The `pqErr` variable name (confusing once `lib/pq` is gone) was renamed to `pgErr` repo-wide.
- Opportunistic fix: `plugins/b2b/plugin_test.go` had no database driver blank-import at all anywhere in its transitive import graph (confirmed via `go list -test -deps`) — a pre-existing latent bug, invisible unless `SHOPANDA_TEST_DSN` is set, that would have failed with "unknown driver" on its `sql.Open("pgx", dsn)` call. Fixed by adding the pgx import while touching this exact call site.
- `lib/pq` fully removed from `go.mod`/`go.sum` via `go mod tidy`.
- Confirmed via `go test -race` that a `*pgtype.Map` shared across concurrent requests races on its first `SQLScanner(...).Scan(...)` call (its internal reflect-type cache is built lazily with no locking) — not just a theoretical concern. `pgTypeScanner` (`internal/infrastructure/postgres/zone_repo.go`) avoids this by never sharing the map across calls at all — see Round 2 below.
- Added `database.query_exec_mode` (`SHOPANDA_DATABASE_QUERY_EXEC_MODE`) config, validated against pgx's five allowed values. Needed because pgx defaults to server-side prepared statement caching (`QueryExecModeCacheStatement`), which does not survive a transaction-pooling proxy — DEPLOYMENT.md already recommends PgBouncer "for larger deployments," and `lib/pq` never had this failure mode. Operators running behind PgBouncer in transaction-pooling mode should set this to `exec`; documented next to the existing PgBouncer paragraph in `docs/guides/DEPLOYMENT.md`.
- Added `internal/infrastructure/postgres/webhook_endpoint_repo_test.go` — this repo had zero test coverage before this PR, and its scan path is the one that changed the most (`pq.Array(&ep.Events)` → `pgTypeScanner(&ep.Events)`), so it was previously the least-verified part of the migration.

## Validation

- `go build ./...` — clean.
- `go vet ./...` — clean.
- `go test ./... -count=1` — all packages pass. `SHOPANDA_TEST_DSN`-gated integration tests (including the new webhook endpoint tests) skip in this sandbox (no live Postgres available here — same disclosed limitation as PR-1024's OTLP collector delivery) but are **not** skipped in CI: `ci.yml:76-91` starts a real Postgres and sets `SHOPANDA_TEST_DSN`, so this diff's array-scan and error-mapping paths, including the previously-untested webhook endpoint repo, do get exercised there.
- `gofmt -l` / `goimports -l` — no diffs introduced by this PR (pre-existing unrelated drift in some `_test.go` files, untouched by this change).
- Repo-wide sweep confirms zero remaining `lib/pq`/`pq.*` references, and zero remaining raw `err.(*pgconn.PgError)` assertions.
- `go test -race` against an isolated repro of a shared `pgtype.Map` confirmed the data race described above; `pgTypeScanner`'s call-local map has no shared state for that race to occur on.
- **Not validated here**: this sandbox has no live Postgres, so the new `webhook_endpoint_repo_test.go` integration tests and the `database.query_exec_mode=exec` DSN parameter were checked by reading pgx's source (`stdlib/sql.go`, `conn.go`, `pgtype/pgtype.go`) rather than by running them against a real server or a real PgBouncer instance. CI's `SHOPANDA_TEST_DSN` job covers the former; the latter (an actual PgBouncer transaction-pooling deployment) is not covered by any test in this repo and remains an operational configuration choice.

## Code review follow-ups

A follow-up review after the initial migration raised one blocker, two major concerns, and three minor concerns. All were verified against the code (not assumed from the review text) before acting:

- **Blocker — fixed.** No exec-mode override for PgBouncer compatibility. See `database.query_exec_mode` above.
- **Major — fixed.** Zero test coverage on `webhook_endpoint_repo.go`'s changed scan path. See the new test file above. The review's claim that CI's `SHOPANDA_TEST_DSN` coverage was already narrower than the disclosed gap suggested was correct; the Validation section above now distinguishes "skipped in this sandbox" from "covered by CI."
- **Major — fixed.** Four remaining raw `err.(*pgconn.PgError)` assertions brought in line with `errors.As`.
- **Minor — fixed.** `pqErr` → `pgErr` rename repo-wide.
- **Minor — not a bug, rationale corrected.** The review described the `plugins/b2b/plugin_test.go` blank-import fix as cosmetic, reasoning that `internal/infrastructure/postgres` (already imported by that file) transitively registers the driver. Checked with `go list -test -deps ./plugins/b2b/...`: the `postgres` package does not itself blank-import `pgx/v5/stdlib`, and no other file in that test binary does either — without the added import, `sql.Open("pgx", dsn)` in that file would fail with "unknown driver" if `SHOPANDA_TEST_DSN` were set. The fix was necessary, not defensive style; no change made.
- **Minor — fixed, and elevated.** The suggested fix was a code comment noting `pgtype.Map`'s "read-only" concurrency invariant. Checked whether that invariant actually holds with `go test -race`: it does not — first concurrent use races on the map's lazily-built internal cache. Initially fixed with an `init()`-forced pre-warm of a shared map; superseded below by removing the shared map entirely.

### Round 2 — follow-up on the follow-up

- **Fixed.** The `init()`-forced pre-warm above still left a shared, mutable `pgTypeMap` package var — safe only as long as the invariant ("nothing calls RegisterType on it later") holds forever, which a future contributor could silently break. Replaced with `pgTypeScanner(dest)`, which builds a fresh, unshared `*pgtype.Map` per scan call — no shared state left to race under any future change, at the cost of one small per-scan allocation.
- **Fixed.** `spanSafeError`'s context-error branch returned the original (possibly-wrapped) error, not the bare `context.Canceled`/`context.DeadlineExceeded` sentinel. `errors.Is` matches through an arbitrary wrapping prefix, so a step wrapping `ctx.Err()` with its own message (e.g. customer detail) would have had that prefix reach the span unbounded, despite the function's own doc comment claiming otherwise. Now returns the bare sentinel. New test: `TestWorkflow_Execute_SpanRedactsWrappedContextErrorPrefix`.
- **Fixed.** Both panic-recovery blocks in `workflow.go` (`runStep` and `Execute`) recorded the raw recovered panic value on the span via `fmt.Errorf("panic: %v", r)` — the same class of leak `spanSafeError` exists to prevent for normal errors, just bypassing it entirely. Now records a fixed `"panic"` error; the original value still propagates via the unchanged `panic(r)` re-raise. New test: `TestWorkflow_Execute_PanicSpanRedactsPanicValue`.
- **Fixed.** Webhook delivery treated every 4xx as a permanent failure, including 408 (Request Timeout), 425 (Too Early), and 429 (Too Many Requests) — all transient conditions where an identical retry can succeed, unlike a genuine client error such as 400 or 404. These three now fall through to the existing retryable-error path instead of being marked permanent. New test: `TestDeliverHandler_TransientStatusesStillRetry`.
- **Fixed.** `SHOPANDA_STORE_CREDIT_MAX_ISSUE_AMOUNT`'s env override silently dropped a negative value (`n >= 0` guard) instead of letting it reach `validateStoreCredit`, unlike the YAML path for the same field. Removed the guard so both paths get the same validation error. New test: `TestStoreCreditConfig_NegativeEnvOverlayRejected`.
- **Fixed.** This PR document's own Documentation updates table was missing rows for artifacts this PR itself had already changed (`configs/config.example.yaml`, the phase-10 PR index/ROADMAP/README) and had no explicit "no change" rows for the artifacts checked and found unaffected, unlike the convention established in PR-1023/PR-1024. Both gaps closed above.
