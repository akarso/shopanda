# PR-1024 — OpenTelemetry Traces

Status: done

## Summary

- Optional OTLP/HTTP trace export, default **off**
- Instruments HTTP requests (one span per request, route template + status attributes) and the checkout workflow (one root span per `Execute` call, one child span per step)
- New `internal/platform/tracing` package configures the global OTel SDK tracer provider; everything else calls `otel.Tracer(...)` directly and gets a safe, effectively-free no-op unless tracing is enabled

## Why

Metrics without traces still make checkout/payment latency hard to debug — knowing the checkout failure *rate* went up doesn't say which step, or whether it's slow vs. failing. A+ observability bar (PR-1020's metrics follow-up).

## Scope decisions

**No package-level cached `Tracer` handles.** OTel's global provider (`internal/global/state.go`) only migrates a `Tracer` handle obtained *before* a real SDK provider is installed to that provider **once** (`sync.Once`) — a handle cached in a package `var` before `tracing.Setup` runs would stay bound to the no-op default forever, even across later `SetTracerProvider` calls. `TracingMiddleware()` and `checkout.NewWorkflow(...)` both resolve `otel.Tracer(...)` at construction time instead (once per process, when `cmd/api` wires the router / checkout workflow — after `tracing.Setup` has already run). This was caught by actually running the middleware's own tests with multiple test-local providers, not by inspection — the first test passed and the second and third silently exported to the first test's already-discarded exporter.

**Route-pattern-after-dispatch reuses the mechanism `MetricsMiddleware` already built (PR-1023 CR).** `Request.Pattern` isn't populated until `net/http.ServeMux` has matched the request, which happens *inside* `next.ServeHTTP` from `TracingMiddleware`'s perspective. `TracingMiddleware` reads the same `*routeMatch` box (`shared/router.go`) that `MetricsMiddleware` reads, rather than adding a second, independent mechanism.

**No raw request path in span attributes.** `http.route` (the templated pattern, e.g. `/products/{id}`) is recorded; the raw `r.URL.Path` is not — it can carry a customer/order ID or a password-reset/email-verification token in storefront and admin routes, and spans export to a configurable, possibly third-party OTLP endpoint. Same reasoning as the metrics package's bounded-label policy, applied to a different sink.

**DB spans: deferred, not implemented.** The spec allowed this "if affordable via wrapper." There is no single `*sql.DB` wrapper shared across the ~40 postgres repo files — each repo calls `db.QueryContext`/`ExecContext` directly. Adding spans there means either (a) touching every repo file (large, mechanical, but still a real per-file review burden across a 218-file-diff branch already in flight — see PR-1021/1022/1023), or (b) introducing a wrapper type now and migrating repos to it incrementally, which is a structural change beyond "add tracing." Deferred to a follow-up once/if a DB access wrapper exists for other reasons; HTTP + checkout spans already answer "which step, how long" for the checkout path this PR is motivated by.

**Sample ratio: explicit `0` means "record spans, export none," not "unset."** `TracingConfig.SampleRatio` is seeded to `1.0` in `defaults()` (not applied as a post-YAML-parse fallback) specifically so `sample_ratio: 0` in an operator's YAML — a deliberate value — survives `yaml.Unmarshal` distinguishably from the field never being mentioned at all. A post-parse `if ratio <= 0 { ratio = 1 }` fallback (the first draft of this) cannot tell those two cases apart.

**`insecure: true` is validated, not just commented.** Cleartext OTLP export is the same risk shape as `database.sslmode=disable` (`validateSecureDefaults`) — trace data (which can include the same sensitive info the `url.path` decision above guards against) crossing the network unencrypted. `tracing.insecure=true` is rejected unless `SHOPANDA_DEV_MODE` is truthy or the endpoint resolves to a loopback host (reusing `isLoopbackHost`, the same DNS-resolving loopback check from the PR-1023 CR round).

## Scope

- `internal/platform/config`: `TracingConfig` (`enabled`, `endpoint`, `insecure`, `sample_ratio`, `headers`), `SHOPANDA_TRACING_*` env overrides, validation (endpoint required + no scheme prefix, sample ratio not negative, insecure requires dev-mode/local), `tracing.headers.*` redacted in the `Get()`/`GetOrDefault()` flatten map
- `internal/platform/tracing`: `Setup(ctx, cfg, serviceName) (Shutdown, error)` — installs an OTLP/HTTP exporter + batching `TracerProvider` as the global provider when enabled; a no-op when disabled or on failure
- `internal/interfaces/http/shared/tracing_middleware.go`: `TracingMiddleware()`, wired in `cmd/api/wire_routes.go` alongside `MetricsMiddleware` (outermost, so the span covers the full request)
- `internal/application/checkout/workflow.go`: root span `checkout.execute` + one child span `checkout.step.<name>` per step, status/error recorded through the same defer that already finalizes the metrics outcome
- `cmd/api/main.go`: `tracing.Setup` called early in both `runServe` and `runWorker` (before anything that resolves a `Tracer` at construction time), shutdown called last, bounded, after the existing graceful-drain sequence
- `go.mod`: `go.opentelemetry.io/otel`, `.../otel/sdk`, `.../otel/trace`, `.../otel/exporters/otlp/otlptrace/otlptracehttp`

## Out Of Scope

- DB query spans (see Scope decisions)
- Full baggage/campaign analytics
- Replacing the JSON logger
- Job/worker-level spans (the worker process calls `tracing.Setup` for parity with `serve` and future instrumentation, but no job handler is instrumented in this PR — none currently resolves a `Tracer`)

## Code review follow-ups

Responding to the CR on this PR — each item fixed directly unless noted:

**Blockers — fixed:**
- Stray `docs/phase-10-platform-excellence/prs/.PR-1023.md.swp` removed from the index (`git rm --cached`); `*.swp`/`*.swo` added to `.gitignore` so this class of accident can't recur.
- `tracing.Setup`: reordered so `resource.New` runs *before* `otlptracehttp.New` — there is no longer a fallible step between exporter creation and the exporter being handed to the `TracerProvider`, so the "exporter created, then a later step fails and leaks it" path this flagged is now structurally unreachable rather than patched with compensating cleanup code.
- `Workflow.Execute`: moved the span-start's `cctx.CartID` read to *after* the `defer recover()` registration (guarded with a nil check, since `cctx == nil` is a contract case every `Step` already guards against). Before the fix, a nil `*checkout.Context` panicked before any recovery was in place — a genuinely new, unrecovered crash this line introduced. New regression test: `TestWorkflow_Execute_NilContextPanicIsCaughtByRecover`.

**Major concerns — fixed:**
- Dropped the raw `url.path` span attribute entirely; `http.route` (already templated) is the only path-shaped attribute recorded. New test: `TestTracingMiddleware_RecordsRouteAndStatus` asserts `url.path` is absent.
- `tracing.insecure=true` now rejected unless `SHOPANDA_DEV_MODE` is truthy or the endpoint is a loopback host — mirrors `validateSecureDefaults`'s DB-sslmode pattern exactly, including reuse of `isLoopbackHost`. New tests cover reject/allow-via-devmode/allow-via-localhost.
- `sample_ratio: 0` now means what it says (0% sampling) instead of being silently promoted to `1.0` — fixed by seeding the "unset" default in `defaults()` rather than in a post-parse fallback, so YAML's own zero-value semantics do the distinguishing. New test: `TestTracingConfig_ExplicitZeroSampleRatioIsPreserved`.

**Minor concerns:**
- Fixed: `validateTracing` now rejects an `Endpoint` containing `://` with a config-time error instead of letting it fail at dial time.
- Fixed: `tracing.headers.*` now goes through `redactSecret` in the config flatten map, matching every other secret-bearing field there (`plugins.*.api_key`, etc.) — closes the gap before anything reads it, rather than after. (Noticed in passing: `webhooks.secrets.*` in the same function is *not* redacted, unlike everything else there — pre-existing, unrelated to this PR, flagged separately rather than fixed here.)
- Fixed: `SHOPANDA_TRACING_SAMPLE_RATIO`'s env parser now accepts `0` (was `f > 0`, silently dropping an explicit zero) — same fix as the YAML path, for the same reason.
- Fixed: added the two missing regression tests named in the CR (`TestSetup_Enabled_InstallsProviderAndShutdownSucceeds` already covered the happy path; the nil-`cctx` panic-recovery path didn't have coverage before this round — see blockers above).
- Not changed: `http.request.method` stays as both a span-name component and a separate attribute. This isn't accidental duplication — it's standard OTel semantic-convention practice (the name is for human display/grouping, the attribute is what a trace backend actually filters/aggregates on) — but the CR's "worth trimming" note is fair enough that it's called out explicitly here rather than silently left as-is.
