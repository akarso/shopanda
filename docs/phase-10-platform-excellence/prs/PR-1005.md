# PR-1005 — JWT Secret Strength

Status: planned

## Summary

- One canonical JWT secret parser/validator shared by config validation and `jwt.NewIssuer`
- Enforce ≥32 **decoded** secret bytes; accept installer `openssl rand -hex 32` (64 hex chars → 32 bytes)

## Why

`jwt.NewIssuer` only checks non-empty. Weak secrets allow offline forging of admin tokens. Installer already emits 64-character hex (`openssl rand -hex 32`).

## Scope

- Add a shared helper (e.g. `platform/jwt.ParseSecret` or `platform/authsecret`) used by:
  - `internal/platform/config` validation / load
  - `jwt.NewIssuer`
- Behavior:
  - Trim trailing newlines/whitespace
  - Accept raw secrets of ≥32 bytes **or** the documented 64-character hex form decoded to 32 bytes (same as installer output)
  - Reject ambiguous shorter character counts that are neither ≥32 raw bytes nor valid 64-hex
  - Minimum: **32 decoded secret bytes**
  - Clear error naming `SHOPANDA_AUTH_JWT_SECRET`
- Update `install.sh` / `.env.example` guidance to document the canonical 64-hex representation
- Tests: reject empty/short/odd-length hex; accept 64-hex and ≥32-byte raw; newline trimming

## Out Of Scope

- Rotating secrets / multi-key JWT
- Moving off HS256
