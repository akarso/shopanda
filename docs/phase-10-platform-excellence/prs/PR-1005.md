# PR-1005 — JWT Secret Strength

Status: done

## Summary

- One canonical JWT secret parser/validator shared by config validation and `jwt.NewIssuer`
- Enforce ≥32 secret bytes (trimmed); accept installer `openssl rand -hex 32` (64 hex chars) **as-is** (no hex decode)

## Why

`jwt.NewIssuer` only checked non-empty. Weak secrets allow offline forging of admin tokens. Installer already emits 64-character hex (`openssl rand -hex 32`).

## Scope

- Add `jwt.ParseSecret` used by:
  - `internal/platform/config` validation (`normalizeAuthJWT`)
  - `jwt.NewIssuer` / `jwt.NewIssuerFromKey`
  - `cmd/api` MFA / account-security (same trimmed string bytes as issuer)
- Behavior:
  - Trim trailing newlines/whitespace
  - Accept raw secrets of ≥32 bytes (installer 64-hex qualifies as-is; never decoded)
  - Reject empty/short values
  - Errors name `SHOPANDA_AUTH_JWT_SECRET`
  - `NewIssuerFromKey` enforces the same minimum length
- Test helpers live in `internal/platform/jwt/jwttest` (not the runtime package)
- Update `install.sh` / `.env.example` / `config.example.yaml` / `DEPLOYMENT.md`
- Tests: reject empty/short; accept 64-hex and ≥32-byte raw without decoding; newline trimming; config load gate

## Out Of Scope

- No change — Rotating secrets / multi-key JWT
- No change — Moving off HS256
- No change — Hex-decoded key format (would require dual-verify migration)
