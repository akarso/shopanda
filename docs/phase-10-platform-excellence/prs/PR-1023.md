# PR-1023 — HTTP Package Split (Storefront)

Status: done

## Summary

- Move all storefront-facing HTTP surface (customer REST API + SSR views) to `internal/interfaces/http/storefront`, continuing PR-1021/1022's split
- Finish the `auth_middleware.go` split that PR-1021/1022 explicitly deferred: customer JWT auth (`AuthMiddleware`, `RequireAuth`) moves to `storefront`; admin RBAC (`RequirePermission`, `RequireRole`, `AdminContextMiddleware`) moves to `admin`
- `cmd/api` wiring updated to construct/reference storefront handlers from the new package
- Behavior-identical: no route, permission, or response-shape changes

## Why

Storefront god-handler (~36 deps, multi-file) is the worst HTTP hotspot after the admin split.

## Scope decisions

**`auth_middleware.go` split (deferred by PR-1021/1022, done here):** the file mixed two unrelated concerns — customer JWT identity (`AuthMiddleware`, `RequireAuth`) and admin RBAC (`RequireRole`, `RequirePermission`, `AdminContextMiddleware`, `sanitizeAdminScopeValue`). `RequirePermission`/`RequireRole`/`AdminContextMiddleware` are used **exclusively** to gate `/api/v1/admin/*` routes in `wire_routes.go` — zero storefront coupling — so they moved to `admin/admin_middleware.go`. `AuthMiddleware`/`RequireAuth` depend on `storefrontSessionToken` (storefront cookie helper) and gate customer-facing routes, so they moved to `storefront/auth_middleware.go`. This also means `admin` no longer needs to import the legacy `http` package for these — it defines them itself now. `auth_middleware_test.go` was split the same way.

**`refund.go` → `admin` (PR-1022 scope gap):** `RefundHandler` only serves `POST /api/v1/admin/orders/{orderId}/refund` — 100% admin, missed in PR-1022 because it matches neither the `*_admin.go` nor `admin_*.go` naming convention (same class of gap as `media.go`/`schema_handler.go` in that PR). Moved to `admin/refund_admin.go` + `refund_admin_test.go`.

**Genuinely-shared handlers/helpers stayed exported from `storefront`, not duplicated:** `CategoryHandler`, `VariantHandler` (public read + admin CRUD reuse the same handler struct), `OrderResponse`/`ToOrderResponse` (`order.go`), `ToReturnResponse(s)` (`return_response.go`), `ToAdminReviewResponse(s)`/`ParseReviewStatus` (`review.go`), `AccountDeleter` (`account.go`), `NewReturnAccountHandler`, `NewAuthHandler`/`AuthHandler`. `admin` now imports these from `storefront` (aliased `storefront`) instead of the legacy `http` package — same pattern PR-1022 established, just re-pointed to the new home.

**What stayed in `internal/interfaces/http`** (neither admin nor storefront — platform/integration-level): `docs.go` (OpenAPI/Swagger, developer-facing), `health.go` (liveness/readiness probes), `setup.go` (first-run setup wizard — runs before any admin/customer exists), `payment_webhook.go`/`stripe_webhook.go` (server-to-server payment provider callbacks), `shared_compat.go` (PR-1021 shim — still needed by these five files).

**Moved to `storefront` despite not being obviously "storefront" by name:** `sitemap.go`, `robots.go` (public SEO surface for the storefront catalog), `rewrite_handler.go` (resolves the storefront's catch-all canonical-URL routing, companion to `ResolverMiddleware` which already moved to `shared` in PR-1021).

Responding to the CR round on this PR — each item fixed directly unless noted otherwise:

**Fixed:**

- `worker.go processNext`: a `queue.Complete` failure after a successful handler run now also records `JobFailure` — previously silent, despite being a real, actionable redelivery risk
- Added `metrics.OutcomeSucceededEventFailed` — checkout's final `EventCheckoutCompleted` publish failing after every step succeeded is no longer conflated with a real checkout failure in the `CheckoutResult` metric

Investigation traced the gap back to the feature's original introduction in Phase 1 (`docs/phase-1-core/prs/PR-089.md`, `PR-090.md`): the write side (`rewrite.Subscriber` populating `url_rewrites`) was wired into `main.go` at the time, but the read side (middleware + catch-all handler) never was — **not a regression from this PR or PR-1021/1022**, a years-old pre-existing gap. Registered as `router.Handle("GET /{path...}", shophttp.ResolverMiddleware(rt.repos.rewriteRepo, log)(storefront.NewRewriteHandler().Resolve()))` in `cmd/api/wire_routes.go` — root-level, matching the exact path format `rewrite.Subscriber` writes (`"/"+slug`) and the original spec's `GET /*` catch-all (`docs/phase-1-core/specs/ROUTING.md`). Kept as a root-level JSON resolver rather than an SSR-aware redirect: `RewriteHandler.Resolve()` returns `{type, entity_id}` by design (PR-089: "upstream consumers decide how to render"), and building an HTML redirect would mean looking up each entity's current slug per type — a larger, untested change beyond wiring up what already exists. Scoped as a single low-priority route (not global middleware) so the per-request DB lookup only fires for requests no other route claims — confirmed via `TestRewriteRouting_MoreSpecificRouteTakesPrecedence` (new, `internal/interfaces/http/storefront/rewrite_router_test.go`) that literal routes like `/products/{slug}` still win over the catch-all. Two more new tests in the same file exercise the full `shared.Router` dispatch end-to-end (resolves a match, 404s an unknown path) — closing the gap the CR called out: only mocked unit tests existed before, never a real router. **A later review round asked to confirm this unauthenticated, DB-hitting catch-all has adequate rate limiting**: it does — `router.Use(shophttp.RateLimitMiddleware(...))` (`wire_routes.go`) is registered globally, wrapping the entire `shared.Router`, including every route registered via `router.Handle`/`HandleFunc` regardless of registration order (see `shared.Router.Handler()`), so the catch-all is covered by the same rate limiter as every other route with no separate wiring needed.

### Round 2 — whole-branch review

A second CR reviewed the branch as a whole (HTTP split + metrics subsystem + admin store-credit issuance) rather than a single PR. Its findings span store-credit correctness (introduced pre-split, now living in `internal/interfaces/http/admin/store_credit_admin.go`), the `shared` package's router/metrics internals (PR-1021), and `cmd/api` process wiring — logged here since this is the PR doc the prior round's follow-ups already live in.

**Blockers: none.**

**Major concerns — fixed:**
- **Store credit issuance had no idempotency protection** (a retried `POST .../store-credit/issue` minted credit twice). Added an optional `Idempotency-Key` header (same convention as `internal/infrastructure/stripepay` and `internal/platform/plugin/integration.go`), threaded through `storecredit.Service.Issue` → `storecredit.Repository.Issue` → `StoreCreditRepo`, persisted on the ledger row (migration `064_store_credit_idempotency.sql`: nullable `idempotency_key` column + partial unique index on `(customer_id, idempotency_key) WHERE idempotency_key IS NOT NULL`). `StoreCreditRepo.applyEntry` checks for an existing entry with the same key before touching the balance (handles the common sequential-retry case), and separately catches a `23505` unique-violation on that specific index as a race-condition fallback (concurrent identical retries), treating either as a no-op success rather than a double-credit. No idempotency key means no dedup — unchanged behavior for callers that don't opt in, including checkout's rollback-`Issue` call sites in `create_order_step.go`, which now pass their own key (`"rollback:save:"+orderID` / `"rollback:apply:"+orderID`) as a low-cost bonus consistency win since the interface already had to change.
- **Store credit issuance was not audited.** `StoreCreditAdminHandler` now takes an `*adminapp.Auditor` (matching `NewPaymentAdminHandler`/`NewReturnAdminHandler`) and logs `AuditStoreCreditRead`/`AuditStoreCreditIssue` (new `AuditAction` constants) on both `Get()` and `Issue()`, success and failure. `cmd/api/wire_services.go` now passes `sharedAuditor`.
- **No upper bound on issuable amount.** Added `config.StoreCreditConfig.MaxIssueAmount` (minor units, default 100000 via `DefaultStoreCreditMaxIssueAmount`; `0` explicitly disables the cap), enforced in `storecreditApp.Service.Issue` before the customer/repo calls. Wired via `storecreditService.WithMaxIssueAmount(cfg.StoreCredit.MaxIssueAmount)` in `wire_services.go`. Documented in `configs/config.example.yaml`.

**Minor concerns — fixed:**
- `isLoopbackHost`'s `"localhost"` check now resolves the hostname via `net.LookupHost` and requires every resolved address to be loopback, instead of trusting the bare string — closes a tampered-`/etc/hosts`/DNS-override edge case. Falls back to trusting the literal if resolution itself fails, so config validation doesn't gain a hard resolver dependency in minimal environments.
- `MetricsMiddleware` no longer re-runs `ServeMux` route matching a second time just to get a bounded label. `Router.Handle`/`HandleFunc`/`TryHandle` now wrap every registered handler in `captureRoute`, which reads `Request.Pattern` (already populated by the mux's own dispatch, by the time the matched handler runs) and writes it into a `*routeMatch` box shared via context; `MetricsMiddleware` reads that box after `next.ServeHTTP` returns instead of calling `RoutePattern(r)` independently. The box is a pointer specifically because intervening middleware (auth, store resolution, ...) calls `r.WithContext(...)`, replacing the `*http.Request` on the way down — a plain post-dispatch read of `r.Pattern` on `MetricsMiddleware`'s own request would not see the mux's mutation, verified by `TestMetricsMiddleware_SurvivesRequestSwapBetweenMetricsAndDispatch` (new). `Router.RoutePattern()` itself is unchanged and still available as a standalone utility.
- `runWorker` now waits (bounded, 10s, via the existing `runtime.ShutdownBackground` helper `runServe` already uses) for the metrics server's `Serve` goroutine to actually return after `Close()`, instead of a bare `defer metricsSrv.Close()` that didn't wait for it — matches `runServe`'s drain sequence.

**New tests:** `internal/application/storecredit/service_test.go` (new file — max-amount cap inclusive/exclusive/disabled, idempotency key pass-through); `internal/infrastructure/postgres/store_credit_repo_test.go` (new file, DB-gated — same-key dedup, distinct-key both-credit, no-key unprotected); `store_credit_admin_test.go` (idempotency header dedup, max-amount rejection/boundary); `secure_defaults_test.go` (`isLoopbackHost` literal IPs, "localhost", unresolvable hostname); `metrics_middleware_test.go` (request-swap survival).

### Round 3 — whole-branch review (checkout, worker, config, webhooks, tracing)

A third whole-branch review, logged here (rather than split across every PR doc it touches) since it's a single review pass over the branch as a whole — same rationale as Round 2. This round's tracing-specific items (`internal/platform/tracing`, `checkout/workflow.go`'s span instrumentation, `cmd/api/main.go`'s shutdown wiring) touch code PR-1024 introduced; see [PR-1024.md](PR-1024.md) for that PR's own scope, and its own follow-up pointer back to the items below.

**Blockers — fixed:**
- **The rollback idempotency keys added in Round 2 (`"rollback:save:"+orderID` / `"rollback:apply:"+orderID`) gave no real protection** — `orderID` is `order.NewOrder(id.New(), ...)`'s freshly generated UUID, different on every `Execute` attempt including retries, so the unique constraint they relied on could never actually fire. Both call sites in `create_order_step.go` now pass `""` (no key) instead of a key that only looked like protection. A naive replacement — key by `cctx.CartID` instead, since a cart is single-use (`CartStatusActive` → `CartStatusCheckedOut`/`CartStatusAbandoned`, a one-way transition) — was considered and **rejected**: it closes the crash-mid-request gap but opens a worse one. Full reasoning is now a doc comment on `applyStoreCredit` in `create_order_step.go`; short version: a `cartID`-only key would dedupe a *second, legitimate* redeem-then-rollback cycle on the same cart against the *first* one's now-already-reversed ledger entry, silently letting an order through with store credit applied that was never actually debited. `Redeem` itself remains without an idempotency key for the same reason — adding one to it and not to the rollback `Issue` calls (or vice versa) wouldn't fix anything, and a real fix needs to distinguish "retry of the same in-flight attempt" from "a new attempt after the previous one resolved," which requires state that survives a crash and gets explicitly invalidated on resolution (e.g. a pending-order-id persisted on the cart itself). That's a real feature, not a one-line idempotency key — flagged as its own follow-up task rather than guessed at under review pressure.
- **`ledger.go`'s doc comment claimed `OrderID` protects `Redeem` against double-debit** — there is no unique constraint on `order_id`, and (per the point above) `orderID` changes every attempt anyway, so it couldn't provide that guarantee even if a constraint existed. Comment corrected to say plainly that `Redeem` is not deduplicated, with a pointer to the reasoning above.
- **`worker.go`: no `recover()` around a job handler's `Handle` call** — a panicking handler propagated out of `processNext` and killed the entire poll loop (every other job the worker would otherwise have kept processing, not just the one that panicked). Added `Worker.safeHandle`, which recovers and converts the panic into a normal error on the exact same path a handler-returned error already takes (logged, counted, `queue.Fail`'d). New test: `TestWorker_HandlerPanic_DoesNotCrashWorker` (asserts a second, unrelated queued job still gets processed after the first one panics).
- **`worker.go`: `Fail`/`Complete` reused the poll-loop's `ctx`** — exactly what shutdown cancels. A handler finishing right as shutdown fires could have its outcome-recording call aborted by the same cancellation, leaving the job neither completed nor properly failed/requeued. `recordFail`/`recordComplete` now run on `context.WithTimeout(context.WithoutCancel(ctx), outcomeRecordTimeout)` — detached from the poll loop's cancellation, still bounded (10s). New test: `TestWorker_OutcomeRecording_SurvivesContextCancellation` (a handler cancels the outer context itself mid-handle, then the recorded `Fail` call's context is asserted `ctx.Err() == nil`).
- **`tracing.go`'s `SampleRatio` clamp reintroduced the exact bug Round 2 fixed at the config layer** — `if ratio <= 0 || ratio > 1 { ratio = 1 }` in `Setup` silently turned an explicit "export nothing" (`0`) back into "export everything," one level down from where `config.normalizeTracing` had already been fixed to preserve it. Removed entirely: `sdktrace.TraceIDRatioBased` already treats `fraction <= 0` as never-sample and `fraction >= 1` as always-sample per its own doc comment, so no clamping was needed in the first place. New tests: `TestSetup_SampleRatioZero_NeverSamples`, `TestSetup_SampleRatioOne_AlwaysSamples` (both exercise the installed provider end-to-end and check `span.SpanContext().IsSampled()`, not just the config value).

**Major concerns — fixed:**
- `database.password` and `plugins.integrationdemo.integration_api_key`/`integration_hmac_secret` were exposed raw through `flatten()`/`Get()`, inconsistently with `webhooks.secrets.*`/`plugins.warehousedemo.warehouse_api_key`/etc. right next to them — all four now go through `redactSecret()`.
- `SHOPANDA_AUTH_MFA_ENABLED`, `SHOPANDA_AUTH_LOCKOUT_ENABLED`, `SHOPANDA_FRONTEND_CSP_ENABLED`, `SHOPANDA_RATE_LIMIT_ENABLED`, and 16 other boolean env vars in `applyEnv` each had their own inline `v == "true" || v == "1"` (two of them used `strings.EqualFold(v, "true") || v == "1"` instead) — so `"True"` silently failed to enable some of these and not others, with no error or log, depending on which copy-pasted comparison a given flag happened to get. All 20 now go through one `parseEnvBool` helper (extracted from `EnvTruthy`'s existing 1/true/yes, case-insensitive convention). New test: `TestApplyEnv_CaseVariantBooleansEnableSecurityFlags`.
- `payment.stripe.enabled=true` with an empty `secret_key`/`webhook_secret` passed `config.Load()` and only failed at the first real payment/webhook request. New `validateStripe` rule rejects it at load time, matching how every other "enabled requires X" field in this file already behaves (metrics, tracing).
- Webhook delivery treated a 4xx (permanent — the receiver rejected this exact request, retrying won't change that) the same as a 5xx (transient, worth retrying), burning retry budget against endpoints that will never accept the payload. `DeliverHandler.Handle` now returns `nil` (no worker retry) on a 4xx while still recording `OutcomeFailed` (a `permanentFailure` flag distinct from `skipped`, since this was a real attempted-and-rejected delivery, not a never-attempted one) and logging it distinctly (`webhook.deliver.permanent_failure`). 5xx and transport errors are unchanged (still retried). The transport-error return also picked up the `"webhook deliver: "` prefix every other error path already had. New tests: `TestDeliverHandler_4xxDoesNotRetry`, `TestDeliverHandler_5xxStillRetries`.
- `store_credit_repo.go`'s idempotency check only verified the key existed, not that the replay's amount/currency/note matched the original — a key reused for a *different* amount would silently no-op (or apply the wrong amount) instead of surfacing the collision. Both the pre-check and the race-lost path (concurrent identical requests hitting the unique constraint) now compare all three and return `apperror.Conflict` on a mismatch. New tests: `TestStoreCreditRepo_Issue_IdempotencyKeyReuseWithDifferentAmountConflicts`, `..._DifferentNoteConflicts`.
- `balance+delta` (both `int64`) had no overflow guard before computing the new balance — checked *before* the addition now (`if delta > 0 && balance > math.MaxInt64-delta`), not after, since checking a sum that already wrapped can't reliably detect that it wrapped.
- A panicking checkout step never reached the straight-line `stepSpan.End()` that used to sit after `step.Execute` — only the root span (via `Execute`'s own `recover`) got closed; the step's own span leaked, permanently open. Extracted into `Workflow.runStep`, which ends the span via `defer` so it always closes, panic or not. New test: `TestWorkflow_Execute_PanicInStepStillClosesStepSpan`.
- `Workflow.Execute` still returned an error when only the final `EventCheckoutCompleted` publish failed — even though every step up to that point (order created, payment captured) had already succeeded. `checkout.Service.Checkout` propagates that error as-is, so a customer whose order was actually fine would see a failure and could be prompted to retry, risking a genuine duplicate order over what is really just a downstream notification/event-bus problem. `Execute` now returns `nil` in that case (the existing `succeededEventFailed`/`OutcomeSucceededEventFailed` metrics distinction already made this failure visible to operators; it just also made it visible to the customer, which was the actual bug). Test updated: `TestWorkflow_WithMetrics_RecordsSucceededEventFailed` now asserts `err == nil`.
- Checkout spans recorded raw `err.Error()` strings via `RecordError`/`SetStatus` — not guaranteed free of customer or payment-processor detail, and these spans may export to a third-party OTLP collector, same reasoning as the `url.path` redaction in Round 2. New `spanSafeError` records an `*apperror.Error`'s bounded `Code` instead of its free-text message; a `context.Canceled`/`DeadlineExceeded` error (fixed, safe strings) passes through unchanged; anything else becomes a fixed generic message. The original text isn't lost — `w.log` already records the full error, cross-referenceable by cart/order ID. New tests: `TestWorkflow_Execute_SpanRedactsErrorMessage`, `..._SpanPreservesContextErrorMessage`.
- `tracing.Setup` in `cmd/api/main.go` had no matching `tracingShutdown` call on the error paths that can occur *after* `Setup` succeeds (`wireServeRuntime`/`buildServeHandler`/cron-trigger/metrics-bind failures in `runServe`; `setupWorker`/metrics-bind failures in `runWorker`) — masked in practice only by `main()` calling `os.Exit(1)` immediately after any returned error, which skips all cleanup regardless.
