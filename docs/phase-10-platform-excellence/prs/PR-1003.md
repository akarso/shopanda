# PR-1003 — CI Integration Job

Status: in progress

## Summary

- Second CI job (`CI / integration`) with Postgres 17 service and `SHOPANDA_TEST_DSN`
- Wait for Postgres readiness, then run the full DSN-gated suite with a real anti-skip gate

## Why

Postgres package tests (`testDB` + `SHOPANDA_TEST_DSN`) and related DSN-gated packages only run with a real DSN. Unit CI alone leaves the data layer ungated.

## Scope

- Extend `.github/workflows/ci.yml` with `integration` job
- Service: Postgres 17 (digest-pinned, same as compose) with fixed credentials matching the job DSN
- **Readiness gate:** `pg_isready` retry loop (max ~60s); fail clearly if not ready
- Run via [`.github/scripts/run-integration-tests.sh`](../../../.github/scripts/run-integration-tests.sh):
  - Assert `SHOPANDA_TEST_DSN` non-empty
  - `go test -p 1 -count=1 -json` on `./internal/infrastructure/postgres/... ./internal/platform/migrate/... ./plugins/b2b/...`
  - Fail on any `Action==skip` (default `go test` text hides skip reasons — do not grep plain output)
  - Require canary DSN tests to `Action==pass` (proves DB suite ran; `^ok` alone is insufficient)
- Document local integration run + require both checks in branch protection notes

## Out Of Scope

- No change — Meilisearch/Redis/RabbitMQ in CI
- No change — Load tests
- No change — Automating GitHub rulesets (manual admin step)

### DSN-suite fixture/isolation fixes (found running against a genuinely empty Postgres 17)

Running the gated suite against a fresh DB (not one with leftover state from ad hoc local runs) surfaced 34 failures — all fixture/test-isolation bugs plus one real repo bug, not schema gaps (tests self-apply `migrations/` via `migrate.Run`, confirmed working):

| File | Root cause | Fix |
| --- | --- | --- |
| `internal/platform/migrate/migrate_test.go` | `TestPendingCount_NoPending`/`_WithPending` reused generic basenames (`001_first.sql`/`002_second.sql`) on the same persistent test DB; `schema_migrations` tracks by basename only, so the second test's files were already "applied" | Unique per-test basenames (`nopending_`/`withpending_` prefixes) |
| `internal/infrastructure/postgres/reservation_repo.go` | `Release`/`Confirm` passed a malformed ID straight to `WHERE id = $1` on a `uuid` column → raw driver error `22P02`, not `apperror.CodeNotFound` | Added `id.IsValid` check → `apperror.NotFound(...)` (production code fix) |
| `cart_repo_test.go` | `variant_id`/`customer_id` are `UUID` columns; test hardcoded `"var-1"`, `"cust-1"`, `"no-customer"` | Use `id.New()` |
| `consent_repo_test.go` | `consents.customer_id` FKs to `customers(id)`; no customer row inserted | Seed a customer via `CustomerRepo.Create` first (`seedConsentCustomer`) |
| `coupon_repo_test.go` | `coupons.promotion_id` FKs to `promotions(id)`; no promotion row inserted | Seed a minimal promotion row first (`seedPromotion`) |
| `invoice_repo_test.go` | `invoices.order_id` FKs to `orders(id)`; test passed a random ID with no order row | Seed a real order via `OrderRepo.Save` first (`seedOrderForInvoice`) |
| `credit_note_repo_test.go` | `credit_notes` has a composite FK `(invoice_id, order_id) → invoices(id, order_id)`; test's `orderID` didn't match any real invoice | Seed a real order + invoice chain first (`seedInvoiceForCreditNote`); `mustNewCreditNote` now takes `orderID` explicitly |
| `reset_token_repo_test.go` | `password_reset_tokens.customer_id` FKs to `customers(id)`; no customer row inserted | Seed a customer first (`seedResetCustomer`) |
| `price_history_repo_test.go` | `price_history.variant_id` FKs to `variants(id)` `ON DELETE CASCADE`; test used a bare `id.New()` | Reuse `seedVariant` (from `stock_repo_test.go`) |
| `cache_store_integration_test.go` (`TestCacheStoreDB_CompareAndSubtractVsIncrConcurrent`) | No bug — reran 5x with `-race` on a fresh DB, always green. Original failure was leftover state from earlier ad hoc runs against a shared, non-fresh DB | No change |

First live re-run (real Postgres 17) surfaced two more real bugs beyond the fixture gaps above:

| File | Root cause | Fix |
| --- | --- | --- |
| `internal/domain/promotion/promotion.go` (`NewPromotion`) | `Conditions`/`Actions` (`[]byte`) were left nil; `database/sql` binds a nil `[]byte` as SQL `NULL`, and `promotion_repo.Save`'s `INSERT` lists those columns explicitly, so the column's `DEFAULT '[]'` never applies → `23502 null value in column "conditions"` (this was the disputed "D" item from the earlier investigation — confirmed real, not a test artifact) | `NewPromotion` now initializes both to `[]byte("[]")` (production code fix) |
| `invoice_repo_test.go` (`seedOrderForInvoice`, added by this PR) | Called `mustNewOrder(t, "", "USD")` — empty customer ID with no contact email hits the guest-order validation (`order: contact email must not be empty for guest orders`); `orders.customer_id` has no FK, just `NOT NULL`, so any non-empty string is valid | Seed with `mustNewOrder(t, id.New(), "USD")` instead |

### Code review pass (applied)

| Severity | Finding | Fix |
| --- | --- | --- |
| Blocker | `seedInvoiceForCreditNote`/`seedOrderForInvoice` left `orders`/`invoices` rows with no cleanup; `invoices.order_id → orders(id)` has no `ON DELETE CASCADE`, so a later test's unchecked `DELETE FROM orders` (`return_repo_test.go`, via `mustExec` which fails the test on error) would hit the FK and fail | Added `cleanupOrderAndInvoiceRows` (in `invoice_repo_test.go`, shared with `credit_note_repo_test.go`) — deletes children before parents (credit notes → invoices → orders); wired into all 5 affected `t.Cleanup` blocks |
| Major | `ReservationRepo.FindByID` runs the same unguarded `WHERE id = $1` on the `uuid` column as `Release`/`Confirm`, but wasn't fixed — same bug class left unpatched | Added the same `id.IsValid` guard; returns `(nil, nil)` (matching this method's existing not-found contract, not `apperror.NotFound` like `Release`/`Confirm`, which already error on not-found) |
| Major | The `id.IsValid` guard on `Release`/`Confirm` had no dedicated regression test, and — worse — it silently changed what the *existing* `_NotFound` tests exercise: `"nonexistent"` is itself malformed, so those tests now hit the new format guard instead of the original DB-lookup `sql.ErrNoRows` path, leaving that path uncovered | Added `_ValidIDNotFound` tests (well-formed but unknown UUID) for both `Release` and `Confirm` to keep the DB-lookup path covered; added `TestReservationRepo_FindByID_MalformedID` for the new `FindByID` branch; commented the existing `_NotFound` tests to clarify they now test the format guard |
| Major | `seedResetCustomer` had no `t.Cleanup`, unlike the sibling `seedConsentCustomer` added in the same PR | First fix was wrong: registering the customer delete inside `seedResetCustomer` raced the test's own token-delete cleanup. `t.Cleanup` runs LIFO, and the customer-delete was registered *after* the token-delete (seeded later in the test body), so it ran *first* — deleting the customer while its token row still pointed at it. `password_reset_tokens.customer_id` has no `ON DELETE CASCADE` (unlike `consents`, which does — why `seedConsentCustomer` didn't hit this), and the delete used a bare `db.Exec` with the error swallowed, so the FK violation was silent and the customer row never actually got removed. Fixed by removing the self-registered cleanup from `seedResetCustomer` and adding `cleanupResetTokenRows(db, customerID)`, registered once per test *after* seeding, deleting tokens before the customer explicitly, independent of registration order. |
| Minor | `seedPromotion` (`coupon_repo_test.go`) used raw SQL, duplicating schema knowledge instead of reusing the domain constructor | Switched to `promotion.NewPromotion` + `PromotionRepo.Save` (only possible after the `NewPromotion` fix above, which made a bare construct-and-save produce a valid row) |

**Deliberately not changed** (flagged in review, scoped out):

- Did **not** extend the shared cleanup helper to `order_repo_test.go`/`payment_repo_test.go`/`return_repo_test.go`, and did not convert their existing unchecked `db.Exec("DELETE FROM orders")` calls to `mustExec`. That's a pre-existing, package-wide convention predating this PR (every order-creating test there already cleans up its own orders) — reworking it is a separate, wider-blast-radius change than fixing the leak this PR introduced.
- `id.IsValid` checks UUID **v4** specifically, which conflates "well-formed" with "existence" and would misclassify a valid non-v4 ID as not-found. Matches the existing convention already used in `content_block_repo.go:239`; a codebase-wide ID-validation redesign is out of scope here.
- Softened the `cache_store_integration_test.go` claim below — re-running a concurrency test 5x clean is evidence, not proof, of no race.

`cache_store_integration_test.go` (`TestCacheStoreDB_CompareAndSubtractVsIncrConcurrent`): reran 5x with `-race` on a fresh DB, always green, consistent with `Incr`'s `ON CONFLICT DO UPDATE` and `CompareAndSubtract`'s `SELECT ... FOR UPDATE` both taking a row-level lock. Treated as no bug for this PR, but this is corroborating evidence, not a guarantee — flag if it resurfaces.
