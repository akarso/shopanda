# PR-1006 — HTTP Boundary Hardening

Status: planned

## Summary

- Route-aware request body size limits (default for JSON; higher cap for media)
- Security headers middleware for API + SSR with exact-value tests

## Why

Most JSON handlers decode `r.Body` without `MaxBytesReader` (DoS). No `X-Content-Type-Options` / frame options / Referrer-Policy / HSTS anywhere; SSR storefront is clickjackable. Media already uses a 10MiB `MaxBytesReader`.

## Scope

- **Body limits (route-aware, not a uniform top-level wrap):**
  - Default max body (e.g. 1MiB) on non-media JSON/API routes
  - Media upload routes retain their higher configured cap (`maxUploadSize` / 10MiB today)
  - Do **not** wrap the entire mux in one `MaxBytesReader` that would break large media uploads
- **Security headers middleware** (exact values):
  - `X-Content-Type-Options: nosniff`
  - `X-Frame-Options: DENY` **or** CSP `frame-ancestors 'none'` (pick one; document)
  - `Referrer-Policy: strict-origin-when-cross-origin` (or chosen fixed value; document)
  - `Strict-Transport-Security` **only** when request is TLS (`r.TLS != nil`) or trusted proxy proto is configured/honored; **absent** otherwise
- Tests:
  - Exact header values for the non-HSTS headers
  - HSTS present on TLS/trusted-proto; absent on plain HTTP
  - 413 for oversized JSON under default limit
  - Media payload larger than default limit but under media cap succeeds

## Out Of Scope

- Full CSP policy design beyond frame-ancestors if X-Frame-Options chosen
- CORS configuration changes

## Validation

- `go test ./internal/interfaces/http/... -run 'Body|SecurityHeader|MaxBytes|Media'`
- `go build ./cmd/api/`
