# PR-700 — Extension Field Domain + Registry (Track A, OSS)

Status: done

## Summary

- Define `ExtensionField` domain types (code, type, scope, storage_mode, visibility, validation)
- In-process registry service with register/get/list
- Plugin port for compile-time field registration at init

## Why

Customization today fragments across catalog attributes, ad hoc JSON, and template edits. Phase 7 needs a single domain model before persistence or HTTP.

## Scope

- `internal/domain/extension/` — field definition, target types, validation constraints
- `internal/application/extension/` — registry service, duplicate-code guard, namespace rules
- `plugin.App.Extensions().RegisterField(...)` — sole plugin registration surface; thin adapter forwarding to the registry service (no separate `RegisterExtensionField` API)
- Unit tests: register, lookup, validation rejection, namespaced code rules

## Out Of Scope

- Database persistence (PR-701)
- HTTP handlers (PR-702)
- Field values (PR-703)

## Validation

- Plugin can register `acme.gift.wrap_level` on `product` at init
- Duplicate `code` rejected deterministically
- Invalid type/scope combinations rejected at register time
- `go test ./internal/domain/extension/... ./internal/application/extension/...`

## What changed

- Added `internal/domain/extension/` — `FieldDef`, `ExtensionField`, target/type/storage/visibility enums, namespaced code validation, scope/storage_mode rules
- Added `internal/application/extension/` — thread-safe in-process `Registry` (register, get, list with private-field filter)
- Added `plugin.App.Extensions().RegisterField(...)` forwarding to the shared registry; `SetExtensionRegistry` / `ExtensionRegistry` for core wiring
- Wired extension registry in `cmd/api/main.go` before plugin `InitAll`
- Unit tests: domain validation, registry duplicate guard, plugin adapter
