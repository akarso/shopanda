# PR-703 — Extension Value Storage + API (Track B, OSS)

Status: planned

## Summary

- JSONB persistence for extension values keyed by `(target_type, target_id, field_code)`
- Admin value REST: batch GET/PUT/DELETE per target
- ACL enforcement and explicit error codes for private fields

## Why

Definitions without values are inert. Values need a consistent envelope and access rules before any entity UI.

## Scope

- `migrations/` — `extension_values` table (composite key + JSONB `value` column; one row per target/field)
- Domain port + Postgres repo + application service
- `GET/PUT/DELETE /api/v1/admin/extensions/values/{targetType}/{targetID}`
- Optional alias `GET/PUT /api/v1/admin/products/{id}/extensions`
- Stable write error contract: `forbidden_private_field`, `field_validation_failed`, `unknown_field_code`
- Tests: upsert, batch read, private field write denied, validation

## Out Of Scope

- Admin product panel (PR-704)
- Cart/order targets (PR-705–706)
- Storefront read APIs (later PRs)

## Validation

- Set public product field value via PUT; GET returns typed payload
- Write to private field without capability → `403` with `code: forbidden_private_field`
- Unknown field code → `422` with `code: unknown_field_code`
- Invalid value shape → `422` with `code: field_validation_failed`
- Audit logs field_code only for private values (no payload)
