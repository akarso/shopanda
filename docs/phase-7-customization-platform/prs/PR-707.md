# PR-707 — Dynamic Hook Registry (Track D, OSS)

Status: done

## Summary

- Plugin-registerable named hooks with ordered handlers and shared context
- Catalog endpoint listing registered hooks (for docs/tooling)
- Invoke hooks from at least one core path (`cart.add_item.after`)

## Why

Static hook lists require core changes for every new extension point; dynamic registration matches plugin author expectations.

## Scope

- `internal/application/hooks/` — registry, priority ordering, chain execution
- `plugin.App` — `Hooks(registrant).Register(name, priority, handler)`
- `GET /api/v1/admin/extensions/hooks` (read-only catalog; admin RBAC)
- Wire cart `AddItem` through `cart.add_item.after` hook chain
- Tests: priority order, error propagation, panic recovery, catalog API

## Out Of Scope

- Hook authoring UI
- Async hooks (use events for that)

## Validation

- Plugin registers hook; core invocation runs handler with mutable context
- Catalog endpoint lists hook name and registrant metadata
- Handler panic does not corrupt cart state (recovered and returned as error)

## What changed

- Added `internal/application/hooks` — `Context`, `Registry`, `HookCartAddItemAfter` constant
- Handlers run in ascending priority order; first error stops the chain; panics are recovered
- `plugin.App.Hooks(registrant).Register(...)` and `SetHookRegistry` wiring in `main.go`
- Cart `AddItem` invokes `cart.add_item.after` after persist with shared payload (`cart`, `cart_id`, `variant_id`, etc.)
- `GET /api/v1/admin/extensions/hooks` catalog endpoint (`extensions.read` RBAC)
- Tests: registry ordering/errors/panic, plugin registration, cart hook integration, admin catalog
