# PR-1086 — `RegisterMigrations` + `app migrate`

Status: done

## Summary

- Plugins register an embedded FS during `Init` via `app.RegisterMigrations(name, fsys, dir, opts)`.
- `app migrate` / `setup` apply core `migrations/` then every registered plugin FS through `RunPluginFSOptions` (`migrate.PluginFSResult`).
- `Init` remains an idempotent apply (same runner + lock) so a forgotten migrate still converges; deploy docs say run `app migrate` first.

## Why

Operators already treat `app migrate` as the schema step. Plugin tables appearing only as a boot side effect is a different, surprising lifecycle. Dual path (CLI + locked Init) keeps local/dev unblocking without racing production.

## Scope

- `plugin.App.RegisterMigrations` / `Migrations` / `ApplyMigrations` (plugin name + FS + dir + `PluginFSOptions`; name must match `InitAll` plugin when set).
- B2B registers its embed FS (still applies in `Init` via the same helper).
- `app migrate` + `setup`: load config, register plugins, `InitAll`, apply core then `ApplyMigrations`.
- `docs/guides/DEPLOYMENT.md` + `RUNBOOK.md`: migrate applies plugin schema; do not rename recorded versions.
- `PLUGINS.md`: plugin-owned tables go through `RegisterMigrations`, not raw `RunFS`.

## Out Of Scope

- Down migrations.
- A separate `plugin_schema_migrations` table.
- Failing boot when pending (safety-net apply in `Init` stays).

## What changed

- `internal/platform/plugin` — `RegisterMigrations`, `ApplyMigrations`, Init-scoped plugin name.
- `plugins/b2b` — registers embed FS during `Init`.
- `cmd/api` — `applyPluginMigrations` used by `migrate` and `setup`.
- Docs: PR-1086, phase index/roadmap/README, PLUGINS, DEPLOYMENT, RUNBOOK, B2B README.
