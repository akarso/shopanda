# PR-1086 — `Migrator` + `app migrate`

Status: done

## Summary

- Plugins that own SQL implement optional `plugin.Migrator` (`Migrations() []MigrationSpec`) — one declaration of FS / dir / options.
- `app migrate` / `setup` apply core `migrations/` then every Migrator FS via `RunPluginFSOptions` (**no `InitAll`**).
- `InitAll` applies each plugin’s Migrator specs **before** `Init` when `Bootstrap.DB` is set (automatic boot safety net).

## Why

Operators already treat `app migrate` as the schema step. Calling `InitAll` on that path forced broker/Redis dials and full app wiring, and made migrate stricter than `serve`. Declaring SQL on the plugin type (not as an Init side effect) keeps migrate Postgres-only and makes the boot safety net automatic for every Migrator, not a B2B convention.

## Scope

- `plugin.Migrator`, `CollectMigrations`, `ApplyMigrationRegistrations`, `PluginMigrateResult`.
- `InitAll` applies Migrator SQL before `Init` when DB is present.
- B2B implements `Migrator`; removes Init-time `RunPluginFS` / dual declaration.
- `app migrate` + `setup`: register plugins, collect Migrators, apply (no Init).
- Docs: DEPLOYMENT, RUNBOOK, PLUGINS, B2B README, phase index/roadmap.

## Out Of Scope

- Down migrations.
- A separate `plugin_schema_migrations` table.
- Failing boot when pending (InitAll still applies).

## What changed

- `internal/platform/plugin` — `Migrator` interface + collect/apply helpers; InitAll pre-Init apply.
- `plugins/b2b` — `Migrations()` only; Init assumes schema already applied.
- `cmd/api` — `applyPluginMigrations` without InitAll; setup/migrate report plugin counts.
- Tests: collect without Init; promo/integrationdemo migrate path; InitAll-before-Init; stop-on-error with plugin name.
