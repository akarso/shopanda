# PR-1086 — `RegisterMigrations` + `app migrate`

Status: planned

## Summary

- Plugins register an embedded FS during `Init` via `app.RegisterMigrations(fsys, dir)`.
- `app migrate` applies core `migrations/` then every registered plugin FS through `RunPluginFS`.
- `Init` remains an idempotent apply (same runner + lock) so a forgotten migrate still converges; deploy docs say run `app migrate` first.

## Why

Operators already treat `app migrate` as the schema step. Plugin tables appearing only as a boot side effect is a different, surprising lifecycle. Dual path (CLI + locked Init) keeps local/dev unblocking without racing production.

## Scope

- `plugin.App.RegisterMigrations` / list of registrations (plugin name + FS + dir).
- B2B registers its embed FS (still applies in `Init` via the same helper).
- `app migrate` composition: load config, register plugins, `InitAll` or a migrate-only path that does not need HTTP, apply core then plugins.
- `docs/guides/DEPLOYMENT.md` + `RUNBOOK.md`: migrate applies plugin schema; do not rename recorded versions.
- PLUGINS.md: plugin-owned tables go through `RegisterMigrations`, not raw `RunFS`.

## Out Of Scope

- Down migrations.
- A separate `plugin_schema_migrations` table.
- Failing boot when pending (safety-net apply in `Init` stays).
