# PR-1091 — Enforce `Access.PluginOnlyWrite` on extension value writes

Status: done

## Summary

- `Access.PluginOnlyWrite` was declared but never enforced. Writes to such fields
  through untrusted paths (public cart API, SSR `/storefront/cart/*`, admin
  extension values API, GraphQL) now fail with **403** `forbidden_plugin_only_field` and store nothing.
- Trusted plugin writes are marked on the context, **per field code**:
  `extensionapp.WithPluginWrite(ctx, registrant, fieldCodes...)`; plugin-facing
  `func (a *App) WithPluginWrite(ctx context.Context, pluginName string, fieldCodes ...string) context.Context`.
  Panics on blank name / no codes. Rows get `updated_by = "plugin:<name>"`.
  The helper lives in the application layer (no context key in domain).
- Checked in `ValueService.validateBatchValues` next to `canAccessPrivate`, and in
  `ValueService.Delete`. No public method signatures changed.
- Dedicated error code `forbidden_plugin_only_field` (HTTP 403); all mapping goes
  through `extensionapp.MapValueError` (admin and GraphQL delegate to it).
- `FieldService.Update/Delete` reject plugin-only fields (403), so the admin field API
  cannot flip the flag off, write, and flip back.

## Why

Metal Dogs needs a *visible* cart-item field (`metaldogs.design_id`) that only the
plugin can set. Visibility=private is rejected by the public API, so
"public but plugin-written" was not expressible.

## Scope

- `application/extension/plugin_write.go`, domain `ErrForbiddenPluginOnlyField`
- `ValueService` validation; error mapping in `MapValueError`, admin
  `extensionValueAPIError`, GraphQL `extensionAPIError` → `apperror.Forbidden`
- Docs: `EXTENSION_POINTS.md`, `HEADLESS.md`, `openapi.yaml` (403 on add item)

## Core-internal paths (trusted by default)

- `DeleteAllForTarget` / orphan cleanup (line removal) are not gated; do not expose them to request-driven callers.
- `CopyTarget` (ClaimGuestCart / merge / `copyCartItemExtensions`) and
  `SnapshotCartItemToOrderItem` skip validation: they keep copying PluginOnlyWrite
  fields (documented in code). If claim/merge sources ever become untrusted this is a bypass.
- `ValueService.Delete` (admin DELETE, GraphQL) **is** gated.

## Known limits

- Definition guard: service pre-check (fails closed on repo errors) **plus** an atomic guard in the
  Postgres repo (`Save` upsert `WHERE ... NOT PluginOnlyWrite`, `SoftDelete` likewise; repo returns
  `plugin_only_field_immutable`, service maps it to `ErrFieldPluginOnly`). `SoftDelete` is one
  statement (CTE: lock row, delete unless plugin-only, report found/deleted); real lookup errors are
  returned, not reported as not-found. A soft-deleted (retired) plugin-only row **may** be restored by
  `Save` (same as `Create`); encoded in SQL + test. The JSON path
  `definition->'access'->>'PluginOnlyWrite'` is locked by `TestExtensionField_JSONPathUsedByPostgresGuard`.
  **Run against real Postgres 17** (throwaway container, `postgres:17-alpine`): all 11
  `TestExtensionFieldRepo_*` pass. `CI / integration` (Postgres service in `ci.yml`, `scripts/ci/integration.sh`
  → `./internal/infrastructure/postgres/...`) runs them; `CI / unit` skips them. With `-p 1` the same
  7 unrelated tests (`StoreCreditRepo_Issue_*`, `CacheStoreDB_CompareAndSubtractVsIncrConcurrent`,
  `NotificationDedupeRepo_TryInsert_ReclaimsStalePending`) fail on `dev` and on this branch.
- Trust stripping: the event bus strips the marker on `Publish` by default (platform `pluginwrite`
  package) and `cart.AddItem` strips it for pricing/hooks; any new core code forwarding `ctx` elsewhere
  (e.g. workers started outside the bus) must call `extensionapp.StripPluginWrite`.
- Async handlers get the bus shutdown ctx (never the publisher ctx), so they cannot inherit trust; outbox/worker paths outside the bus are not covered.
- `App.WithPluginWrite` panics are recovered only by HTTP `RecoveryMiddleware`; in events/workers/goroutines they crash the process — never pass runtime-built codes.
- OpenAPI has no error-code enum; the new codes are named in the add-item 403 description only.
- `make check` waiver: red on pre-existing gofmt/vet findings in files this PR does not touch (touched files are gofmt-clean); cleanup is a separate PR.
- Follow-ups (planned specs): [PR-1092](PR-1092.md) field ownership; [PR-1093](PR-1093.md) narrow
  core-internal port; [PR-1094](PR-1094.md) retire plugin-only definitions; [PR-1095](PR-1095.md)
  trust-propagation hardening + missing tests; [PR-1096](PR-1096.md) gofmt/vet cleanup (`make check` green).

- `DeleteAllForTarget` / `CopyTarget` are exported on the same service and rely on caller discipline (cart service only); a narrow core-internal port is a possible follow-up.
- Field owners are not recorded: trust is per code, not per owning plugin; `updated_by` plugin label is advisory.
- `plugin_only_field_immutable` (403) guards definitions; making a field plugin-only is a one-way latch via the API (operator DB change to retire).
- Trust is stripped from `ctx` inside `cart.AddItem` before hooks/pricing/events (test: event handler cannot write).
- Checkout/order extension paths map to the same 403 but are not separately tested.
- `make check` is red on pre-existing gofmt/vet findings in files this PR does not touch; fix in a separate PR.

- The registry does not record field owners, so plugin A can name plugin B's code in
  `WithPluginWrite`; trust is per code, not per owner.
- Unknown field → 422, plugin-only field → 403 for any caller (same field-existence
  probing as private fields).
- Context propagation: marker survives derived contexts (`WithoutCancel` keeps values);
  background workers must set it themselves.
