# PR-1092 — Field ownership for plugin-only extension fields

Status: done

## Summary

- Record which plugin registered an extension field and enforce it on plugin-only writes.

## Why

Today "plugin-only" means trusted in-process code that knows the field code; plugin A can write plugin B's field and the `plugin:<name>` label is advisory (see PR-1091 Known limits).

## Scope

- `app.Extensions()` gets a scoped, named wrapper (like `app.Hooks(name)`); `RegisterField` records the owner on the registry entry.
- `WithPluginWrite(ctx, registrant, codes...)` (app entry point) rejects codes owned by another plugin; `updated_by = plugin:<owner>` becomes trustworthy.
- Compatibility: unnamed `app.Extensions().RegisterField` keeps working (owner empty = any trusted code may write).

## What changed

- `Registry.RegisterOwned(def, owner)` / `Registry.Owner(code)`; `Remove` clears the owner.
- Ownership is assigned by the loader **after** each plugin's `Init` (snapshot of registered codes before/after; no shared "current plugin" state on `App`): new unowned fields get the plugin's name, a field owned by another plugin fails that `Init`, and a failed `Init` rolls back every field it registered (`Registry.AssignOwner`, `Remove`). Outside `Init`, `Extensions()` is unowned; `ExtensionsFor(name)` records `name` explicitly.
- `App.PluginWriteContext` returns errors (blank name, no codes, unregistered / non-plugin-only code, owner mismatch); `WithPluginWrite` panics on the same errors. Use the former in events/workers/goroutines.
- `App.WarnUnownedPluginOnlyFields` (`extension.plugin_only.unowned`) runs at the end of `InitAllContext` (every boot path, each field once) and again in `wire_services` after `LoadPersisted`; `Replace` refuses to clear `PluginOnlyWrite` on owned plugin-only fields; `Registry.UnownedPluginOnly` lists from one consistent snapshot.
- Registration folded into one `register(def, owner)`; `ValueService.pluginWriter` returns `(registrant, allowed)` in one lookup; owner/registrant are trimmed, case-sensitive.
- `ValueService.pluginMayWrite`: for plugin-only fields with an owner the trusted registrant must equal it (write and `Delete`); unowned fields keep the PR-1091 behavior.
- `App.WithPluginWrite` panics early on an owner mismatch.
- `TestValueService_PluginOnlyWrite_AnyPluginMayNameAnyCode` became `..._OwnerIsEnforced`.
- Stacked on PR-1091 (branch `pr-extension-plugin-only-write`); merge after it.
- Not solved (documented, not a security boundary): a goroutine registering during another plugin's `Init` is attributed to it (test documents it; fix needs a per-plugin `App` facade / `Init` signature change); `Registry.Remove` is not owner-aware; rollback covers extension fields only (hooks/events stay); registrations after boot are not reported; ownership is enforced at load time and at write time but `ExtensionsFor` / `PluginWriteContext` names are caller-supplied outside `Init`; the registrant is a string, so in-process code can impersonate an owner; persisted/admin-created fields stay unowned (`mergeField` never overrides a plugin's registration); field codes are not required to use the owner's namespace; `Extensions()` is not deprecated. A cross-plugin write is not reachable over HTTP (the marker is in-process only), so there is no HTTP-level test. No C4 change.

## Out of scope

- Anything not listed above (one PR = one responsibility).

## Validation
