# PR-1087 — `manual` trigger + `Enqueue` + queue bind

Status: planned

## Summary

- Third sync-job trigger: `extapi.Manual()` (no cron, no event).
- `app.Integration(slug).Enqueue(ctx, name, payload)` enqueues `integration.sync.{slug}.{name}` on the bound queue.
- Composition root binds the resolved `jobs.Queue` onto `plugin.App` after `InitAll` wherever a queue is already resolved (serve, worker, and any CLI that enqueues).

## Why

Plugins cannot enqueue today: `Bootstrap` has no queue, and `app.Queue()` is the backend slot filled by core plugins / `resolveJobQueue` **after** `InitAll`. Inbound webhooks and admin “run now” need 202 + retry, not a long `OnAsync` body.

Keep the existing type namespace and `RegisterSyncJobHandlers` path so Phase 11 jobs admin works with no new UI.

## Scope

- `pkg/extapi` — `SyncTriggerManual`, `Manual()`.
- `registerSyncJob` accepts `manual` (no cron spec / event name).
- `Integration.Enqueue`; errors: unknown name, wrong slug, queue not bound.
- `plugin.App.BindQueue(jobs.Queue)` (or equivalent) called from existing resolve sites — do not resolve a second queue.
- Worker registration unchanged (already iterates `SyncJobs()`).
- Tests: register + enqueue payload shape; bind required; duplicate type still rejected.

## Out Of Scope

- Generic `jobs.Handler` / free-form types (`email.send` remains core-only).
- SDK wrappers and doc sweep (PR-1088).
- HTTP admin “trigger plugin job” route (use `Enqueue` from the plugin’s own route, or existing `jobs` retry).
