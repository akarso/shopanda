# PR-1111 — Same-origin storefront cart JSON add

Status: done

## Summary

A same-origin configurator cannot use `POST /api/v1/carts` and then open SSR `/cart`: those are different carts. HTML `POST /cart/add` works but is a form post. This PR adds a JSON mutation that writes the storefront cookie cart.

## Scope

- `GET /storefront/csrf` — envelope `{"data":{"csrf_token":"..."},"error":null}`; mints `shopanda_csrf`; `Cache-Control: no-store`
- `POST /storefront/cart/items` — JSON `{variant_id, quantity?, extensions?}`; uses `ensureCartForRequest` only after the body is valid
- Quantity: omitted → 1; explicit `null` / `0` / negative → 422 (no guest cart minted)
- Guest `shopanda_storefront_cart` is set only after a successful add; a failed first guest add discards the empty created cart and any leftover cart_item extension rows
- Unexpected `AddItem` errors are logged (`storefront.cart.json.add.failed`) and returned as a generic JSON 500
- CSRF middleware accepts `X-CSRF-Token` on `/storefront/*` (header only; query/form token rejected). Failures are JSON 403; mint failure on this prefix is JSON 500
- HTML `POST /cart/add` stays form-only and outside CSRF
- Success envelope: `{"data":{"item_count":n,"total_quantity":n,"cart_url":"/cart"},"error":null}` — no `cart_id`
- Extension / `cart.validate` errors reuse the headless cart mapper (`ValidationFailedFrom` then `MapValueError`) → 422 with the real code
- `/storefront` is a Cache-Control and FPC deny prefix; `/storefront/*` is not a CORS prefix
- Routes register only inside `cfg.Frontend.StorefrontHTML()`

## Out of scope

- JSON update/remove — shipped in [PR-1112](PR-1112.md)
- Merging REST `cart_id` into the storefront cookie
- Cross-origin / CORS credentials for this path
- CSRF on `/cart/add`
- OpenAPI — these paths are the SSR cookie-cart seam, not `/api/v1`. Documented in HEADLESS.md instead.
